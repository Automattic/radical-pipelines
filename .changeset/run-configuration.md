BREAKING: Record the conventions each run reads in its run configuration, keep `.rp.md` as prose, and have `rp` write each role's whole assignment.

`.rp.md` is prose a person reads and edits, at conventions version 7: its frontmatter is the one line `conventions: 7`, and every convention is a prose section. A guardrail or resource is an entry under its name, with a `profiles` field and its text written as its own lines. Each Agents profile and lane is an entry with its `model` and `subagents`, a lane's brief as its text; the Agents section may sit in the shared conventions or in an agentic tool's section. The worktree folder root, the new optional **Landing commit** — the template of the commits `rp land` makes — and each template of the new optional **Variables** are code spans. Setup migrates a version-6 `.rp.md` into this form with every text unchanged, offers Landing commit and Variables, and adds `run-config.local.json` to `.gitignore`; apply the same entries to `.rp.local.md` by hand.

At every run start the orchestrator records the run configuration, `run-config.json` at the pipeline folder root, which replaces `run-config.md`: the target phase, the base, and the agents the owner confirmed; the worktree folder root, landing commit, commit format, guardrails, resources, and variables, copied verbatim from `.rp.md`; and the owner's directions for the run, one entry each. What `.rp.local.md` overrides of those conventions, and of the models of a profile or lane, goes to `run-config.local.json` beside it, which no commit holds. A model or subagent model the owner asks for, while confirming a run or during it, holds on that clone for the rest of the run, whatever `.rp.local.md` overrides. Editing `.rp.md` therefore changes no run under way, and a merged pipeline keeps the conventions it ran under. The run confirmation shows, under each profile, the models the run gives with this clone's overrides beside them, and names the guardrails and resources the run will carry.

`rp` reads `run-config.json`, and never `.rp.md` or `.rp.local.md`. Before every spawn and wake, `rp next --apply` takes it with `run-config.local.json` over it by name, computes the role's turn from the frontier, fills its template, writes the assignment where the role reads it, and prints its path and the role's model. On a reviewer's later turn it also writes the diff the reviewer reads. A reviewer woken to fix files `rp check` rejects gets a request of its own, which asks it to change only what each reason names and to keep every message, and an approval is certified at the commit its reviewer's last heading names. A malformed entry stops `rp check`, `rp next`, and `rp land`, naming the file and the entry, and they write nothing; so does a `run-config.local.json` Git tracks. The orchestrator copies no convention, path, or model into an assignment.

Model names travel as the project writes them, such as `sonnet`: the orchestrator resolves a role's model through its tool when it spawns it, and a role runs its subagents on the model its tool finds by its subagent model name, or on its own model when the tool finds none.

Guardrail, resource, commit-format, and brief texts may name pipeline facts in braces — `{pipeline-slug}`, `{role}`, `{profile}`, `{lane}`, `{worktree}`, `{branch}`, `{base}` — and variables a project declares over them, such as `agent` as `{pipeline-slug}-{role}`, which `rp` expands for each role. A placeholder that names neither reaches the role as written, with those facts listed in its assignment.

A pipeline carries no format: a folder of the pipelines folder root is a pipeline when it holds `run-config.json`, and `rp pipelines` lists only such folders, without a format. It reads each pipeline's intent as `rp check` does, and stops on one it rejects, naming the intent and the reason. A pipeline started before this change is not continued: work on its issue starts a new pipeline, whose slug names no folder in the pipelines folder root of the commit its branch starts from. Its folder is no pipeline to `rp`, so each review lane's tree keeps it, as it keeps a project's tooling.
