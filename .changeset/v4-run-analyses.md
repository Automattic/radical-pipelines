Fix the mechanisms the analyses of finished runs exposed. A role writes only in a thread it opens or one that awaits it; a closed thread is history. The spec producer reads its spec as the design doc's producer would, and the design doc's producer reads it as the implementer would. A role whose file is malformed is woken with the `malformed` lines under a **Malformed files** slot of its assignment and fixes them first. The files the orchestrator prepares for a role, such as the net change a reviewer reads, live beside the role's assignment in its worktree's assignment folder, inside its git directory. A running role is stopped with its transcript kept: on opencode with `POST /api/session/<id>/interrupt`, together with its subagents; on Claude Code with `TaskStop`. A lane's brief is optional: a lane without one covers its profile's whole scope. A configuration may declare the `default` review lane itself, with or without a brief, alongside other review lanes; without any `reviewer` lane, `default` runs alone. The reviewer's assignment is the request a developer would get: review the code on this branch, which addresses this issue, and report anything wrong, missing, risky, or more than the issue needs, writing the review as it would be posted on the pull request and approving when it would merge the change as it stands; a later turn asks it to check the author's answers and what changed since its last message. Setup proposes two `reviewer` lanes without a brief, on models from different providers. Roles answer every point of a review message, numbered or not. Each producer's closing self-read names what it removes again: the spec's mechanisms and implementation detail and the fixtures, sequences, and variants that prescribe how a criterion is proved; the design doc's passages that choose a component's internals — control flow, call sequences, internal names, literal values, test cases — and the inputs, fixtures, or steps that prescribe how a proof is performed. Every spec clause — requirement, acceptance criterion, exclusion, and the outcome an assumption claims — states observable behavior, never how the software is built or which code it touches. `rp pipelines` takes the pipelines folder root as its argument, `rp pipelines <pipelines folder root> --base <branch>`. The orchestrator lands a role only after its turn has ended: its report ends with "Completion declared: no work remains." or reports a blocker; after any other report, it waits. The message that starts a role's turn is `Read your assignment: <absolute path>.`, so the role's conversation shows which file it read. The reviewer has no supporting folder: it pastes what it wants to share in its thread. A review lane's branch is built, not merged: each turn it is rebuilt from the pipeline tip as a review base — the merge-base without the pipelines folder — and a review head on it, both holding only the pipeline's intent, later inputs, and the lane's own threads, so the reviewer finds nothing else of the pipeline in its tree or history. The review head is the reviewer's turn commit, and the reviewer's commits land on the pipeline branch by cherry-pick. Tooling a project keeps in the pipelines folder root is no pipeline: discovery does not list it, and a review lane keeps it at the tip's version.
