## Shared conventions

### Issues

Issues live in GitHub, `Automattic/radical-pipelines`, reached through the `gh` CLI. Linear mirrors each one for status only, through the Linear MCP: an issue in project Billow Pipelines (`15a89be6fe3c`) of team `BILLOW`, with the same title, the `radical-pipelines` label, and only the GitHub issue URL as its description. Find an issue's mirror by searching Linear for that URL. Create an issue in GitHub first, then its mirror; modify only the GitHub issue. Pipelines reference an issue by its GitHub issue number, such as `377`.

When the Linear MCP is unavailable — not authorized in a non-interactive session, or disconnected — the pipeline is not blocked: tell the owner at once, continue the run, record every skipped Linear update, and list them for the owner at close-out.

### Pipeline slug

`<GitHub issue number>-<short kebab-case description>`

### Artifact storage

`artifacts-in-repo`: `.rp.md` and the pipelines folder live in this repository. The artifact base branch is `trunk`.

### Worktree folder root

`.worktrees`

### Commit format

Use imperative mood, sentence case, no period at the end. End with the profile name in parentheses, or `(assisted)` for a commit a person made with an agent outside a pipeline.

Examples:

- `Add intent (orchestrator)`
- `Add spec (spec-producer)`
- `Support for X (implementer)`
- `Open review thread (reviewer)`
- `Fix bug Y (assisted)`

### PR format

Follow the PR template at `.github/PULL_REQUEST_TEMPLATE.md`.

### Resources

#### test suite and scripts

- profiles: spec-producer, design-doc-producer, implementer, reviewer

The repository's test suite and scripts. `npm test` runs the unit tests; `npm run test:rp`, `npm run test:opencode-unit`, and `npm run test:release` run parts of them, and `npm run test:opencode` runs the opencode integration suite. `node skills/radical-pipelines/scripts/rp.mjs` runs `rp`, and every script under `scripts/` may be run directly.

### Lanes

The spec-producer runs two lanes: two copies of itself that each write their own candidate spec, which the spec-producer then merges into the spec. Each lane follows its brief, the instruction that sets it apart:

- `demands`: Read the intent for what it demands: every outcome it asks for, and each input intended use produces that an outcome must handle.
- `omits`: Read the intent for what it leaves out: the cases, mechanisms, and guarantees it does not ask for and no intended use produces, and keep the spec to what remains.

The reviewer runs two lanes, each named after the model it runs on. Each reviews the change on its own, with the default review request and no brief, and both must approve.

The design-doc-producer and the implementer run alone, without lanes.

### Models

The model each agent and lane runs on, and the subagent model it delegates to, depend on the tool: see **opencode** and **Claude Code**.

### Lifecycle hooks

#### after-creating-worktree

- **Blocking:** run `npm ci --no-audit --no-fund` from the worktree root.

#### after-creating-pipeline

- Set the Linear issue status to `0 - Intent`.

#### run-started

- Add the `running…` label to the Linear issue, and remove the `Needs Input` label.
- Assign the Linear issue to the person running the pipeline: the current Linear user, found via the Linear MCP. Overwrite whoever was assigned before.

#### phase-started

- Set the Linear issue status to the phase: `1 - Spec`, `2 - Design Doc`, `3 - Implementation`, or `4 - Review`.

#### phase-completed

- When phase 4 completes, every review lane has approved the change: set the Linear issue status to `Pipeline approved`.

#### escalation-raised

- Add the `Needs Input` label to the Linear issue.

#### run-ended

- Remove the `running…` label from the Linear issue.

#### after-opening-pr

- Set the Linear issue status to `Upstream PR opened`.

#### after-merging-pr

- Set the Linear issue status to `Done`.

#### after-closing-without-merge

- Set the Linear issue status to `Canceled`.
