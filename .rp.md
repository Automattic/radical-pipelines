# Radical Pipelines project conventions

This file holds shared conventions for this project. The orchestrator loads this file at the start of every workflow.

## Agentic coding tool conventions

Per-tool project conventions live alongside this file. Read the one matching the active tool:

- **Claude Code:** `.rp.claude-code.md`
- **opencode:** `.rp.opencode.md`

## Shared conventions

### Issues

All issues are tracked in two mirrored trackers. **GitHub is the source of truth**; Linear mirrors it for status tracking only.

- **GitHub**: https://github.com/Automattic/radical-pipelines — accessed via the `gh` CLI.
- **Linear**: the Linear project with id `15a89be6fe3c` — accessed via the Linear MCP and filtered by the `radical-pipelines` label. Both the project and the label live in the **Billow** team (id `49ae3cbc-a6f1-4c22-a064-1ef8f168aeff`); scope label lookups to that team.

To find the Linear issue that mirrors a given GitHub issue, search Linear for the GitHub issue URL — it lives in the Linear issue's description.

The canonical issue reference written into `Origin:` lines is the GitHub issue number.

#### Creating an issue

1. Create the issue in GitHub first with `gh`.
2. Once the GitHub URL is known, create a matching Linear issue in the project above via the Linear MCP, with:
   - The same title.
   - A description containing **only** the GitHub issue URL.
   - The `radical-pipelines` label.

#### Modifying an issue

Edit the GitHub issue description using `gh`. Do not modify the Linear description — the GitHub URL in its description is enough for traceability.

### Pipeline slug

A pipeline's slug is `<issue-number>-<short-description>`, where `<issue-number>` is the **GitHub** issue number (never the Linear id) and `<short-description>` is lowercase kebab-case. It must not contain `_`.

### Pipelines folder root

`.pipelines/`

### Artifact storage

`artifacts-in-repo`: `.rp.md` and the pipelines folder live in this repository. The artifact base branch is `trunk`.

### Commit format

Use imperative mood, sentence case, no period at the end. End with the profile name in parentheses, or `(assisted)` for a commit a person made with an agent outside a pipeline.

Examples:

- `Add intent (orchestrator)`
- `Add spec (spec-producer)`
- `Support for X (implementer)`
- `Open review thread (reviewer)`
- `Fix bug Y (assisted)`

### PR format

Follow the PR template at `.github/PULL_REQUEST_TEMPLATE.md`.

### Agents

#### spec-producer

- model: opus
- lanes:
  - `demands`, on `opus` — brief: Read the intent for what it demands: every outcome it asks for, and each input intended use produces that an outcome must handle.
  - `omits`, on `sonnet` — brief: Read the intent for what it leaves out: the cases, mechanisms, and guarantees it does not ask for and no intended use produces, and keep the spec to what remains.

#### design-doc-producer

- model: opus

#### implementer

- model: opus

#### reviewer

- model: opus
- lanes: one, `default`, with no brief.

### Worktree folder root

Worktrees live under `.worktrees/` — one worktree per branch, at `.worktrees/<branch>`.

### Guardrails

#### tests

- rule: Run `npm test` and confirm it passes.
- agents: implementer, reviewer

#### documentation

- rule: Follow `AGENTS.md` and `docs/glossary.md`, the canonical vocabulary.
- agents: implementer, reviewer

### Resources

#### test suite and scripts

- resource: The repository's test suite and scripts. `npm test` runs the unit tests; `npm run test:rp`, `npm run test:opencode-unit`, and `npm run test:release` run parts of them, and `npm run test:opencode` runs the opencode integration suite. `node skills/radical-pipelines/scripts/rp.mjs` runs `rp`, and every script under `scripts/` may be run directly.
- agents: spec-producer, design-doc-producer, implementer, reviewer

### Lifecycle hooks

#### run-started

- Add the `running…` label to the Linear issue.
- Assign the Linear issue to the person running the pipeline: the current Linear user, found via the Linear MCP. Overwrite whoever was assigned before.

#### phase-completed

- Set the Linear issue status to the phase that completed: `0 - Intent`, `1 - Spec`, `2 - Design Doc`, `3 - Build` for Implementation, `4 - Document` for Review.

#### run-ended

- Remove the `running…` label from the Linear issue.

#### after-merging-pr

- Set the Linear issue status to `Done`.
