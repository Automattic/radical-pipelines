# Glossary

The canonical vocabulary of Radical Pipelines. Terms are used exactly as defined here: no synonyms or alternate notation. [The v4 model](./model.md) explains the design these terms describe.

- **Agents** — The project convention giving each profile's model, its subagent model, and its lanes: production lanes for `spec-producer` and `design-doc-producer`, review lanes for `reviewer`. It is conventions data, and a run configuration records the run's in its schema.
- **Assignment** — A role's filled template, written by `rp assign` before every spawn and wake to `git rev-parse --git-path rp/<profile>.md` in the role's worktree, outside the tree. The message that starts a turn only says to read it, and the role rereads it after a compaction and whenever it is unsure of its seat, mode, materials, or rules.
- **Artifact** — A file a role owns and the pipeline's state is computed from: `spec.md`, `design-doc.md`, `notes.md`, and the production lanes' candidates.
- **Artifact storage** — The project convention naming where `.rp.md` and the pipelines folder live — the project's repository or a fork — and the artifact base branch: where pipelines start.
- **Awaiting** — Whose turn an `open` thread is: it awaits its opener when its owner wrote the last message, and its owner otherwise.
- **Base** — The merge-base of the inspected tip with the branch its run configuration's `base` names.
- **Blocker** — A role's report that something it was given failed it — its materials, its worktree, or the worktree's environment. The orchestrator repairs it and wakes the role again.
- **Brief** — A lane's direction: what a production lane explores, or the review request a review lane's assignment carries, in place of the default one.
- **Candidate** — A production lane's version of the spec or the design doc, written in `<phase folder>/lanes/<lane>/`. Candidates are required inputs only while their root artifact is missing.
- **Certification** — `rp`'s record of a landed artifact, candidate, or approval, in `certification/<its path>.json` in the pipeline folder: a pin of each required input and, on an approval, its approved commit. Only `rp stamp` writes it; no role or orchestrator step touches it.
- **Closure action** — A moment the owner invokes on a pipeline: opening its pull request, merging it, or closing without merging. Each is bracketed by lifecycle hooks.
- **Considered and not required** — The spec section listing, one line each, the cases its producer examined and left out because no intended use produces them, and the readings of the intent it did not take.
- **Conventions data** — The conventions an assignment carries — the commit format, guardrails, resources, agents, and variables — as named entries in `.rp.md`'s JSON frontmatter, which `rp assign` validates whole and fills assignments from. A developer's `.rp.local.md` overrides them entry by entry. Every other convention is prose.
- **Consolidate** — The producer mode that writes the root artifact from the candidates: a case or decision every lane reached is kept; one only one lane reached is kept only when intended use is observed to produce its input; where lanes chose differently, the producer decides from the evidence and records the alternative in one line.
- **Consolidated** — A root artifact written from candidates.
- **Constraint** — A binding owner ruling, in the intent or a later `0-intent/constraint-<n>.md` with `target` and `origin`. Constraints are owner territory.
- **Disagreement** — A reply that repeats a position without new evidence. About a derived requirement or a design decision, it resolves inside its thread by observation. About what the intent means or demands, either party — the implementer, on a review thread — opens a thread to `owner` about `intent` with status `disagreement`, the only status that reaches the owner, its `cites` naming the thread. A question the intent's words leave open is no disagreement: the producer takes the reading the Goal and intended use support and records the other.
- **Frontier** — What `rp check` says to do next: the first that holds of a malformed file (`INVALID`), a disagreement (`escalate`), the lowest phase whose role has work (`lane`, `consolidate`, `produce`, `respond`, or `review`), or `complete`.
- **Frontmatter** — The YAML between `---` lines at the top of a file that holds the values `rp` reads: the intent's origins, a later input's `target` and `origin`, `notes.md`'s `status`, and a thread's header. Each line is `<key>: <value>`, the value text on one line; `rp check` reports anything else as `INVALID`.
- **From-intent / derived** — The origin every requirement carries. `from-intent`: the intent states it, and the requirement cites the intent item. `derived`: the producer inferred it, and the requirement cites the input observed in intended use that makes the case material. A derived requirement without an observed input is written as an assumption.
- **Guardrails** — The project convention listing the rules a profile must satisfy — prose it follows, or a check it runs — as conventions data. The reviewer evaluates each against the change.
- **Identity** — The first 12 hexadecimal characters of the blob id Git stores for a whole file, so the working tree and a commit agree.
- **Instance name** — A spawned role's name, `<pipeline slug> <profile>[ <lane>]`.
- **Intended use** — A use the intent names, or one that the project's documentation or code shows a consumer making. It is how roles judge whether a case matters: an input an artifact or the code merely admits, or a consumer no source shows, is not intended use.
- **Issue** — The unit of work a pipeline realizes.
- **Landing** — Verifying a role's commits are on its branch, stamping its artifact at its turn commit and every review thread its turn closed `approved` at the commit its reviewer's last heading names, and committing their certifications on top.
- **Later input** — What the owner brings after the intent: a constraint, a proposal, or a reported failure, each in `0-intent/` with `target` naming the artifacts it targets and `origin` naming where it came from, holding only what the owner gave in the fewest words that carry it. A later input is a required input of every artifact it targets, never of a candidate.
- **Missing** — An artifact whose file is absent. `notes.md` is also missing until its `status` is `done`.
- **Mode** — The procedure a role's assignment selects: produce, respond, or consolidate for a producer; implement or respond for the implementer. The reviewer has none: its first turn, its later turns, and a turn that only repairs files it wrote each have their own assignment template, the first two carrying the review request.
- **Net change** — The pipeline's change outside the pipelines folder: the diff from its base to its tip, what the reviewer reads.
- **Notes** — `3-implementation/notes.md`, the implementer's resumption file: the inputs it started from, what is done, what remains, the decisions a successor should know, and the approaches that failed. `status: done` in its frontmatter declares the implementation complete.
- **Observed / assumed** — The label on every claim. A claim about current behavior is `observed: <how>`; a claim about what the solution will do is `assumed: <what will confirm it>`, and the implementer verifies it.
- **Orchestrator** — The session running the skill. It triages with the owner, records phase 0, creates branches and worktrees, wakes the roles the frontier names, lands their turns, carries disagreements on owner territory to the owner, and opens the pull request. It judges no content and relays no message.
- **Origin** — The source from which something was born: an issue reference, the URL of an external source, a pipeline it starts from or re-attempts, or the thread an owner's answer settles.
- **Owner** — The person running the pipeline; talks only to the orchestrator. As a thread role, `owner` is the party of a thread about `intent`.
- **Owner escalation** — A thread with status `disagreement`, opened for a disagreement on what the intent means or demands, or for evidence that every kind of approach fails an intent goal or constraint; its `cites` names that thread or evidence. The run stops; the owner's answer is recorded as a constraint or a proposal, as the owner rules, targeting the disputed artifact, and the thread is closed `answered`.
- **Owner territory** — What the intent means or demands: its Goal, its constraints, and later constraint files. Everything after the intent is chosen by a role and settled between roles.
- **Phase** — One pipeline stage: Intent, Spec, Design doc, Implementation, or Review.
- **Placeholder** — A name in braces, such as `{role}`, in a guardrail's, a resource's, or the commit format's text, or in a lane's brief. `rp assign` replaces one that names a vocabulary fact or a variable with its value for the role; any other reaches the role as written, with the vocabulary listed in its assignment, and the role substitutes it.
- **Pin** — An entry `<path>@<identity>` in a certification, recording the version of an input at the turn commit.
- **Pipeline** — A set of artifacts, each owned by one role. It is done when every artifact through the target phase exists and is not stale, no thread is open or in disagreement, and, when the target is the review, every review lane's approval is fresh.
- **Pipeline branch** — The branch a pipeline's commits land on: the **Pipeline branch format** convention applied to its slug, with `_<n>` appended for work on the pipeline once merged. Lane branches extend it.
- **Pipeline branch format** — The project convention giving the pipeline branch as a template over `<pipeline slug>`, defaulting to the slug itself.
- **Pipeline slug** — The project convention deriving a pipeline's identifier from its issue, and that identifier: one path segment, a valid git ref, without `_`, naming the pipeline folder.
- **Pipelines folder root** — The project convention naming where pipeline folders live, defaulting to `.pipelines/`.
- **Production lane** — A named `spec-producer` or `design-doc-producer` lane with a model and an optional brief, which writes a candidate in its own branch and worktree, in parallel with the other lanes. It decides every question as any producer does, holds only its final reading, and opens no thread; the consolidator resolves where lanes differ.
- **Proposal** — A direction or hypothesis to investigate, in the intent or a later `0-intent/proposal-<n>.md` with `target` and `origin`. Roles adopt or refute it with evidence; the owner's approval authorizes investigation, not its outcome.
- **Reported failure** — A result observed outside the run that contradicts the work — a command the owner ran, CI, a bug — recorded as given, with its evidence, in `0-intent/failure-<n>.md`. It carries no ruling: its targets' owners reproduce it and adopt or refute it.
- **Required inputs** — What an artifact must pin: the spec, the intent; the design doc, the spec; `notes.md`, the spec and the design doc; each, also every later input targeting it. A candidate pins its root's upstream artifacts only: the later inputs targeting the root are read by the consolidator.
- **Resources** — The project convention describing what roles may run and use — environments, services, accounts, data, tools — and how, as conventions data.
- **Review lane** — One `reviewer`, with its brief when it has one, in its own branch and worktree, which `rp review` builds each turn as a review base and the change on it: the reviewer sees the intent, its later inputs, the net change, and its own threads, and nothing else of the pipeline in the lane's tree or history. Without a configured lane, one lane named `default` runs. A review lane is approved when its latest review thread is `approved` and fresh; the implementation is approved when every lane is.
- **Review thread** — A thread a review lane opens to `implementer` about `implementation`. Closed `approved` and landed, its certification pins the intent and every later input at the change its reviewer read, and records its approved commit: the pipeline-branch commit holding the approval, whose code is that change's. It is stale when a required input changed, or when the tip's code differs from that commit's by anything other than clean merges of the base; in a clone that lacks that commit, it is no approval.
- **Role names** — The parties of a thread: `spec-producer`, `design-doc-producer`, `implementer`, `reviewer-<lane>`, and `owner`. Each artifact pairs with its owner: `intent` with `owner`, `spec` with `spec-producer`, `design-doc` with `design-doc-producer`, `implementation` with `implementer`.
- **Run configuration** — `run-config.md` at the pipeline folder root: the conventions format it was written under, the target phase, the base, and the agents the owner confirmed — each profile's and lane's model and subagent model, the lanes, and their briefs — with the owner's directions in its body.
- **Seating** — Starting a role inside its assigned worktree, its branch checked out, by the active tool's mechanics (`tools/<tool>.md`).
- **Stale** — An artifact or approval with a required input that is unpinned or pinned at an identity that differs from the current one; an approval also when the code moved past it (see Review thread). Its owner responds by revising it.
- **Stamp** — The orchestrator's `rp stamp` operation, which writes a landed file's certification and never the file.
- **Subagent model** — The model name a role delegates on, named in its assignment's Seat as the project writes it: the role's tool finds the model by it. The run configuration sets it per profile and lane; without one, or when the tool finds no model, the role's subagents run on its own model.
- **Supporting folder** — The folder where a role keeps the screenshots, logs, command output, and transcripts its file cites: `1-spec/spec/`, `2-design-doc/design-doc/`, and `3-implementation/notes/` beside their artifacts; `<phase folder>/lanes/<lane>/<artifact>/` for a candidate. The reviewer has none: it pastes what it wants to share in its thread. It is not pipeline state.
- **Target** — What a later input addresses: one or more artifacts, whole or by clause id.
- **Target phase** — The highest phase a run executes before stopping.
- **Thread** — The conversation between two roles about one artifact, in one file, `threads/<n>-<opener>-<owner>-<artifact>.md`, opened by a role that consumes the artifact. Its status is `open`, `approved`, `withdrawn`, `answered`, or `disagreement`. Each message ends its author's turn.
- **Turn commit** — The tip of a role's worktree when `rp assign` writes its assignment, named there. The role reads its materials at it, and landing stamps at it, reading it from the assignment.
- **Triage** — The orchestrator's entry for incoming work: it normalizes the request into an issue, scans the issue's pipelines, routes each statement, and confirms the runs that need it.
- **Variable** — A placeholder a project declares in its conventions data, with a template over the vocabulary, such as `agent` as `{pipeline-slug}-{role}`.
- **Vocabulary** — The pipeline facts a placeholder may name, each valued for a role and its turn: `pipeline-slug`, the pipeline slug; `role`, the role's name; `profile`, its profile; `lane`, its lane, empty for a role without one; `worktree`, its worktree's absolute path; `branch`, its branch; and `base`, the Base of its turn commit.
- **Worktree** — A checkout of one branch. The orchestrator creates it and seats roles in it.
- **Worktree folder root** — The project convention naming the folder under which one worktree is created per branch.
