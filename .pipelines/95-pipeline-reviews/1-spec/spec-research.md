# Spec Research

## Rough Idea

> Source: GitHub issue [Automattic/radical-pipelines#95](https://github.com/Automattic/radical-pipelines/issues/95).

### Goal

The owner can request a **review** of a pipeline and have the requested changes applied by running the **whole pipeline again** (prompt → spec → design doc → plan → code → docs) as an additional run layered on top of the existing work, on the **same branch and worktree**.

### Constraints

- A review re-runs the **entire pipeline from scratch**: a new prompt → a new spec (from that prompt) → a new design doc (from that spec) → a new plan (from that design doc) → code and docs (from that plan). The agent profiles stay the same (or very nearly so).
- The **only** difference from the base run is that the branch/worktree already contains the previous runs, so agents build on top of existing code rather than an empty tree. Reviews stay on the **same branch and worktree** as the pipeline — never a new branch (this is what distinguishes a review from a fork).
- The original issue and the base prompt are **never** rewritten. Each review is driven by its **own new prompt**, generated the same way an issue is (Goal/Context/Constraints/…).
- The new prompt must also include a reference to where the review came from to provide context — for example, if it was a conversation with a user or if it came from a GitHub comment or review, etc.
- Artifacts are organized into sibling **run folders** at the root of the pipeline's artifact folder: `base`, then `review-1-<short-description>`, `review-2-<short-description>`, … Each run folder holds the full phase structure (`0-prompt` … `5-docs`). `base/0-prompt` is the issue; `review-N-<short-description>/0-prompt` is that review's prompt.
- Reviews run **sequentially**, not in parallel. (Parallel runs would require extra worktrees and are out of scope here.)
- The prompt format and its generation are now shared between issue creation, base-prompt-generation and review-prompt generation, so the shared parts must be **factored into common files with no duplication in the skill**.
- **Naming:** `reviews` is the user-facing concept ("I want a review of this pipeline"); the first run folder is `base` and subsequent ones are `review-N-<short-description>` (the `-<short-description>` suffix mirrors the pipeline slug naming).
- **Prior-run awareness:** a review is agnostic to previous runs.
- **Orchestrator judgment:** for drastic changes the orchestrator may recommend a from-scratch fork instead of a review.

### Context

- The elegance is that **almost nothing changes in the agents**. A review is just the pipeline run again, except its branch already carries prior runs — so the same spec → design → plan → code → docs flow naturally produces only the incremental change.
- **Splitting one input into multiple reviews:** if the owner surfaces several apparently unrelated changes at once, the orchestrator can suggest capturing them in **separate reviews (one per change)** to run **sequentially** (`review-1-<short-description>`, then `review-2-<short-description>`), so unrelated changes can be inspected separately.
- **Consolidation at close-out:** a pipeline ends up with several prompts/specs/design-docs/plans. This is out of scope for this issue and will be added once we add the cleanup phase.

### Related

- Supersedes #58 (`review-pipeline.md` reference) — reviews are a whole way of working, not a single reference file.

### Q1b: Concretely — eager vs. lazy `base/`, and migrate vs. leave-flat for existing pipelines? Pick the option most consistent with the prompt and the existing skill philosophy.

**A:**

**(a) Eager `base/` (high confidence).** Every new pipeline gets a `base/` run folder from creation; a brand-new never-reviewed pipeline already has `base/0-prompt`, then `base/1-spec`, … The run-folder layer is unconditional, not review-triggered. The prompt treats `base` as the first run folder by definition ("the first run folder is `base`"; "`base/0-prompt` is the issue") with no flat-then-migrate intermediate state. Lazy creation would force a destructive in-place restructuring of already-committed, owner-inspected artifacts the moment the first review starts — contradicting "almost nothing changes". Eager creation means a review only ADDS a new sibling folder and never touches `base/`, which is exactly what "the only difference … is that the branch/worktree already contains the previous runs" requires.

**Key design-localizing insight (to carry as a requirement about agent-agnosticism, leaving the mechanism to design):** the lowest-duplication way to express eager `base/` is for the per-run folder `<pipeline-folder>/<run>/` to be what the orchestrator hands agents as "the artifact folder." Then every phase reference keeps saying `<artifacts-folder>/1-spec/...` unchanged, and the entire path change localizes to orchestrator-level references (workflows, create-pipeline, fork, versioning). This directly serves "almost nothing changes in the agents" and "no duplication." The spec must require that **agents remain run-agnostic**: they receive a folder and neither know nor care whether it is `base` or `review-N`. The prompt confirms this ("a review is agnostic to previous runs"; "the agent profiles stay the same (or very nearly so)").

**(b) Forward-only — no migration of existing flat pipelines (high confidence).** On disk: three pipelines use the current flat phase layout (`70-…`, `81-…`, `83-…`); two are pre-phase-structure legacy with loose files and no phase folders (`8-…`, `9-…`); and `95-…` itself is flat. Nothing in the prompt asks to migrate history; the only backward-shaped concern it raises (consolidation of accumulated artifacts) is explicitly deferred to the future cleanup phase. A review only happens on a pipeline being actively iterated, so migrating completed/merged flat pipelines would be churn with zero behavioral payoff. **Open sub-decision the spec must surface (not resolve silently):** whether the skill's listing/reconstruction logic must explicitly tolerate BOTH shapes — legacy flat `<pipeline-folder>/<phase>` treated as an implicit single `base` run — (option A, dual-shape reading) versus simply grandfathering pre-existing flat pipelines and documenting only the run-folder layout (option B, clean break). Researcher's lean: require reading to be backward-tolerant enough that `work-on-an-issue.md` step 2 (list/reconstruct existing pipelines) does not choke on the committed flat pipelines, with no rewrite — but flag the dual-shape-vs-grandfather choice explicitly.

**Reasoning:** Both core calls are directly supported by the prompt text (eager `base`; deferred consolidation). The agent-agnosticism point follows from the "almost nothing changes" + "no duplication" constraints. The dual-shape question is genuinely under-determined by the prompt, so it is recorded as an open assumption rather than a derived requirement.

Create `review-1-<short-description>/` as a sibling and let the flat phase folders stand as the implicit base run. This preserves the never-rewrite-prior-runs guarantee for legacy pipelines too. ### Q2: How does an owner trigger a review, and must the pipeline be COMPLETE (all 5 phases done) before a review can start?

**A:**

1. **Completeness precondition — YES.** A review requires the latest run to be complete: completed phase = 5, `5-docs/docs-review-approved.md` committed, no active phase. An incomplete run is handled by resume (finish it) or fork (try a different approach from a completed earlier phase), both of which already exist. Grounding: the existing dangling hook already encodes this — `work-on-an-issue.md:32-35` offers the Review/Merge/Close trio ONLY when "the pipeline's completed phase is the last phase (phase 5) and there is no active phase"; Resume/Fork are the in-progress actions (`:30-31`). Semantically, "build on top of existing code rather than an empty tree" is false if the prior run never produced code/docs. **ASSUMPTION flag:** the prompt says "re-runs the whole pipeline" but never states the precondition; derived from menu placement + layering semantics (high confidence).

2. **Merged pipelines.** Branch merged AND deleted → NO review (there is no branch/worktree to satisfy "same branch and worktree"); the correct action is a FORK from main, which the prompt itself names as the off-ramp ("for drastic changes the orchestrator may recommend a from-scratch fork"). Branch merged but still alive → a review is technically possible but unusual (layering onto an already-merged branch); offer it with a caveat or steer to fork. Canonical happy path: complete, **unmerged**, branch+worktree live — you review BEFORE merging (Review sits beside Merge in the menu). Grounding: prompt "never a new branch"; `pipeline-versioning.md:52` (merged+deleted pipeline is "only visible [in artifact folders on main]"). **ASSUMPTION flag:** merged-but-branch-alive sub-case is genuinely open.

3. **Entry point.** Canonical surface is `work-on-an-issue.md` step 2's existing menu — this feature FILLS the dangling "Review → read `review-pipeline.md`" hook (`:34`). The owner can also say "review this pipeline" mid-session; the orchestrator identifies the issue, lists pipelines (step 2), and routes to the same review procedure. Do NOT invent a second top-level entry point — keep it funneled through `work-on-an-issue.md`, consistent with Resume/Fork/Merge/Close. **Naming decision for spec/design:** because #95 "supersedes #58 (`review-pipeline.md` reference) — reviews are a whole way of working, not a single reference file," the menu target may NOT literally remain a single `review-pipeline.md`; the spec/design must decide what the Review action points at (a new reference, or a procedure spread across shared files).

4. **Sequencing.** review-N+1 may begin only after review-N is complete through `5-docs/docs-review-approved.md`. "Sequential" means strictly one-completed-run-then-the-next, not merely "not simultaneously." Observable rule: before creating `review-(N+1)-<desc>/`, verify the current latest run folder's phase-5 completion predicate is met (reusing `pipeline-versioning.md`'s predicate within that run folder); if not, finish/resume the current run first. Grounding: same layering semantics as facet 1, applied recursively; reinforced by single-worktree physics — all runs share one branch/worktree, so only one run can advance at a time; the splitting note's "review-1-…, THEN review-2-…" uses "then" = after completion. **ASSUMPTION flag:** "sequential" is stated; the precise complete-through-docs threshold is derived, not stated.

### Q3: How is each review's NEW prompt generated, what must it contain (esp. the source-of-the-review reference), and how is the prompt format/generation factored to satisfy the "no duplication" constraint?

**A:**

1. **Authorship/mode.** The orchestrator authors `review-N-<desc>/0-prompt/prompt.md` by running a `manage-issues.md`-style CAPTURE Q&A with the owner about the requested change, then writing to the run folder (NOT the tracker; the original issue and base prompt are never rewritten). It is the issue-creation flow re-pointed at a run folder. **Three generation SITES, two generation MODES:** (a) issue creation = capture Q&A → tracker; (b) base prompt = ADAPT existing issue → `base/0-prompt/` (`create-pipeline.md:23-28`, "do not add requirements", no re-Q&A); (c) review prompt = capture Q&A about the change → `review-N/0-prompt/`. The capture Q&A must gracefully handle a source that is already written down (a GitHub comment / PR review): then there is little to ask and the orchestrator mostly transcribes the source into the format. **ASSUMPTION flag:** "orchestrator runs a capture Q&A" is derived from "generated the same way an issue is" + orchestrator-driven manage-issues; the prompt doesn't literally say "Q&A," and the Q&A may be minimal-to-absent for an already-written source.

2. **Required contents — the source/origin reference.** MANDATORY for review prompts, ABSENT for issue/base prompts. The REQUIREMENT (must include the origin reference, reviews only) is DERIVED directly from the prompt.

3. **No-duplication factoring.**
   - **SHARED (common part):** the prompt FORMAT schema (Title, Goal [required, outcome-not-solution], Constraints, Context, Assumptions/directions-to-explore — all optional except Goal), the rendering rules (omit-empty / no N/A; a vague idea yields just Title+Goal), and the authoring discipline (outcome-not-solution; no requirements/design/implementation; reflect hypotheses as open; capture-don't-converge) — currently inline in `manage-issues.md:14-32`.

Each site keeps its own DESTINATION, SOURCE, and trigger/flow; only the FORMAT+discipline is hoisted.
   - **MECHANISM:** a NEW shared reference file (e.g. `prompt-format.md`) defines the schema + rendering + discipline; `manage-issues.md` and `create-pipeline.md` become thin call-sites that link to it (replacing inline prose); the new review procedure links to it too, adding only the Source-section requirement + destination. **DESIGN decision (granularity):** one file vs. splitting the format-schema (shared by all three) from the capture-discipline (used only by issue creation + review, since base-prompt adaptation does not run a Q&A). The run-folder NAMING PATTERN (`base`, `review-N-<short-description>`) is a fixed SKILL-level structure (not owner-configurable); only the `<short-description>` char-formatting borrows the project's slug convention. Crucially, a run folder is NOT a slug/branch/worktree and gets NO `-v<N>` suffix — it is purely a folder name on the same branch, orthogonal to the fork version axis. **ASSUMPTION flag:** the derivation algorithm (from Goal, kebab-case) is inferred from "mirrors the pipeline slug naming"; the per-pipeline counter reading is strongly implied by "review-1, review-2, …".

### Q4: How do reviews reconcile with the fork-based versioning/lineage model — do review runs appear in the pipeline tree, and how are "completed phase"/resume/listing defined when one branch carries multiple runs?

**A:** Governing principle: **RUNS and FORKS are two ORTHOGONAL axes.** A fork is a new BRANCH (new pipeline, `-v<N>` slug); a run is a layer WITHIN one branch (`base`, `review-N`). The clean reconciliation keeps the fork machinery operating at the BRANCH level and inserts a run level UNDERNEATH it.

1. **Completed/active phase with reviews.** A pipeline's completed/active phase is determined by its LATEST run (highest-numbered run folder), with the completion predicate evaluated WITHIN that run's folder: `<artifacts-folder>/<latest-run>/<phase>`. E.g. base complete-through-5, review-1 in progress at phase 2 → the pipeline's active phase = review-1's phase 2. Because eager `base/` guarantees there is always a latest run, this rule has no special case — it's the existing `pipeline-versioning.md:34` semantics with `<artifacts-folder>` → `<artifacts-folder>/<latest-run>`. **The spec must name TWO notions of pipeline state:** (i) the OVERALL pipeline state = its latest run's completed/active phase (used by resume); (ii) per-run completion (used to decide whether a NEW review may start — needs the latest run complete-through-5, Q2 facet 4). They coincide except during an in-flight review. DERIVED (from eager-base + strict-sequential: only one in-flight run ever).

2. **Resume.** Operates on the LATEST run's active phase; rollback target becomes `<artifacts-folder>/<latest-run>/<active-phase>`. Branch/worktree re-attach (`resume-pipeline.md:11-17`) is UNAFFECTED — same branch/worktree regardless of run (the reviews-stay-on-same-branch invariant). It is a path-scoping change, not a logic change. **NEW sub-case to define (DESIGN, prompt silent):** an abandoned review whose only artifact is its own `review-N/0-prompt/prompt.md` — resume should continue from phase 1 (spec) using that prompt (the prompt is the input, analogous to base's never-rolled-back phase 0); the alternative is deleting the empty review run folder. Define resume-from-prompt vs. delete-empty-run.

3. **Listing / tree reconstruction (CRUX) — Model (A).** The fork tree stays a FORK tree (one node-chain per forked pipeline/branch); **reviews are an INTRA-pipeline detail reported as run metadata on that pipeline's node, NOT rendered as new trie nodes.** Decisive evidence: the trie's shared root is "`0-prompt` is identical across every pipeline of an issue (it IS the issue)" (`pipeline-versioning.md:66`), but `review-N/0-prompt` is a DIFFERENT prompt (a new prompt, not the issue) — so if runs were trie nodes the "shared root = the issue" invariant collapses. Runs are a LINE within one pipeline node (sequential: "review-1, THEN review-2"); forks are a TREE. So step 2 lists pipelines (forks) and renders the fork tree exactly as today, ADDITIONALLY annotating each pipeline with its run sequence, e.g. `v1: base (complete) → review-1-add-x (complete) → review-2-fix-y (in progress)`. DERIVED (same-branch + trie-invariant). DESIGN: exact rendering of run metadata (inline vs. separate per-pipeline list).

4. **Lineage SHAs.** The `(phase, tree-SHA)` lineage trie stays STRICTLY a fork-vs-fork, cross-BRANCH concept; it does NOT compare run folders (runs within one branch are never seeded by copying from a sibling run — there's no cross-pipeline sharing to compute). The embedded real question — which RUN's phase folders the trie reads when comparing two FORKS — is answered: **compare each pipeline's `base/` run** (`<artifacts-folder>/base/<phase>`). Rationale: lineage is about what a fork inherited at creation; `base` is the original, never-rewritten run, so comparing latest-runs would wrongly make a fork's lineage shift whenever its parent later gets reviewed. ASSUMPTION (prompt silent on fork×run interaction — thinnest-evidence corner): lineage ignores runs; cross-fork comparison uses each pipeline's `base/`.

5. **Fork procedure run-awareness.** (a) The NEW fork starts with its OWN eager `base/` run — inherited phases land in `<new-artifacts-folder>/base/<phase>`; the fork's first run IS its base. (b) WHICH run of the PARENT a fork inherits from: **for THIS issue, keep fork behavior unchanged — inherit from the parent's `base/` run** (the original line), which keeps lineage=base everywhere (facet 4) and keeps "almost nothing changes" literally true for the fork machinery. **DEFER as OUT-OF-SCOPE:** "fork from a reviewed run" (inheriting from a parent's `review-N`) and any change to fork-inheritance semantics — it's a fork feature, not a review feature, and it would force lineage to record/compare the inherited run. DERIVED (new fork gets eager base); DESIGN/SCOPE (defer fork-from-reviewed-run).

**Minimal coherent reconciliation for #95 (researcher's recommendation, adopted):** insert a run level under each pipeline's artifact folder (eager base); run-scope completion/resume/"current state" to the LATEST run; keep FORK tree/lineage/listing at the BRANCH level comparing each pipeline's `base/` run (forks still inherit from base, unchanged); report reviews as per-pipeline run metadata, NOT new tree nodes; defer "fork from a reviewed run" and any fork-inheritance change as out-of-scope.

**DESIGN/SCOPE surfaced:** run-metadata rendering (F3); empty-review-run resume-vs-delete (F2); defer fork-from-reviewed-run (F5).

### Q5: What does a review RUN actually produce on top of existing code/docs — how do the design/plan/code/docs agents "build on the existing work", and what is the code-review diff base for a review run?

## Consolidated Requirements

Each requirement is an observable outcome. Tags: **[D]** derived directly from explicit prompt text; **[A]** assumption where the prompt is silent (well-supported, flagged for owner/design confirmation); **[design]** a decision deferred to phase 2. The HOW lives in the Q&A above; these state WHAT.

### A. Run-folder structure

1. **[D]** A pipeline's artifact folder is organized into sibling **run folders** at its root: `base`, then `review-1-<short-description>`, `review-2-<short-description>`, … Each run folder holds the full phase structure (`0-prompt` … `5-docs`). `base/0-prompt` is the issue; `review-N-<short-description>/0-prompt` is that review's own prompt.
2. **[A]** Every new pipeline is created with an **eager `base/` run folder** from the moment of creation — a brand-new, never-reviewed pipeline already has `base/0-prompt`, then `base/1-spec`, … `base` is always present; reviews only ADD sibling folders and never restructure `base/`.
3. **[D]** The artifact folder a run operates in is `<pipeline-folder>/<run>/`; agents are handed that per-run folder as "the artifact folder" and remain **run-agnostic** — they neither know nor care whether it is `base` or `review-N`. The base run never changes any agent profile.
4. **[D]** A run folder is purely a folder on the same branch — it is NOT a slug, branch, or worktree, carries NO `-v<N>` suffix, and does not change the pipeline's version. `review-N-<short-description>`: `N` is a per-pipeline monotonic counter (count existing `review-*` folders + 1); `<short-description>` is an orchestrator-derived kebab-case summary of that review's Goal, following the project slug char-rules (lowercase, hyphens, no spaces), mirroring the pipeline-slug naming.
5. **[A]** Existing flat-layout pipelines (phase folders directly under the pipeline folder, no `base/` run folder) are NOT migrated or rewritten, AND the skill contains no instruction, reference, or mention of how to handle a pipeline that lacks a `base/` folder — its guidance is authored solely for the run-folder model (`base/` always present). Encountering a legacy flat pipeline is left to the orchestrator's runtime judgment ("does what it can"), deliberately not codified or documented anywhere in the skill. _(Refined by owner direction after spec approval; this supersedes the original wording, which had the skill read a flat pipeline as an implicit single `base` run and left the earlier **[design]** dual-shape-reading-vs.-grandfathering question open. That question is now resolved: neither is written into the skill — it stays silent on the legacy shape. The Q&A history above is left intact as the record of the original deliberation.)_

### B. Triggering a review

6. **[D]** The owner requests a review through the existing `work-on-an-issue.md` step-2 menu — this feature FILLS the currently-dangling "Review" action — or by asking directly ("review this pipeline"), which routes to the same procedure. No second top-level entry point is introduced.
7. **[A]** A review can begin only when the pipeline's **latest run is complete** through phase 5 (`<latest-run>/5-docs/docs-review-approved.md` committed, no active phase). An incomplete latest run is handled by resume or fork, not review.
8. **[A]** A review is offered for a complete, **unmerged** pipeline whose branch/worktree is live (the canonical case: review before merge). If the pipeline was merged and its branch deleted, a review is NOT possible (no branch to layer onto) and the owner is directed to a fork; merged-but-branch-alive may be offered with a caveat. **[design]** exact handling of merged-but-branch-alive.
9. **[D]** A review stays on the **same branch and worktree** as the pipeline and NEVER creates a new branch. Starting a review re-attaches to the existing branch/worktree using the same logic as resume (re-enter if present, recreate from the branch if gone), reusing that behavior rather than reinventing it; it does not roll back anything (the latest run is complete).

### C. The review prompt

10. **[D]** Each review is driven by its **own new prompt** at `review-N-<short-description>/0-prompt/prompt.md`. The original issue and the base prompt are NEVER rewritten.
11. **[A]** The review prompt is authored by the **orchestrator** via a `manage-issues.md`-style capture pass about the requested change (generated the same way an issue is — Goal/Context/Constraints/…), written to the run folder (not the tracker), and committed by the orchestrator as the entry step of the review procedure (mirroring base phase 0). The capture pass gracefully handles an already-written source (e.g. a GitHub comment), where there is little to ask and the orchestrator mostly transcribes.
12. **[D]** The review prompt MUST include a **reference to where the review came from** (a conversation with a user, a GitHub comment, a PR review, etc.) — a section that is mandatory for review prompts and absent from issue/base prompts. It is self-contained: it carries the substance (quote/paraphrase) plus a convenience link, and any source assets (e.g. images) are placed in the run's `0-prompt/` and referenced relatively. **[design]** section name/placement (dedicated "Source"/"Origin" vs. under Context).

### D. Shared prompt-format factoring

13. **[D]** The prompt-format **definition** (section schema Title/Goal/Constraints/Context/Assumptions; omit-empty/no-N/A; outcome-not-solution; capture-not-converge; reflect-hypotheses-as-open) is single-sourced in one common file; **issue creation, base-prompt generation, and review-prompt generation all reference it with no duplication** — no site restates the schema or the authoring discipline. Each site retains its own distinct destination, source, and trigger (and the review-only Source section). **[design]** one shared file vs. splitting format-schema (all three sites) from capture-discipline (issue + review only, since base-prompt generation adapts an existing issue without a Q&A).

### E. What a review run produces

14. **[D]** A review run produces FULL, standalone phase artifacts (identical file structure to base) whose **content is scoped to the incremental change** described by the review prompt — the review's spec is a spec of the change, not a re-spec of the whole feature; the same holds for the design doc, plan, code, and docs.
15. **[D]** A review run **builds on top of the existing work** already in the worktree: the design/plan/code/docs agents extend the prior run's code and docs rather than rebuilding. This is achieved by the delta-scoped prompt propagating through the phases plus the agents' normal investigation of the live (non-empty) tree; "almost nothing changes in the agents" holds at the agent-profile level (no agent profile is rewritten). **[design]** how the "the worktree already contains a working implementation; extend it" cue is conveyed to the design/plan teams.
16. **[D]** For a review run, the code-review (and, symmetrically, the docs-review) **diffs against the prior run's tip** (the commit where the previous run ended), so the review inspects only the run's incremental change, not the accumulated tree. This is an orchestrator-supplied base-ref rule, requiring no agent change. **[design]** the precise mechanism for capturing/passing the prior-run tip.
17. **[D]** A review runs in either **autonomous or assisted** mode, chosen per run like any pipeline run. After the orchestrator authors the review prompt (mode-independent phase 0), the chosen mode drives phases 1-5. An assisted review can only advance through phase 3 (the existing assisted-mode limit on phases 4-5), so an assisted-only review is itself incomplete and cannot satisfy the completeness precondition for a subsequent review until finished autonomously.

### F. Sequencing and multiple reviews

18. **[D]** Reviews run **strictly sequentially**, never in parallel: `review-(N+1)-…` may begin only after `review-N` is complete through phase 5. Parallel reviews are out of scope.
19. **[D]** If the owner surfaces several apparently unrelated changes at once, the orchestrator MAY **suggest splitting** them into separate reviews (one per change) run sequentially, so unrelated changes are inspected separately; the owner decides the count and boundaries and may decline and put everything in one review. The orchestrator confirms boundaries before creating any run folder.

### G. Versioning, lineage, and tree reconciliation

20. **[A]** A pipeline's **completed/active phase is that of its latest run**, with the completion predicate evaluated within the latest run folder (`<pipeline-folder>/<latest-run>/<phase>`). All phase artifacts, including approval/rejection files, live under the run folder. Two distinct notions are kept explicit: the overall pipeline state (latest run's phase, used by resume) and per-run completion (used to gate the next review).
21. **[D]** Resume operates on the **latest run's active phase**; its rollback targets `<pipeline-folder>/<latest-run>/<active-phase>`. Branch/worktree re-attach is unchanged. **[design]** handling of an abandoned review whose only artifact is its own prompt (resume-from-prompt vs. delete the run folder).
22. **[A/D]** The **fork tree / lineage / pipeline listing stays at the branch level**: reviews are reported as per-pipeline **run metadata** (a linear chain within a pipeline node), NOT as new tree nodes. Cross-fork lineage comparison reads each pipeline's `base/` run (`<artifacts-folder>/base/<phase>`); reviews do not participate in cross-pipeline lineage. (Model A — required because review prompts are not the issue, so making runs trie nodes would break the "shared root is the issue" invariant.) **[design]** exact rendering of run metadata.
23. **[D]** Forking is unchanged for this issue: a new fork starts with its own eager `base/` run and **inherits from the parent's `base/` run**. Forking from a reviewed run (and any change to fork-inheritance semantics) is out of scope.

### H. Orchestrator judgment (advisory, non-gating)

24. **[D]** The orchestrator always **assesses** whether a requested change is drastic and, if so, MAY **recommend a fork instead of a review** — but this is advisory: the owner decides, the orchestrator never unilaterally redirects, and a review proceeds if the owner chooses it even for a large change. "Drastic" is a qualitative, anchored heuristic (the change would not layer cleanly onto the existing implementation — reworks the architecture / invalidates most existing code / is "redo differently" rather than "add/adjust"), with no numeric threshold.
25. **[D]** The orchestrator presents a clear **RESUME / REVIEW / FORK decision rule**: resume = finish an incomplete latest run (same branch); review = layer an incremental change on a complete run, same branch, build on existing code; fork = diverge onto a fresh branch from main. The sharpest discriminator is same-branch-build-on-existing (review) vs. new-branch-from-main-diverge (fork). **[design]** exact wording and placement.
