# Spec Research

## Rough Idea

# Bring the reviews-feature prose into AGENTS.md compliance

## Goal

The skill and agent prose introduced by this pipeline (PR #106) complies with the rules in `AGENTS.md` — minimalist wording, no duplicated information within a reading path, no duplication across paths, and no unnecessary negative phrasing — without losing meaning.

## Origin

The owner asked the orchestrator to check whether the changes in PR #106 (https://github.com/Automattic/radical-pipelines/pull/106/) follow the rules in `AGENTS.md` (https://github.com/Automattic/radical-pipelines/blob/trunk/AGENTS.md), then requested a review covering all findings. The check found the structural rules (genericity, cross-path dedup via `intent-format.md` and the single **Reviewer base ref** definition) are followed, but the new and edited prose violates the minimalism and no-repeat rules in these spots:

1. `fork-pipeline.md` states that forks never inherit the parent's reviews three times: step 4 ("a fork starts a fresh `base/` and never inherits the parent's reviews"), step 5 ("the parent's `review-*` runs (if any) are never inherited"), and again in the copy bullet ("from the parent's `base/` run").
2. `review-pipeline.md` states that the advisories are non-gating three times: step 1 ("The fork-vs-review and split advisories (next step) never gate a review the owner chooses"), step 2's heading "(non-gating)", and step 2's body ("Both advisories are recommendations only — the owner decides, and the orchestrator never unilaterally redirects").
3. `review-pipeline.md` step 3 restates the content of the **Reviewer base ref** rule it cites ("capture the review's base ref = the prior-run tip… While HEAD is still the prior-run tip (before the review intent is committed)"), which `pipeline-versioning.md` already states. `autonomous-workflow.md`'s "and hold it constant for the whole run" duplicates the cited rule the same way.
4. `pipeline-versioning.md` states that reviews are not part of the cross-pipeline tree three times: the lineage section ("reviews are not part of the cross-pipeline tree…"), tree-building step 3 ("a pipeline's reviews are not nodes"), and the rendering bullet ("reviews never add or move nodes"). "A pipeline with no reviews shows no run chain" is a defensive negative whose content is already implied.
5. `work-on-an-issue.md`'s new decision guide ends with a bullet ("The sharpest discriminator is…") that only restates the three bullets directly above it.
6. Minor: `pipeline-versioning.md`'s "The rows are unchanged; only their root is the run folder" adds nothing after the preceding sentence; `review-pipeline.md`'s opener "it never creates a new pipeline" overlaps step 6's "Same branch, same pipeline, so the version is unchanged"; the README and the changeset carry the same run-model sentence nearly verbatim.

The owner confirmed a single review covering all findings, including the minor ones.

## Q&A

### Q1: What exactly do the rules in `AGENTS.md` (repo root) say about minimalist wording, duplication within a reading path, duplication across reading paths, and negative phrasing — and which files do those rules govern? In particular, do they apply to `README.md` and `.changeset/` entries, or only to the skill/agent prose under `skills/`?

**A:** The rules live under `AGENTS.md`'s single heading "Rules when modifying the skill" (line 5), with five bullets:

- (a) Minimalism (line 7): the skill must be written in a minimalist way with the minimum amount of information possible to convey the same meaning; every word must serve a purpose; after writing, ask "Can I say this in fewer words without losing meaning?" and rewrite if yes.
- (b) Within-path duplication (line 8, quote): "The skill must not contain duplicate information in the current reading path. For example, if a file can only be accessed through another and that one already contains certain information, there is no need to repeat it again."
- (c) Cross-path duplication (line 11, quote): "On different paths, the skill must remain free of all duplication: if there is an instruction that is repeated in multiple files, that instruction must be moved to a separate file that the other files reference."
- (d) Negative phrasing (line 9, quote): "The skill must not contain negative phrases (don't do this, don't do that) unless that information is strictly necessary for its operation. That is, if by default the orchestrator or any of the agents have no reason to do something, there is no need to tell them not to do it."
- (Fifth bullet, line 10: stay generic/tool-agnostic — not among (a)–(d) but part of the same rule set.)

**Jurisdiction:** The rules are scoped, by their own wording, to "the skill" — every bullet begins "The skill must…". "The skill" resolves to the directory `skills/radical-pipelines/` (README.md:94). The reference prose under `skills/radical-pipelines/reference/` is inside that scope. `agents/` is a sibling top-level directory not named by these rules (README.md:94–95 lists the skill and the agent profiles as two separate bundled things). `README.md` and `.changeset/` entries are outside the jurisdiction these rules claim — nothing in AGENTS.md asserts authority over them (README.md:153 and CONTRIBUTING.md:82 treat AGENTS.md as shared cross-agent instructions / a meta file). So the intent's finding #6 README/changeset duplication cannot rest on AGENTS.md rules (b)/(c); it rests on the owner's request (the owner confirmed a single review covering all findings, including the minor ones).

**Caveat (separate, pre-existing issue):** README.md:167 says the standing changeset rule "lives in `AGENTS.md`," but current AGENTS.md (11 lines) contains only the five skill-modification rules — the standing rules were removed in commit 859826a. A stale cross-doc pointer; it does not change the jurisdiction answer and is not part of this pipeline's findings.

**Reasoning:** Scope is determined by the rules' own subject ("The skill must…") and heading ("Rules when modifying the skill"). None of the five bullets names README, changesets, or agents. Independently confirmed by a second research pass, which added: AGENTS.md contains zero occurrences of "README", "changeset", or "update" (grep, no matches), and jurisdiction over `agents/` profiles is at most inferred from the rules' spirit (README.md:62 frames skill + agents as one methodology), never stated — so the spec must state explicitly whether the compliance bar is the literal AGENTS.md text (skill-scoped) or the owner's broader request (which covers the README/changeset findings).

**Sources:** `AGENTS.md:5,7,8,9,10,11`; `README.md:94–95,153,167`; `CONTRIBUTING.md:82`; git commits 859826a, 6498f79, 94385ad.

### Q4: What repo conventions and checks govern delivering this change? Specifically: (a) does this review need its own changeset, or does the existing `.changeset/pipeline-reviews.md` on the same branch/PR cover it; (b) is editing that unreleased changeset entry (for finding 6c) permissible; (c) are there CI checks or lints that run on skill prose, or is verification purely a manual re-check against AGENTS.md; (d) does any README-update convention apply to a prose-only compliance edit?

**A:**

- **(a) No new changeset needed.** The Changeset Gate runs `npx changeset status --since=origin/trunk` over the whole PR and is satisfied by at least one valid changeset per PR, not per commit. PR #106 already carries `.changeset/pipeline-reviews.md` (`minor`, valid), which covers a prose-compliance edit on the same branch. The touched paths (`skills/**`, `README.md`) are release-relevant `changedFilePatterns`, but that only requires changeset *presence*. Were this a standalone PR, the documented choice for prose-only would be an empty changeset (`npx changeset --empty`, bump `none`) — not `patch`. Adding one here is optional, not mandatory.
- **(b) Yes, editing the unreleased changeset entry is permissible.** Changeset files are ordinary committed markdown, mutable until consumed (deleted) by `changeset version` at release. The only constraint is shape: `validate-changesets.mjs` checks the front matter (`---`/bump-type/`---` must stay valid; `minor` is fine; pre-1.0 forbids `major`). The prose body is free-form. `.changeset/` itself is not a release-relevant path, so editing it triggers no new changeset requirement.
- **(c) No prose or markdown CI exists.** package.json has only `release:version` and `test` (`node --test 'scripts/test/**/*.test.mjs'`); CONTRIBUTING.md:25–27 states there is no lint/typecheck. No markdownlint/prettier/remark/vale/textlint anywhere. The only PR-time gate is the Changeset Gate (npm ci, npm test, validate-changesets, changeset status). **Verification of this change is purely manual** — a re-check of the edited passages against the five AGENTS.md rules. Acceptance criteria must be defined in prose terms; there is no automated oracle. CI stays green as long as the changeset stays shape-valid and `scripts/test/**` is untouched.
- **(d) No enforced README-update convention.** The phrase "README-update rule" appears only in README.md:167 and is defined/enforced nowhere (grep across CONTRIBUTING.md and AGENTS.md: zero matches). README is in scope solely because finding 6c targets the README:157 ↔ changeset:5 duplication.

**Reasoning:** Full reads of CONTRIBUTING.md, all three workflows (changeset-gate.yml, release.yml, deploy-website.yml), package.json scripts, and .changeset/config.json; greps for linters and for any README-update rule.

**Sources:** CONTRIBUTING.md:25–27,38–59,61–85,88–97,130–143,181–187; changeset-gate.yml:4–5,29–37; release.yml:4–5; deploy-website.yml:4–6; package.json:11–14; .changeset/config.json:12; .changeset/pipeline-reviews.md:1–2; README.md:167.

## Consolidated Requirements

Compliance bar (from Q1/Q3): findings 1–5 and 6a/6b are violations of the literal AGENTS.md rules (which govern only `skills/radical-pipelines/`); finding 6c (README ↔ changeset) is in scope by the owner's explicit request, not by AGENTS.md's text. The six findings are the complete known violation list from a whole-diff check of PR #106.

1. `skills/radical-pipelines/reference/fork-pipeline.md` conveys the fact that a fork seeds only from the parent's `base/` run (reviews are not inherited) exactly once in its reading path — currently stated at lines 34, 38, and 42–43 — while step 5's copy instructions remain complete and executable (the `cp -r … /base/<phase>` paths themselves are operational content, not duplication).
2. `skills/radical-pipelines/reference/review-pipeline.md` conveys the fact that the fork-vs-review and split advisories do not gate an owner-chosen review exactly once — currently stated at lines 14, 16 (heading "(non-gating)"), and 18.
3. `review-pipeline.md` step 3 (line 31) and `autonomous-workflow.md` step 5 (line 37) instruct capturing the run's base ref by referencing the **Reviewer base ref** rule in `pipeline-versioning.md` without restating that rule's substance (what the value is, when to capture it, holding it constant); the substance remains stated only in `pipeline-versioning.md:21–28`. The steps remain executable by following the reference.
4. `skills/radical-pipelines/reference/pipeline-versioning.md` conveys the fact that reviews are not nodes of the cross-pipeline tree exactly once — currently stated at lines 65, 87, and 115 — and no longer contains the defensive-negative sentence "A pipeline with no reviews shows no run chain" (line 115), whose content is implied.
5. `skills/radical-pipelines/reference/work-on-an-issue.md`'s decision guide presents the resume/review/fork distinctions exactly once: the "sharpest discriminator" bullet (line 40), which only restates the three definitions at lines 37–39, is gone or replaced by content that adds information.
6. `pipeline-versioning.md`'s per-phase completion passage (line 51) no longer carries the sentence "The rows are unchanged; only their root is the run folder," which adds nothing after the preceding sentence.
7. `review-pipeline.md` states the same-branch/same-pipeline fact once: the overlap between the opener (line 3, "it never creates a new pipeline") and step 6 (line 48, "Same branch, same pipeline, so the version is unchanged") is resolved. (Research note: line 29's "NEVER create a new branch" restates the same fact and is available to the design as part of the same cluster.)
8. `README.md` (line 157) and `.changeset/pipeline-reviews.md` (line 5) no longer share the run-model sentence near-verbatim; each still serves its own purpose (README documents the run model; the changeset summarizes the release change). If the changeset body is the side edited, its front matter stays valid (`minor` bump unchanged).
9. No meaning is lost: every distinct fact conveyed by the flagged passages before the change is still conveyed afterwards — stated once at a canonical location or reachable through an explicit reference in the same reading path.
10. No new violations are introduced: the edits do not add duplication, unnecessary negative phrasing, or non-minimal wording anywhere in the PR #106 prose, and they leave the already-compliant patterns untouched (e.g., the pointer-only parentheticals in `autonomous-phases/4 - code.md` and `5 - docs.md`, and the `intent-format.md` dedup structure).
11. Delivery: the change lands on the existing branch/PR (#106) with no new changeset required (the existing `.changeset/pipeline-reviews.md` satisfies the per-PR gate); the Changeset Gate CI (npm test, validate-changesets, changeset status) remains green. Verification is a manual re-check of the edited passages against the five AGENTS.md rules — there is no automated prose oracle.

Out of scope: the stale README.md:167 pointer to standing rules absent from AGENTS.md (pre-existing, not introduced by PR #106); agent profiles under `agents/` (no findings; AGENTS.md jurisdiction there is inferred at most); pipeline artifacts under `.pipelines/`; `website/` and `.rp.md`; any compliance rewrite of prose outside the PR #106 diff.
