# Spec — Bring the reviews-feature prose into AGENTS.md compliance

## Overview

PR #106 introduces the reviews feature: new and edited prose across the skill (`skills/radical-pipelines/reference/`), plus a `README.md` paragraph and a changeset entry. A whole-diff check against `AGENTS.md` found the structural rules already satisfied — the feature is generic/tool-agnostic, and cross-path duplication is handled via the shared `intent-format.md` file and the single canonical **Reviewer base ref** definition. The remaining problems are local prose violations of the minimalism and no-repeat rules: the same fact stated three times within one reading path, a cited rule's substance re-derived next to its own pointer, a defensive negative whose content is already implied, and a near-verbatim sentence shared between the README and the changeset.

This review brings that prose into compliance with the five `AGENTS.md` rules (minimalism; no within-path duplication; no cross-path duplication; no unnecessary negative phrasing; stay generic) **without losing meaning** — every distinct fact the flagged passages convey today must still be conveyed afterwards, stated once at a canonical location or reachable through an explicit same-path reference.

This spec follows the intent's finding numbering: **findings 1–5** plus a **finding 6** that is a trio of minor items — **6a** (`pipeline-versioning.md`'s "rows are unchanged" sentence), **6b** (`review-pipeline.md`'s opener/step-6 within-path overlap), and **6c** (the README ↔ changeset near-duplicate). The compliance bar has two tiers, established by the research:

- **Findings 1–5 and 6a/6b (the `AGENTS.md`-governed prose).** The rules are scoped by their own wording to "the skill" (`AGENTS.md:5,7–11`), which resolves to `skills/radical-pipelines/`. All flagged skill passages — findings 1–5 and the two skill-internal minor items 6a and 6b — fall inside that jurisdiction. These are violations of the literal rules.
- **Finding 6c (README ↔ changeset).** `README.md` and `.changeset/` sit outside the jurisdiction the `AGENTS.md` rules claim (nothing in `AGENTS.md` names them). This pair is in scope **only because the owner explicitly requested a single review covering all findings, including the minor ones** — not by the literal rule text. It is still required; the spec records its different basis so the design treats it on the owner's authority rather than inventing rule jurisdiction.

The six findings (1–5 plus the 6a/6b/6c trio) are the **complete known violation list** from a whole-diff check of PR #106. A fresh pass is unlikely to surface large new violations, but the change must not introduce new ones (requirement 11).

All flagged passages have been re-verified against the current working tree; every line reference below is current at the time of writing.

## Requirements

### Within-path duplication — state each fact once (findings 1–2, 4, 5)

1. **`skills/radical-pipelines/reference/fork-pipeline.md`** conveys the fact that a fork seeds only from the parent's `base/` run (reviews are not inherited) **exactly once** in its reading path. The fact is currently stated three times: line 34 (step 4, "a fork starts a fresh `base/` and never inherits the parent's reviews"), line 38 (step 5, "the parent's `review-*` runs (if any) are never inherited"), and lines 42–43 (the copy bullet restating "from the parent's `base/` run"). The step-5 copy instructions stay complete and executable: the `cp -r <parent-worktree>/<parent-artifact-folder>/base/<phase> <artifacts-folder>/base/<phase>` paths are operational content (which phase folders to copy and from where), not a restatement of the no-inherit fact.

2. **`skills/radical-pipelines/reference/review-pipeline.md`** conveys the fact that the fork-vs-review and split advisories do not gate an owner-chosen review **exactly once**. The fact is currently stated three times in adjacent lines: line 14 (step 1, "The fork-vs-review and split advisories (next step) never gate a review the owner chooses"), line 16 (the heading "### 2. Advisories (non-gating)"), and line 18 (step 2 body, "Both advisories are recommendations only — the owner decides, and the orchestrator never unilaterally redirects").

3. **`skills/radical-pipelines/reference/pipeline-versioning.md`** conveys the fact that a pipeline's reviews are not nodes of the cross-pipeline tree **exactly once**. The fact is currently stated three times: line 65 (lineage section, "reviews are not part of the cross-pipeline tree, because lineage is a cross-fork comparison…"), line 87 (tree-building step 3, "a pipeline's reviews are not nodes"), and line 115 (rendering bullet, "reviews never add or move nodes").

4. The defensive-negative sentence **"A pipeline with no reviews shows no run chain"** (`pipeline-versioning.md:115`) is removed. Its content is already implied by the run-chain description that precedes it (a pipeline's runs render as `base → review-1-… → …`; with no reviews there is nothing after `base`, so no chain is shown). This is an `AGENTS.md` negative-phrasing violation: the orchestrator has no default reason to render a chain for a review-less pipeline, so it need not be told that none appears.

5. **`skills/radical-pipelines/reference/work-on-an-issue.md`**'s same-issue decision guide presents the resume/review/fork distinction **exactly once**. The "sharpest discriminator" bullet (line 40, "The sharpest discriminator is same-branch-build-on-existing (review) vs. new-branch-from-main-diverge (fork); resume is the option when the latest run is incomplete.") only restates the three definitions immediately above it (lines 37–39: Resume = same branch, finish incomplete latest run; Review = same branch, layer onto a complete run; Fork = fresh branch from main). It is removed, or replaced by content that adds information the three definitions do not already carry.

### Cross-pointer restatement — cite the rule without re-deriving it (finding 3)

6. **`review-pipeline.md` step 3 (line 31)** and **`autonomous-workflow.md` step 5 (line 37)** instruct capturing the run's base ref by **referencing** the **Reviewer base ref** rule in `pipeline-versioning.md`, without restating that rule's substance — specifically what the value is (the prior-run tip / the merge-base), when to capture it (while HEAD is still the prior-run tip, before the review intent is committed), and that it is held constant for the whole run. That substance remains stated only at its canonical location, `pipeline-versioning.md:21–28`. Each step stays executable by following the reference: the reader who needs the value reads the cited rule.
   - Currently `review-pipeline.md:31` re-derives the value and timing ("While HEAD is still the prior-run tip (before the review intent is committed), capture the review's base ref = the prior-run tip, per the **Reviewer base ref** rule in `pipeline-versioning.md`."), and `autonomous-workflow.md:37` re-derives the hold-constant clause ("capture the run's base ref per the **Reviewer base ref** rule in `pipeline-versioning.md` and hold it constant for the whole run…").
   - The near-compliant pointer parentheticals in `autonomous-phases/4 - code.md:35` and `5 - docs.md:36` are the closest existing model, but they are not the exact target: each reads "(the start of the current run — see the **Reviewer base ref** rule in `pipeline-versioning.md`)" — a reference plus a brief orienting gloss ("the start of the current run") that paraphrases the rule's own keying clause (`pipeline-versioning.md:23`, "keyed on the start of the current run"). The target for the two edited steps is **stricter than those parentheticals**: a reference to the **Reviewer base ref** rule with at most a minimal orienting phrase, and **no restatement of the rule's substance** — not the value (the prior-run tip / merge-base), not the capture timing (while HEAD is still the prior-run tip, before the review intent is committed), and not the hold-constant clause. The orienting gloss "the start of the current run" is the keying phrase from the rule itself, not part of the substance the steps must drop, so a parenthetical at the 4/5 level is acceptable; a bare reference is also acceptable.

### Minimalism — drop wording that adds nothing (finding 6a)

7. **`pipeline-versioning.md`'s per-phase-completion passage (line 51)** no longer carries the trailing sentence **"The rows are unchanged; only their root is the run folder."** The sentence before it already states the predicate is evaluated at `<artifacts-folder>/<run>/<phase>` (for the base run, `<artifacts-folder>/base/<phase>`), which is the same fact; the trailing sentence adds no information.

### Within-path overlap — resolve the same-branch/same-pipeline cluster (finding 6b)

8. **`review-pipeline.md`** states the "a review reuses the existing branch and pipeline, so it creates no new pipeline and leaves the version unchanged" fact **once**. The overlap to resolve is the pair the intent's finding 6b names: the opener (line 3, "A review reuses the existing branch and worktree — it never creates a new pipeline.") and step 6 (line 48, "Same branch, same pipeline, so the version is unchanged."). The resolution keeps each location's distinct operational content — the opener's framing of what a review is, step 6's instruction to re-assert the version — while the shared "no new pipeline / same branch / version unchanged" assertion appears once across those two locations.

   Line 29's "and NEVER create a new branch" is **classified as operational content of the re-attach step**, not part of this cluster, and is left in place. The re-attach step (line 29) directs the orchestrator through resume's branch/worktree re-attachment; "NEVER create a new branch" is an override of what that procedure could otherwise do at that point — directly analogous to the same line's "Do NOT perform resume's rollback step", which overrides resume's rollback. Both are step-3 operational overrides of the cited resume procedure, so neither counts against the once-stated assertion and both are preserved. (This scopes the dedup to the opener/step-6 pair, matching the intent, whose finding 6b names only those two.)

### README ↔ changeset duplication (finding 6c — owner's request, outside `AGENTS.md` scope)

9. **`README.md` (line 157)** and **`.changeset/pipeline-reviews.md` (line 5)** no longer share the run-model sentence near-verbatim. Today both carry it:
   - README:157 — "Every pipeline carries a `base/` run from creation — the original run, never rewritten — and each review adds a sibling `review-N-<short-description>/` run on the same branch."
   - changeset:5 — "Every pipeline now carries a `base/` run from creation (the original run, never rewritten), and each review adds a sibling `review-N-<short-description>/` run…"

   Each file still serves its own purpose afterwards: the README documents the run model for a reader of the project docs; the changeset summarizes the release change for the changelog. The resolution differentiates the two so they are no longer near-duplicates, not by stripping one to a pointer (a changelog entry must stand alone and cannot reference the README). If the **changeset body** is the side edited, its front matter stays valid and unchanged: the `"@automattic/radical-pipelines": minor` bump is preserved (per Q4, `minor` is shape-valid and a prose-compliance edit warrants no bump change).

### Meaning preservation and no new violations

10. **No meaning is lost.** Every distinct fact the flagged passages convey before this change is still conveyed afterwards — stated once at a canonical location, or reachable through an explicit reference in the same reading path. Concretely, after the edits a reader still learns: that a fork inherits only `base/` and not reviews (1); that the advisories never gate an owner-chosen review (2); that reviews are not cross-pipeline-tree nodes (3); how to render a review-less pipeline's run chain (4 — by the general run-chain rule, now without the redundant restatement); the resume/review/fork distinction (5); the base-ref value, timing, and hold-constant rule (6 — at its canonical location, reachable from both citing steps); where the per-phase predicate is evaluated (7); that a review reuses the branch and leaves the version unchanged (8); and the run model in both the README and the changelog (9).

11. **No new violations are introduced.** The edits add no duplication, no unnecessary negative phrasing, and no non-minimal wording anywhere in the PR #106 prose, and they leave the already-compliant patterns untouched — specifically the **Reviewer base ref** reference parentheticals in `autonomous-phases/4 - code.md:35` and `5 - docs.md:36` (each a reference plus the orienting gloss "the start of the current run", not a restatement of the rule's value/timing/hold-constant substance), the `intent-format.md` cross-path dedup structure, and the single canonical **Reviewer base ref** definition in `pipeline-versioning.md:21–28` (which is the dedup target for requirement 6 and must remain intact and complete). Fixes for one finding must not reintroduce the same fact at another in-path location.
