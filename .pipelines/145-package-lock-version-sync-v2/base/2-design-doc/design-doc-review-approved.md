# Design Doc Review

## Verdict: approved

## Summary

The design is complete, traceable, feasible, and stays at design altitude. Every one of the 11 spec requirements and every acceptance criterion maps to a concrete decision or component, and each Key Decision carries an explicit "Traces to:" line citing the requirement(s) and AC(s) it serves. The architecture is a single one-directional propagation (`package.json` → manifests → lockfile, wired into the existing `release:version` script that both the CI path and the manual escape hatch already funnel through) plus a read-only drift guard mirroring the existing `validate-changesets.mjs` and wired into the existing PR gate. I verified the load-bearing factual claims against the real codebase and they all hold: the comparison set is exactly the four version-bearing JSON-path locations; the guard compares by structured JSON path rather than text search, which is justified because the lockfile genuinely contains unrelated `0.4.0`/`0.1.1` strings; the lockfile self-name is unique to the root `.packages[""]` entry with no `node_modules/` self-entry and no top-level `.dependencies` mirror; and both release paths reach the appended sync step with no per-path duplication. The owner-fixed `npm install --package-lock-only` constraint is honored throughout and not re-litigated. Alternatives and trade-offs are credibly considered for every decision, dependencies and failure modes are named, and the few residual items are correctly classified as accepted trade-offs, risks, or open questions deferred to later phases rather than design gaps.

## Verification notes

- **Coverage and traceability.** Reqs 1-3 → append `&& npm install --package-lock-only --no-audit --no-fund` to `release:version`; reqs 4-7 → empirically-verified `--package-lock-only` behavior; reqs 8-9 → one-time backfill via the same command; reqs 10-11 → `check-version-sync.mjs` + gate step. The "How each acceptance criterion is met" section walks every AC individually.
- **Feasibility confirmed in the codebase.** `package.json` `release:version` is `changeset version && node scripts/sync-version.mjs` (append point exists); `release.yml` calls `version: npm run release:version`; `CONTRIBUTING.md` manual hatch step 1 calls `npm run release:version` and step 2 commits with `git commit -am`, so the modified lockfile is staged automatically with no manual lockfile edit; `changeset-gate.yml` has an adjacent identical-shape "Validate changeset shape" step and a job-level `if: github.head_ref != 'changeset-release/trunk'` exemption the new step inherits; `validate-changesets.mjs` and its `scripts/test/` paired test exactly match the proposed pure-function + `main()` + `isMainModule()` + `spawnSync` shape.
- **Structured-path decision is load-bearing and correct.** Confirmed unrelated string matches in `package-lock.json`: `@changesets/get-version-range-type@0.4.0`, `@changesets/write@0.4.0`, `node >= 0.4.0` engines, `@changesets/logger@0.1.1` (multiple), and an `ip-address ^10.1.1` substring — a text search would false-fail. Dependency `.version` fields equal to the targets confirm the guard must read the exact paths `.version` and `.packages[""].version`, not iterate all `.version` keys; the design specifies exactly those.
- **Lockfile comparison set is exhaustive.** `lockfileVersion: 3`; the only `.packages` entry named `@automattic/radical-pipelines` is the root `""` key; no `node_modules/@automattic/radical-pipelines` self-entry; no top-level `.dependencies` mirror. So the two cited lockfile fields are the complete lockfile set.
- **Owner constraint honored.** `sync-version.mjs` is left untouched and the lockfile is never added to `TARGET_MANIFESTS`; the lockfile version is synced exclusively by `npm install --package-lock-only`.

## Issues

None. The residual items (final script/test filenames, a possible one-line CONTRIBUTING note, the feature's own changeset bump type, and node-22 verification of `--package-lock-only`) are correctly recorded as open questions or low risks deferred to later phases, and the wide-diff and registry-dependence cases are correctly classified as accepted trade-offs per the spec rather than design gaps.
