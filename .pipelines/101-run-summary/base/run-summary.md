# Run Summary

## What

Adds a generic per-run summary artifact to the Radical Pipelines skill. Every run (`base` and each `review-N`) now produces exactly one `run-summary.md` at the run-folder root, written once when the run completes its final phase (5 – Docs). The summary records what the run changed and why, plus the run's key decisions, rejected approaches, and known limitations. The phase-5 completion predicate is extended so a run does not count as complete until its summary exists. When a review run starts, the orchestrator collects all prior runs' summaries in run order and feeds them into the review's phase 1, so a review builds on an accurate picture of the runs before it. The skill ships a default What/Why/How-plus-context format that a project can override through a new optional convention.

The change is documentation-and-orchestration only — no application code. Concretely it ships:

- A new skill format file `reference/run-summary-format.md` defining the default structure (`# Run Summary` with H2 sections What, Why, How, Key decisions, Rejected approaches, Known limitations), with omit-empty (no `N/A`) and standalone-document discipline.
- A new single-shot `run-summary-writer` agent (`agents/run-summary-writer.md`) that writes the summary from the run's committed artifacts and shipped code/docs read as files, registered in `.rp.md`'s Agent models table on `opus`.
- An extended phase-5 completion predicate and generalized artifact-layout wording in `reference/pipeline-versioning.md` so a run-level path (`run-summary.md`) is valid alongside the common `<phase>/…` case.
- The phase-5 procedure (`reference/autonomous-phases/5 - docs.md`) launching the writer after docs approval and verifying the extended predicate as its final step.
- Prior-summary collection in `reference/review-pipeline.md` (step 7).
- Fork handling in `reference/fork-pipeline.md` (step 7): a fork inheriting `5-docs` produces its own summary so it lands complete.
- The run summary named in `SKILL.md`'s phase-5 "Produces" cell, the optional "Run summary format" convention in `reference/conventions/load.md` and `setup.md`, README updates to the run model and conventions list, and a minor changeset.

## Why

A pipeline executes as a sequence of runs on one branch (`base`, then `review-1`, `review-2`, …), each a full pass of the phase flow. Reviews are by design agnostic to the runs before them — nothing carried one run's outcome into the next. This left later review runs without an accurate picture of what earlier runs decided and why. The run summary is the artifact that selectively reintroduces prior-run awareness: each run leaves a single, generic, inspectable record of its change, and review runs read the prior summaries to build on that history — all without coupling Radical Pipelines to GitHub, git, or any issue tracker. Each project also gets one artifact per run it can consume however it needs, while the artifact itself stays a run summary, not a PR description.

## How

The summary is folded into phase 5 rather than given a new phase: it is produced as the final step after `doc-reviewer` approval, and the existing **Per-phase completion** predicate's phase-5 row is extended to require `run-summary.md` alongside `docs-review-approved.md`. Because both moments that evaluate completion — end-of-phase and the review-start gate — read that one predicate table, extending a single row gates run completion everywhere at once, with no second completion condition to keep in sync. Resume delegates to the same predicate, so a run with docs approved but no summary automatically has phase 5 as its active phase and re-runs it.

The artifact lives at `<artifacts-folder>/<run>/run-summary.md` — at the run-folder root, outside any phase folder, with a constant filename. Run identity is carried by the `<run>/` path segment, never the filename, matching every existing artifact and keeping run-agnostic agents from ever seeing the run name. This placement makes two properties structural rather than special cases: fork's copy loop touches only phase folders, so the run-level summary is never copied on fork; and the lineage tree-SHA logic hashes only `base/<phase>` folders, so a run-level file never pollutes a phase tree SHA. Supporting this placement required generalizing two co-located sentences in `pipeline-versioning.md` that previously pinned all artifacts to `<run>/<phase>`.

A new single-shot `run-summary-writer` agent produces the summary from the run's own committed artifacts and the shipped code/docs read as files. It is given no git base ref and never inspects a diff, keeping the mechanism git-free. The orchestrator resolves the summary format (project override else the skill default `run-summary-format.md`) and hands it to the writer as a launch-specific extra input, following the existing reviewer-base-ref precedent. The writer is launched in two places: the phase-5 procedure on approval, and `fork-pipeline.md` when a fork inherits a complete `5-docs` (so the fork produces its own summary from its inherited artifacts and lands complete).

For review input, `review-pipeline.md` collects each prior run's `run-summary.md` in run order (`base, review-1, …, review-(N-1)`) before mode dispatch, then delivers the collected content into the review's phase 1 — as content in spawn prompts for an autonomous review, read directly by the orchestrator for an assisted one. Summaries are passed as content, never as run-named paths, so phase-1 agents stay run-agnostic; phases 2–5 are unchanged because phase 1 has already absorbed the prior context.

## Key decisions

- **Fold the summary into phase 5, gated by the existing predicate.** Producing it as phase 5's final step and extending the one **Per-phase completion** row keeps a single completion source that every completion, resume, and review-gate check already reads — rather than a new phase 6 (which the spec's fixed final phase forbids and which would bring a review apparatus the spec excludes) or a separate close-out condition (which would split "run complete" across two places).
- **Run-level placement with a constant filename.** `<artifacts-folder>/<run>/run-summary.md` makes fork-exclusion and lineage-cleanliness structural, at the cost of only the layout-wording generalization in `pipeline-versioning.md`. The constant filename matches the universal naming convention (run-agnostic agents never see the run name); the `run-` prefix makes the name read as a single run's summary.
- **A new single-shot `run-summary-writer`, artifacts-only.** A dedicated agent follows the established add-a-role pattern and keeps the mechanism generic. Orchestrator authorship would break the rule that agents author their own artifacts; overloading `doc-reviewer` (review-only, may iterate) or a `doc-writer` (single-task-scoped) would break their contracts. Grounding it in committed artifacts with no diff keeps it git-free.
- **Skill default format plus a new optional override convention.** A dedicated format file plus the existing inherit-or-override semantics composes two established precedents (`intent-format.md` and `.rp.local.md` resolution) with the least new surface. The convention is optional so `load.md`'s missing-required block never fires on a silent project; the skill file is the silent fallback.
- **Default structure: What / Why / How plus run-level context.** The three context concerns (key decisions, rejected approaches, known limitations) each get their own H2 rather than being folded under "How," matching the house style's section-per-concern and keeping the summary legible to a later review run that reads it with no other prior-run context.
- **`review-pipeline.md` collects prior summaries; no new immutability rule.** It is the only file that already knows run names and already uses the extra-spawn-input channel. R6 immutability is already covered by the general "a review only ADDS a sibling run folder, never rewrites prior runs" rule, so no summary-specific immutability sentence was added.
- **A fork inheriting `5-docs` produces its own summary.** Reusing the writer for the fork's `base` run satisfies R10's "each pipeline's runs produce their own" and prevents a fork from landing phase-5-incomplete under the extended predicate.

## Rejected approaches

- **A dedicated phase 6 for the summary**, or a separate run-completion condition in the orchestrator's close-out. The phase contradicts the spec's fixed final phase and adds a writer/reviewer/folder apparatus the spec excludes; the close-out condition splits "run complete" into two definitions that every completion path would have to restate.
- **Placing the file inside the phase folder** (`<run>/5-docs/run-summary.md`) or in a dedicated pseudo-phase subfolder (`<run>/summary/`). A file under `5-docs/` would be copied by a fork inheriting phase 5 (violating the no-copy requirement unless a negative exclusion is added) and would pollute the `5-docs` lineage tree SHA; a pseudo-phase subfolder is heavier with no benefit.
- **Having the orchestrator write the summary**, or overloading an existing phase-5 agent (`doc-reviewer` on approval, or the last `doc-writer`). Orchestrator authorship breaks the agents-author-their-own-artifacts rule; the existing agents' contracts (review-only/iterating; single-task-scoped) do not fit a once-after-approval ungated write.
- **Defining the format inline in the phase-5 procedure**, or only in the project-side agent. Inline mixes a format spec into a procedure and offers no override hook; project-only fails the requirement that the skill define a default.
- **What/Why/How only**, with the three context concerns folded under "How." This buries the decisions/rejected/limitations that a later review most needs.
- **Folding prior-summary context into the review intent**, or having the shared `autonomous-workflow.md` detect review runs and gather siblings itself. Folding into the intent fails the requirement that summaries be inputs in their own right and bloats the intent past its capture-the-request discipline; putting collection in the shared workflow breaks that workflow's deliberate run-agnosticism.
- **For forks: constraining inheritable phases to `4-code`** so a fork always runs phase 5 itself, or defining a bespoke inherited-`5-docs` completion path, or doing nothing. Constraining inheritance removes a capability the skill currently offers; a bespoke path adds new state semantics for no gain; doing nothing regresses a supported state into a blocked review gate and a destructive resume rollback.

During the run, the design, plan, and code reviews each rejected an iteration before approval, and those rejections shaped the final result. The design review surfaced that the extended predicate would otherwise leave a fork inheriting `5-docs` permanently incomplete (resolved by the fork producing its own summary), that the phase-5 predicate-verification step had to move after the summary rather than stay in place, and that `SKILL.md`'s phase table needed updating. The plan review corrected the verify step so it extends rather than replaces today's artifact enumeration, reordered the convention task before the procedures that consume the resolved format, fixed the optional-convention heading style, scoped the no-git constraint to the format and mechanism (leaving the skill's established commit/branch vocabulary untouched), and removed mandated negative phrasing and a duplicated spawn-prompt statement. The code review fixed `review-pipeline.md` to make collection (not delivery) the pre-dispatch step and drop a non-operational rationale clause, and removed a restated resolution rule from `fork-pipeline.md` step 7.

## Known limitations

- **Summary accuracy is ungated.** The spec excludes a content review gate, so an inaccurate summary could mislead a later review run. The only mitigation is grounding: the writer reads the full committed run record — all phase artifacts, the rejection files, and the shipped code/docs.
- **A project override replaces the format wholesale.** The key-decisions / rejected-approaches / known-limitations guarantees hold only for the skill default; a project that overrides the format takes responsibility for its own structure. This is deliberate and sanctioned by the spec.
- **Resume rewrites an incomplete run's own summary.** A run with docs approved but no summary has phase 5 as its active phase, so resume re-runs phase 5 and rewrites `run-summary.md`. This is correct: immutability applies to completed runs' summaries, not to one being written by its own still-incomplete run.
- **Out of scope by design:** consuming the artifact (opening, updating, or pushing a PR) is left to each project; later runs never edit prior runs' summaries; summaries are never copied when a pipeline is forked; and no application code, runtime, or CI behavior changes.
