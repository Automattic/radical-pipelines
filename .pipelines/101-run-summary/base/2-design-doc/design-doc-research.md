# Design Research: Generic per-run pipeline summary artifact

## Research

### How runs execute and complete today (Q1)

- **Run lifecycle.** A run is one pass of the full phase flow recorded under a pipeline. Runs execute sequentially on one branch/worktree: `base` first, then `review-1-<short-desc>`, `review-2-<short-desc>`, … — each review added only on top of a complete prior run. Reviews never create a new branch; they add a sibling run folder. Source: `reference/pipeline-versioning.md` ("Runs within a pipeline"), `reference/review-pipeline.md` steps 3–4.
- **Folder layout.** Artifacts live at `<artifacts-folder>/<run>/<phase>/`, with `<run>` ∈ {`base`, `review-N-<short-desc>`} and six phase subfolders `0-intent` … `5-docs`. Verified on disk (e.g. `.pipelines/95-pipeline-reviews/`). Older flat layouts (no `<run>/` layer) exist on disk but are migration leftovers; the current design is the `<run>/` layout and the skill documents only that. Source: `pipeline-versioning.md`, `SKILL.md` phases table, `autonomous-workflow.md` step 5.
- **Run completion.** Governed by the **Per-phase completion** predicate table in `pipeline-versioning.md`; paths are relative to the run folder; same predicate regardless of workflow mode. Phase 5's entire predicate today: `5-docs/docs-review-approved.md` committed. "Per-run completion" = complete through phase 5; it gates whether a new review may start (`review-pipeline.md` step 1a).
- **Phase 5 today.** Sequential fresh `doc-writer`s per task, then one fresh `doc-reviewer` per batch; rejection writes `docs-review-N-rejected.md`, approval writes the singleton `docs-review-approved.md`; orchestrator then verifies the phase-5 predicate (`autonomous-phases/5 - docs.md` step 6). Only autonomous runs reach phase 5 — the assisted workflow advances only through phase 3 (`SKILL.md`, `review-pipeline.md` step 7).
- **Who evaluates completion.** The orchestrator, at two moments reading the same predicate: end-of-phase (`autonomous-workflow.md` step 5.4) and the review-start gate (`review-pipeline.md` step 1a). Extending the phase-5 predicate row therefore gates run completion everywhere at once.
- **Review-run inputs today.** A review run's only seed input is its own self-contained `0-intent/intent.md`; phase 1 consumes only that. **No mechanism passes prior-run artifacts into a review run** — reviews are by design agnostic to prior runs. Requirement 5 (prior summaries as review input) is net-new plumbing.
- **Fork behavior.** `fork-pipeline.md` step 5 copies **only phase folders** (`base/0-intent` up to the inherited phase). Run-level files (outside phase folders) are structurally never copied.

### Run-level file feasibility, fork inheritance, naming (Q2)

- **Resume.** `resume-pipeline.md` delegates state entirely to the **Per-phase completion** predicate ("Read the actual files on the branch and confirm the state against the Per-phase completion predicate… evaluated within the pipeline's latest run"). Once the phase-5 row requires the summary, a run with docs approved but no summary has phase 5 as its *active* phase and resume re-runs it — correct behavior, no resume changes needed. Small interaction: resume's rollback reverts the active phase's commits assuming one phase folder; since the summary is a single file written last, the design should state that re-running phase 5 rewrites the run summary.
- **Predicate wording tension.** Two sentences in `pipeline-versioning.md` pin artifacts to `<run>/<phase>`: line 15 ("Artifacts live at `<artifacts-folder>/<run>/<phase>`…") and line 51 ("a phase's predicate is evaluated at `<artifacts-folder>/<run>/<phase>`…"). A run-level path in the phase-5 row requires generalizing both sentences — 2 co-located sentences plus 1 table cell, all in `pipeline-versioning.md`.
- **Fork inheritance reaches phase 5.** `fork-pipeline.md` step 1 lists `5-docs` as an inheritable phase, and step 5 copies `cp -r … base/<phase> …` for every inherited phase folder. A summary inside `5-docs/` **would** be copied by a fork inheriting phase 5, violating Req 10 unless a negative fork-exclusion is added. A run-level file is structurally never copied: the copy loop only touches `<phase>` folders. Run-level placement is therefore *necessary* for a clean Req 10, not just cleaner.
- **Lineage.** The tree-SHA lineage logic in `pipeline-versioning.md` hashes `base/<phase>` folder trees only. A run-level file stays out of lineage comparison; a summary inside `5-docs/` would pollute the phase-5 tree SHA (summaries always differ per run).
- **Health monitoring.** Reads the artifact folder generically (signals, not layout); no phase-folder enumeration to break.
- **Naming convention.** Every artifact filename is constant (`intent.md`, `spec.md`, `design-doc.md`, …); run identity is carried only by the `<run>/` path segment, never the filename. Agents are run-agnostic and never see the run name (`autonomous-workflow.md`), so a filename cannot embed it. Grep finds no existing `summary*` file or path — no collision.

### Producer precedent and content sources (Q3)

- **Who authors artifacts.** Rule: agents author all phase artifacts. `SKILL.md` (autonomous workflow): "You orchestrate teams of agents to do each phase's work; you do not produce the artifacts yourself"; `autonomous-workflow.md`: "Agents commit their own artifacts… The orchestrator does not commit on their behalf." Exceptions are narrow: phase-0 intent is orchestrator-authored (`create-pipeline.md` step 4, `review-pipeline.md` step 5), and the assisted workflow (phases 1–3 only) has the orchestrator write artifacts — neither reaches phase 5.
- **Skill/project division for agents.** The skill defines roles generically in each phase's "Required agents" table (name, one-line role, persistent?); the project supplies the concrete definition (`agents/<name>.md`) and a model row in `.rp.md` ("Agent models" convention). Spawning follows the "Team spawning" convention. Adding an agent costs: one table row + one step + one outputs line in the phase reference (skill side); one agent file + one model row (project side).
- **Existing agents can't absorb it.** `doc-reviewer` is review-only ("Do NOT rewrite the docs. You only review") and may iterate; the summary is written exactly once and is not review-gated. Each `doc-writer` is contractually scoped to a single doc task ("Single task only"). Overloading either breaks its contract.
- **Content sources, all inside `<run>/` and committed by end of phase 5** (each phase's predicate requires its artifacts committed before the next phase runs): what changed — `1-spec/spec.md`, `3-plan/code-plan.md` + `doc-plan.md`, the shipped code/docs; why — `spec.md`, `2-design-doc/design-doc.md`; key decisions — `design-doc.md`; rejected approaches — `design-doc.md` alternatives plus the `*-review-N-rejected.md` files of phases 1–5; known limitations — `design-doc.md` risks, `spec.md` out-of-scope. Nothing needed lives outside the run folder; for a review run, its own folder holds its own artifacts — the correct scope.
- **Genericity.** Writers work purely from artifacts; only reviewers touch git, via an orchestrator-computed base ref ("Reviewer base ref" in `pipeline-versioning.md`; `code-reviewer.md`/`doc-reviewer.md` "Inspect the diff… base ref → current HEAD"). Reading shipped code as files is an established writer pattern (`doc-writer.md`). Grounding the summary in artifacts only keeps the mechanism git-free per Req 9.

### Conventions, format precedents, house style (Q4)

- **Conventions mechanism.** Named conventions live in the `conventions/load.md` table (nine, plus "Artifact storage" from `setup.md`); project values live in `.rp.md`, read by the orchestrator at workflow start. Agents never read `.rp.md`: convention values reach them via the spawn prompt ("Each time you spawn an agent, include the following project conventions in its initial prompt: Artifact folder… Commit format…" — `autonomous-workflow.md`).
- **No existing skill-default-with-project-override format convention.** `setup.md`'s "Suggested default:" bullets are setup-time suggestions, not runtime fallbacks. The only true inherit-or-override merge is `.rp.local.md` over `.rp.md` (`load.md` "Local overrides": "where it names a convention its value wins, where it is silent the committed value is inherited") — right semantics, different layer. Req 7 establishes a new (small) pattern composed from two precedents.
- **Format-definition precedents.** (a) `intent-format.md` is the only skill-owned artifact format: a reference file with "Schema and rendering" ("Render these sections and omit any that are empty — no `N/A` placeholders"), authoring discipline, read by the orchestrator. Not overridable. (b) Every other artifact format (spec.md, design-doc.md, review files) is a fenced template embedded in the project-side agent file (e.g. `agents/spec-writer.md`). The summary would be the second skill-owned format and the first overridable one.
- **Optional vs required conventions.** `load.md` blocks on missing *required* conventions ("If one or more required conventions are missing, do not proceed"). An override convention must be optional with a skill-default fallback so a silent project still gets a summary.
- **House style** (from `intent-format.md`, `spec-writer.md`, `doc-reviewer.md`): H1 naming the artifact (`# Spec: <feature name>`, `# Docs Review`) + H2 section per concern; HTML-comment placeholders describing each section's intent (`<!-- Problem statement… 1-2 paragraphs. -->`); omit-empty-sections discipline; standalone-document discipline ("A reader should understand… from `spec.md` alone").

### Review-run start flow, run-agnosticism, immutability (Q5)

- **Nothing in the phase-launch path distinguishes review from base.** `review-pipeline.md` step 7 returns to `work-on-an-issue.md` step 3, which dispatches the chosen workflow; `autonomous-workflow.md` runs phases in "the active run's folder" with no run-specific branching. The run name is purely a folder choice made by the orchestrator in `review-pipeline.md`/`create-pipeline.md` — so review-specific input plumbing belongs in `review-pipeline.md`, not the shared workflow.
- **Run-agnosticism rule, exact wording** (`autonomous-workflow.md` step 5): the spawn prompt includes "**Artifact folder** — the absolute and full path to the active run's folder… The agent is run-agnostic and never sees the run name." Passing prior-summary *content* preserves the rule; passing run-named *paths* (`base/run-summary.md`) would leak run identity into the agent.
- **Precedent for extra spawn-prompt inputs.** The orchestrator already passes inputs beyond folder + conventions: the rejection-file path on re-dispatch (`5 - docs.md`/`4 - code.md` step 3.1) and the reviewer base ref. All existing extras are within-run; prior summaries are the first cross-run input — needs explicit new wording.
- **The intent is the wrong carrier.** Its Origin section discipline ("self-contained… carries the substance of the request") captures what prompted the review, not pipeline history; `intent-format.md`'s capture-don't-converge discipline argues against folding summaries in. Req 5/AC 4 also frame the summaries as inputs in their own right, not material melted into the intent.
- **Enumerating prior runs.** Order is derivable: `N` is "a per-pipeline monotonic counter — the next integer after the existing `review-*` folders" (`pipeline-versioning.md`), latest run = "the highest-numbered `review-N` run, or `base` if there are no reviews", and runs are reported as a linear chain `base → review-1 → review-2 …`. But no existing step collects across *all* prior runs (existing logic only ever needs the latest), so the collection rule must be stated once.
- **Immutability already covered.** `pipeline-versioning.md`: "`base` is always the first run, always present, and never restructured or rewritten by a review; a review only ADDS a sibling run folder." Prior runs' summaries are artifacts in prior run folders, already covered by that general rule — a summary-specific immutability sentence would duplicate it, against the skill's authoring rules.
- **Assisted reviews.** A review's mode is picked at `work-on-an-issue.md` step 3, so a review can run assisted (phases 1–3, orchestrator writes the artifacts, no agents). The orchestrator collects the prior summaries either way; only the delivery channel differs.

## Topics

### Topic: Approach — where the summary fits in the run lifecycle

- **Spec link:** Requirements 1, 2, 3 / Acceptance criteria 1, 2
- **Options:**
  1. Fold the summary into phase 5: produce it after docs approval as the final step of `autonomous-phases/5 - docs.md`, and extend the phase-5 row of the **Per-phase completion** table to also require it.
  2. Add a new final phase (phase 6) dedicated to the summary.
  3. Produce it in the orchestrator's run close-out (`autonomous-workflow.md` step 7) with a separate run-completion condition alongside the phase-5 predicate.
- **Trade-offs:** Option 2 contradicts the spec, which fixes 5 – Docs as the final phase (Req 2), and brings phase machinery (folder, writer/reviewer loop) the spec excludes — the summary has no review gate. Option 3 splits "run complete" into two conditions defined in different places; the review-start gate and end-of-phase check read the per-phase predicate, so a second condition would need restating on every path. Option 1 keeps a single completion source: both evaluation moments (end-of-phase, review-start gate) already read the predicate table, so extending its phase-5 row gates run completion everywhere with no duplication.
- **Decision:** Option 1. The summary is produced as the final step of phase 5, after `doc-reviewer` approval, and the phase-5 completion predicate is extended to require it alongside `docs-review-approved.md`.
- **Rationale:** Matches Req 2 (produced only at final-phase completion) and Req 3 (gates run completion) through the one predicate every completion check already reads; respects the spec's exclusion of a content review gate; mode-independence of the predicate is consistent since only autonomous runs reach phase 5.

### Topic: Artifact location and naming

- **Spec link:** Requirements 1, 8, 10 / Acceptance criteria 1, 7, 8
- **Options:**
  1. Inside the phase folder: `<run>/5-docs/run-summary.md`. No wording change in `pipeline-versioning.md`, but a fork inheriting phase 5 copies it — requires a negative fork-exclusion in `fork-pipeline.md` — and it pollutes the `5-docs` lineage tree SHA.
  2. Run-level file: `<run>/run-summary.md`, outside any phase folder. Requires generalizing two sentences in `pipeline-versioning.md` (artifact layout, predicate evaluation path) plus the phase-5 predicate row; fork and lineage correctness come free.
  3. Dedicated run-level subfolder treated as a pseudo-phase (e.g. `<run>/summary/`). Heavier than either; no benefit.
- **Trade-offs:** Option 1's costs are spread across files and include a special-case exclusion the skill's authoring rules discourage; option 2's cost is three co-located edits in one file. Fork inheritance of phase 5 is real, so option 1 cannot satisfy Req 10 structurally.
- **Decision:** Option 2 — `<artifacts-folder>/<run>/run-summary.md`, a constant filename at run level.
- **Rationale:** Run identity carried by the `<run>/` path matches the universal naming convention (constant filenames, run-agnostic agents who never see the run name, so the filename cannot embed it). The `run-` prefix makes the name read as a single run's summary, not a pipeline-level one (Req 8 / AC 7). Outside phase folders, fork's phase-folder-only copy never touches it (Req 10 / AC 8) and lineage tree SHAs ignore it. The predicate row addition (`run-summary.md`, run-level path) gates completion; resume then handles the missing-summary case automatically.

### Topic: Producer — who writes the summary and from what sources

- **Spec link:** Requirements 2, 4, 9 / Acceptance criteria 1, 3, 9
- **Options:**
  1. A new dedicated single-shot agent (`run-summary-writer`), spawned by the orchestrator as the final step of phase 5 after docs approval.
  2. The orchestrator writes the summary itself (the phase-0 intent pattern).
  3. An existing phase-5 agent absorbs it (`doc-reviewer` on approval, or the last `doc-writer`).
- **Trade-offs:** Option 2 breaks the autonomous-workflow rules ("you do not produce the artifacts yourself"; "the orchestrator does not commit on their behalf") — the intent exception is phase-0-specific and predates the team. Option 3 breaks agent contracts: `doc-reviewer` is review-only and may iterate; each `doc-writer` is single-task-scoped; the summary is written exactly once, after approval. Option 1 follows the exact pattern every phase already uses to add a role, and since the spec excludes a review gate, it needs no writer/reviewer loop — one agent, one shot.
- **Decision:** Option 1. A new single-shot `run-summary-writer` agent, launched after `doc-reviewer` approval as the final step of `5 - docs.md`. It reads the run's own committed artifacts — `spec.md`, `design-doc.md`, the plans, the `*-review-N-rejected.md` files, and the shipped code/docs as files — and writes and commits `run-summary.md` at the run folder root. It is given no git base ref and never inspects a diff.
- **Rationale:** Consistent with "agents author all artifacts" in the autonomous workflow; agent name follows the `<artifact>-writer` pattern (`spec-writer` → `spec.md`); all Req-4 content is sourceable from the run folder, so the mechanism stays generic (Req 9 / AC 9). Skill-side cost is one Required-agents row, one step, and one outputs line in `5 - docs.md`; the agent definition and model row are project-side, as for every agent.

### Topic: Default format and project override

- **Spec link:** Requirements 4, 7, 9 / Acceptance criteria 3, 6, 9
- **Options (where the default format lives):**
  1. A new skill reference file `reference/run-summary-format.md` (the `intent-format.md` pattern), plus a new optional "Run summary format" convention in `conventions/load.md`/`setup.md`: the project's `.rp.md` value wins; if silent, the skill default applies.
  2. The format inline in `autonomous-phases/5 - docs.md`.
  3. The format only in the project-side `agents/run-summary-writer.md`.
- **Trade-offs:** Option 3 fails Req 7 — the skill would not define the default. Option 2 mixes a format spec into a procedure file and has no override hook; `intent-format.md` establishes that formats get their own reference file. Option 1 composes the two existing precedents: a skill-owned format file plus the inherit-or-override semantics already used by `.rp.local.md`.
- **Decision:** Option 1. The skill ships `reference/run-summary-format.md` as the default; a new **optional** "Run summary format" convention lets a project name its own format in `.rp.md` — where the project names it, its format wins; where silent, the skill default applies. The orchestrator resolves the winner and passes it to the `run-summary-writer` in its spawn prompt, like Artifact folder and Commit format. `setup.md` gets the matching entry with the skill file as suggested default.
- **Rationale:** Satisfies Req 7's two halves (skill-defined default, project-overridable in its conventions) through the established channels: orchestrator reads `.rp.md`, agents receive values in the spawn prompt and never read `.rp.md`. Optional marking keeps `load.md`'s missing-required-conventions block from firing on silent projects (AC 6's no-override leg).
- **Decision (default structure):** The What/Why/How working hypothesis is confirmed as the skeleton, extended with the Req-4 content as sibling sections: `# Run Summary`, then `## What`, `## Why`, `## How`, `## Key decisions`, `## Rejected approaches`, `## Known limitations` — each with an HTML-comment placeholder, omit-empty-sections (no `N/A`), written as a standalone document.
- **Rationale:** Req 4's decisions/rejected-approaches/limitations earn explicit H2 sections rather than burial under "How" — matching the house style's section-per-concern; the H1 stays run-name-free since the writer is run-agnostic. The standalone discipline serves the consumer: a later review run reads the summary with no other prior-run context.

### Topic: Prior summaries as review-run input

- **Spec link:** Requirements 5, 6 / Acceptance criteria 4, 5
- **Options:**
  1. `review-pipeline.md` gains a step: when starting the review run, the orchestrator collects the prior runs' `run-summary.md` files in run order (`base`, `review-1`, …, `review-(N-1)`) as input to the review run's phase 1 — delivered as collected content in the phase-1 spawn prompts (autonomous) or read directly by the orchestrator while it authors the phase-1 artifacts (assisted).
  2. The orchestrator folds prior-summary context into the review intent it authors.
  3. The shared `autonomous-workflow.md` detects review runs and gathers sibling summaries itself.
- **Trade-offs:** Option 2 fails Req 5/AC 4 as written — the summaries would no longer be run inputs — and bloats the intent beyond its capture-the-request discipline. Option 3 breaks the shared workflow's deliberate run-agnosticism (it operates on "the active run's folder" with no run branching). Option 1 places the run-aware logic in the only file that already knows run names and uses the established extra-spawn-input channel (rejection-file path, base ref precedents).
- **Decision:** Option 1. `review-pipeline.md` states the collection rule once — the prior runs of `review-N` are `base, review-1, …, review-(N-1)`, in that order; collect each one's `run-summary.md` — and makes the collected summaries, in run order, part of the review run's phase-1 input. The orchestrator passes them as collected content, never as run-named paths, so phase-1 agents stay run-agnostic. Phases 2–5 are unchanged: they work from the review run's own artifacts, into which phase 1 has already absorbed the prior context.
- **Rationale:** "When a review run starts" = phase 1, the first phase a review executes; the spec phase is where the review's scope is set, so prior-shipped context belongs there and nowhere downstream (re-feeding it to every phase would re-introduce cross-run input agents shouldn't need). Mode-independent because collection happens in `review-pipeline.md` before mode dispatch; delivery follows each mode's existing artifact-authoring channel.
- **Decision (immutability):** No new immutability rule. Req 6/AC 5 are already covered by the general rule that a review never restructures or rewrites prior runs and only adds a sibling run folder; a summary-specific restatement would duplicate it. The producing writer only ever writes within its own run folder.

## Open Questions

- **Exact generalized wording** for the two `pipeline-versioning.md` sentences that currently pin artifacts to `<run>/<phase>` (layout sentence and predicate-evaluation sentence) — implementation-phase wording choice; the constraint is that the phase-5 predicate row can name the run-level `run-summary.md`.
- **Spawn-prompt phrasing** for handing the resolved summary format and the collected prior summaries to agents — implementation detail; constraints decided here: format resolved by the orchestrator (project override else skill default), summaries passed as content in run order without run names.

## Risks

- **Resume after partial phase 5.** When a run has docs approved but no summary, phase 5 is the active phase and resume re-runs it. The design should state that re-running phase 5 rewrites `run-summary.md`; immutability (Req 6) applies to *completed* runs' summaries, not a summary being (re)written by its own still-incomplete run.
- **First cross-run input.** Prior summaries are the first input that crosses run boundaries; every existing extra spawn input is within-run. If implemented as run-named paths instead of collected content, it would leak run names into agents and erode their run-agnosticism — the design pins content delivery for this reason.
- **Override replaces content guarantees.** The default format carries Req 4's content (decisions, rejected approaches, limitations); a project override replaces the format wholesale, so those guarantees hold only for the default. AC 6 sanctions this; the design doc should state it as deliberate.
- **Summary accuracy is ungated.** No reviewer verifies the summary (spec out-of-scope), so an inaccurate summary would mislead later review runs. Accepted by the spec; mitigated only by the writer reading the full committed run record.
