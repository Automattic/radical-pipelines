# Design Doc Review

## Verdict: rejected

## Summary

The design is strong: every decision traces to specific requirements and acceptance criteria, credible alternatives are weighed with real trade-offs, and the claims about the existing skill files (the predicate table and its two layout sentences, fork's phase-folder-only copy loop, resume's delegation to the predicate, the lineage tree-SHA scope, the conventions mechanism, review-pipeline's step structure) all verify against the codebase. The failure-modes section is unusually honest. But the design has one genuine gap and one internal inconsistency. The gap: extending the phase-5 predicate changes the state semantics of a fork that inherits `5-docs` — such a fork lands permanently incomplete with no path to a summary, and the design's "Explicitly untouched" section affirmatively claims fork correctness "comes free" without addressing it. The inconsistency: C1 leaves the existing phase-5 step that verifies the completion predicate in place while extending the predicate so that verification cannot pass at that point. Both are fixable within the design's existing decisions.

## Issues

### Issue 1: A fork inheriting `5-docs` becomes permanently incomplete under the extended predicate, and the design doesn't address it

**What's wrong:** `fork-pipeline.md` step 1 explicitly allows inheriting `5-docs`, and its step 5 copies only phase folders. A parent whose base run is complete (including `base/run-summary.md`) therefore seeds a fork whose `base/` has `5-docs/docs-review-approved.md` but no `run-summary.md` — which is exactly the R10 behavior the design wants. But under the extended predicate (C2), that fork's phase 5 is now incomplete: its completed phase is 4 and its active phase is 5 (the `5-docs` artifacts "have started appearing" per `pipeline-versioning.md`). Consequences the design never examines: the pipeline tree renders the fork's `5-docs` as "(in progress)" and `work-on-an-issue.md` misreports its state; the review-start gate (`review-pipeline.md` step 1a) blocks any review of the fork; and the resume path that gate steers the owner to would identify phase 5 as the active phase and roll back "the active phase's commits" — which in a fork is the single seed commit from `fork-pipeline.md` step 6, containing all inherited artifacts. Today the same fork is complete the moment it is seeded. The fork's base run also has no in-design way to ever produce its own summary, since it never executes the phase-5 procedure where the `run-summary-writer` is launched — even though the spec's R10 rationale is "each pipeline's runs produce their own."
**Where in design doc:** "Explicitly untouched" (the `fork-pipeline.md` bullet), D2, Failure Modes (none covers it).
**Suggestion:** Decide and state how a fork that inherits `5-docs` reaches completeness. Options consistent with the existing decisions: have `fork-pipeline.md` launch a `run-summary-writer` for the fork's base run when `5-docs` is inherited (the fork produces its own summary from its own — inherited — artifacts, satisfying R10's "each pipeline's runs produce their own"); or constrain the inheritable phases to `4-code` so a fork always runs phase 5 itself; or explicitly define the inherited-`5-docs` state and a non-destructive completion path. Whichever option, it is a design-level choice because it decides which skill file changes.
**Why it matters:** The design's own correctness argument for fork ("comes free from D2") holds only for the no-copying half of R10. The predicate extension (C2) silently regresses a state the skill explicitly supports, and the failure surfaces as a blocked review gate and a destructive rollback offer — exactly the kind of cross-file interaction this design exists to settle.

### Issue 2: C1 leaves the existing predicate verification in a position where it can no longer pass

**What's wrong:** `5 - docs.md` step 6 currently ends the phase: "On **approved**, verify the phase 5 completion predicate per `pipeline-versioning.md`…". C1 extends that predicate to require `run-summary.md` and says only "Add a step after approval: launch the `run-summary-writer` …, then verify the extended phase-5 predicate." It never says what happens to step 6's existing verification. Taken literally ("add a step"), step 6 survives and now verifies an extended predicate before the summary exists — a check that always fails. Two implementers diverge: one appends a step 7 and leaves the broken step-6 check in place; the other rewrites step 6. C1's framing parenthetical also misdescribes the current file: it says step 6 "writes `docs-review-approved.md`", but the `doc-reviewer` writes that file in step 4; step 6 only verifies.
**Where in design doc:** C1 ("Concrete edits" and the opening paragraph).
**Suggestion:** State that the predicate verification moves: step 6's "On approved" outcome becomes "launch the `run-summary-writer`…", and the phase-5 predicate verification happens once, after the summary is committed (the new final step). Fix the parenthetical to attribute `docs-review-approved.md` to the `doc-reviewer` in step 4.
**Why it matters:** The clarity criterion for this phase is that two independent implementers produce the same skill text. As written, one plausible reading yields a phase reference containing a verification step that can never succeed.

### Issue 3: The design is silent on `SKILL.md`'s phase table

**What's wrong:** `SKILL.md`'s Phases table describes what each phase produces ("5 – Docs … Documentation (both internal and external)"). The run summary is a new phase-5 output — the one that now gates run completion — yet `SKILL.md` appears neither in Components nor in "Explicitly untouched". The design's own structure sets the expectation that every adjacent file is either changed or deliberately left alone with a reason; this one file is left undetermined, so implementers will differ on whether to touch it.
**Where in design doc:** Components / "Explicitly untouched".
**Suggestion:** Add `SKILL.md` to one of the two lists: either extend the phase-5 "Produces" cell (e.g. "Documentation (both internal and external) and the run summary") or state why the table's altitude deliberately excludes it.
**Why it matters:** Removing exactly this kind of ambiguity is what the Components and "Explicitly untouched" sections are for; an undetermined file reopens a question the design phase is supposed to close.
