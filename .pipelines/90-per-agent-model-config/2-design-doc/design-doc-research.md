# Design Research: Optional convention for per-agent model configuration

This is the running design record for issue [#90](https://github.com/Automattic/radical-pipelines/issues/90). It is built incrementally by the `design-doc-analyst` driving Q&A with the `design-doc-researcher`. Inputs: `1-spec/spec.md` (15 requirements, 16 ACs) and `1-spec/spec-research.md`.

The codebase under study is the `radical-pipelines` project itself. This feature is **documentation-as-implementation**: the "code" is the prose in `.rp.md` and the reference Markdown files the orchestrator (an LLM agent) reads and follows. "Components" are reference files and `.rp.md` sections; "interfaces" are the conventions table, the per-tool `.rp.md` blocks, and the spawn-time instructions the orchestrator follows.

### `.rp.md` house style and per-tool sectioning (verified)

From the design-doc-researcher (sources: `.rp.md:1,5,11-12,32-36,58,80-82,86,108-109,119,142-144`; `conventions/claude-code.md:9,42`; `conventions/pi.md:7,30,41`; `conventions/load.md:11`; `autonomous-phases/2 - design-doc.md:22`; `agents/*.md` frontmatter):

- **`.rp.md` contains zero Markdown tables** (`grep -c '^|' .rp.md` → 0). Every convention in the project-authored config is expressed as prose, a **bold-label bullet list**, or a **fenced code block** for commands. Tables appear only in the reference/skill files (the conventions table in `load.md`, the "Required agents" tables in the phase references) — documentation *about* the system, not the project-authored config.
- **No YAML/TOML/JSON fenced blocks exist anywhere under `skills/.../reference/`.** The only fenced languages are ` ```markdown ` (canonical `.rp.md` templates) and bare ` ``` ` for shell commands. A structured-data block would be a foreign idiom; the orchestrator reads prose, it does not run a parser.
- **Per-tool sectioning is by heading:** `## Claude Code` (`.rp.md:58`) and `## Pi` (`.rp.md:86`) are level-2 tool sections, each holding level-3 `###` sub-conventions (`### Team spawning`, `### Pi team spawning`, etc.). A new convention slots in as another `###` under each tool section — the established pattern.
- **The 17 agent names** (verified from `agents/*.md` frontmatter): `spec-researcher`, `spec-analyst`, `spec-consolidator`, `spec-writer`, `spec-reviewer`, `design-doc-analyst`, `design-doc-researcher`, `design-doc-writer`, `design-doc-reviewer`, `code-plan-writer`, `code-plan-reviewer`, `code-writer`, `code-reviewer`, `doc-plan-writer`, `doc-plan-reviewer`, `doc-writer`, `doc-reviewer`. None is named `default`, so a reserved `Default` label cannot collide with an agent.
- **LLM-reader hazard:** the CC and Pi blocks carry the *same agent names* with *different value strings*; the biggest risk is the orchestrator conflating the two tools' blocks. Mitigation is structural — keep entries under the existing per-tool `##` headings and state "use the block for the active tool" in the lead-in. All candidate shapes are safe under per-tool headings; none is safe if flattened into one list.
- **Settings surface is unverified** (CC reasoning `effort`; Pi spawn settings keys) — model knowledge, not checked this session. Per the spec this is opaque pass-through, so the file *shape* does not depend on the exact keys.

### Optionality, canonical-template consumption, and persistence (verified)

From the design-doc-researcher (sources: `conventions/load.md:5-7,11-20,22-28`; `conventions/claude-code.md:1-9`; `conventions/pi.md:1-7`; `conventions/setup.md:27-30,54-60,82-86,159-166,176-182`; `README.md:153-167`; `autonomous-workflow.md:32-62`; `health-monitoring.md` recovery table):

- **The "missing → stop and offer setup" branch keys ONLY off `Required? = Yes`.** `load.md:24-28` triggers on "one or more **required** conventions are missing," and "required" is defined solely by the `Required?` column. The two existing `Required? = No` rows (`Commit format` `load.md:15`, `Team spawning` `:19`) confirm optional conventions can be absent without ever tripping the stop. An optional `Agent models` row therefore satisfies AC7 by construction — no extra `load.md` prose is needed beyond the `No` row.
- **The canonical ` ```markdown ` blocks in `claude-code.md`/`pi.md` are read as reference templates, not copy-pasted verbatim by setup.** `setup.md:176-182` (step 5) says only "Write `.rp.md` with the conventions" — there is no instruction to reproduce the canonical fence literally. Step 1 (`:15-25`) reads the tool rules; step 3 (`:159-166`) consults the tool rules only for a **"Setup actions"** section (Pi has one — agent install; CC has none). So the canonical blocks tell the orchestrator the *forced shape*, which it then reproduces — they are not a literal copy-paste source. This means an optional convention does **not** have to live inside those blocks to be writable.
- **`claude-code.md:1-8` frames its block as tool-forced** ("three project conventions are **forced** by Claude Code's tool surface … the tools constrain the answer … canonical content for `.rp.md`"). `pi.md:1-7` says "Canonical `.rp.md` content for Pi" (no "forced"). Either way these blocks are tool-mechanism conventions, the opposite of a project-taste choice — so adding an *optional, project-chosen* `### Agent models` stanza inside them is a semantic mismatch.
- **Setup already handles both flavors of optional convention:** prompt-for-a-choice (**Commit format** `setup.md:54-60` — optional yet actively prompted with a default) and document-the-mechanism (**Spawning teams** `setup.md:82-86` — optional, captured once as tool research, not an owner taste choice).
- **Persistence holds by location alone.** `load.md:5-7`: "Read [`.rp.md`] at the start of any workflow … load and verify it before starting any workflow." README:163 corroborates ("loads and verifies conventions before launching phase agents"). Anything in `.rp.md` is re-read every run with zero extra machinery, satisfying R4/AC5. **The one path deliberately NOT persisted** is the failure-recovery model swap (it lives in the live monitor's session, not `.rp.md`) — which is exactly correct for AC14/AC15. Boundary to keep crisp: the *config* is only ever read from `.rp.md`; the *recovery swap* is never written back, so each fresh spawn returns to the configured model.
- **README:167 catalogs the per-tool section contents** ("worktrees, branch names, team spawning, health monitoring") and should gain an "Agent models" mention for documentation completeness, regardless of the canonical-template decision.

### Real spawn surfaces for model + settings, per tool (CC verified; Pi inferred)

From the design-doc-researcher (CC probed live, `claude` v2.1.168; Pi binary absent — `which pi` → "pi not found"):

- **Claude Code — VERIFIED.** `claude --help` and `claude agents --help` expose `--model <model>` ("alias for the latest model e.g. 'sonnet'/'opus', or a model's full name e.g. 'claude-opus-4-8'" — exactly the spec's CC value forms) and `--effort <level>` with the enumerated set **`{low, medium, high, xhigh, max}`**, both as **per-dispatched-agent defaults** ("Default model/effort for sessions dispatched from agent view"). Also `--fallback-model <model>` (relevant to recovery/AC16). A real prior subagent run was observed executing on `claude-opus-4-8`, so per-agent model-at-spawn is real and observable, not theoretical.
- **CC frontmatter `model:` exists and works — but is the WRONG channel.** Verified two real files carrying a `model:` frontmatter key (radical-pipelines' own `agents-examples/spec-writer.md` → `model: opus`; the official CC `feature-dev/code-reviewer.md` → `model: sonnet`). This is exactly the channel R10/AC11 forbids — it would change the agent's generic profile file. Our project's own `agents/*.md` deliberately carry no `model:` key. **The design must use the spawn-parameter channel and explicitly forbid adding `model:` to the profiles** so the writer/implementer does not "helpfully" do so.
- **Exact `TeamCreate`/`Agent` model/effort argument — NOT verifiable here.** `TeamCreate` is not an introspectable tool in this environment; the cached orchestrator-example docs describe "create team, then launch each agent" but document no model/effort argument on either call. So CC *clearly supports* per-agent model+effort at spawn (verified via the `--model`/`--effort` surfaces and real application), but the specific tool-parameter name is a runtime detail to confirm at implementation. The design stays at "apply via the active tool's spawn mechanism" and names the verified CC `--model`/`--effort` surface as the concrete example.
- **Pi — INFERRED, NOT verified (binary absent).** Repo docs (verified) give the convention: `pi-teams` with `create_predefined_team` preferred, else `team_create` + `spawn_teammate`, spawning with provider-qualified `provider/model` (`conventions/pi.md:24,30`; `.rp.md:119,121-130`). The repeated "prefer provider-qualified `provider/model`" guidance only makes sense if `spawn_teammate` accepts a per-teammate model argument, so a per-teammate `model` is almost certainly supported — but the exact argument name, and whether Pi exposes a per-teammate effort/settings knob, are **model knowledge, not verified**. Design stays at "apply the configured `provider/model` (and any settings) via Pi's `pi-teams` spawn mechanism, verbatim," flagging the per-teammate settings surface as confirmed-at-implementation. Consistent with the spec's opaque-pass-through + no-pre-validation stance.
- **Existing generic-vs-tool-specific split (verified):** the generic workflow refers to conventions *by name* and never names tool primitives — `autonomous-workflow.md:58` says "Follow the **Team spawning** convention," not "`TeamCreate`." Tool primitives live only in `conventions/claude-code.md` / `pi.md`. The prompt-channel instruction (`autonomous-workflow.md:59-62`) is likewise generic (names *what* to pass; conventions supply values). So: generic workflow owns the algorithm + the channel; per-tool conventions own the concrete mechanism.

### Failure-recovery and escalation machinery, current state (verified)

From the design-doc-researcher (sources: `health-monitoring.md:13,30-39,41-50,79`; `.rp.md:115-130`; `conventions/pi.md:30`; `conventions/claude-code.md` grep for login/recovery → none; `claude --help` `--fallback-model`):

- **The Pi login/API-key recovery instructions live in TWO places that must stay consistent:** `.rp.md:121-130` (this repo's hand-maintained dogfood copy) and `conventions/pi.md:30` (the compressed canonical block that *seeds* a project's `.rp.md`). Both are **Pi-only**. There is **no Claude Code equivalent** — `conventions/claude-code.md` and `.rp.md`'s CC section have zero login/recovery/model-swap text (CC auth is interactive `/login`, not provider-qualified model selection). So any AC16 disambiguation must edit **both** `.rp.md` and `pi.md` to avoid drift.
- **Escalation payload today** (`health-monitoring.md:43-48`): Agent name / Error verbatim / Last-known progress / Suggested next step. The "rejected configured value" that AC12 wants is **not cleanly covered** — folding it into "Suggested next step" is a category error (it's a fact about the failure, not an action), and the runtime's verbatim error may not echo the exact configured string the orchestrator sent.
- **Recovery table** (`health-monitoring.md:32-37`) has 4 rows, all assuming **transient** failures (stall, lost message, network blip, expired auth) where a retry *can* succeed, with a 2-retry budget before escalation. The "Login/API-key error" row (`:36`) already does swap→re-spawn→escalate. **Two of the three AC12 rejection cases are unmodeled and deterministic:** a bad `effort` for the chosen model and an unknown/mistyped model string will fail identically on re-spawn — so burning the 2-retry budget on an identical re-spawn is pure waste. The unauthenticated-provider case IS the existing Login/API-key row.
- **Recovery is entirely in-session** (`pi --list-models` → pick → retry; `.rp.md:125-127`). Nothing in `health-monitoring.md` or `.rp.md` writes the swapped model back to any file — so AC15 (no `.rp.md` mutation) holds by construction today; the spec wants it stated as an explicit invariant to guard against a future reader persisting the swap.
- **The AC16 collision is at `.rp.md:126`** (mirrored in `pi.md:30`): "prefer the owner's configured default provider/model when present." With this feature, "configured default provider/model" is ambiguous between (intended) the owner's *environment/Pi* default fallback preference, and (newly colliding) the per-agent **Agent models** entry — which is exactly the model that may have just failed auth. The second reading would re-pick the failed model → loop.
- **CC `--fallback-model` is orthogonal** (verified `claude --help`): it is an *automatic, in-CLI* fallback for when a model is **overloaded or unavailable** (capacity, HTTP-529-class), NOT an *authentication* failure, and it is CC-only. It does not know which model "just failed auth" in the orchestrator's sense and is not provider-qualified-model recovery. It must be noted as an explicit **non**-mechanism for AC16 so a future reader does not conflate them.

### Overview: approach, components, interfaces, data flow

**Approach (the implementer's mental model).** The feature is **purely additive documentation/convention work** — no executable code. A project optionally records, in `.rp.md`, an `### Agent models` block under each per-tool section (`## Claude Code`, `## Pi`). The block is a bold-label bullet list: a reserved `**Default:**` bullet plus one `**<agent-name>:**` bullet per configured agent, each carrying a tool-native model string and optional settings (at minimum `effort`). At the start of every run the orchestrator already reads `.rp.md`. In the autonomous spawn loop, for each agent it spawns, the orchestrator resolves — under the active tool, **per key** (model and each setting independently) — the agent's entry → else the `Default` → else today's behavior, and applies the resolved model/settings as **parameters of the spawn itself** (a different channel than the prompt-embedded conventions), passing values **verbatim** with no translation and no pre-validation. The runtime is the authority on validity: a rejected value surfaces through the existing escalation path (now carrying the rejected configured value); an unauthenticated provider flows through the existing login/API-key recovery swap, which is transient, never written back to `.rp.md`, and must never re-select the model that just failed auth.

**Components (files touched; all Markdown — the "code" is prose the LLM orchestrator follows):**

**Interfaces / data flow.**
- *Authoring interface (project → `.rp.md`):* the `### Agent models` bullet list; keys are exact agent names + the reserved `Default`; values are tool-native, opaque.
- *Conventions interface:* the `load.md` table row marks it `Required? = No`, so the missing-conventions stop never fires on it.
- *Resolution interface (orchestrator, per spawn):* `(active tool, agent name) → {model?, settings?}` via per-key most-specific-wins (entry → Default → nothing).
- *Application interface (orchestrator → runtime):* resolved values become spawn parameters (CC `--model`/`--effort`-equivalent; Pi `provider/model` + settings), distinct from the prompt channel (Artifact folder + Commit format).
- *Failure interface (runtime → owner):* rejection → existing escalation payload + the rejected configured value; auth failure → existing recovery swap (transient, excludes the failed model).

### Topic: Concrete shape and syntax of the per-agent model map in `.rp.md`

- **Spec link:** Requirements 1, 2, 3, 8; ACs 1, 2, 3, 4, 9. The foundational topic — the file format the project author writes and the orchestrator reads.
- **Options:**
  1. **Markdown table per tool** — `| Agent | Model | Settings |`, with a reserved `(default)` row. Most scannable for "find the row whose key == X"; mirrors the agent-name-keyed tables used elsewhere in the repo. But would be the *first ever table in `.rp.md`*, which is otherwise table-free.
  2. **Bold-label bullet list per tool** — a `**Default:**` bullet plus one `**<agent-name>:**` bullet per configured agent, each carrying model + inline settings. Matches `.rp.md`'s actual house style (every convention there is a bullet list or fenced block). Lightest when `effort` is usually the only setting.
  3. **Fenced structured block per tool** (YAML/TOML-ish). Rejected: foreign to the repo (no structured-data blocks exist anywhere in the conventions tree), and the worst fit for an LLM reader (invites mis-parsing of a block that is never actually parsed).
  4. **Nested sub-bulleted list** — variant of (2) where `model` and each setting are nested bullets under the agent's bold label. Scales best when an entry carries multiple settings ("other runtime-supported settings").
- **Trade-offs:** (1) wins on columnar scannability and on visually separating the default row, but breaks `.rp.md`'s table-free voice and puts project config in a heavier idiom. (2) matches the file being edited and is unambiguous (each agent is its own bold key), at a slight cost in scannability vs. a table. (4) is (2) with better headroom for multiple settings, at the cost of more vertical space. (3) is worst on every axis here. Tool-conflation risk is identical across all shapes and is handled structurally (per-tool `##` headings), not by the row/bullet shape.
- **Decision:** **Bullet list under a per-tool `###` heading (option 2), with nested sub-bullets (option 4) as the form an entry takes when it carries more than just a model** — i.e. the model is given inline after the agent's bold label when it is the only value, and settings are added either inline (`effort \`high\``) for the common single-setting case or as nested bullets when an entry carries multiple settings. The project-wide default is a reserved `**Default:**` bullet at the top of each tool block; per-agent entries are `**<agent-name>:**` bullets. A one-sentence lead-in states the resolution rule the orchestrator executes: *for the active tool, use the agent's entry if present, else the `Default`, else today's behavior (no override).*
- **Rationale:** `.rp.md` is the artifact being edited and has a deliberate, consistent, table-free voice (verified: zero tables, all conventions are bullet lists or fenced blocks). Matching that voice keeps the project config coherent and keeps the new convention reading like the others a project author already maintains. A bullet list is unambiguous for the orchestrator because each agent is its own bold key, and the reserved `Default` label cannot collide with any of the 17 real agent names. Tables and structured blocks were rejected to avoid importing a foreign idiom into the one file that has consistently avoided it; the agent-name-keyed *tables* that do exist live in reference/skill docs, not in project-authored config, so they are not the precedent to mirror here. The new convention is named **`### Agent models`** under each of `## Claude Code` and `## Pi`.
- **Illustrative shape (Claude Code block; Pi block identical structure with `provider/model` values):**

  ```markdown
  ### Agent models

  Optional. For the active tool, spawn each agent on the model/settings of its entry below; an agent with no entry uses **Default**; with no applicable default it keeps today's behavior (no model/settings override).

  - **Default:** `sonnet`, effort `medium`
  - **spec-writer:** `claude-opus-4-8`, effort `high`
  - **code-reviewer:** `opus`
  ```

  (Pi: `**Default:** anthropic/claude-sonnet-4-6, effort medium`, `**spec-writer:** anthropic/claude-opus-4-8, effort high`, etc. Exact value strings and settings keys are project-authored and opaque pass-through — the design fixes the *shape*, not the value vocabulary.)

### Topic: Conventions-table row, optionality wiring, and where the convention is documented/seeded

- **Spec link:** Requirements 4, 5, 6; ACs 5, 6, 7. Makes the convention optional (no setup-blocking) and persistent (re-read every run), and documents the `### Agent models` block so a project author knows the shape.

**Sub-decision 2.1 — `load.md` conventions table row.**
- **Decision:** Add one optional row to the `load.md` table:
  `| Agent models      | Which model/settings each spawned agent runs on               | No        |`
  Key the `Convention` cell to the same name as the `.rp.md` heading (`Agent models`) so table and file agree.
- **Rationale:** The "missing → stop" branch keys only off `Required? = Yes` (verified `load.md:24-28`), so `Required? = No` makes an absent/empty `### Agent models` block inert by construction — AC6/AC7 hold with no special-casing, exactly like the existing `Commit format`/`Team spawning` optional rows. The `What it covers` cell mirrors the terse present-tense voice of the other rows.

**Sub-decision 2.2 — Where the `### Agent models` shape is documented (canonical-template tension).**
- **Options:** (i) add the block to the tool-forced canonical templates in `claude-code.md`/`pi.md`, marked optional/example; (ii) keep it OUT of those forced blocks and document the shape in `setup.md` (+ a one-clause README catalog update); (iii) hybrid — forced blocks untouched, plus a short prose breadcrumb below each canonical block pointing to the `setup.md` documentation.
- **Trade-offs:** (i) maximizes inline discoverability but contradicts `claude-code.md`'s explicit "forced / the tools constrain the answer" framing, and risks an "example, delete if unused" stanza being copied into a project's `.rp.md` as dead scaffolding — violating "absence = zero footprint." (ii) preserves the forced block's purity and puts the optional convention where the analogous optional conventions already live (`setup.md` already documents Commit format and Team spawning), at a small discoverability cost. (iii) recovers the discoverability with a one-line pointer at the forced-block site without polluting the fence. Key enabling fact: the canonical blocks are *read as templates, not copy-pasted verbatim* (verified `setup.md:176-182`), so the optional convention does **not** need to live inside the forced block to be writable.
- **Decision:** **Option (ii) plus the (iii) breadcrumb.** The tool-forced canonical ` ```markdown ` blocks in `claude-code.md`/`pi.md` stay exactly as they are (purely tool-forced). The `### Agent models` shape — lead-in sentence + `Default`/per-agent bullet form + resolution rule — is documented in a new short subsection of `setup.md` (the file that already documents the other optional, project-chosen conventions). A one-line prose breadcrumb is added *below* each canonical block (outside the fence) noting that a project may add an optional `### Agent models` block per the `setup.md` documentation. README:167's per-tool-contents catalog gains an "Agent models" mention.
- **Rationale:** This honors the literal "these are not choices" framing of `claude-code.md`, keeps a truly-absent config at zero footprint in a fresh `.rp.md`, and places the new optional convention alongside the existing optional ones. The breadcrumb is a cheap discoverability hedge so a reader of the forced block still learns the option exists.

**Sub-decision 2.3 — Setup-flow handling (prompted vs documented-only).**
- **Options:** (a) prompted-optional (setup actively asks, like Commit format); (b) documented-only/not-prompted (shape documented, owner adds by hand or asks); (c) mentioned-but-skipped (one sentence in setup that the capability exists + where the shape is, no Q&A loop).
- **Decision:** **Option (c) mentioned-but-skipped.** Setup does not run a per-agent Q&A loop; it states in one sentence that per-agent models can optionally be pinned and points to the `### Agent models` shape documentation, then moves on. The shape itself **is** documented in `setup.md` (non-optional) so the orchestrator can produce a correct block when the owner opts in.
- **Rationale:** The spec repeatedly emphasizes that absence must be truly inert and frictionless (R5/R6/AC7). A prompted step (option a) forces every setup to answer a question that the common case ("defaults are fine") does not need; documented-only (option b) loses discoverability. Mentioned-but-skipped keeps setup frictionless while still telling the owner the capability exists — the best balance. Precedent exists for both prompted-optional (Commit format) and document-once (Team spawning); this convention is an owner *choice* like Commit format but with a stronger zero-friction requirement, so it lands between them.

**Sub-decision 2.4 — Persistence (R4/AC5).**
- **Decision / Rationale:** No new machinery. Persistence is satisfied purely by the block living in `.rp.md`, which `load.md:5-7` re-reads at the start of every workflow (verified). The design must keep one invariant explicit: the per-agent config is read *only* from `.rp.md` and the transient failure-recovery model swap is *never* written back to it — so each fresh spawn returns to the configured model (consistent with AC15). This boundary feeds the failure-recovery topic below.

### Topic: How the orchestrator reads the config and applies model/settings at spawn, per runtime

- **Spec link:** Requirements 1, 3, 8, 9, 10; ACs 1, 2, 3, 4, 9, 10. The core mechanism — where the "read config, resolve, apply at spawn" instruction lives and how concretely it names the per-runtime spawn surface.

**Sub-decision 3.1 — Placement of the apply-at-spawn instruction.**
- **Options:** (1) tool-agnostic step in `autonomous-workflow.md` (resolution algorithm + "apply via the active tool's spawn mechanism, verbatim") + concrete per-tool surface in `conventions/claude-code.md` / `pi.md`; (2) put the whole instruction in the per-tool files only; (3) hybrid (algorithm in the workflow, surface in the tool files). Options (1) and (3) collapse to the same design.
- **Decision:** **Option (1)/(3).** Add one tool-agnostic step to the spawn loop in `autonomous-workflow.md` (sibling to the existing prompt-channel step) that names the **Agent models** convention by name, states the resolution algorithm, and says to apply the result via the active tool's spawn mechanism, passing values verbatim with no translation or pre-validation. The concrete spawn surface (CC: the `--model`/`--effort`-equivalent on the agent spawn; Pi: the `provider/model` and any settings on `spawn_teammate`/`create_predefined_team`) is added as one line each in `conventions/claude-code.md` and `conventions/pi.md`, next to the existing team-spawning convention.
- **Rationale:** This matches the established generic-vs-tool-specific split exactly (verified): the generic workflow refers to conventions by name and never names tool primitives (`autonomous-workflow.md:58` → "Follow the **Team spawning** convention," not `TeamCreate`), while tool primitives live only in the per-tool files. Option (2) was rejected because it would duplicate the tool-independent resolution algorithm into two files, inviting drift. The new step is a sibling of the existing prompt-channel step (`autonomous-workflow.md:59-62`), reinforcing that model/settings ride a *different channel* than the prompt (Topic: application channel, below).

**Sub-decision 3.2 — Resolution algorithm (per agent, under the active tool).**
- **Decision:** For the agent being spawned, under the active tool's `### Agent models` block:
  1. If the agent has an entry → use that entry's model and settings.
  2. Else if a project-wide **Default** is configured → use the Default's model and settings.
  3. Else → spawn with **today's behavior** (no model/settings override; inherit the runtime/session model and its default settings).
  Configured values are passed **verbatim** to the spawn mechanism — no translation between tools, no pre-validation against any capability matrix.
- **Rationale:** Directly realizes AC1 (agent-specific), AC2 (default for unconfigured), AC3 (agent overrides default), AC8 (partial config), AC6/AC7 (no config → today's behavior), and AC9/AC10 (per-tool form, verbatim pass-through). Verbatim pass-through is the spec's explicit stance (`spec.md:37,116-119`) and is directly supported by the verified CC `--model`/`--effort` surface.

**Sub-decision 3.3 — Per-key vs whole-entry settings resolution (AC4 precision point).**
- **The ambiguity:** AC4 (`spec.md:82-85`) says settings use "the same name-keying and the same 'agent-specific overrides default' precedence as the model itself." This can be read two ways when an agent entry sets a model but no `effort`, while the Default sets an `effort`: (per-key) the agent's model combines with the Default's effort; (whole-entry) the agent's entry fully replaces the Default for that agent, so it gets the agent's model and *no* effort.
- **Decision:** **Per-key resolution.** Model and each named setting resolve **independently**, each by the same most-specific-wins rule: for a given key (the model, `effort`, or any other runtime setting), use the agent entry's value if it specifies that key, else the Default's value for that key, else nothing for that key (today's behavior for that dimension). An agent entry that pins only a model inherits the Default's `effort`.
- **Rationale:** This is the most literal reading of AC4 — "settings use the same name-keying and the same precedence **as the model itself**" frames each setting as a parallel, independently-keyed dimension resolving exactly like the model, not as a bundle that the model's presence overrides wholesale. It is also more expressive (the common "everything on the Default effort, but agent X on a bigger model" case works without restating effort on X) and never produces the surprising whole-entry result where adding a model to an agent silently strips its effort. **The writer must state this per-key rule unambiguously** in `design-doc.md`, since the spec does not pin it down (logged as a resolved precision point, not an open question).

**Sub-decision 3.4 — Forbid the frontmatter `model:` channel.**
- **Decision / Rationale:** The design explicitly forbids using the CC agent-frontmatter `model:` key (or any edit to the generic `agents/*.md` profiles) to carry the configured model. Although that channel is verified to exist and work, using it would change the agent's generic profile file, violating R10/AC11 (configuring a model must not change the agent's profile/behavior instructions). The model/settings must ride the *spawn-parameter* channel only. This is called out so the design-doc-writer and implementer do not "helpfully" add `model:` to the profiles. (Feeds the application-channel topic below.)

### Topic: Application channel — spawn parameters vs initial prompt; profiles untouched

- **Spec link:** Requirement 10; AC11. Model/settings ride the spawn-parameter channel, not the prompt-conventions channel, and configuring a model changes neither the agent's behavior instructions nor its generic profile file.
- **Decision (no new research needed — follows from Topics 3.1 and 3.4):** Two distinct channels exist in the spawn loop and the design keeps them separate:
  1. **Prompt channel (unchanged):** the orchestrator places convention *instructions* in each agent's initial prompt — Artifact folder and Commit format (`autonomous-workflow.md:59-62`). Model/settings are **not** added here.
  2. **Spawn-parameter channel (new):** the orchestrator applies the resolved model/settings as parameters of the spawn itself (CC `--model`/`--effort`-equivalent on the agent spawn; Pi `provider/model` + any settings on `spawn_teammate`/`create_predefined_team`).
  The new `autonomous-workflow.md` step (Topic 3.1) is worded as a sibling of the prompt-channel step and explicitly says "apply as parameters of the spawn itself, not in the agent's initial prompt." The generic `agents/*.md` profiles are **untouched** — no `model:` frontmatter, no behavior-instruction edits (Topic 3.4).
- **Rationale:** Directly realizes AC11's two clauses: (a) model/settings are applied via the spawn, separate from the prompt-embedded conventions; (b) the agent's behavior instructions and generic profile file are unchanged. Keeping the two channels textually distinct in the workflow file prevents the orchestrator from conflating "configured model" with "a thing to write into the prompt," and prevents the writer/implementer from editing profiles.

### Topic: Error/escalation on runtime rejection of a configured value

- **Spec link:** Requirement 11; AC12. A rejected configured value surfaces via the existing escalation path with affected agent + rejected configured value + runtime's verbatim error; never silently ignored or substituted.

**Sub-decision 5.1 — Escalation payload gains a conditional field.**
- **Decision:** Add one **conditional** bullet to the escalation payload in `health-monitoring.md:43-48`, between **Error verbatim** and **Last-known progress**:
  > **Rejected configured value** *(when the failure is a rejected model/settings configuration)* — the exact configured value the runtime rejected (the agent's configured model string or `effort` level), as written in the **Agent models** convention.
- **Rationale:** AC12 requires the escalation to identify the affected agent + the rejected configured value + the verbatim error. Agent name and Error verbatim already exist in the payload; the rejected configured value does not, and folding it into an existing field is a category error (it's a fact about the failure, not a suggested action, and the runtime error may not echo the exact configured string). The "(when…)" qualifier keeps it from cluttering the four non-config escalation types (stall, message failure, login, network).

**Sub-decision 5.2 — Deterministic configured-value rejection escalates without retries.**
- **Options:** (a) add one new recovery-table row for the deterministic case (no retries, escalate immediately); (b) a single sentence under the table. Both satisfy the AC.
- **Decision:** **Option (a): add one new row** to the recovery table (`health-monitoring.md:32-37`):
  > `| Rejected configured value (non-auth) | — (deterministic; re-spawning the same value fails identically) | — | Report to owner immediately, do not retry |`
  plus a one-line note under the table: a configured-value rejection that is **not** an auth error is deterministic — escalate without spending the retry budget on an identical re-spawn. **Keep the unauthenticated-provider case in the existing Login/API-key row** (it is recoverable via model swap — that is AC14); route only bad-effort/mistyped-model to the new row.
- **Rationale:** The recovery table's 2-retry budget assumes transient failures; a deterministic bad-parameter rejection violates that assumption and re-spawning the identical configured value wastes the budget and delays the owner's fix. The new row is additive (touches none of the four existing rows) and uses the table's existing Retry 1 / Retry 2 / Escalate columns. The discriminator "did the runtime reject *authentication* (→ swap, AC14) or reject the *value as invalid* (→ escalate immediately, AC12)" is exactly the AC12-vs-AC14 split, so two rows keep the two ACs from colliding. Option (b) is more minimal but less scannable; the row matches how the other failure classes are modeled. Honors the spec's "no silent ignore, no silent substitute, runtime is the authority, no pre-validation."

### Topic: Interaction with the existing failure-recovery model-swap path

- **Spec link:** Requirements 12, 13, 14, 15; ACs 13, 14, 15, 16. Configured model at initial spawn; recovery swap applies only to the recovery re-spawn and is transient (no `.rp.md` mutation); recovery never re-selects the exact model that just failed auth.

**Sub-decision 6.1 — AC13 (configured model at initial spawn): no recovery-text change.**
- **Decision / Rationale:** Confirmed no contradiction. All recovery text is gated on a failure having already occurred (`.rp.md:121` "**If** a spawned Pi teammate fails…"; the recovery row is a *retry* action) and says nothing about the initial spawn. AC13 is owned entirely by the Topic 3 resolution step. The only latent collision is the `.rp.md:126` phrase, fixed under 6.4 — and that is recovery-time text, so it does not touch the initial spawn.

**Sub-decision 6.2 — AC14 (swap applies only to the recovery re-spawn): optional one-clause tightening.**
- **Decision:** Already scoped correctly (the swap is a retry action; `.rp.md:123` already says "Treat the failed provider as unavailable **for this retry**"). Append one clause to the "Retry the spawn" step (`.rp.md:127`): "— this replacement model applies only to this recovery re-spawn, not to the agent's configured model."
- **Rationale:** Makes the retry-scoping explicit at the point of action and sets up the transience invariant (6.3), without redesigning recovery.

**Sub-decision 6.3 — AC15 (swap is transient; no `.rp.md` mutation): add an explicit invariant in `health-monitoring.md`.**
- **Decision:** Add one tool-agnostic one-liner immediately after the recovery table (`health-monitoring.md:~39`):
  > A recovery model swap is **transient**: it applies only to the recovery re-spawn and is **never written back to `.rp.md`**. The next fresh spawn of any agent re-reads the **Agent models** convention and runs on the configured model again.
- **Rationale:** No current text writes a swapped model back (recovery is in-session), so AC15 holds today — but the spec wants it stated as an invariant, and an explicit statement guards against a future reader persisting the swap. `health-monitoring.md` is the tool-agnostic home of recovery semantics and covers both runtimes from one place, avoiding duplication into the Pi-only `.rp.md`/`pi.md`. The 6.2 clause at the Pi site doubles as local reinforcement.

**Sub-decision 6.4 — AC16 (recovery never re-selects the just-failed model): disambiguate `.rp.md:123/126/127` and mirror into `pi.md:30`.**
- **The collision:** `.rp.md:126` "prefer the owner's configured default provider/model when present" is now ambiguous between the owner's *environment/Pi* default (a recovery fallback preference) and the per-agent **Agent models** entry (which may be exactly the model that just failed auth). The second reading loops.
- **Decision:** Revise the Pi recovery steps so recovery's fallback is explicitly distinct from the per-agent config and excludes the just-failed model. Concretely:
  - **Step 1 (`.rp.md:123`):** broaden the exclusion to the *model*, not just the provider — "Treat **the model that just failed authentication** as unavailable for this retry (and the failed provider, unless the owner explicitly asked to use it)."
  - **Step 4 (`.rp.md:126`):** replace the ambiguous phrase — "Choose a provider-qualified replacement model from authenticated providers, **excluding the model that just failed authentication**. This recovery choice is a **fallback preference**, distinct from the per-agent **Agent models** configuration (which governs the initial spawn): prefer the owner's **environment/Pi default** authenticated provider/model when present; otherwise the closest suitable authenticated model for coding work. **Do not re-select the per-agent configured model that just failed.**"
  - **Step 5 (`.rp.md:127`):** append the transience clause from 6.2.
  - **`conventions/pi.md:30`:** mirror the compressed version — "…pick an authenticated provider-qualified model **other than the one that just failed**, and retry — this recovery fallback is distinct from the per-agent **Agent models** config and must not re-select the failed model…"
  - Keep `.rp.md:130` ("Keep this recovery provider-neutral. Do not hardcode any provider as the fallback default") **unchanged** — the fallback remains "among authenticated providers," no provider hardcoded.
  - Note **CC `--fallback-model` as an explicit non-mechanism** for AC16 (it handles overload/availability, not auth; CC-only; automatic in-CLI) so a future reader does not conflate the two.
- **Rationale:** Satisfies AC16's three sub-requirements: (a) per-agent **Agent models** governs the initial spawn (stated as the distinction), (b) recovery's fallback explicitly excludes the just-failed model, (c) the ambiguous "configured default" phrase now unambiguously means recovery's fallback preference among authenticated providers, not "re-read the Agent models entry." Editing **both** `.rp.md` and `pi.md` keeps the dogfood copy and the canonical seed consistent (the recovery text is duplicated across them). Provider-neutrality is preserved. No recovery *mechanism* redesign — only the invariant wording the spec fixes (R12-15).

### Topic: Name-pattern / glob grouping (e.g. `spec-*`) — scope decision

- **Spec link:** Out of Scope ("Name-pattern / glob grouping … considered and deferred; it may be revisited in the design phase but is not a requirement"). Also touches the granularity decision (per-agent + project-wide default, no per-phase).
- **Decision:** **Do not include name-pattern/glob matching in this design.** The `### Agent models` block has exactly two key kinds: an exact agent name, and the reserved `Default`. No prefix/glob keys (`spec-*`, etc.) are interpreted. The two-step resolution (exact entry → Default → today's behavior) is the whole rule.
- **Rationale:** The spec explicitly defers this and does not require it; my mandate is to realize the spec's outcomes, not to design unasked-for capability. Excluding it keeps the resolution rule maximally simple and unambiguous for the LLM orchestrator (one exact-match lookup plus a single reserved default), which is the safest reading behavior. It is a clean future extension: a later revision could add an intermediate "name-pattern" tier between exact-match and `Default` (spec-research's precedence sketch: exact > pattern > default > unset) without disturbing the file shape or the exact/Default entries already in use. Recorded as a deliberate scope exclusion with a forward path, not an open question.

## Open Questions

These do not block the design (the design is feasible and complete against the spec), but the implementation phases should resolve them concretely:

1. **Exact CC spawn-parameter name for per-agent model/effort.** Verified: CC supports per-agent `--model` and `--effort {low,medium,high,xhigh,max}` at session and dispatched-agent scope, and per-agent model application is real and observed. **Not verifiable in this environment:** whether the orchestrator sets these via a field on the team-create/agent-launch tool call, via the `claude agents` CLI surface, or another path. The design stays at "apply via the active tool's spawn mechanism"; the implementer must confirm the concrete `TeamCreate`/`Agent` (or CLI) parameter against the live tool and write it into `conventions/claude-code.md`.
2. **Pi per-teammate model and settings arguments.** Pi binary was absent (`which pi` → not found), so the exact `spawn_teammate`/`create_predefined_team` argument for a per-teammate `provider/model`, and whether Pi exposes any per-teammate `effort`/settings knob at all, are inferred-but-unverified. The implementer must confirm against a live Pi and write the concrete surface into `conventions/pi.md`. If Pi has **no** per-teammate settings knob, the `effort`/settings portion of the Pi `### Agent models` block is simply inapplicable for Pi (model-only) — which the opaque-pass-through design already tolerates, but the Pi docs should say so.
3. **Settings vocabulary beyond `effort`.** The spec allows "other runtime-supported settings" but only names `effort`. The design keeps settings opaque, so the file shape (inline or nested sub-bullets) already accommodates unknown keys. The implementer need not enumerate them; the `setup.md` shape documentation should show `effort` as the worked example and state that other runtime-supported settings follow the same form.
4. **Exact final wording of every edited line.** This design fixes the *content and placement* of each edit and gives proposed wording; the design-doc-writer/plan phase will finalize exact prose (e.g. the `load.md` row text, the recovery-step rewrites, the new `autonomous-workflow.md` step). The proposed wordings here are starting points, not frozen strings.

## Risks

1. **Tool-block conflation by the orchestrator (LLM-reader risk).** The CC and Pi `### Agent models` blocks carry the *same agent names* with *different value strings*. If the orchestrator reads the wrong tool's block, it would pass a Pi `provider/model` to Claude Code or vice-versa. **Mitigation (in the design):** entries live strictly under the existing per-tool `## Claude Code` / `## Pi` headings, and both the `autonomous-workflow.md` step and the block's lead-in say "use the block for the **active tool**." The verbatim pass-through + runtime-rejection path is the backstop — a cross-tool value would be rejected at spawn and escalated (AC12), not silently mis-run.
2. **AC16 recovery-loop regression if the two Pi recovery copies drift.** The disambiguation must land in **both** `.rp.md:121-130` and `conventions/pi.md:30`. If only one is edited, a project seeded from the canonical block could still read "prefer the configured default" and loop on the just-failed model. **Mitigation:** the design explicitly lists both files as a paired edit; the plan phase should treat them as a single change.
3. **Implementer "helpfully" using the frontmatter `model:` channel.** The CC frontmatter `model:` key is verified to exist and work, making it a tempting shortcut that would violate R10/AC11. **Mitigation:** the design explicitly forbids editing `agents/*.md` and names the spawn-parameter channel as the only allowed one (Topic 3.4 / Topic 4); the writer must carry this prohibition into `design-doc.md`.
4. **Dogfood `.rp.md` vs. seeded `.rp.md` divergence.** This repo is the unusual multi-CLI consumer whose `.rp.md` carries both tool sections and is hand-maintained (`README.md:167`). The `### Agent models` block, the `load.md` row, the `setup.md` shape doc, and the `pi.md`/`claude-code.md` seeds must all describe the *same* shape, or a fresh project's seeded `.rp.md` will not match what the orchestrator expects to read. **Mitigation:** the design keeps one canonical shape and routes all documentation to it; the README catalog update is the cross-check.
5. **Per-key settings resolution is a design choice the spec did not pin.** If a downstream reviewer expected whole-entry override, the per-key decision (Topic 3.3) could be challenged. It is defensible (most literal reading of AC4, more expressive, no surprising effort-stripping) and is recorded with rationale; the writer must state it explicitly so it is reviewed on its merits rather than assumed.
