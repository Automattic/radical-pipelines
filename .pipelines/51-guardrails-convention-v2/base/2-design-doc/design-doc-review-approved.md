## Non-blocking observations (for the plan/code phases, not grounds for rejection)

1. **`load.md` body placement style.** D1 leaves the writer to choose between a `### Guardrails` subsection and a paragraph under the table. Note that `load.md` today has no `###` subsections at all — its body is `##`-level sections (`## Conventions`, `## Missing conventions`, `## Local overrides`). A new `### Guardrails` would be the first `###` in the file and would dangle without a parent `##`. The lighter, more consistent touch is a short paragraph (or a `## Guardrails` body section after the table), not a `###`. The design's "writer picks the lighter touch that matches load.md's existing prose density" guidance already points here, so this is a hint, not a gap.

2. **Setup sub-section optional-marker convention.** D5 says mark the step "optional." In `setup.md`, optionality is signalled by the *absence* of a `(required)` suffix (e.g. `### Commit format`, `### Spawning teams of agents`), not by an explicit `(optional)` tag. The writer should follow the existing pattern (a bare `### Guardrails` heading) rather than inventing an `(optional)` suffix, to stay consistent with spec req 11's "consistent with the existing one-capture-step-per-convention pattern." Minor wording guidance for the code phase.

3. **Bucket 2.3 line anchor.** D2 cites code-writer `:50` ("Failing gates are work, not blockers") and the doc-writer `:65` tail as already encoding the "runs-but-nonzero ⇒ work" outcome — confirmed accurate. The writer must ensure that when `:51`/`:45` (the "missing or unrunnable … is a blocker" sentences) are removed, the surviving "failing gates are work" sentence is re-anchored so the three-way split reads as one model and no orphaned wording remains. The design already calls for stating the "did it execute? vs did it pass?" spine, which covers this; flagged only so the code phase keeps the `:50` sentence and rewords around it rather than deleting wholesale.

None of these change a design decision or contradict the spec; they are implementation hints the plan/code phases can absorb. The design is approved.
