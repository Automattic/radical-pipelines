# Design Doc: Default output rules for pipeline-produced code

## Overview

Radical Pipelines runs teams of agents that ship real product into a host repository — source code, tests, inline and external documentation, and the commit messages that carry that work. Two qualities expected of hand-written work are not guaranteed by the tool today: a change should leave untouched comments and prose exactly as they were (**Rule 1**), and the shipped product should read as if a person wrote it, with no trace of the pipeline that produced it (**Rule 2**). Until now these were corrected by hand-passing guidelines into individual runs. This feature promotes both into permanent, always-on rules of the tool, in force for every run with no owner action and no opt-out.

The realization is deliberately small: this feature ships **no code and no runtime mechanism**. It is a change to the tool's *instructions* — edits to the Markdown agent profiles under `agents/`. The rules become standing text in the profiles of the agents that produce host-project product and the agents that review it. Producers honor the rules while writing; reviewers enforce them at the existing per-phase review gate, where a violation is a must-fix issue that blocks the phase from completing — the same path every other review finding already takes. A one-line product-commit constraint, layered onto each producing profile's existing commit step, keeps pipeline-naming provenance out of product commit messages. Nothing in the orchestrator, the conventions, `.rp.md`, the guardrails, or the phase references changes.

## Approach

The mental model for the implementer:

1. **The rules live in agent profiles, duplicated verbatim.** An agent reads only its own profile (`agents/<name>.md`) and its orchestrator-composed initial prompt; a profile cannot reference a skill or convention file (per CLAUDE.md, a shared profile instruction is *duplicated* into each profile, never extracted to a referenced file). So the canonical statement of Rule 1 and Rule 2 is written **once** as a single block of canonical wording and copied **byte-identically** into each profile that carries it. "Stated once and consistently" (Req 11) is satisfied the way the skill satisfies it everywhere else: one canonical wording, duplicated verbatim, with no surviving narrower or conflicting variant.

2. **Which agents carry the rules is determined by the product/artifact boundary.** Host-project product is everything a run writes that is **not** under the pipeline's artifacts folder (`.pipelines/<slug>/` per the Artifact folder convention): source code, tests, inline and external documentation, and the commit messages that ship them. Pipeline artifacts are specs, design docs, plans, reviews, and summaries — every file under the artifacts folder. Only the agents that touch product carry the rules: the three **producing** profiles (`code-writer-tdd`, `code-writer-e2e`, `docs-writer`) and the two **reviewing** profiles (`code-reviewer`, `docs-reviewer`). Earlier-phase agents (spec/design/plan writers, analysts, researchers, consolidators, and their reviewers) emit only artifacts and do **not** carry the rules — their output is *supposed* to reference the pipeline freely.

3. **Producers honor; reviewers enforce.** Each producing profile gains the canonical Rule 1 + Rule 2 statement so the agent avoids violations while writing. Each reviewing profile gains the *same* canonical statement **plus** an enforcement instruction: a Rule 1 or Rule 2 violation found in the batch is a must-fix issue. This reuses the reviewer's existing "every issue is must-fix" / "reject liberally" machinery unchanged — a recorded violation forces a `rejected` verdict, no approval artifact is written, the phase-completion predicate is not met, and the flagged tasks are re-dispatched until the violation is resolved.

4. **Product commits drop pipeline-naming provenance at authoring time.** The agent-name provenance tag (e.g. `(code-writer-tdd)`) comes entirely from the host commit-format string delivered in the initial prompt's `## Conventions` block (default `<commit-description> (<agent-name>)`); each agent substitutes its own name when it commits. The fix is a one-line constraint in each producing profile's commit step: author the message in the host commit format **but omit the pipeline-naming provenance**. Reviewers — which commit only artifact files (their review/summary) — keep the full format including the tag, unchanged.

Producers are the first line of defense; the review gate is the authoritative one. Detection is a semantic judgment, not a mechanical scan — consistent with Req 12's explicit guarantee that a *seen* violation cannot be approved (not that detection is exhaustive) and with Out-of-Scope #2's ban on any token/keyword/path scan.

## Components

All paths are agent profiles under `agents/`.

**Modified — producing profiles** (host-project product authors):

- `agents/code-writer-tdd.md` — produces code, unit tests, and symbol-level inline API documentation. Gains the canonical Rule 1 + Rule 2 statement. Its existing narrower line at step 2 of the implement workflow — *"Comments must be self-contained — never reference the spec, the plan, or any other artifact."* (currently `code-writer-tdd.md:33`) — is **replaced** by the canonical Rule 2 (Req 11). Its commit step gains the product-commit no-provenance constraint.
- `agents/code-writer-e2e.md` — produces end-to-end test code (comments, string literals, identifiers in tests). Gains the canonical Rule 1 + Rule 2 statement, phrased to read sensibly for an agent whose product is test code rather than API docs (it has no inline-API-docs step and carries no narrower-Rule-2 line today). Its commit step gains the product-commit no-provenance constraint.
- `agents/docs-writer.md` — produces external documentation (READMEs, guides, examples, changelogs, configuration descriptions) and non-symbol inline narrative. Gains the canonical Rule 1 + Rule 2 statement scoped naturally to documentation surfaces. Its commit step gains the product-commit no-provenance constraint.

**Modified — reviewing profiles** (host-project product gates):

- `agents/code-reviewer.md` — gains the canonical Rule 1 + Rule 2 statement (including the referent-based discriminator) and a must-fix review-checklist item enforcing both rules, added to its step 2 "Review the changes" checklist, alongside inspection of product-commit messages for provenance leaks.
- `agents/docs-reviewer.md` — gains the same canonical statement and must-fix checklist item in its step 2 "Review the changes" checklist, including product-commit-message inspection.

**Untouched but relevant** (no change required; the design layers onto them):

- The `## Conventions` block / `reference/conventions/passing.md` — still delivers the full commit-format string to all agents; producers apply the no-provenance subtraction themselves. Unchanged.
- The commit-format convention in `.rp.md` (default `<commit-description> (<agent-name>)`, captured per `reference/conventions/setup.md:54-60`) — unchanged. The rule never reads or alters the host's specific format.
- The fork-mode **Upstream commit format** convention and the PR-time cherry-pick/rewrite (`reference/conventions/setup.md:129-160`) — unchanged; now layered with the new authoring-time rule (see Key Decisions).
- The orchestrator phase references (`reference/autonomous-phases/4 - code.md`, `5 - docs.md`) and the completion predicate (`reference/pipeline-versioning.md`) — unchanged; the review gate already blocks completion on a rejected verdict.
- Spec/design/plan agents and their reviewers, and the analysts/researchers/consolidators — untouched (artifact-only producers).

## Interfaces and Data Flow

The only "interface" is **profile prose → agent behavior**. There is no API, message shape, or file format to define. The canonical Rule 1 + Rule 2 statement is the single shared artifact; its physical instances are the five profiles, kept byte-identical.

Data flow at a host-product producing phase (the code phase shown; the docs phase mirrors it):

1. The orchestrator spawns a producer (`code-writer-tdd` / `code-writer-e2e` / `docs-writer`) with its profile (now carrying the rules) plus an initial prompt whose `## Conventions` block contains the resolved Artifact folder and the full commit-format string.
2. The producer writes product honoring Rule 1 (leaves untouched comments/prose alone) and Rule 2 (no reference to this run's pipeline).
3. The producer commits its product files using the host commit format **minus the pipeline-naming provenance** (no `(<agent-name>)` tag, no phase/artifact/task naming).
4. After every producer in the batch has committed, the orchestrator spawns the reviewer (`code-reviewer` / `docs-reviewer`) with its profile (rules + enforcement), the batch's base ref, and the rejection iteration number N.
5. The reviewer inspects the batch diff (`code-reviewer.md` step 1.6 / `docs-reviewer.md` step 1.8) and the product commit messages. Applying the canonical rules and the referent test:
   - **Violation seen** → it records the violation as a must-fix issue in `## Issues`, tagged to the offending task, and writes `4-code/code-review-N-rejected.md` (or `5-docs/docs-review-N-rejected.md`). No approval artifact is written. The orchestrator re-dispatches the flagged task(s); the cycle repeats until resolved.
   - **No violation** → the reviewer proceeds through its normal verdict path and, on approval, writes the singleton `*-review-approved.md` and the phase completes.

**Commit classification** is the one decision point with a concrete predicate: the **changed-path test** against the artifacts folder. A commit is a *product commit* iff at least one changed path is **not** under the artifacts folder (`.pipelines/<slug>/`); equivalently, it is an *artifact-only commit* iff **none** of its changed paths fall outside the artifacts folder. In today's division of labor producers commit only product and reviewers commit only artifacts, so each agent's commit class is statically known from its role — a producer can be told plainly "omit pipeline-naming provenance from your commits" with no per-commit path inspection. The path-based definition remains the **authoritative** classifier and the safe fallback: a hypothetical mixed commit has at least one path outside the artifacts folder, so it classifies as *product* and goes untagged — the Rule-2-safe outcome.

## Key Decisions

### Decision: The canonical rules live in agent profiles, duplicated verbatim — not injected via the conventions block

- **Choice:** Write Rule 1 and Rule 2 as a single canonical block and duplicate it byte-identically into the three producing and two reviewing profiles. Do **not** put the rule text in the per-spawn `## Conventions` block or any injected runtime payload.
- **Alternatives:** (a) *Conventions-block-style injection only* — define the rules once in a skill `reference/` file and inject them verbatim at spawn. (b) *Hybrid* — inject the rule statement, duplicate only the enforcement behavior into reviewers.
- **Trade-offs:** Injection-only gives a literal single source but under-delivers enforcement (an injected statement does not make the reviewer treat a violation as must-fix and block) and mis-models a fixed tool rule as a configurable per-run convention; it also puts a standing rule into transient runtime text rather than the reviewer's standing checklist. Duplication is the dominant pattern the codebase already uses for every cross-cutting profile instruction; CLAUDE.md mandates duplication over a shared referenced file. Its cost is drift risk across the copies (see Risks), accepted as the deliberate price of the no-references constraint. The `## Conventions` block stays reserved for genuinely per-run resolved values (artifact folder, commit-format string, guardrail commands).
- **Traces to:** Req 1 (always-on, no owner action / no opt-out), Req 10 (governs every host-product phase), Req 11 (stated once and consistently). Acceptance: "Always-on application", "Single source and consistency".

### Decision: Replace the pre-existing narrower Rule 2 line with the canonical Rule 2

- **Choice:** Delete `code-writer-tdd.md`'s line *"Comments must be self-contained — never reference the spec, the plan, or any other artifact."* and put the canonical Rule 2 in its place. This is the **only** occurrence of the narrower statement anywhere in `agents/` or `skills/`.
- **Alternatives:** Keep the narrower line and add the canonical rule alongside it. Rejected — that leaves a separate, overlapping version that can drift from the canonical rules, exactly what Req 11 forbids.
- **Trade-offs:** None of consequence; the canonical Rule 2 is strictly broader (it covers identifiers, string literals, log/error messages, and inline API docs, not just comments) and subsumes the narrower line.
- **Traces to:** Req 11 (the earlier narrower statement no longer exists as a separate, conflicting version). Acceptance: "Single source and consistency".

### Decision: Rule 2 is expressed as a referent-based test with concrete negative examples — never a token checklist

- **Choice:** State Rule 2 with a one-sentence decisive test framed by **referent**: a reference violates Rule 2 only if it identifies the concrete pipeline run that produced this output — its phases, artifacts, plan tasks, or agents as the authors of this work. A reference that merely uses pipeline vocabulary, documents the methodology, names an artifact *type*, or shows an illustrative path is the product's subject matter, not a reference to this run, and is never a violation — explicitly including in the self-hosting Radical Pipelines repository. The wording follows the house template (a named rule, a one-line decisive criterion, a concrete *"this is NOT a violation"* example such as a `spec.md` filename literal or an illustrative `.pipelines/<slug>/…` path, then the action), and carries the mental check: *"Is this reference about the subject matter of the product, or about the process that produced this artifact?"* The observable tells of a violating referent — naming a writing agent as the author, citing a plan task / phase iteration / decision of this run, pointing at this run's real artifacts path, narrating the writing agent's own process, or claiming the pipeline produced this output — appear as *illustrations*, never as a checklist of tokens.
- **Alternatives:** (a) *List the signals as the rule* (e.g. "a comment must not name an agent / a task / a path"). Rejected — a token checklist by another name; it would flag the legitimate catalog (filename literals, illustrative paths, methodology prose) and violate Out-of-Scope #2. (b) *State Rule 2 only abstractly with no examples.* Rejected — without the concrete negative example (especially the self-hosting carve-out) agents over-flag legitimate vocabulary.
- **Trade-offs:** The referent test demands judgment rather than mechanical matching, which is exactly the point — it is self-hosting-safe by construction (a doc *about* pipelines is subject matter; a doc *betraying that this run wrote it* is producing-process) and keeps the rule out of the forbidden keyword-scan trap. The same wording is what reviewers apply, so producers and reviewers share one referent test with no divergent second statement.
- **Traces to:** Req 4 (total content reach: comments, identifiers, string literals, log/error messages, inline API docs), Req 5 (external docs), Req 6 (referent-based; never flags vocabulary). Out-of-Scope #2. Acceptance: "Rule 2 — content", "Rule 2 — referent-based discriminator".

### Decision: Rule 1 is a content-discipline rule stated in the producing profiles, on the touched-vs-untouched axis

- **Choice:** State Rule 1 as a one-paragraph rule in the three producing profiles, keyed to the decisive **touched-vs-untouched** axis: do not reword, reflow, reformat, or tidy a comment attached to code the change does not modify, or a prose section of a doc the change edits but does not otherwise touch — leave it exactly as it was. Updating a comment or prose that belongs to content the change *is* modifying is permitted; there is no duty to preserve a still-valid comment beside code that was changed. Rule 1 does not touch the commit step (it does not apply to commit messages).
- **Alternatives:** A mechanical diff-shape check (flag any diff hunk that touches a comment line with no adjacent functional change). Rejected — Rule 1 is semantic (a naturally-updated comment beside a changed line is *permitted*), so no mechanical rule decides it; the reviewer already sees the relevant signal in the batch diff and judges it.
- **Trade-offs:** Like Rule 2, Rule 1 relies on reviewer judgment, but the touched-vs-untouched distinction is diff-visible — a tidied untouched comment surfaces as a changed comment/prose hunk whose surrounding code is unchanged. Stating both the *permitted* and *forbidden* examples prevents over-correction (it adds no duty to preserve still-valid comments — Out-of-Scope #1).
- **Traces to:** Req 2 (no tidying of untouched comments/prose), Req 3 (naturally updating a changed line's own comment is fine; no duty to preserve a still-valid comment; Rule 1 does not apply to commit messages). Out-of-Scope #1, #6. Acceptance: "Rule 1".

### Decision: Strip pipeline-naming provenance from product commits at authoring time, as a format-agnostic property

- **Choice:** Express the constraint as a property on product commits applied **at authoring time**: a product commit's message carries no pipeline-naming provenance — in particular no agent-name tag and no phase/artifact/task naming. The host commit format governs product commits in full **except** that it contributes no pipeline-naming provenance to them. Mechanically, each producing profile's commit step says to follow the host commit format but omit the provenance; reviewers (which commit only artifact files) keep the full format including the tag.
- **Alternatives:** (a) *Strip provenance only via a post-hoc rewrite* (extend the fork-mode cherry-pick to repo mode). Rejected — `artifacts-in-repo` pushes commits as authored with no PR-time rewrite, so a new rewrite pass would mean rewriting already-shared history, a larger and more fragile mechanism, and would still leave the as-authored commit tagged on the pipeline branch. (b) *Change the commit-format default to drop the tag globally.* Rejected — that would strip provenance from artifact-only commits too (Req 8 wants them tagged) and would make the rule depend on / alter the host format (violates Req 9). (c) *Have the orchestrator rewrite product commit messages after each producer commits.* Rejected — adds an orchestrator post-processing step and on-branch history rewriting; the producer is already the message author, so omitting the tag at authoring is strictly simpler.
- **Trade-offs:** Authoring-time omission is the only **mode-independent** point — it makes the product commit untagged as authored in both `artifacts-in-repo` and `artifacts-in-fork`. It coexists with the pre-existing fork-mode PR rewrite as two **layered** mechanisms, not competitors: the new rule is tool-fixed, authoring-time, both modes; the fork-mode **Upstream commit format** convention is per-project, PR-time, fork-only. With authoring-time omission in place the PR rewrite already targets an attribution-free upstream format, so it becomes a no-op on the provenance axis for product commits while still reshaping the description to upstream's guidelines. The pre-existing convention is **not removed**. The rule never needs the host's specific format — it forbids one property (pipeline-naming provenance) on one commit class (product commits).
- **Traces to:** Req 7 (product commit carries no pipeline-naming provenance / no agent-name tag, regardless of artifact storage mode and host format), Req 8 (artifact-only commit exempt; boundary by file path), Req 9 (rule and host commit format do not contradict; rule forbids one property on one commit class, never needs the host's specific format). Acceptance: "Rule 2 — commit messages and provenance".

### Decision: Enforcement reuses the existing review gate — a violation is a must-fix issue, no new mechanism

- **Choice:** Realize enforcement by adding Rule 1 and Rule 2 as must-fix items to the step-2 review checklist of `code-reviewer` and `docs-reviewer`, and adding product-commit-message inspection for provenance leaks. A violation found in the batch is recorded as a tagged issue in the rejection's `## Issues`, which forces a `rejected` verdict; no `*-review-approved.md` is written; the phase-completion predicate (which requires that approval artifact) is not satisfied; the affected task(s) are re-dispatched until the violation is resolved. No new gate, no orchestrator change, no bypass.
- **Alternatives:** (a) *A deterministic guardrail gate / script that scans for violations.* Rejected — Out-of-Scope #2 forbids token/keyword/path scans; Rule 2 is referent-based and Rule 1 is semantic, neither mechanically decidable. (A reviewer *may* use tooling to aid judgment per Out-of-Scope #4, but the gate is the reviewer's verdict, not a script.) (b) *Enforce in the producing agent only (self-check, no reviewer item).* Rejected — a producer self-checking does not block completion (Req 12 requires the gate to block), and the producer is the party most likely to have introduced the leak. Both layers exist: producers carry the rules to avoid violations; the independent reviewer is the gate.
- **Trade-offs:** The spec's enforcement requirement is precisely "a seen violation cannot be approved," which is exactly what "every issue is must-fix + a rejection withholds the approval artifact" already guarantees. Detection remains a semantic judgment (Req 12's explicit non-guarantee of mechanical exhaustiveness). The reviewer must honor the referent-based discriminator when applying the check, so it does not manufacture false rejections from legitimate vocabulary — most acute in the self-hosting repo.
- **Traces to:** Req 12 (a violation blocks its producing phase; the review gate is the only route to completion, no bypass; a seen violation cannot be approved), Req 10 (governs every host-product phase). Acceptance: "Enforcement".

### Decision: Scope by the product/artifact boundary — only host-product agents carry the rules

- **Choice:** Apply the rules to exactly the agents that touch host-project product: producers `code-writer-tdd`, `code-writer-e2e`, `docs-writer` (in-content rules + product-commit constraint) and reviewers `code-reviewer`, `docs-reviewer` (enforcement + referent discriminator). Earlier-phase artifact-only agents do not carry the rules.
- **Alternatives:** Load the rules into all agents uniformly. Rejected — artifact-only agents' output is *supposed* to reference the pipeline freely (their commits keep the provenance tag, Req 8); loading the rules there would be wasted instruction and would invite the wrong outcome.
- **Trade-offs:** Uses the single product/artifact boundary (path under the artifacts folder) consistently for both content scope and commit classification, so there is one notion of "product" across the design.
- **Traces to:** Req 1, Req 6/8 (product vs. artifact boundary by path), Req 10, and the Overview's product-vs-artifact distinction. Acceptance: "Always-on application", commit-classification criteria.

## Dependencies

No new external libraries, services, or tools. The design adds **no** dependency and changes **no** convention. It leans only on pre-existing internal mechanisms, all unchanged:

- The per-phase review gate and its must-fix / reject-liberally machinery (`code-reviewer.md`, `docs-reviewer.md`; the code/docs phase references; the completion predicate in `pipeline-versioning.md`).
- The commit-format convention and its delivery through the `## Conventions` block (`reference/conventions/passing.md`, `reference/conventions/setup.md`).
- The Artifact folder convention, which defines the product/artifact path boundary (`.pipelines/<slug>/`).
- The fork-mode PR rewrite (`reference/conventions/setup.md:129-160`), with which the new authoring-time rule coexists.

## Failure Modes and Observability

- **Missed detection (primary, accepted).** Enforcement is semantic judgment, so a reviewer can miss a violation; Req 12 explicitly does not guarantee mechanical exhaustiveness, and Out-of-Scope #2 forbids a mechanical scan that would close the gap. Mitigation: producers carry the rules too (first line of defense) and the reviewer is adversarial / reject-liberally. The guarantee is only that a *seen* violation cannot be approved. Residual risk accepted per spec.
- **Over-flagging legitimate vocabulary (false positive).** Most acute in the self-hosting repo, whose product is saturated with pipeline vocabulary. Mitigation: the referent-based test plus the explicit "not a violation" negative examples in the canonical wording are load-bearing — they are the design's main guard against false rejections.
- **Drift between the duplicated copies.** The canonical wording is duplicated across the five profiles; if a future edit changes one copy and not the others, the "stated once and consistently" guarantee (Req 11) erodes and a narrower variant could reappear. Mitigation: treat the canonical wording as a single block copied identically; any future change touches every copy. The implementation must make the canonical wording explicit so the copies are verifiably identical.
- **Observability.** A caught violation is visible in the committed `*-review-N-rejected.md` (the tagged must-fix issue) and in the subsequent re-dispatch — the normal, inspectable review-artifact trail. No new logging surface is needed or appropriate: this is an instruction change, not running code.

## Risks and Open Questions

**Risks**

- **Mixed-content commit (product + artifact in one commit).** The path-based discriminator assumes a commit is cleanly one class. Today writers commit product only and reviewers commit artifacts only, so the two are always separable. If a future agent ever commits product and artifact files together, the rule classifies it as a *product* commit (at least one path outside the artifacts folder) and it goes untagged — the Rule-2-safe outcome. Flagged in case the division of labor changes.
- **Drift between the duplicated canonical wordings (Req 11).** As above — the deliberate cost of CLAUDE.md's duplication-over-reference rule. The implementation should publish the canonical wording as one explicit block so every copy is verifiably identical.
- **Referent-test over-flagging in the self-hosting repo.** The most likely false-positive source; the wording's negative examples (filename literals, illustrative paths, methodology prose, self-hosting carve-out) are load-bearing.
- **Enforcement is judgment, not mechanical (accepted per spec).** Recorded so downstream phases do not try to add a forbidden mechanical scan (Out-of-Scope #2).

**Open questions for the plan / implementation phases**

- **Exact canonical wording of Rule 1 and Rule 2.** This design fixes the *home* (each producing/reviewing profile, duplicated verbatim), the *substance* (per spec), the *referent-based discriminator framing* (with negative examples and the subject-matter-vs-process mental check), and the *product-commit provenance constraint*. The single authoritative prose is to be settled at implementation, using the house template the existing profiles use to state a fine semantic line with a negative example. The binding constraint: one canonical wording, copied identically into every profile that carries it, with no surviving narrower variant (Req 11).
- **Whether each producing profile scopes its statement to its own surfaces or states the full rule identically.** Leaning toward stating Rule 1 + Rule 2 with one canonical wording everywhere (to keep the copies byte-identical and drift-free per Req 11) and letting each profile's surrounding context make clear which surfaces that agent produces. Either way the wording is identical across profiles.
- **`code-writer-e2e` fit.** The e2e writer commits tests only and has no inline-API-docs step today. It still emits product (test code, including test comments, string literals, and identifiers), so it carries the rules — the implementation should confirm the canonical wording reads sensibly for an agent whose product is test code rather than API docs.
- **Optional phase-reference / per-spawn backstop pointer.** Whether to also mention the output rules in the phase references (`4 - code.md`, `5 - docs.md`) or the per-spawn payload as a redundant reminder. Not required — the profile home is authoritative and sufficient. If added, it must be a pointer, not a second restatement of the rules (Req 11).
