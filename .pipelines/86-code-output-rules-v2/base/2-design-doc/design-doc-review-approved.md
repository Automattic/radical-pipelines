# Design Doc Review

## Verdict: approved

## Summary

The design doc is sound, complete, and faithfully traceable to the approved spec, and every load-bearing claim it makes about the codebase checks out against the actual files in this worktree. It correctly frames the feature as an instructions-only change (edits to five Markdown agent profiles under `agents/`, no code and no runtime mechanism), which is the right realization given CLAUDE.md's hard constraint that an agent reads only its own profile plus its initial prompt and that shared profile instructions are duplicated, never referenced. All twelve spec requirements map to a concrete decision or component; each Key Decision carries an explicit `Traces to` line; credible alternatives and trade-offs are weighed for every decision; the product/artifact boundary, the authoring-time provenance subtraction, the referent-based discriminator, and the review-gate enforcement are each realizable against the existing machinery. The deferred items (exact canonical wording, optional backstop pointer) are correctly scoped to the plan/implementation phase and are bounded tightly enough that they do not leave the design ambiguous. I verified the design against the real profiles, conventions, phase references, and the completion predicate; nothing is silently changed and no convention or `.rp.md` is altered.

## Verification performed

- **Named profiles exist and match.** `agents/code-writer-tdd.md`, `agents/code-writer-e2e.md`, `agents/docs-writer.md`, `agents/code-reviewer.md`, `agents/docs-reviewer.md` all exist at the cited paths (the design's `agents/<name>.md` references resolve at the worktree root).
- **The narrower Rule 2 line is real and unique.** `code-writer-tdd.md:33` carries exactly *"Comments must be self-contained — never reference the spec, the plan, or any other artifact."*; a repo-wide search confirms this is the only occurrence anywhere in `agents/` or `skills/`. The design's "replace, do not duplicate" decision (Req 11) is grounded.
- **Review-gate enforcement machinery exists as described.** Both reviewers have a step 2 "Review the changes" checklist, a "Convention compliance" item, "Every issue is must-fix", "Reject liberally", and per-issue task tagging — exactly the hooks the design reuses. The batch-diff inspection steps cited (`code-reviewer.md` step 1.6, `docs-reviewer.md` step 1.8) are present.
- **Completion predicate and no-bypass route confirmed.** `pipeline-versioning.md` requires `code-review-approved.md`/`docs-review-approved.md` (plus the summaries) for phases 4 and 5; `4 - code.md`/`5 - docs.md` mark the phase complete only on an approved verdict and re-dispatch flagged tasks on rejection. A withheld approval artifact therefore blocks completion, validating the Req 12 enforcement claim.
- **Commit-format provenance is real and unconditional.** `.rp.md:49-58` mandates the agent-name tag on every commit; the default `<commit-description> (<agent-name>)` lives at `setup.md:60`. This is the exact tag Req 7 targets, and the design's authoring-time subtraction sits where the tag is added.
- **Fork-mode layering is accurate.** `setup.md:129-160` describes the PR-time cherry-pick excluding artifact commits and rewriting to the upstream format (default no attribution). The design's claim that the new authoring-time rule coexists with this as a layered, non-competing mechanism holds.
- **Reviewer commits are artifact-only.** The phase references confirm reviewers commit only `*-review-*.md`/`*-summary.md` under the artifacts folder, so they correctly keep the full tag — consistent with the design's product/artifact classification.

## Notes (non-blocking)

- The exact canonical wording of Rule 1 and Rule 2 is deferred to implementation. This is appropriate altitude for a design doc — the design fixes the home (each carrying profile, duplicated verbatim), the substance, the referent framing with negative examples, the product-commit constraint, and the binding "one wording, copied identically, no surviving variant" rule (Req 11). The plan phase should pin the single authoritative prose and ensure every copy is byte-identical.
- The reviewers do not inspect commit messages today (step 1 inspects the batch diff). The design explicitly *adds* product-commit-message inspection to the reviewer checklist; this is a feasible addition (the reviewer has full tool access and a "commit conventions" compliance item already), not an unstated assumption. The plan should make the commit-message inspection an explicit checklist line.
