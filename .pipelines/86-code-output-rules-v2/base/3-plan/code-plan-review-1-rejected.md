# Code Plan Review

## Verdict: rejected

## Summary

The plan is well-traced and its codebase assumptions hold: `agents/code-writer-tdd.md:33` carries exactly the narrower Rule 2 line the plan replaces and it is the only occurrence in `agents/`/`skills/`; the five in-scope profiles have the commit steps and step-2 "Review the changes" checklists the tasks target; the reviewers carry the "every issue is must-fix" / "reject liberally" machinery the enforcement tasks reuse; and `.rp.md` defines no guardrails, so `## Guardrail scopes` is correctly rendered as `None`. Coverage of the spec acceptance criteria and the design's key decisions is essentially complete, and the ordering (settle canonical wording in Task 1, then duplicate verbatim) is sound. The plan is rejected on one decisive defect that it surfaces but does not resolve: this is a prose-only change to Markdown agent profiles, yet every task is typed `tdd`/`e2e` with acceptance criteria that are pure profile-content assertions, while CLAUDE.md forbids structural tests over skill/agent file content and the host's only executable test surface (`scripts/test/**`) tests release/versioning scripts — so the code-writers are handed a contract they can satisfy only by writing the forbidden test, with no sanctioned alternative. A few smaller issues are listed alongside it.

## Issues

### Issue 1: Tasks 1–6 are typed `tdd` but their acceptance criteria are prose-content assertions with no sanctioned test, colliding with the project's no-structural-tests rule

**What's wrong:** Tasks 1–6 are all `Type: tdd` and edit only Markdown agent profiles. Their per-task Acceptance criteria are entirely profile-content assertions — e.g. Task 1: "`agents/code-writer-tdd.md` contains a single self-contained canonical block…", "The sentence `Comments must be self-contained …` no longer appears anywhere in the repository"; Tasks 3–6: "byte-identical to the instance in `agents/code-writer-tdd.md`". The `code-writer-tdd` profile (the agent these tasks dispatch to) mandates RED/GREEN/REFACTOR over unit tests, "every Acceptance criterion must be exercised by at least one test" (`agents/code-writer-tdd.md:19`) and "Confirm every per-task Acceptance criterion is covered by a passing test before declaring the task done" (`agents/code-writer-tdd.md:45`). For these acceptance criteria the only test that could exist is a structural assertion over the content/wording/ordering of `agents/*.md`. CLAUDE.md (the binding project convention, via the `CLAUDE.md -> AGENTS.md` symlink) states: "The skill is prose, not software. Do not write structural tests that assert the content of skill or agent files — their sections, wording, or ordering." The host's only test surface is `npm test` → `node --test 'scripts/test/**/*.test.mjs'`, which exercises the version-sync/changeset/release scripts; no existing test reads `agents/`/`skills/` Markdown, and CONTRIBUTING.md confirms there is no lint/typecheck. The plan therefore hands every `tdd` writer a contract it cannot satisfy without violating a project rule, and gives no sanctioned way to meet "covered by a passing test" for a prose-only edit.

**Where in plan:** Tasks 1, 2, 3, 4, 5, 6 (`Type: tdd`); their `Acceptance` blocks; plan Overview's claim "verification is by reading the profiles … (there is no executable suite to add)".

**Suggestion:** Resolve the prose-only nature explicitly in the plan rather than leaving the writer to discover the contradiction mid-task. Make the tasks' verification approach deterministic and consistent with CLAUDE.md — for example, state in each task that the change ships no executable code and that the per-task Acceptance is verified by direct profile inspection (not by an added structural test over agent-file content, which the project forbids), and reconcile this with whatever task `Type` the plan assigns so the dispatched writer is not forced into the RED/GREEN test contract on un-testable prose. The fix is the planner's to choose; the binding constraints are (a) no structural test over skill/agent file content, and (b) no other executable surface these edits touch.

**Why it matters:** As written, two `code-writer-tdd` agents executing the same task would diverge — one writes a `scripts/test/**` structural test asserting profile content (violating CLAUDE.md and producing a test that "break[s] on every legitimate edit"), the other reports it cannot run RED. Either way the per-task acceptance is not met by the means the profile demands, and the plan is not independently reproducible.

### Issue 2: Task 7's e2e realization is non-deterministic and risks producing the forbidden structural test

**What's wrong:** Task 7 is `Type: e2e` and tells the writer to "Realize Flows 1–6 as repository-inspection checks per the host testing convention," with an escape hatch: "If the host project has no executable test surface for Markdown profiles, the realization is the documented inspection procedure (file reads plus text searches)…". The `code-writer-e2e` profile instructs the agent to "Write an automated e2e test that realizes the Steps and asserts the Expected, and add it to the project's e2e suite per the host project's testing convention" (`agents/code-writer-e2e.md:21`). The escape-hatch condition is ambiguous: the host *does* have an executable test surface (`node --test`), and a `node --test` file can trivially read Markdown and assert on it — so a writer can reasonably conclude an "executable test surface for Markdown profiles" exists and write exactly the structural test CLAUDE.md forbids (and which would land in `scripts/test/**`, the suite CONTRIBUTING.md and the e2e profile point at). Flows 1–6 are themselves pure structural assertions over agent-file wording/ordering (Flow 1 "byte-identical across all five profiles", Flow 3 "states the referent-based test … not a token/keyword/path checklist", Flow 6 scope search), so any automated realization is a forbidden structural test.

**Where in plan:** Task 7 (`Files to change`, `Changes`); E2E test plan Flows 1–6.

**Suggestion:** Make the realization deterministic and aligned with CLAUDE.md. State plainly that these flows are inspection procedures (file reads plus text searches) re-driven by the reviewer — not tests added to `scripts/test/**` — and remove the conditional ("if the host has no executable test surface…") that lets the writer branch toward an automated structural test. Note that `code-reviewer.md` step 3 already manually re-drives every E2E flow, so the inspection-procedure framing is the consistent one.

**Why it matters:** The conditional makes the task non-reproducible and invites a direct violation of a binding project convention. Two writers would produce materially different artifacts (a committed `.test.mjs` vs a documented inspection procedure).

### Issue 3: "Single source and consistency" depends on a byte-identical block, but the plan never fixes the canonical bytes in a verifiable form

**What's wrong:** Tasks 3–6 require their copies to be "byte-identical to the instance in `agents/code-writer-tdd.md`," and Flow 1 asserts all five are byte-identical. But Task 1 only requires that `code-writer-tdd.md` "contains a single self-contained canonical block" satisfying a list of substance requirements — it never pins the exact bytes anywhere a later task or the reviewer can compare against independently. The design's own risk register flags this: "The implementation should publish the canonical wording as one explicit block so every copy is verifiably identical" (design-doc Risks). The plan defers the wording entirely to Task 1's output and then asks Tasks 3–6 and Flow 1 to compare against that output — which is fine for execution order, but Task 1's Acceptance has no criterion that the produced block is captured as a single copyable unit with stable surrounding-context boundaries, so "byte-identical" has no fixed referent until Task 1 happens to produce one. Task 1's `Changes` mention this ("the canonical block's own wording must stand as a self-contained, copyable unit") but it is absent from Task 1's `Acceptance`, so it is not an enforced, observable outcome.

**Where in plan:** Task 1 `Acceptance` (missing the "self-contained, copyable unit with identifiable boundaries" criterion that `Changes` describes); Tasks 3–6 and Flow 1 (which depend on it).

**Suggestion:** Add a Task 1 Acceptance criterion that the canonical block is delimited as a single self-contained unit whose exact span is identifiable, so "byte-identical" in Tasks 3–6 and Flow 1 has a fixed, inspectable referent. This makes the drift guarantee (Req 11) verifiable rather than incidental.

**Why it matters:** Req 11 ("stated once and consistently") and the design's primary risk (drift between copies) both hinge on a verifiable canonical span. Without it in Task 1's Acceptance, the byte-identity checks in later tasks have no anchor and the consistency guarantee is not observably enforced.

### Issue 4: The "no opt-out exists" acceptance criterion is not traced by any task or flow

**What's wrong:** The spec's Always-on acceptance criterion "when the owner looks for a way to disable, override, or opt out of either output rule …, then no such mechanism exists" is satisfied only by construction (the plan adds no override surface), but no task or E2E flow asserts the absence of an opt-out, and no task traces to it. Flow 6 verifies scope (rules appear only in the five profiles) but not the no-opt-out property.

**Where in plan:** E2E test plan (no flow covers the no-opt-out criterion); Tasks (none traces to it).

**Suggestion:** Either add a brief flow/assertion that no opt-out or per-run/per-project override mechanism is introduced (e.g. confirm no conventions/`.rp.md`/phase-reference surface gains a toggle), or explicitly record in the plan that this criterion holds by construction because the change adds no configurable surface, so its coverage is intentional rather than dropped.

**Why it matters:** Every spec acceptance criterion should map to at least one task or flow, or be explicitly accounted for. As written this criterion is silently relying on "we added nothing," which is true but untraced and unverified.
