# Spec Review

## Verdict: rejected

## Summary

The v2 spec is strong overall: it cleanly reverses v1's "always-on, no opt-out" decision into a default-on, per-project-overridable model, splits Rule 2 into two independent switches (content-transparency and commit-provenance) with the correct WHAT-altitude framing, and consistently defers the switch encoding and enforcement mechanism to the design phase. The requirements trace tightly to the v2 Q&A, and the acceptance criteria are mostly in Given-When-Then form and cover the switch matrix (AC10/AC11/AC12). The narrower statement the spec promises to replace (`agents/code-writer-tdd.md:33`) exists exactly as described, and the override home (`.rp.md`) and the two enforcing reviewers exist, so the feature is feasible against the current architecture. However, the spec has one substantive gap that must be closed before approval — it mandates a default (untagged product commits) that directly contradicts an existing, in-scope project convention without ever acknowledging or scoping that contradiction — plus one acceptance-criterion ambiguity that would let two test authors disagree.

## Issues

### Issue 1: The default-on provenance switch contradicts this project's existing commit-format convention, and the spec never surfaces or scopes the reconciliation

**What's wrong:** R6 mandates that, by default, a commit introducing host-project product "must not... carry a provenance tag that names the pipeline or its agents," and AC5 makes this concrete ("no product commit message carries an agent-name provenance tag"). But this project's own Commit-format convention in `.rp.md` currently mandates the `(agent-name)`/`(assisted)` suffix on **every** commit (`.rp.md:50-58`: "Include the name of the agent in parenthesis or `assisted`"). The spec's default therefore directly conflicts with an existing convention. This is not a hypothetical edge case: R4 and AC6 explicitly establish that the Radical Pipelines repository is itself a host project that "builds itself," so the very first project the feature governs is one whose current convention forbids the new default. The v2 research surfaced this exact tension and flagged the reconciliation as work the downstream phases must do (`spec-research.md`, A8, line 78: "this project's Commit format convention currently mandates the `(agent-name)`/`(assisted)` suffix on *all* commits; reconciling it so product commits comply with Rule 2 is downstream work, surfaced here so the design phase resolves it"), but the spec dropped it entirely. The spec never states whether reconciling the commit-format convention is in scope of this feature, and no requirement or acceptance criterion addresses it — even though AC8 already commits the feature to eliminating one conflicting pre-existing statement (`code-writer-tdd.md:33`). The reader is left to infer that an existing project convention must change, with no signal of whether that is this feature's job.

**Where in spec:** R6 (Commit messages), R9 (provenance switch default-on), AC5, AC8, Out of Scope.

**Suggestion:** Add an explicit statement — as a requirement clause or an Out-of-Scope item — settling whether reconciling a host project's existing commit-format convention (so its product commits can be untagged under the default-on provenance switch) is in scope. If it is in scope, mirror AC8's approach with a requirement/AC that the conflicting "tag every commit" convention is reconciled with R6's product-commit default (analogous to how AC8 retires the `code-writer-tdd.md:33` statement). If it is out of scope (left to design), say so explicitly and name the conflict, the way the research did. Either way, the contradiction must be named, not left silent.

**Why it matters:** A spec defines defaults for all host projects; when a mandated default contradicts an existing convention of the canonical host project (RP itself), an implementer cannot tell whether the feature is supposed to change that convention, leave it, or treat the conflict as a per-project override the owner must set. Two implementers would build different things: one would edit `.rp.md`'s commit format, another would leave it and rely on the owner disabling the provenance switch. That is exactly the ambiguity the spec phase exists to remove.

### Issue 2: AC5 bundles two independently-switched concerns under one ambiguous "relevant switches enabled" condition

**What's wrong:** AC5 covers two distinct things in a single criterion — (1) external documentation content and (2) the provenance tag on product commit messages — and gates them on "with the relevant switches enabled" (plural, unspecified). But per R6/R9 these are governed by **different** switches: docs-content transparency is the content-transparency switch (R3/R5), while the agent-name provenance tag on commits is the provenance switch (R6b). A test author writing from AC5 alone cannot tell which switch must be enabled for which half of the "Then" clause; they must cross-reference R6 and R9 to split it correctly. AC4 (content transparency, single switch) and AC11 (provenance, single switch) are unambiguous by contrast — AC5 is the only criterion that fuses two switch domains under one vague precondition.

**Where in spec:** AC5.

**Suggestion:** Either split AC5 into two criteria (one for Docs-phase external-documentation content under the content-transparency switch, one for the product-commit provenance tag under the provenance switch), or keep it as one criterion but name each switch against the concern it governs in both the Given and the Then, so the mapping is unambiguous without consulting R6/R9.

**Why it matters:** Acceptance criteria must be specific enough to write tests from directly. As written, AC5 forces the test author to reconstruct the switch-to-concern mapping, and a wrong reconstruction would produce a test that passes when the feature is actually broken (e.g., asserting docs transparency while only the provenance switch is on).
