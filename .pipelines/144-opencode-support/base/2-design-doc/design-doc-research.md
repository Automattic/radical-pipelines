### RP-side integration points (lead's own reads, 2026-07-17)

The design must plug into these existing surfaces; verified by direct file reads in this worktree:

- **Per-tool surface is exactly two artifacts** (spec req 8): the setup Tool→Read table (`skills/radical-pipelines/reference/conventions/setup.md:19-23`, currently one row: Claude Code → `claude-code.md`) and the packaging manifests (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`). `claude-code.md` (21 lines) holds the canonical `.rp.md` blocks for Team spawning and Health monitoring and has no "Setup actions" section. The convention file is read only at setup; at run time only `.rp.md` is read (`load.md`).
- **Run-time consumption of the per-tool conventions**: `autonomous-workflow.md:63-68` (spawn per Team spawning convention, hold identifier, pass `## Conventions` block, resolve model via Agent models, apply at spawn), `:71` (agents message the orchestrator on completion), `:93` (close-out cancels the monitor per Health monitoring); `health-monitoring.md:13` (convention provides the start command), `:79` (cancel leftover loops before launching a new one); `resume-pipeline.md:7-9` (leftover loop persists until cancelled, cancel from a fresh session).
- **Loader has no tool-match guard** (spec req 10's gap): `load.md` "Missing conventions" checks required-convention presence only; nothing compares `.rp.md`'s per-tool section against the active tool. Setup is skipped when all required conventions are present (`setup.md:222`). — check: full read of `load.md` and `setup.md`.
- **Agent profiles**: 17 files in `agents/`, frontmatter exactly `name` + `description`; body is plain prose; profiles never reference skill files or `.rp.md` (project rule, confirmed on sampled profiles). Claude Code derives the agent type from frontmatter `name`; file name equals frontmatter name for all 17 — check: `head -8 agents/*.md`.
- **Version flow**: root `package.json` `version` (0.10.0) is the single source of truth; `scripts/sync-version.mjs` propagates to `TARGET_MANIFESTS = [".claude-plugin/plugin.json"]`; `package-lock.json` synced via `npm install --package-lock-only` in the `release:version` script. Adding a new version-bearing manifest means appending to `TARGET_MANIFESTS` — check: read of `scripts/sync-version.mjs` and `package.json`.
- **Packaging precedent**: Claude Code plugin serves `skills/radical-pipelines/` and `agents/` directly from the repo root — "the canonical sources themselves, with no hidden source directory and no mirror-symlink scheme" (README "Project Usage"). An opencode packaging artifact should follow the same no-mirror principle.
- **Repo rules constraining the design** (CLAUDE.md): generic skill stays tool-agnostic (only per-tool convention files may name a tool); agent profiles must not reference skill files or `.rp.md`; every change records a changeset; README updated when behavior it describes changes.
- **Health-monitor contract to satisfy** (`health-monitoring.md`): 4 signals (no-output stall, message failure, login/API-key error, network failure), 2-retry recovery table, identifier propagation after restart (:66), self-contained loop prompt template (:54-68), stop at close-out (:74-79).

### Topic 1 findings: opencode v2 coordination runtime (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

All items below marked VERIFIED were run live against a sandboxed non-global install (`npm install @opencode-ai/cli@next @opencode-ai/sdk@next @opencode-ai/plugin@next`, bin `opencode2`, `opencode2 --version` → `v0.0.0-next-15757`).

- **Version skew (pin-relevant):** under the `next` tag the packages are not in lockstep — CLI `0.0.0-next-15757`, but `@opencode-ai/sdk` and `@opencode-ai/plugin` at `0.0.0-next-15718`. A pin must name all package versions individually. `autoupdate` is a config field (`{"autoupdate": false}` in `opencode.json`), not a flag. VERIFIED.
- **Client-server architecture:** default is a detached background daemon (`opencode2 service start`) at `127.0.0.1:4096`, one shared daemon per environment serving all projects, sessions namespaced by projectID derived from directory; `--standalone`/`serve` give a private per-invocation server over the same on-disk store. VERIFIED.
- **Discovery + auth:** HTTP Basic, username `opencode`, per-service generated password (or `OPENCODE_PASSWORD` env). Service record at `$XDG_STATE_HOME/opencode/service-<hash>.json` = `{id, version, url, pid, password}` — readable by a shell subprocess. `opencode2 api <method> <path>` auto-discovers and auto-authenticates (VERIFIED: `opencode2 api get /api/session` with no creds returned data). OpenAPI spec served at `/openapi.json` (90 paths).
- **Plugin API that loads on this build:** the v2 `Plugin.define({ id, setup(ctx) })` API (config field `plugins`, auto-discovery from `.opencode/plugins/`). The legacy `(input) => Hooks` factory with `input.client`/`input.serverUrl` did NOT load (probe never invoked). VERIFIED.
- **Plugin ctx surface (logged live):** keys `options, agent, aisdk, catalog, command, event, integration, plugin, reference, skill, tool, session`. `ctx.session` = create/get/prompt/generate/command/synthetic/interrupt only — no list/active/fork/remove/wait (confirms upstream #34957). `ctx.event.subscribe` exists (in-process events). `ctx.serverUrl`, `ctx.client`, `ctx.$` undefined. Tool registration via `ctx.tool.transform(tools => tools.add({name, description, jsonSchema, execute}))` worked and the primary agent actually invoked the registered tool (`session.tool.called` → `session.tool.success`). Tool execute receives `{sessionID, agent, messageID, callID, progress}`; execute closures capture `ctx.session`/`ctx.event` from `setup(ctx)`. VERIFIED.
- **In-process session control:** `ctx.session.create` with agent+model+location succeeded (location seats an absolute directory, fixed for the session); `ctx.session.prompt` posts to any session by id; `ctx.session.interrupt` exists. Session enumeration is NOT reachable from plugin ctx — needs the HTTP/CLI path (`GET /api/session`, `/active`, `/wait`, model/agent switch endpoints). VERIFIED.
- **Cross-session injection:** `POST /api/session/{id}/prompt` `{text, delivery?, ...}` durably admits input by session id (returns `admittedSeq`). Idle target → new execution runs to completion. Busy target with `delivery:"queue"` → admitted then promoted into the active execution as a following step (VERIFIED live). `delivery` enum = `steer | queue` (default steer). `POST /synthetic` injects a non-user message; no `/message` write path exists. Finer steer/interrupt/Conflict semantics governed by open upstream #32157 — not exhaustively characterized.
- **Observability:** SSE `GET /api/event`. Live-observed events: `session.created`, `session.input.admitted/promoted`, `session.execution.started`, `session.step.*`, `session.text.*`, `session.tool.*`, `session.execution.succeeded`. Also defined: `session.execution.failed` (payload `Session.StructuredError`), `session.execution.interrupted`, `session.error` with error union including `ProviderAuthError` (auth) and `APIError` (network) — grounds req 14's auth/network surfacing — and `session.retry.scheduled`. *(Corrected by Topic 7 tails: a live auth failure surfaced as structured error `type:"provider.auth"` on `session.execution.failed`/`session.step.failed`; no separate `session.error` event fired in that flow.)* Polling alternatives: `POST /api/session/{id}/wait` (block until idle), `GET /api/session/{id}/pending`, `GET /api/session/active`. Caveat (source-level, not stress-tested): SSE is volatile — slow consumer overflows, disconnect loses events; events carry a `durable {aggregateID, seq}` block and a durable event log exists at the store level.
- **Durability:** session state is durable SQLite at `$XDG_DATA_HOME/opencode/opencode-next.db`; sessions survived server kill and `service restart`, remained retrievable, and accepted new prompts. In-flight execution is per-process (`/api/session/active` empty after restart): if the serving process dies, running turns stop but session records persist and a new process resumes by posting a prompt. VERIFIED.
- **Free-model test path:** model `opencode/hy3-free` (provider `opencode`) ran real turns at cost 0 with no provider auth configured — integration tests can exercise real turns for free. VERIFIED.
- **Not empirically verified (flags):** the interactive TUI itself (headless environment; "TUI is a client of the background service" rests on CLI design + docs, consistent with everything run); exhaustive steer/queue semantics; SSE overflow behavior under load; whether multiple daemons can be keyed side by side.

### Topic 2 findings: install and load (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

- **Plugin loading topology (VERIFIED):** three declare/place locations all load — global config `~/.config/opencode/opencode.json` `"plugins"` (loads at daemon start, re-instantiated in every project's scope), project `opencode.json(c)` `"plugins"` (that project only), project `.opencode/plugins/` auto-discovery (that project only). The one shared daemon loads project-local plugins per-project with no cross-project leak (proven with distinctive tools in projA vs projB; `/api/plugin?location[directory]=` reflects per-project resolution). A plugin's scope is created once per project and cached; file or config edits do NOT reload for new sessions — **`opencode2 service restart` is the universal reload trigger** (verified for file edits, config edits, and npm version bumps).
- **Channel (VERIFIED):** `plugins` entries route by shape: `file://`/`./`/`../`/absolute → local import (no npm install, no dep install); everything else → npm resolver (arborist). (a) npm `name@version` works; installs to `$XDG_CACHE/opencode/packages/<spec>/node_modules/<name>`, **transitive deps installed** (is-odd → is-number observed); cache keyed on the exact spec string → exact-version pinning, versions coexist. (b) **git/github specifiers work** (contradicts the spec-phase "untested" flag — now tested): `github:jonschlinkert/is-number` git-fetched and installed. Caveat: spec-keyed cache + install-once short-circuit → a moving branch ref will NOT auto-refresh; pin a tag or commit. (c) local paths (relative and absolute) load without npm install. Postinstall scripts skipped (source-level).
- **Skill delivery (VERIFIED, three mechanisms):** (a) plugin `ctx.skill.transform(d => d.source({type:"directory", path:<abs>}))` loads a bundled skill dir — registered by a global plugin it is available in ALL projects; `SkillSource` = `directory` | `url` | `embedded`; the `path` is a directory containing skill subdirs (each with SKILL.md). (b) scanned paths work, including `.claude/skills/` (req 6's premise re-confirmed on this build). (c) a `skills` config field (array of dirs/URLs) works. Progressive disclosure: the skill record advertises `{id, name, description, location, content}` where content = SKILL.md body; `reference/**` is not advertised, read on demand. Invocation: the native agent-invoked `skill` tool is the primary path; `POST /api/session/{id}/skill` → 204 also works; SKILL.md frontmatter `slash: true` would add an owner slash command (source-level) — a generic-skill modification, so not available under req 6.
- **Agent delivery (VERIFIED):** agents cannot be added in-process, have no Source mechanism, and no config field points at extra agent directories — the one deliverable that requires a **file copy**. Fixed dirs only: project `.opencode/agents/<name>.md`, global `~/.config/opencode/agents/<name>.md`; name derived from filename; project agents per-project, global agents everywhere. **A file with only `description:` frontmatter + prose body loads as an agent**; `mode` defaults to `all`; body becomes the system prompt — RP profiles need only the `name:` key dropped (filename already equals the name). `session.create({agent})` accepts agents of mode `all` AND `subagent` (both verified as session agents).
- **Version surface + update (VERIFIED):** `/api/plugin` and `ctx.plugin.list` return `{id}` only. The plugin id is **free-form and surfaced verbatim** — an id like `radical-pipelines@0.11.0` puts the version in `opencode2 api get /api/plugin`. Plugin-registered tools are agent-callable (an `rp_version`/status tool works as an in-session surface). Update path verified end-to-end: bump the pinned spec in config → `opencode2 service restart` → new version installs to its own spec-keyed cache dir and takes effect; without restart nothing changes; moving refs (`@latest`, git branch) do not refresh even on restart. `{"autoupdate": false}` is accepted config.
- **Repo-side premise (lead's own check):** RP releases are tagged — `git tag -l` → `v0.2.0` … `v0.10.0`, present on origin as annotated tags; `.changeset/config.json` sets `privatePackages: {version: true, tag: true}`, so tagging is part of the release flow. A pinned `github:Automattic/radical-pipelines#v<X.Y.Z>` specifier has a durable ref for every release.
- **Not fully verified (flags):** transitive-dependency install for a git-specifier parent package (verified for registry packages only); whether a plugin module can avoid importing `@opencode-ai/plugin` (zero-dependency plain-object export); whether extra `name:` frontmatter in an agent file is tolerated (verbatim copy) or must be stripped; whether agent files written during plugin `setup()` are discovered in the same restart or need a second one. → All four resolved by the Topic 2 tail below.

### Topic 2 tail findings (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

- **Zero-dependency plugin: WORKS.** `Plugin.define` is the identity function (`dist/v2/promise/plugin.js`). A plugin file default-exporting a plain `{id, setup}` object with no `@opencode-ai/plugin` import loaded, ran setup, registered a tool, and appeared in `/api/plugin`. Tool args use the plain `jsonSchema` (DynamicDefinition) form — no schema-lib import needed. RP's plugin can be a zero-dependency single file (node builtins only). VERIFIED.
- **Git-spec transitive deps: moot** (zero-dep plugin needs none). Registry-path transitive install was verified in Topic 2; git specifiers reify through the same arborist path (source-reasoned, not re-run — acceptable: no longer load-bearing).
- **Verbatim agent copy: WORKS.** An agent file with frontmatter `name: totally-different-name` loaded as the agent named by its FILENAME (`/api/agent` listed the filename id; `session.create` ran under it). The extra `name:` key is ignored — RP profiles copy byte-for-byte, with the filename setting the agent id. VERIFIED.
- **Materialization discovery order: ONE restart.** Global-plugin `setup()` is lazy — it runs at first scope/session init after a restart, and is awaited before agents are scanned/served: agent files written inside `setup()` were usable by `session.create({agent})` in the same restart (airtight clean-run: file absent → restart → first session triggers setup which writes it → second session governed by the materialized agent). This matches RP's ordering — the orchestrator's own first session initializes the plugin before any spawn. VERIFIED.
- **Spawn nuance (for Topic 3):** `session.create({agent})` does NOT validate the agent id — any string returns a session; a bogus agent yields a session whose turn produces no assistant message (fails rather than falling back to the default). Spawn design must validate the agent name up front and detect mis-spawn from the execution outcome, not the create call. VERIFIED.

### Topic 3 findings: team spawning semantics (design-doc-researcher, live experiments on `0.0.0-next-15757` with a real git repo + `git worktree add`, 2026-07-17)

- **Model param (VERIFIED):** `session.create` `model` is an object `Model.Ref {providerID, id, variant?}` — the string `"opencode/hy3-free"` is rejected with HTTP 400 (`Expected Model.Ref | null`); the object form works and persists (`variant` defaults to `"default"`). A bogus model is NOT validated at create (200) and fails at execution (`session.execution.failed`) — same pattern as bogus agents. The owner-facing canonical string is `provider/model[#variant]` (opencode's own `run --model` syntax); the API never takes the string, so RP's spawn must parse it.
- **Seating (VERIFIED):** all built-in tools resolve relative to `location.directory` — a worktree-seated session's shell reported the worktree as cwd and a relative `write` landed inside the worktree. No agent-facing tool can retarget the directory (built-in tool inventory checked); the only retarget path is the API `POST /api/session/{id}/move` (verified working). Unlike Claude Code's `EnterWorktree` hazard, opencode's seat is immovable from the agent side — no profile warning needed; RP simply never calls `move` mid-run.
- **Worktree project scoping (VERIFIED, load-bearing):** a git worktree belongs to the SAME opencode project as its main repo (identical projectID — resolution follows the shared `.git` common dir), so all of a pipeline's worktrees are one project. The plugin's `ctx.event.subscribe` is **global, not project-scoped** — it received the worktree session's `session.created` and `session.execution.succeeded`, and even a different project's events. The global SSE `GET /api/event` carries all projects' events too (complete HTTP fallback). **Caveat:** plugin `setup(ctx)` re-instantiates per directory-scope (repo root and each worktree each ran a fresh setup + subscribe) — an unguarded in-plugin subscribe delivers duplicate events (observed N× logging). The completion listener must be a singleton (module-level guard) or a single SSE consumer — never a naive per-setup subscribe.
- **Session record as ledger (VERIFIED):** no arbitrary metadata at create, but native fields suffice: `GET /api/session` returns `{id, projectID, agent, model{...}, cost, tokens, time{created,updated}, title, location{directory}, subpath}` per session. `agent` and `model` persist when set at create (unset agent shows undefined — RP must always set it); `title` is settable via `POST /api/session/{id}/rename` (204). Title, agent, model, location.directory, and timestamps all **survive `service restart`** (durable SQLite) and are filterable by title prefix. `time.updated` = last activity (liveness input). The list spans all projects — filter by title prefix and/or projectID.
- **Agent-list validation (VERIFIED):** `ctx.agent.list()` works from a tool's closure and returns built-ins (capitalized) plus custom filename-derived ids; scoped to the plugin's project/dir context — RP's globally-materialized agents appear everywhere. `GET /api/agent` is the HTTP equivalent. `rp_spawn` can reject a typo before creating a dead session.

### Topic 4 findings: messaging semantics (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

- **Module singleton (VERIFIED, resolves the Topic 3 open question):** the plugin module is imported ONCE per daemon; `setup()` runs per directory-scope with SHARED module state (same moduleId, setupCount 1→2→3 across repo root, worktree, and another project). A module-level `if(!subscribed)` guard produced exactly-once event delivery across all scopes — the Topic 3 duplication was purely the unguarded probe. A service restart re-imports fresh and re-subscribes once (correct). The SSE-consumer fallback is unnecessary.
- **Plugin tools in spawned sessions (VERIFIED):** a `session.create`d session seated in a worktree, running an RP-materialized agent, had the plugin tool available and its agent called it — spawned RP agents can call `rp_send`.
- **Sender identity (VERIFIED):** in a plugin tool's execute, `toolCtx.sessionID` is the CALLING session's id and `toolCtx.agent` its agent — `rp_send` self-attributes; prompt content cannot spoof the sender.
- **LOAD-BEARING CORRECTION — auto-title:** opencode auto-generates a session title from the conversation on the FIRST turn, overwriting any title set before it (verified: pre-set `rp:` titles were clobbered by turn 1). Auto-titling fires only on the first turn: a title re-set AFTER the first execution survived a second turn. No documented v2 config disables it. Also verified: `session.create` accepts a custom `id` (must match `^ses`), an alternative RP-controlled durable key. Consequence: Topic 3's create→rename→prompt ordering loses its title; the ledger design is amended (see Topic 3 correction and Topic 4 decision).
- **Delivery modes (VERIFIED):** into an IDLE session, `steer` and `queue` behave identically (one new execution each). Into a BUSY session, both were durably admitted (`session.input.admitted`, transiently visible in `/pending` with their `delivery` value) and promoted into the ongoing execution as a following step; a destructive steer interruption was not reproducible with the fast free model — the steer-interrupts-current-step distinction is source-level (upstream #32157). `queue`'s contract ("strictly after the current step") is the non-destructive one.
- **`agents` / `resume` params (VERIFIED / SOURCE):** `agents:[{name}]` does NOT switch the session's agent (execution still governed by the session's persisted agent) — it only attaches delegation mentions; `resume` is source-level (resumes execution). `rp_send` omits both.
- **Receiver's view (VERIFIED):** an injected message appears as a USER-role message in the target's history and the ensuing execution is governed by the target session's own persisted agent+model — never the sender's.
- **Delivery-failure observability (VERIFIED — the req 14 chain):** (a) prompt to a nonexistent/deleted session → synchronous HTTP 404 `SessionNotFoundError` (dead target detected at send time); (b) admitted-but-unpromoted input sits observably in `GET /api/session/{id}/pending` (`[{admittedSeq, delivery, text}]`) — a lingering entry past a threshold = "never delivered"; (c) post-promotion failure → `session.execution.failed` carries the sessionID (`durable.aggregateID` and `data.sessionID`) plus a structured error (e.g. `{"type":"provider.no-route",...}`), and `session.error` carries `ProviderAuthError`/`APIError`.

### Topic 5 findings: health-loop scheduler mechanics (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

- **Timer reliability (VERIFIED):** a plugin module-level `setInterval` fired every ~15.00s with <2ms drift across consecutive ticks, each injecting successfully; nothing in the plugin lifecycle killed or GC'd the timer while the daemon lived. Module-level `started` guard required (per-scope setup re-runs) — with it, no duplicate timers.
- **Idle signal + no-overlap (VERIFIED):** `GET /api/session/active` is authoritative server-side truth (`{"<sessionID>":{"type":"running"}}` observed mid-turn), one cheap localhost call per tick, correct immediately after a restart. In-memory event pairing also works within a daemon lifetime but is empty after restart and lags by event-delivery ms. Idle ticks produced exactly one execution per tick (no pile-up, `/pending` empty); with a busy target, a fast loop logged `busy → SKIP` for 4 consecutive ticks and injected exactly once when the target went idle — "fire only when idle, no overlapping turns" holds exactly.
- **Registry location (VERIFIED):** plugin ctx has no writable storage (`ctx.reference` = reference docs, `ctx.options` = read-only config passthrough, `ctx.filesystem` = read-only; the SDK's `Path` type is not exposed). opencode's own data dir (`$XDG_DATA_HOME/opencode/`) is its private store. Writing `$XDG_DATA_HOME/radical-pipelines/loops.json` via node fs worked.
- **Re-arm after restart (VERIFIED, trigger nuance):** setup is lazy; after `service restart` the timer is dormant until the first PROJECT-scoped touch — a global-scope call (`api get /api/session` with no directory) did NOT re-arm; a project-scoped call (`api get /api/plugin` from the repo cwd) DID (`SETUP` → `RE-ARMED from registry`, timer firing again). No re-registration needed; a resuming orchestrator opening a session in the run repo is that touch.
- **Leftover semantics (VERIFIED):** a registry-recorded loop survived restart, re-armed on touch, was listed from a fresh session (`rp_loop_list` returns registry contents), and `rp_loop_cancel` stopped the timer (zero ticks after) and removed the entry. Loop tools are agent-callable (the free model called `rp_loop_cancel`).
- **Client-less injection (VERIFIED):** all targets were API-created with no attached TUI; every loop injection ran a full server-side execution — a loop can ping an orchestrator session whose TUI is gone.

### Topic 7 tail findings: recovery mechanics (design-doc-researcher, live experiments on `0.0.0-next-15757`, 2026-07-17)

- **Mid-life model switch (VERIFIED):** `POST /api/session/{id}/model` with body `{"model": Model.Ref}` → 204. After a turn on model A, switching to B updated `session.model` immediately and the next turns' `session.step.started` events used B. Switching while mid-execution is non-disruptive: the in-flight execution keeps the old model; the new one applies from the next turn. The authoritative per-turn model signal is `session.step.started.data.model` — the message-list ordering is reverse and misleading. Consequence: the monitor's "swap model" retry can reuse the SAME session (switch + queue re-prompt); re-spawn-with-new-model stays the verified fallback.
- **Live ProviderAuthError chain (VERIFIED, with a shape correction):** with a bogus `ANTHROPIC_API_KEY`, a turn on `anthropic/claude-sonnet-5` produced `session.execution.failed` AND `session.step.failed`, both carrying the structured error `{"type":"provider.auth","message":"Provider request failed with HTTP 401: …authentication_error… invalid x-api-key… request_id…"}` with `data.sessionID` and `durable.aggregateID` = the session. **No separate `session.error` event fired** — auth errors are recognized by structured-error `type === "provider.auth"` (sibling of the live-verified `provider.no-route`), and the `message` carries the provider's 401 body verbatim, ready for the escalation payload. After the failure the session persists and is listable with the failing model on record (auto-title never ran — no successful generation).
- **Interrupt (VERIFIED):** `POST /api/session/{id}/interrupt` (no body) on a mid-execution session → 204; `session.execution.interrupted` fired; `/active` cleared; the session stayed usable — a follow-up prompt ran a normal execution to completion. Interrupt is non-destructive.
- **Harness input (for Topic 9):** the `opencode` provider exposes ~20 free models (hy3-free, minimax-m3-free, deepseek-v4-flash-free, glm-5-free, kimi-k2.5-free, …) usable with no credentials at cost 0 — real turns, model-swap between two free models, completion/interrupt flows all free. Deterministic failure injectors: bogus `*_API_KEY` env → `provider.auth`; bogus model id → `provider.no-route`. Free models still call opencode's hosted endpoint (full hermeticity is the harness round's open question).

### Topic 9 findings: pin + integration-test harness (design-doc-researcher, live experiments on `0.0.0-next-15757` and smoke on `0.0.0-next-15772`, 2026-07-17)

- **XDG isolation (VERIFIED complete):** `XDG_CONFIG_HOME` (config, service password record, global `agents/` + `skills/` dirs, provider config), `XDG_DATA_HOME` (`opencode-next.db`, logs, repos/shell/snapshot), `XDG_CACHE_HOME` (plugin `packages/` cache, models.json, bin), `XDG_STATE_HOME` (service record, locks) together redirect ALL v2 state; a fully-redirected instance leaked nothing to the real dirs. **Harness rule:** set the XDG vars on EVERY invocation including `--version` — an unset invocation writes a log line to the real `~/.local/share/opencode/log`. Two instances coexist without collision (4096 daemon + standalone on another port; a second-profile `service start` auto-picked 4097); `opencode2 api` discovers per-profile via the XDG_STATE record.
- **Headless shape (VERIFIED):** `serve --port N` (standalone) and `service start` behave identically for plugin loading, per-directory scope caching, sessions, and events (both were used across Topics 1–7). `serve`: deterministic port, no service record (connect via `api --server http://127.0.0.1:N` — verified — or curl + `OPENCODE_PASSWORD`), teardown = kill. `service`: auto-picked port, auto-discovery, detached lifetime (state can leak between tests). Recommendation adopted: `serve --port <fixed>` under isolated XDG for the harness.
- **Hermetic model (VERIFIED — fully offline turns):** a custom OpenAI-compatible provider in `opencode.json` (`providers.stub` with `package: "@opencode-ai/ai/providers/openai-compatible"`, `settings.baseURL` → localhost stub, mandatory dummy `settings.apiKey` — without it turns fail `provider.auth: Missing auth credential`), models entry `stub-model`, referenced as `{providerID:"stub", id:"stub-model"}`. The stub must serve `GET /v1/models` and `POST /v1/chat/completions` as streaming SSE OpenAI chunks (~40-line node server sufficed; auto-title makes a second call). A session on the stub ran a turn with the stub's text verbatim, cost 0, no network.

### Topic 1: Coordination-layer runtime — where RP's opencode code runs and what API it can reach

- **Spec link:** Requirements 11 (team spawning), 12 (messaging), 13 (health loop), 14 (liveness recovery) — all depend on RP-owned primitives the orchestrator can invoke; Requirement 1 (the coordination layer is installable via native mechanisms).
- **Framing:** On Claude Code, spawn/message/loop are tool-native. On opencode v2 they must come from an RP-owned layer. The foundational question is the runtime shape of that layer: how the orchestrator (itself an opencode session) invokes RP primitives, and what API surface RP code has — the restricted plugin `ctx.session` subset (upstream #34957), the full local server HTTP API, or something else. This decides whether the layer is a plugin exposing custom tools, a sidecar process, shell scripts over `opencode2` CLI/API, or a mix.
- **Options:**
  1. **Plugin-centered hybrid (chosen):** one RP opencode plugin authored against the v2 `Plugin.define` API — registering RP coordination tools the orchestrator agent calls first-class, and subscribing in-process via `ctx.event` — plus the public HTTP API (from shell via `opencode2 api`, or from plugin code via the discovered service URL + Basic auth) for the surfaces the plugin ctx omits (session enumeration, `/wait`, model/agent switch).
  2. **Pure external layer:** no plugin; the orchestrator drives everything through `opencode2 api` shell calls, with RP-shipped scripts and detached watcher/scheduler processes supplying completion notifications and the loop.
  3. **Sidecar daemon:** an RP-owned long-running process providing all coordination over HTTP; the orchestrator talks to it via shell.
  4. **Legacy hooks-API plugin** using `input.client`/`input.serverUrl` — eliminated on evidence: that API does not load on the target build.
- **Trade-offs:**
  - Option 1: coordination tools appear in the orchestrator's native tool list (an LLM calling `rp_spawn` with a JSON schema is more reliable than composing authenticated curl commands); `ctx.event.subscribe` gives completion/error events in-process with no auth, discovery, or SSE-reconnect handling; the plugin loads automatically wherever the serving process runs, so install is config-only (req 1) and in-server residency comes for free. Costs: the plugin API is the beta's most unstable surface, and the restricted ctx forces a second (HTTP/CLI) reach path anyway — two paths to test.
  - Option 2 is the simplest to author (no plugin API exposure; only the OpenAPI surface, which is spec-served and CLI-wrapped) but pushes completion notifications and the idle-gated loop into detached processes RP must spawn, discover, authenticate, and babysit (zombie watchers, PID files, SSE reconnects) — more failure modes on exactly the paths the health monitor exists to keep reliable — and still requires distributing RP code, so it saves no packaging artifact. The orchestrator would also have to compose raw API calls for spawn/message, weakening the most-exercised primitives.
  - Option 3 concentrates the same responsibilities in one process but adds daemon lifecycle management (start, health, restart, discovery) that the plugin gets for free from opencode's own service lifecycle; it duplicates opencode's server rather than extending it.
- **Decision:** Option 1. The RP coordination layer is **one opencode plugin** (v2 `Plugin.define`) that (a) registers RP's coordination tools via `ctx.tool.transform(tools.add)`, (b) uses `ctx.session.create/prompt/interrupt` for in-process session control, and (c) subscribes to `ctx.event` for execution/error events; the orchestrator and the plugin use the **public HTTP API** (preferably via `opencode2 api`, which auto-discovers and auto-authenticates) for what the ctx omits: session enumeration/inspection, `/wait`, model/agent switching. RP-owned durable state (agent ledger, loop registry — shapes decided in later topics) lives on disk, not in the plugin process.
- **Rationale:** Every load-bearing primitive of options 1's two paths is verified on the target build (tool registration + agent invocation, session.create with agent/model/location, cross-session prompt with queue delivery, in-process event subscription, `opencode2 api` auto-auth), so the choice rests on demonstrated capability, not docs. The in-process path eliminates the discovery/auth/reconnect failure modes option 2 would put under the health monitor's most critical duties, and first-class tools give the orchestrator the same call ergonomics it has on Claude Code — the parity target. The plugin-API instability cost is real but bounded by the spec's pin-and-verify model (reqs 2–3): RP is verified against exactly one build, and the integration tests catch breakage on re-pin.
- **Evidence:**
  - v2 `Plugin.define` loads and legacy hooks factory does not — researcher's live probe on `0.0.0-next-15757` (legacy probe never invoked; v2 plugin registered) → confirmed.
  - Registered plugin tools are callable by the session's agent — live `session.tool.called` → `session.tool.success` on a registered `rp_probe_tool` → confirmed.
  - `ctx.session.create` accepts agent+model+location and seats an absolute directory fixed for the session — live create succeeded → confirmed.
  - Plugin ctx lacks list/active/wait/model-switch — runtime ctx keys logged; `ctx.session` = create/get/prompt/generate/command/synthetic/interrupt → confirmed (upstream #34957).
  - The HTTP/CLI path covers the gap — `opencode2 api get /api/session` with no credentials returned data (auto-discovery + Basic auth); OpenAPI at `/openapi.json` lists session list/active/wait and model/agent switch → confirmed.
  - In-process events suffice for completion/error observation — `session.execution.succeeded` etc. observed live; `session.error` union includes `ProviderAuthError`/`APIError` (schema-level) → confirmed / schema-verified.

### Topic 2: Install and load — distribution channel, plugin loading topology, skill and agent delivery, version surface

- **Spec link:** Requirements 1 (install), 2 (pinned target), 4 (version discoverability), 5 (update), 6 (skill loads unchanged), 7 (agents available), 8 (packaging artifact half of the per-tool pattern); spec-research mandated an empirical distribution spike (research item 7 invalidated "direct-from-Git" as documented).
- **Framing:** RP must land on an owner's machine as: the plugin (Topic 1's coordination layer), the unchanged generic skill tree, and the 17 agent profiles in opencode's on-disk format (opencode scans `.claude/skills/` but not `.claude/agents/`; agents/commands cannot be registered in-process). The channel (npm vs git specifier vs local path), where each piece lands, how the plugin loads relative to the shared daemon, and how version/update reporting works are all open.
- **Options (channel):**
  1. **Pinned github specifier of the RP repo itself (chosen):** `"plugins": ["github:Automattic/radical-pipelines#v<X.Y.Z>"]` in the owner's global opencode config. The repo gains an opencode plugin module referenced as its package entry point; the installed package carries `skills/` and `agents/` inside it.
  2. **Publish a dedicated npm package** (e.g. `@automattic/radical-pipelines-opencode`): cleanest resolver behavior (registry metadata, semver), but requires new npm release infrastructure (publish step, tokens) for a repo that today publishes nothing, and splits the distribution artifact from the repo.
  3. **Clone + local path:** clone the repo at the pinned tag and point `plugins` at the absolute path. Zero resolver involvement, but the owner manages the clone, deps are not installed for local paths, and update becomes a git operation — kept as the development variant (parallel to Claude Code's `--plugin-dir`), not the documented owner channel.
- **Trade-offs (channel):** the github specifier keeps RP's established distribution philosophy — the repo is the single artifact, served directly, for both tools (Claude Code installs from this same GitHub repo) — with no new publish infrastructure; exact pinning comes from the tag-keyed cache (verified: spec-keyed dirs, versions coexist, restart applies a changed spec). Its costs: moving refs never refresh (harmless here — the documented procedure only ever pins tags, which req 2 demands anyway), and transitive-dependency install for git-spec parents is not yet verified (flagged; mitigated below by aiming for a zero-dependency plugin module). npm-publish stays available later without design change (same package shape, different specifier).
- **Decisions:**
  1. **Channel:** the documented install adds the pinned github specifier `github:Automattic/radical-pipelines#v<X.Y.Z>` to the owner's **global** opencode config `plugins` array, plus `"autoupdate": false`, then `opencode2 service restart`. Global (not project) config: RP's agents and tools should be available across the owner's projects, matching the Claude Code plugin's user-scope install. The packaging artifact (req 8) is the opencode plugin module in the repo, referenced as the package entry point in `package.json` — parallel to `.claude-plugin/` for Claude Code.
  2. **Skill delivery:** the plugin registers the repo's own `skills/` directory by reference via `ctx.skill.transform(d => d.source({type:"directory", path}))`, resolved from the plugin module's own location (`import.meta.url`). No copy, no modification of the generic skill files (req 6): the installed package carries the canonical tree, and progressive disclosure is native (SKILL.md body advertised, `reference/**` on demand). Invocation is by natural language or the native `skill` tool; no `slash: true` frontmatter is added, since that would modify a generic skill file.
  3. **Agent delivery:** the plugin **materializes the 17 profiles into `~/.config/opencode/agents/`** at `setup()` — idempotent, overwriting only RP-owned files, copying each profile **byte-for-byte** (tail-verified: an extra `name:` frontmatter key is ignored and the filename governs the agent id; filenames already equal agent names, and identical bytes preserve req 7's "equivalent instructions" exactly). Global dir (not project `.opencode/agents/`): available in every repo, matches Claude Code's plugin-scope agents, and avoids committing RP files into owners' repos. Copying is forced by the platform — agents have no by-reference mechanism (verified); the plugin owning the copy keeps install config-only and makes update self-healing (refresh on version change). Tail-verified ordering guarantee: plugin `setup()` is lazy (first scope init) and awaited before agents are scanned, so materialized agents are usable within the **same single restart** — and always before the orchestrator's session can spawn anything.
  4. **Version surface (req 4):** the plugin id embeds the version — `radical-pipelines@<version>` read from the package's own `package.json` at load — so `opencode2 api get /api/plugin` reports it natively (primary surface, works even with no session). A plugin-registered status tool provides the in-session surface (exact tool set decided in the spawning/messaging topics). No sync-version change needed: the version is read at runtime from `package.json`, already the single source of truth.
  5. **Update (req 5):** documented procedure = change the pinned tag in the config specifier → `opencode2 service restart` → plugin refreshes materialized agents at setup. Verified mechanics: new spec installs to its own cache dir and takes effect on restart.
- **Alternatives considered (delivery):** skill into scanned paths by copy (a second tree to keep in sync — rejected); agents in project `.opencode/agents/` written by RP setup as a "Setup actions" step (pollutes every project repo with 17 files, per-project drift, and setup runs after install — rejected as the default; nothing in the design precludes a project choosing it manually); an explicit `rp_install` tool the owner invokes to copy agents (more owner steps for the same result; kept as fallback if setup-time materialization hits a discovery-order problem — open question below); version via a VERSION file only (not surfaced by any native opencode listing — rejected as primary).
- **Rationale:** every load-bearing mechanism of the chosen path is verified on the target build (github specifier installs and loads; global-config plugin loads in every project scope of the shared daemon; skill-source-by-directory loads globally with progressive disclosure; minimal agent files load with filename-derived names; free-form plugin id surfaces verbatim; spec bump + restart applies an update). The chosen shape minimizes moving parts: one pinned specifier delivers plugin + skill + agents; the only file-copy the platform forces (agents) is owned by the plugin, so the owner's procedure is config edit + restart — and identical for update.
- **Evidence:**
  - github specifier installs and loads — researcher: `github:jonschlinkert/is-number` git-fetched into the spec-keyed cache and importable → confirmed live.
  - Tag-pinned refs are durable and available — lead: `git tag -l` shows `v0.2.0`…`v0.10.0`, on origin as annotated tags; changesets config tags releases (`privatePackages.tag: true`) → confirmed.
  - Global-config plugin loads in every project scope; project plugins don't leak across projects — researcher's projA/projB experiment → confirmed live.
  - Skill dir registered by a global plugin is available in all projects with progressive disclosure — researcher's `rp-bundled-skill` experiment; skill record advertises SKILL.md body only → confirmed live.
  - Agents require a file copy; minimal profile (description + prose) loads; `session.create` accepts mode `all` and `subagent` agents — researcher's live experiments → confirmed.
  - Plugin id is free-form and surfaced by `/api/plugin`; update = spec bump + restart; moving refs don't refresh; `autoupdate: false` accepted — researcher's live experiments → confirmed.
- **Follow-ups (tail of this topic, all resolved — see "Topic 2 tail findings"):** the plugin is a **zero-dependency single file** (plain `{id, setup}` default export loads; `Plugin.define` is the identity function), eliminating the git-spec transitive-deps question; agent profiles copy **byte-for-byte** (extra `name:` frontmatter ignored, filename governs); materialization needs **one restart** (setup is awaited before agent scanning); and `session.create` does not validate agent ids — spawn design must validate names up front (carried into Topic 3).

### Topic 3: Team spawning — spawn tool, identifiers, seating, ledger, completion notification

- **Spec link:** Requirement 11 (spawn by name with model, seated in a worktree, stable identifier, completion notification); feeds 12 (messaging by identifier), 14 (restart / re-spawn / identifier propagation), 16 (resume: no reattachment, but leftover state must not confuse a fresh session).
- **Framing:** Topic 1 fixed the runtime (plugin tools + `ctx.session` + `ctx.event`, HTTP/CLI for the rest); Topic 2 guarantees agents exist before any spawn. Open: the spawn tool's contract (params, returned identifier), the exact `session.create` model/location semantics (model string shape; whether built-in tools resolve relative to the seated directory), how sessions seated in worktree directories map to opencode's project scoping (which plugin scope sees their events — load-bearing for completion notifications), whether opencode session metadata can carry the logical agent name (replacing a separate ledger file), and where any RP-owned ledger state lives.
- **Options:**
  - *Ledger:* (1) the opencode session DB itself — the run-unique instance name encoded in the session `title` (`rp:<run>:<name>`), agent/model/directory/timestamps read back from `GET /api/session` (chosen); (2) an RP-owned state file (JSON under a machine-local data dir or the worktree root); (3) in-worktree state files.
  - *Completion listener:* (1) singleton in-process `ctx.event.subscribe` guarded at module level, with the health monitor's HTTP polling as the durability net (chosen); (2) naive per-setup subscribe — eliminated on evidence (duplicate delivery per directory-scope); (3) a dedicated SSE consumer over `GET /api/event` — kept as fallback if the singleton guard proves unreliable across scopes.
  - *Identifier:* (1) the opencode session ID (chosen); (2) the logical name with RP-internal resolution.
- **Trade-offs:** DB-as-ledger has one source of truth that is durable across restarts for free, enumerable over the verified HTTP path, and reconstructable by any fresh orchestrator session (strong for resume, req 16) — at the cost of encoding the name in `title` (no arbitrary metadata field exists). A state file duplicates what the DB already stores and must itself survive restarts and worktree teardowns; in-worktree files die exactly when resume recreates worktrees. Session-ID-as-identifier matches Claude Code parity (identifier from spawn result; changed on restart → propagation per health-monitoring.md:66); logical-name-as-identifier would silently re-bind messages after a re-spawn, hiding the propagation step the health contract requires.
- **Decision** *(parameter list, ledger key, spawner field, and notification policy amended by Review round 1 — see Review Adjudications)*: the plugin registers **`rp_spawn` `{name, agent, model, directory, prompt, run}`**. Two distinct identifiers, defined once: **`agent`** is the profile name (an RP agent id materialized by install, e.g. `spec-reviewer`), validated against `ctx.agent.list()`; **`name`** is the run-unique instance name the orchestrator assigns per the generic skill's spawn step ("Give the agent a name unique within the run", autonomous-workflow.md) — multi-instance profiles are the norm (e.g. two `spec-reviewer` instances per round), so the ledger is keyed by `name`, never by `agent`. `run` is the run branch name. The tool: (1) validates `agent` and rejects unknown profiles (create doesn't validate — a typo would make a dead session); (2) parses the Agent-models convention string `provider/model[#variant]` into `Model.Ref {providerID, id, variant?}` (the convention value stays an opaque tool-native string the orchestrator passes verbatim); (3) calls `ctx.session.create({agent, model, location:{directory}})` — the seat is fixed and agent-immovable; (4) records the ledger entry `sessionID → {name, run, spawner}` where **`spawner` = the caller's `toolCtx.sessionID`** (unspoofable, verified in Topic 4) — opencode has no native session parenting, so the spawner exists only because rp_spawn records it; (5) posts the initial prompt; (6) returns the **session ID as the stable identifier** plus the instance name. The durable title is `rp:<run>:<name>` (asserted after the first turn per the correction below). Completion notification: a **module-singleton event listener** (guarded `ctx.event.subscribe`, global stream) watches terminal events of ledger sessions and notifies the spawner **on the child's first terminal event only** (`succeeded` or `failed`) — the policy decided in Review round 1, Issue 3: subsequent-turn completions are communicated by the agents themselves via `rp_send` (the skill's existing "agents message you when their work completes" protocol), and subsequent-turn failures are monitor observables via the listener's error log and `rp_status` (req 14) rather than push notifications; this keeps orchestrator wake-ups proportional to spawns, not to inter-agent traffic (every injection into an idle session runs a full LLM execution — verified). All terminal events, first or later, still feed the listener's records (error log; first-event title re-assert). **Restart behavior, explicit:** the in-memory map (including `spawner`) dies with the daemon, and in-flight executions die with it too; a post-restart terminal event on a pre-restart child therefore resolves no spawner and produces no notification — consistent with the git-based resume model, where the resumed orchestrator re-spawns agents fresh from committed state. On re-spawn the new session gets a new ID; the newest ledger entry for a `name` wins, and the changed identifier is propagated per the health contract. RP never calls `POST /api/session/{id}/move` during a run.
- **Rationale:** every step of the chosen contract is individually verified on the pinned-candidate build (agent listing from a tool closure, Model.Ref object requirement and 400 on the string form, worktree seating incl. relative-path resolution, same-project worktrees, global event subscription, title rename + restart survival). The DB-as-ledger removes an entire class of state-sync failures and makes the ledger available to any process over the verified HTTP path — the health monitor and a resumed orchestrator read the same truth the plugin wrote. The singleton listener is forced by observed duplicate per-scope delivery; its known residual (module-instance sharing across scopes) is dispatched as a follow-up with a safe fallback (dedupe by event identity, or the SSE-consumer variant).
- **Evidence:**
  - `model` must be `Model.Ref` object; string form → HTTP 400; bogus model fails at execution not create — researcher live experiments → confirmed.
  - Seat resolves all built-in tools to `location.directory` and is agent-immovable; only `POST /move` retargets — live worktree session (`pwd`, relative write landed in worktree) + built-in tool inventory → confirmed.
  - Worktree sessions share the repo's projectID; `ctx.event.subscribe` is global and sees worktree + cross-project events; global SSE carries all projects — live experiment with real `git worktree add` → confirmed.
  - Per-scope setup re-instantiation duplicates naive subscriptions (N× logging observed) → confirmed; forces the singleton/SSE design.
  - `title` settable via rename; title/agent/model/directory/timestamps survive service restart and filter by `rp:` prefix — live experiment → confirmed.
  - `ctx.agent.list()` callable from a tool closure, returns global custom agents everywhere — live experiment → confirmed.
- **Correction (from Topic 4 findings):** opencode auto-generates the title from the conversation on the FIRST turn, overwriting a pre-set title; titles set after the first turn survive. The create→rename→prompt ordering therefore loses its title. Amended ledger design: (1) **live resolution** uses the plugin's module-singleton in-memory map `sessionID → {name, run, spawner}` written by `rp_spawn` (no race, authoritative within a daemon lifetime; `spawner` added per Review round 1, Issue 1); (2) **durable reconstruction** uses the `rp:<run>:<name>` title (keyed by the run-unique instance name — Review round 1, Issue 2), re-asserted by the singleton completion listener on the child's first `session.execution.succeeded`/`.failed` (auto-title fires only on turn 1, so the re-assert sticks), with the health monitor lazily re-asserting any mapped session whose title lacks the `rp:` prefix (self-heals a listener/auto-title race or a daemon restart before turn 1 completes); (3) alternative considered: RP-controlled custom session `id` (`^ses…`, verified accepted at create) — immutable and race-free but with unverified charset/length constraints for name encoding; not needed given (1)+(2), kept as fallback. The identifier the orchestrator holds remains the session ID; the map/title are lookup aids, and a session whose title was never asserted is only DB garbage, never a correctness issue (resume is git-based and re-spawns from committed state). The title deliberately omits the spawner: durable reconstruction serves the monitor and a resumed orchestrator (reqs 14, 16), and post-restart there is never a notification to route — the map's death with the daemon makes that explicit above.

### Topic 4: Messaging — directed messages by identifier, attribution, delivery observability

- **Spec link:** Requirement 12 (directed messages by identifier, orchestrator ↔ agent and agent ↔ agent, both directions); feeds 11 (completion notification delivery mode), 14 (message-delivery state observable; re-send).
- **Framing:** Cross-session injection is verified (`POST /prompt`, steer/queue). Open: the `rp_send` tool contract, which delivery mode serves directed messages vs completion notifications, how the receiver learns the sender (attribution derived from the caller's toolCtx sessionID + ledger, not trusted input), whether plugin tools are actually available inside spawned worktree-seated sessions, and what delivery failure looks like observably.
- **Options:**
  - *Delivery mode:* (1) `queue` for both directed messages and completion notifications (chosen); (2) `steer` (interrupt-flavored semantics per upstream docs); (3) default (steer) for notifications, queue for messages.
  - *Attribution:* (1) derived by the plugin from `toolCtx.sessionID` + ledger, stamped into the delivered text (chosen); (2) sender self-declares its name in the message; (3) no attribution (receiver infers from content).
  - *Addressing:* (1) by session ID, the identifier returned at spawn (chosen — parity with the Team spawning contract); (2) by logical name resolved via ledger.
- **Trade-offs:** `queue` is durably admitted (observable in `/pending` until promoted — never silently lost) and contracts to run strictly after the current step, so it cannot destructively interrupt a turn; `steer` carries interrupt semantics governed by an open upstream issue (#32157) and buys RP nothing it needs. Plugin-derived attribution cannot be spoofed by prompt content and costs nothing; self-declared names can lie or drift from the ledger. Session-ID addressing keeps the identifier-propagation step of the health contract visible (a re-spawned agent has a new ID that peers must be told), exactly as on Claude Code; name-addressing would hide it and silently re-bind.
- **Decision:** the plugin registers **`rp_send` `{to: <sessionID>, message}`**, available in every session (global plugin — verified callable by spawned worktree-seated agents). It: (1) resolves the sender from `toolCtx.sessionID` via the in-memory ledger (title as fallback) and prefixes the delivered text with `[from <name> (<sessionID>)]` — the sender's run-unique instance name; (2) delivers via `ctx.session.prompt({sessionID: to, text, delivery: "queue"})`, omitting `agents` and `resume`; (3) surfaces a synchronous failure (404 `SessionNotFoundError` for a dead/unknown target) back to the calling agent as the tool result. Completion notifications (Topic 3's listener) use the same queue-delivery injection path. The receiver sees a user-role message and replies with its own `rp_send` to the embedded sender ID — both directions, orchestrator ↔ agent and lead ↔ researcher, are the same primitive (req 12).
- **Rationale:** every element is verified on the target build: tool availability and calls from spawned seated sessions, unspoofable `toolCtx.sessionID`, queue's durable admission and non-destructive promotion, identical idle-session behavior, execution under the receiver's own agent+model, `agents` not switching the session's agent, and the three-stage failure chain (404 at send / lingering `/pending` entry / `execution.failed`+`session.error` events with sessionID). The failure chain maps one-to-one onto health-monitoring.md's message-failure signal: send-time 404 → dead target (re-spawn path), lingering pending → never delivered (re-send path), post-promotion failure → delivered-but-failed (re-send or model-swap + re-spawn path).
- **Evidence:**
  - Spawned worktree session's agent called the plugin tool — live → confirmed.
  - `toolCtx.sessionID`/`toolCtx.agent` identify the caller — live → confirmed.
  - Queue admitted+promoted without interrupting; idle behavior identical to steer; `agents` param does not switch the session agent; injected message is user-role and runs the receiver's persisted agent+model — live → confirmed.
  - Failure chain: 404 on deleted session (delete 204 → prompt 404); `/pending` shows admitted-unpromoted entries; `execution.failed` carries sessionID + structured error; `session.error` carries ProviderAuthError/APIError — live (Topic 1 for session.error union) → confirmed.

### Topic 5: Health-loop scheduler — start/list/cancel, idle-only firing, cross-session persistence

- **Spec link:** Requirement 13 (recurring loop: start with interval+prompt, list, cancel by identifier, fire only when the orchestrator is idle, persist across orchestrator sessions); feeds 14 (the monitor runs inside the loop's turns), 16 (leftover loop cancellable from a fresh session).
- **Framing:** opencode has no loop primitive; the plugin must supply one. Candidate shape: `rp_loop_start {interval, prompt, target?}` / `rp_loop_list` / `rp_loop_cancel {id}` tools; a module-singleton timer in the daemon; a durable loop registry file re-armed at plugin setup; at each tick, fire only if the target session is idle (skip the tick otherwise), injecting the prompt via queue delivery. Open: timer reliability in the daemon, the cheap per-tick idle signal, where the registry lives, and setup's lazy-init implication for re-arming after a service restart.
- **Options:**
  - *Scheduler seat:* (1) module-singleton `setInterval` inside the plugin, in the daemon (chosen); (2) a detached RP scheduler process; (3) OS-level cron. Options 2–3 re-introduce the process-babysitting and discovery/auth burden Topic 1 rejected, and OS cron cannot check opencode idle state cheaply or portably.
  - *Idle signal:* (1) `GET /api/session/active` per tick (chosen); (2) in-memory event pairing; (3) hybrid (seed from `/active`, maintain via events).
  - *Busy-tick policy:* (1) skip the tick entirely (chosen); (2) queue the prompt anyway; (3) delay-until-idle within the tick.
  - *Registry:* (1) `$XDG_DATA_HOME/radical-pipelines/loops.json` (fallback `~/.local/share/radical-pipelines/`), RP-owned (chosen); (2) inside opencode's data dir (their private store — rejected); (3) in-repo/worktree files (die with worktree teardown; pollute the repo — rejected).
- **Trade-offs:** `/active` is authoritative immediately after a restart with no warm-up and no event-delivery race, at the cost of one localhost call per tick (measured cheap); event pairing is free per tick but empty after restarts. Skipping a busy tick preserves the exact Claude Code `/loop` contract ("fires only when the agent is idle") with no queue buildup — queueing instead would fold the monitor prompt into the orchestrator's current turn (an overlap by another name), and delay-until-idle turns one tick into an unbounded wait.
- **Decision:** the plugin registers **`rp_loop_start` `{interval, prompt, target_session?}`** — `target_session` is optional and defaults to the calling session (`toolCtx.sessionID`), so the orchestrator needs no self-ID discovery (alignment recorded in Review round 1, Issue 2) — returning a loop id; plus **`rp_loop_list`** and **`rp_loop_cancel` `{id}`**. State: a durable registry at `$XDG_DATA_HOME/radical-pipelines/loops.json`; a module-singleton `setInterval` per loop, armed behind the module-level guard. Per tick: `GET /api/session/active`; if the target is running, skip the tick; otherwise inject the loop prompt via `ctx.session.prompt(..., delivery:"queue")`. `setup()` re-arms all registry entries (guarded), so after a service restart the first project-scoped touch — which a resuming orchestrator performs by opening a session in the run repo — re-arms leftovers without re-registration. `rp_loop_cancel` clears the timer and deletes the registry entry; `rp_loop_list` reads the registry (authoritative across sessions and restarts). Documented nuance: after a restart a leftover loop stays dormant until the repo's scope is next touched — acceptable because a dormant daemon runs nothing at all, and the resume flow's first action in the repo is that touch, followed by the skill-mandated leftover-cancel step.
- **Rationale:** the whole contract of req 13 was demonstrated live on the target build: drift-free in-daemon timers, exactly-one-execution-per-idle-tick, four consecutive busy-skips then one injection, restart-surviving registry, list+cancel from a fresh session, and client-less target sessions executing server-side. The chosen options are the ones the experiments showed to be authoritative (active-check) or contract-exact (skip policy); the registry path follows the platform's data-dir convention without touching opencode's private store.
- **Evidence:**
  - `setInterval` in the daemon fires with <2ms drift and injects successfully; module guard prevents duplicate timers — live → confirmed.
  - `/active` lists a mid-execution session and is correct immediately post-restart; busy ticks skipped (4×) then exactly one injection when idle; idle ticks → exactly one execution each, `/pending` empty — live → confirmed.
  - No plugin storage API exists (ctx surface enumerated); `$XDG_DATA_HOME/radical-pipelines/loops.json` writable via node fs — live → confirmed.
  - Lazy re-arm: global-scope API call does not trigger setup; project-scoped call does, re-arming from the registry — live → confirmed.
  - Leftover loop listed and cancelled from a fresh session; cancel stops ticks and cleans the registry; loop tools agent-callable — live → confirmed.
  - Client-less sessions execute injected prompts server-side — live → confirmed.

### Topic 6: Tool-mismatch guard

- **Spec link:** Requirement 10 (running RP under a tool that does not match `.rp.md`'s per-tool section must not proceed under the other tool's conventions; the owner is informed and offered setup for the active tool). Constraint: the generic skill stays tool-agnostic (req 8; repo rules).
- **Framing:** Today `load.md` checks required-convention presence only; with all conventions present, setup is skipped (`setup.md:222`) and an opencode orchestrator would follow "Spawn each agent as a Claude Code teammate" / `CronList` instructions. The gap becomes reachable exactly when a second tool exists. The guard must live in the generic run-time read path (`load.md` — the only file read at run time) and be worded tool-agnostically.
- **Options:**
  1. **Presence-is-per-tool rule (chosen):** `load.md` gains one rule — a convention under a per-tool section counts as present only when that section's tool matches the active tool (the same active-tool identification setup step 1 already uses). A mismatch thereby reduces to the existing missing-conventions flow — stop, explain, offer setup — with one added requirement: when conventions are unavailable because the per-tool section targets a different tool, say so explicitly.
  2. A separate explicit "Tool mismatch" step in `load.md` with its own stop-and-offer messaging.
  3. Guard in `setup.md` — unreachable: setup is skipped when required conventions are present, which is precisely the mismatch case.
  4. Detection logic in the per-tool convention files — architecturally wrong: those files are read only during setup; run time reads `.rp.md` only.
- **Trade-offs:** Option 1 adds a single definition and reuses the existing stop/inform/offer-setup flow — no new flow, no duplicated messaging, consistent with the repo's minimalism rules (a general rule stated once at the general level). Option 2 duplicates the missing-conventions behavior under a second name and adds a step to the read path for the same observable outcome. Options 3 and 4 fail structurally.
- **Decision:** Option 1. `.rp.md`'s per-tool section already names its tool in the heading (e.g. "## Claude Code conventions"); the loader treats per-tool conventions under a non-matching heading as not present for this run, and the explanation to the owner names the mismatch ("the committed per-tool section targets <tool>; running under <active tool> requires setup for it"). What setup then does with the existing file is setup's existing overwrite/merge behavior — coexistence stays out of scope (spec Out of Scope 5). The opencode convention file (Topic 8) defines its own canonical section heading, giving the guard its second matchable value.
- **Rationale:** the guard must fire at run time under either tool, so it can only live in `load.md`; folding it into the presence check yields the spec's exact observable outcome (does not proceed + informed + offered setup) through a flow that already exists, with the smallest possible change to the generic skill and zero tool-specific content. Options were checked against the actual read-path: `load.md` is read every run; the per-tool files are not.
- **Evidence:**
  - Presence-only check and setup-skip — `load.md` "Missing conventions" (presence only); `setup.md:222` (skip when complete) — file reads → confirmed (RP-side integration points, above).
  - Per-tool section carries the tool name — `.rp.md:75` "## Claude Code conventions"; README.md:118 (shared section + per-tool section for the active tool) → confirmed.
  - Run time reads only `.rp.md`; per-tool files read only at setup — `load.md` full read; `setup.md:15-24, 183-189` → confirmed.

### Topic 7: Liveness observability and recovery actions

- **Spec link:** Requirement 14 (per-agent recent-output/idle state, message-delivery state, auth/network error surfacing observable; status ping, restart, re-send, model-swap + re-spawn, identifier propagation all work); Acceptance criteria 10–13.
- **Framing:** Mostly assembly of verified primitives from Topics 1–5. Three recovery actions still lacked a live check — mid-life model switch (`POST /model`), a live ProviderAuthError chain, and interrupt-then-reuse — dispatched as tails and now verified (Topic 7 tail findings).
- **Decision — observables.** The monitor (the orchestrator session executing the loop prompt, per the unchanged health-monitoring.md template) reads:
  1. *Per-agent recent-output/idle state:* the ledger's sessions via `GET /api/session` (`time.updated` = last activity) + `GET /api/session/active` (running now or not) + worktree git state (last commits — tool-agnostic, unchanged).
  2. *Message-delivery state:* send-time HTTP 404 (dead target), lingering `GET /api/session/{id}/pending` entries (admitted but never promoted), `session.execution.failed` events (delivered but failed).
  3. *Auth errors:* structured error `type === "provider.auth"` on `session.execution.failed`/`session.step.failed`; its `message` carries the provider's HTTP body verbatim — quoted as-is in the escalation payload.
  4. *Network errors* *(re-scoped by Review round 1, Issue 4)*: the verified structured-error channel (`session.execution.failed` with non-auth types, e.g. the live-verified `provider.no-route`; plus `session.retry.scheduled`) covers **provider-call failures** — errors that terminate an execution. A **tool call** failing with a transient network error inside an agent's turn ordinarily returns an error result to the model and the turn continues; nothing verified shows it reaching `session.execution.failed`. Tool-call network failures are therefore observed the same way as on Claude Code: the agent's own report, worktree state, and messaging state — signals the monitor already reads each tick — with the stall signal as the backstop when a turn dies silently. Whether opencode additionally surfaces tool-call failures on any event channel is an open question (extended below); the recovery action (retry once, then wait an interval) is unaffected either way.
  5. *One-call summary:* the plugin's **`rp_status`** tool surfaces version + pin comparison, ledger entries (name, session ID, agent, model, directory, last activity, running?, pending count), and a bounded in-memory log of recent structured errors captured by the singleton listener. In-memory loss at daemon restart is acceptable: in-flight executions died with the process, staleness shows in `time.updated`, and resume re-spawns from committed state. The raw `opencode2 api` surface remains available for depth.
- **Decision — recovery actions** (mapping health-monitoring.md's 2-retry table):
  1. *No-output stall:* retry 1 — status ping via `rp_send` to the agent's session; retry 2 — restart: interrupt if `/active` shows it running (non-destructive, verified), then `rp_spawn` a fresh session (same agent, model, directory, catch-up prompt); the new session ID is sent via `rp_send` to the agents that message it (identifier propagation, health-monitoring.md:66).
  2. *Message failure:* retry 1 — re-send via `rp_send` (queue delivery is durably admitted); retry 2 — restart the target as above.
  3. *Login/API-key error:* retry 1 — same-session swap: `POST /model` with the authenticated provider-qualified Model.Ref (per the Agent models convention) + queue re-prompt; retry 2 — re-spawn on the new model via `rp_spawn`.
  4. *Network failure:* retry 1 — retry the failed call once; retry 2 — wait one interval and retry (orchestrator-level, tool-agnostic).
- **Rationale:** every observable and every action now traces to a live-verified primitive on the target build; the two-channel design (durable HTTP state for polling + event-fed in-memory log for recency) means no signal depends on the volatile SSE stream alone. The same-session model switch upgrades retry 1 of the auth path from "re-spawn" to the least-destructive verified action, preserving the agent's context; re-spawn remains retry 2 exactly as the contract orders.
- **Evidence:** switch/auth/interrupt — Topic 7 tail findings (live) → confirmed. 404 / pending / execution.failed chain — Topic 4 findings (live) → confirmed. `time.updated`, `/active`, ledger fields — Topics 3, 5 findings (live) → confirmed. Escalation-payload verbatim error — the `provider.auth` message contains the provider 401 body verbatim (live) → confirmed.

## Risks

<!-- Anything worth flagging to downstream phases, and accepted residuals with their justification. -->

- **Plugin API instability (beta).** The v2 plugin surface already broke once within the beta (legacy hooks factory silently stops loading — the probe simply never runs). Mitigated by the spec's pin-and-verify model (reqs 2–3): all versions pinned exactly, integration tests against the pin; re-pinning is explicitly follow-up work (spec Out of Scope 3).
- **`next`-tag version skew.** CLI and sdk/plugin packages advance independently under the same tag (`15757` vs `15718` observed same-day). The pin must name every package version individually, not one tag.
- **SSE volatility.** The event stream can overflow a slow consumer and loses events across disconnects (source-level finding). Any design leaning on events must pair them with a durable check (`/wait`, `session.get`, or the durable event log with `{aggregateID, seq}`).
- **Global agents-dir collisions.** Materialization writes 17 flat-named files (`spec-lead.md`, …) into `~/.config/opencode/agents/`, shared with the owner's own agents. Mitigation carried in the decision: the plugin overwrites only files it owns (tracked via a marker or manifest) and reports a collision instead of clobbering a pre-existing same-named agent.

## Review Adjudications

### Round 1 (design-doc-review-1-rejected.md, reviewed revision 15b4675)

All four issues adopted; no refutations, no residuals. No new research was needed — each fix re-arranges or scopes evidence already in the record.

- **Issue 1 (ledger cannot map child → spawner) — ADOPTED.** The ledger entry gains a `spawner` field: `rp_spawn` records the caller's `toolCtx.sessionID` (unspoofable, Topic 4) into `sessionID → {name, run, spawner}`; opencode has no session parenting, so the field exists only because rp_spawn records it.
