### Worktree-cwd mechanics on opencode (verified @ HEAD)

- The opencode instance's working directory is **fixed at process launch and immutable for the life of the instance/session.** Set via the TUI positional `opencode <path>` (handler does `process.chdir(next)`, then `directory: process.cwd()`) or the headless `opencode run --dir <path>`. No global `--cwd` flag; directory is per-command. Source: `packages/opencode/src/cli/cmd/tui.ts` (`resolveThreadDirectory` + `process.chdir`), `cli/cmd/run.ts` (`--dir` resolver), `cli/bootstrap.ts`, `project/instance-store.ts` (directory-keyed cache), `session/session.ts` `createNext` (`directory: input.directory` from `InstanceState.context`, not caller input).
- **No in-session re-root primitive** exists (no tool/command/SDK call re-points a running instance; TUI worker `reload()` does not chdir). Source: `cli/tui/worker.ts`, `project/instance-store.ts`.
- **No per-spawn `directory` override.** Ensemble `team_spawn` schema has no `directory`/`cwd` param; opencode public `session.create` `CreateInput` has no `directory` field (only `parentID?, title?, agent?, model?, metadata?, permission?, workspaceID?`). With `worktree:false`, ensemble passes neither `workspaceID` nor `directory`, so the child session inherits the instance directory. Source: ensemble `src/tools/team-spawn.ts` (schema; `useWorktree` gate ~L90; `session.create` ~L178-183), opencode `session/schema.ts`.
- opencode *can* run N directories per process, but only at the `opencode serve` + SDK-client layer via the `x-opencode-directory` header (`createOpencodeClient({ directory })`). Ensemble builds its client from the plugin-host transport bound to the lead's instance directory, so this is unreachable without forking ensemble — and ensemble explicitly *skips* recovery/dashboard for worktree (non-main) instances (`isWorktreeInstance` guards), so a split-directory design would degrade the always-on supervision Topic 3 depends on. Source: opencode `server/.../middleware/instance-context.ts`, `sdk/js/src/v2/client.ts`; ensemble `src/index.ts` (~L69-73, ~L78-112).

### Health-monitoring edit feasibility + auth recovery (verified @ HEAD)

- **All four "stay-unedited" monitor-lifecycle sentences read as no-ops on opencode** because each defers the mechanism to the Health monitoring convention rather than hard-coding launch/cancel as unconditional imperatives. Confirmed (researcher quotes, cross-checked by analyst's own grep): `autonomous-workflow.md:38` ("Start a recurring health monitor … per `health-monitoring.md`") + `:88` ("stop the health monitor (see `health-monitoring.md` for the cancellation command)"); `resume-pipeline.md:9` ("Cancel any health-monitor loop still registered … per the Health monitoring convention"); `review-pipeline.md:25` (delegates to resume) + `:54` ("If the project runs a health monitor … normal monitor lifecycle (cancel any leftover monitor, launch a fresh one) … an assisted review launches no monitor"); `load.md:21` table row ("How to launch and cancel the recurring run-health loop"). Req 18 holds.
- The current `health-monitoring.md` has launch/cancel-presupposing sections — `## When to launch` (5-min/10-min defaults, "the active tool's rules provide the exact slash command to start the loop"), `## Stopping the monitor` ("Use the tool's loop cancellation command") — plus tool-agnostic content sections (`## What to watch` 4 signals, `## Recovery` 2-retry table, `## Escalation payload`) and a `## Loop prompt template`. CC/Pi reference the template: `/loop 5m <prompt> where <prompt> is the template from reference/health-monitoring.md`.
- **Auth-model enumeration on opencode:** `opencode models [provider]` prints `providerID/modelID` per line over `provider.list()`, which is **auth/env-gated** — a provider appears only when its loader autoloads from credential/env presence (zero-model providers are dropped). So `opencode models` already lists exactly the usable/authenticated `provider/model` strings — the direct `pi --list-models` analog. `opencode auth list` (alias of `opencode providers list`) lists authenticated *providers* (credentials), not `provider/model` strings. Interactive login is `opencode auth login` / `opencode providers login` — the thing recovery must NOT run. Source: opencode `cli/cmd/models.ts`, `provider/provider.ts` (`list()` ~L1620, autoload gate ~L1526/182/187, zero-model delete ~L1603), `cli/cmd/providers.ts` (`aliases:["auth"]`, `ProvidersListCommand`, `ProvidersLoginCommand`). Caveat (honestly labeled): a listed credential can still be expired/revoked at call time — same caveat as `pi --list-models`; the 2-retry budget absorbs a stale pick.
- **Ensemble's auth escalation gives agent name + verbatim error + suggested step** (via `session.error` and fast-idle <15s detection, both messaging the lead) but **not** RP's "last-known progress" — the orchestrator must derive that from the artifact folder / last commit / last message when assembling the full escalation payload (Req 9). Re-confirmed from Q3 + Topic-1 reads of ensemble `src/index.ts`.

### Agent registration + conversion mechanics (verified @ HEAD)

- opencode resolves `team_spawn({agent})` by **pure name lookup** (`agents.get(input.agent)` → `agents[agent]`), with **no `mode` filtering** — a `subagent`, `primary`, or `all`-mode agent is equally spawnable; only `disable:true` removes an agent. `mode` only affects default-primary selection and `@`-autocomplete grouping. Source: opencode `session/prompt.ts` (~L445), `agent/agent.ts` (`get` ~L311, default `mode:"all"` ~L267-270, `disable` ~L265, `defaultInfo` excludes subagent/hidden ~L326-340).
- Frontmatter `name` is in `KNOWN_KEYS` but not in `AgentSchema`, so it's recognized-and-ignored on a file-loaded agent (identity = filename); `description` is valid; deprecated `tools` folds into `permission.edit`. Permission keys: `read,edit,glob,grep,list,bash,task,external_directory,todowrite,question,webfetch,websearch,lsp,doom_loop,skill`, each `ask|allow|deny`, bare string → `{"*":action}`. Source: opencode `packages/core/src/v1/config/agent.ts`, `permission.ts`, `packages/opencode/src/config/agent.ts`.
- **Model resolution chain:** ensemble `resolveModel` precedence = explicit `team_spawn` `model` arg > `config.modelsByAgent[agentType]` > rotate/random pool > `config.defaultModel` > undefined; if ensemble passes nothing, opencode falls back `input.model ?? agent.model ?? currentModel`. So an agent-file `model:` is the last-resort default beneath everything. Source: ensemble `src/tools/team-spawn.ts` (`resolveModel` ~L21-37, ~L219), opencode `session/prompt.ts` (~L453).
- **Worktree-default surprise:** ensemble's read-only auto-detection is a literal `agent === "plan" || "explore"` string match (`team-spawn.ts:89`); none of RP's 17 agent names match, so `isReadOnly=false` for all of them and `useWorktree` is true **unless `worktree:false` is passed** (`team-spawn.ts:90`). `mode`/`permission` in the agent file do not influence this — `isReadOnly` is computed from the agent string before the frontmatter is even loaded. So every RP agent (reviewers/researchers included) would otherwise get its own worktree + later merge.
- **Agent bodies are reusable verbatim** — confirmed by grep across all 17 agent files: zero hard-coded CC tool names (`SendMessage`, `EnterWorktree`, `TeamCreate`, `TaskCreate/Update`, `/loop`, `WebFetch/WebSearch`) and zero tool/provider names. Inter-agent and orchestrator interactions are tool-agnostic prose ("send a message to the orchestrator", "the orchestrator relaunches X"); the artifact "task list" is the plan file, not a tool/board. Tool-specifics live in `.rp.md`/conventions. Source: independent grep of `agents/*.md` + researcher's full read of `code-reviewer.md`.

### Packaging + ensemble config mechanics (verified @ HEAD / @ 0.15.1)

- **This repo is already a multi-tool shared-source package.** It carries two packaging artifacts over the same `skills/` + `agents/` source: the Pi `"pi"` block in the root `package.json` (`private:true`, deps `pi-teams`/`@zenobius/pi-worktrees`/`@pi-agents/loop` + Pi peer-deps), and the Claude Code `.claude-plugin/{plugin,marketplace}.json` (manifest-only, no npm deps, source `"./"`). opencode is the third consumer of that shared source. The opencode plugin's deps (`@hueyexe/opencode-ensemble`, `@opencode-ai/plugin`, `@opencode-ai/sdk`, `engines: node>=24`) are disjoint from the Pi dep set, and a plugin must be publishable whereas the root is `private:true` — so it cannot be a root-package key like the Pi block. Source: this repo's `package.json`, `.claude-plugin/*`, `scripts/sync-version.mjs` (root version → `TARGET_MANIFESTS`), `.changeset/config.json` (`changedFilePatterns` already track `skills/**`,`agents/**`,`.claude-plugin/**`).
- **ensemble re-export shape:** ensemble's default export is `const plugin: Plugin = async (input) => {…return {event,tool,config,…}}` / `export default plugin`; `Plugin` is `(input, options?) => Promise<Hooks>`. A meta-plugin does `const ensembleHooks = await ensemble(input); return {...ensembleHooks, …RP additions}`. ensemble's deps are exactly `@opencode-ai/plugin`+`@opencode-ai/sdk`. **Double-init hazard:** `plugin(input)` has real side-effects — `mkdirSync`+`createDb`+`loadConfig`, watchdog `setInterval`, and (main instance only) dashboard server on port 4747. Listing ensemble in `plugin:[]` *alongside* the re-exporting meta-plugin → two watchdogs + dashboard EADDRINUSE on 4747. So the install rule is **list ONLY the meta-plugin, never ensemble alongside it**; the smoke test is one watchdog + one dashboard with no port error. Source: ensemble `src/index.ts` (`:47`, `:600`, init `:48-54`, watchdog/dashboard `:105-131`).
- **ensemble config = a dedicated `.opencode/ensemble.json` file, NOT opencode's plugin config object.** `loadConfig(projectDir)` reads (later wins): global `~/.config/opencode/ensemble.json` → project `<projectDir>/.opencode/ensemble.json` (where `projectDir = input.directory` = the worktree, Topic 1) → env overrides (`OPENCODE_ENSEMBLE_TIMEOUT`, `OPENCODE_ENSEMBLE_RATE_LIMIT`, `STALL_THRESHOLD_MS`). Keys/types/defaults: `mergeOnCleanup` bool (default **true**), `stallThresholdMs` num (default `300000` — note stale JSDoc says 3min, real `DEFAULT_CONFIG`=5min), `timeoutMs` num (default `1800000`), `dashboardPort` num (default `4747`, `0` disables), plus `stallMinSteps`/`stallTokenThreshold`/`rateLimitCapacity`/`peerMessageLimit`/`peerMessageWindowMs` and the model keys `defaultModel`/`modelPool`/`modelsByAgent`/`modelAssignment`/`promptForModels`. Source: ensemble `src/config.ts` (`EnsembleConfig`, `DEFAULT_CONFIG`, `loadConfig`).
- **Runtime prerequisite:** ensemble `package.json` declares `engines: {node:">=24", bun:">=1.0"}`; it fails at runtime without `node:sqlite` (Node ≥24) or Bun. Source: ensemble `package.json`.
- **Verified-vs-spike (Q5) confirmed:** file-based agent install (`.opencode/agent/`) and file-based skill install (opencode discovers `.opencode/skill(s)/**/SKILL.md`, `.claude/skills/**/SKILL.md`, globals, `config.skills.paths`) are VERIFIED; config-hook agent/skill injection remains a notification whose result is ignored (NEEDS-SPIKE). The feature is fully deliverable via the file-based paths.

### Topic: Overall approach — the implementer's mental model

- **Spec link:** Requirements 1–4, 11, 12, 17–19 (the whole feature shape).
- **Decision:** Add opencode as a third supported tool by following RP's existing per-tool pattern exactly: (a) one new conditionally-loaded convention file `reference/conventions/opencode.md`, (b) a packaging artifact analogous to Pi's, and (c) the two minimal generic edits the spec authorizes (the `setup.md` supported-tools row and the `health-monitoring.md` lifecycle/context-window rewording). The generic skill stays tool-agnostic; every other generic file is left literally true on opencode unedited. The team layer is the third-party `@hueyexe/opencode-ensemble` plugin, used as a coordination layer only (spawn-by-name, peer-to-peer messaging, shared task board, per-agent model selection, always-on supervision); its native per-teammate-worktree + squash-merge behavior is structurally neutralized so RP's one-worktree/one-branch model is preserved. RP's named agents are registered with opencode by converting their frontmatter to opencode's format (body reused verbatim) and installing the converted files where opencode discovers agents. The orchestrator launches by plain skill invocation, exactly as on Claude Code and Pi.
- **Rationale:** This is the smallest design that reaches parity while honoring the spec's hard scope boundary (Req 17–19) and the project's anti-tool-coupling rule for the generic skill. Each piece is a direct analog of an existing, working Claude Code / Pi mechanism, so the implementer reasons by precedent. Spec-research Q1–Q6 verified every load-bearing mechanism against live source; the remaining decisions are HOW to assemble them, recorded as the topics below.

### Topic: One-worktree/one-branch cwd ergonomics

- **Spec link:** Requirements 5 & 6; acceptance criteria "One worktree, one branch."
- **Frame:** Every ensemble teammate is spawned `worktree: false`, which inherits the opencode instance's directory as cwd. So the model hinges on the instance (orchestrator/lead session) running inside the pipeline worktree. Spec-research Q4 flagged the exact mechanics of establishing that as an unresolved spike.
- **Options:**
  1. **Launch a fresh opencode instance rooted in the worktree** — `git worktree add -b worktree-<slug> <path>` (plain git, orchestrator shell), then run the orchestrator from a new instance started inside the worktree (`opencode <path>` for the TUI, or `opencode run --dir <path> …` headless). Single instance; every `worktree:false` teammate inherits the worktree cwd.
  2. **Re-root the current instance mid-session** — unsupported by source; no chdir/re-root primitive exists.
  3. **Per-spawn directory override** — unsupported through ensemble or public `session.create`; the only per-directory mechanism (`x-opencode-directory` header) is unreachable without forking ensemble and would split state across two instances, degrading ensemble's always-on supervision (which skips non-main/worktree instances).
- **Trade-offs:** Option 1 is the only source-supported path. Its one cost: the session that *creates* the worktree (rooted at the main checkout) cannot itself become the worktree-rooted orchestrator — a new instance must be the lead that spawns the team. This is one extra launch step, idiomatic with CC's `EnterWorktree` and Pi's `@zenobius/pi-worktrees` "enter, then work happens here" shape. Single-instance keeps ensemble's supervision, recovery, and dashboard intact. Options 2 and 3 are rejected as unsupported / supervision-degrading.
- **Decision:** Option 1. opencode.md's Worktrees convention specifies: create + enter = `git worktree add -b worktree-<slug> <path> <base>` then launch the opencode instance rooted in the worktree (TUI positional `opencode <path>`, or `opencode run --dir <path>` for automation); the orchestrator runs from that worktree-rooted instance and spawns every teammate `worktree:false` so they share the worktree cwd; remove = `git worktree remove <path>` at close-out. This is the opencode analog of CC's `EnterWorktree` / Pi's `/worktree create`, expressed with plain `git worktree` (the generic `setup.md` default) plus the explicit launch-rooted-in-the-worktree step.
- **Rationale:** Directly realizes Req 5 (single shared worktree + branch; `worktree:false` structurally neutralizes ensemble's per-teammate worktree and squash-merge) and Req 6 (`worktree-<pipeline-slug>` branch name is fully RP's choice under plain `git worktree`). It is the only mechanism the source supports, and it preserves the always-on supervision Topic 3 relies on.

### Topic: Agent-frontmatter conversion and registration

- **Spec link:** Requirements 3 (full-fidelity named agents), 10 (per-agent model), 15 & 16 (Setup actions: discover/install/verify agents); acceptance criteria "Named agents and collaboration", "Per-agent model selection", "Setup actions".
- **Frame:** opencode resolves `team_spawn({agent})` against its on-disk agent registry (`{agent,agents}/**/*.md`, filename→name, frontmatter→config, body→system prompt). It does NOT scan `.claude/agents/` (only `.claude` skills get a free ride), so RP's agents must be installed where opencode discovers them, with frontmatter in opencode's format. The decision is the exact conversion recipe + where the per-agent model lives.
- **Options (model source of truth):**
  1. **Pass `model` per `team_spawn` from the `.rp.md` Agent-models table** — orchestrator reads the table and passes `team_spawn({ agent, model: "<provider/model>" })`. Single source of truth; exact CC/Pi analog.
  2. **Bake `model:` into each converted agent file** — splits the source of truth, forces tool-specific file variants (CC uses bare aliases, opencode needs `provider/model`), diverges from CC/Pi.
  3. **`config.modelsByAgent` in `.opencode/ensemble.json`** — a second competing config surface; works but not needed for parity.
- **Trade-offs:** Option 1 keeps the orchestrator the single reader of `.rp.md`, keeps the agent files model-free (so they stay shared source with CC), and is the highest-precedence path in ensemble's `resolveModel` (explicit arg wins). Options 2/3 fragment the source of truth.
- **Decision:**
  - **Conversion recipe (per agent file):** install to opencode's agent dir as `<name>.md` with frontmatter = `description` (verbatim) + optionally `mode: subagent` (accurate self-description; not required — name lookup ignores `mode`); **drop `name`** (filename is identity); **no `model:`**; **no `permission:`**. **Body byte-identical.**
  - **Per-agent model (Req 10):** Option 1 — orchestrator passes the provider-qualified `provider/model` from `.rp.md`'s Agent-models table as the `team_spawn` `model` arg. `.rp.md` is the single source of truth, exactly as on CC/Pi (the value format is the tool-native string `setup.md` already provides for).
  - **Spawn rule (opencode.md Team spawning):** every agent is spawned `worktree: false`, for every agent type — mandatory both for the one-worktree model (Topic 1) and because ensemble's read-only auto-detection is a literal `plan`/`explore` name match that none of RP's agents satisfy (so without `worktree:false` even reviewers/researchers would get a per-agent worktree).
- **Rationale:** Full fidelity (Req 3) is achieved with zero body changes because opencode loads the Markdown body as the agent's system prompt and resolves the name without mode filtering; the bodies are already tool-agnostic prose. Per-agent model (Req 10) mirrors CC/Pi via the `team_spawn` arg. `permission` hardening is deliberately omitted: RP's reviewers/researchers/analysts all commit their own artifacts (need `bash` for `git commit`), the one-worktree + prose-role model is the existing safety boundary on every tool, and a blanket lock risks blocking commits — no other tool imposes per-agent permission locks, so adding one would be new behavior outside the spec's scope.

### Topic: Health monitoring — always-on supervision, the two authorized edits, and auth recovery

- **Spec link:** Requirements 7, 8, 9 (health monitoring + auth recovery + escalation budget), 17 & 18 (the health-monitoring.md rewording is one of the two authorized generic edits; the other generic monitor-lifecycle files stay unedited); acceptance criteria "Health monitoring", "Scope boundary".
- **Frame:** ensemble's always-on supervision replaces the launched `/loop`; the orchestrator reacts to escalations it surfaces (no recurring orchestrator action, nothing to launch/list/cancel). The design must (a) shape the health-monitoring.md rework so it stays tool-agnostic AND keeps the four other generic monitor-lifecycle files literally true as no-ops, and (b) define opencode.md's auth-recovery rule (the `pi --list-models` analog).
- **Independent scope-boundary check (analyst, against current source):** The four "stays-unedited" monitor-lifecycle sentences and their no-op reading on opencode:
  - `autonomous-workflow.md:38` "Start a recurring health monitor for the run per `health-monitoring.md`." → "start" is a no-op (supervision already on). True unedited.
  - `autonomous-workflow.md:88` "stop the health monitor (see `health-monitoring.md` for the cancellation command)." → "stop" is a no-op; the parenthetical depends on the reworked health-monitoring.md no longer *asserting* a cancellation command always exists. **Constraint on the edit.**
  - `resume-pipeline.md:9` "Cancel any health-monitor loop still registered… must be cancelled before the workflow launches a new one." → on opencode nothing is ever registered; vacuously a no-op. True unedited.
  - `review-pipeline.md:54` "If the project runs a health monitor, an autonomous review follows the normal monitor lifecycle (cancel any leftover monitor, launch a fresh one)." → guarded clause + no-op cancel/launch. True unedited.
  - `load.md:21` table row "How to launch and cancel the recurring run-health loop." → the *question* still resolves on opencode ("always-on; nothing to launch or cancel"). True unedited (most strained, but the spec lists it as unedited).
- **Decision — the health-monitoring.md rework (Req 17a/b), scope-minimal:**
  1. **Lifecycle-as-outcome (17a):** replace the launch/cancel-presupposing prose (`## When to launch`'s "the active tool's rules provide the exact slash command to start the loop"; `## Stopping the monitor`'s "Use the tool's loop cancellation command") with a tool-agnostic outcome: a recurring health monitor watches the autonomous run for its full duration; the active tool's convention describes how the monitor is provided and, **if applicable**, started and stopped — so a tool whose supervision is always-on satisfies start/cancel as no-ops. The CC/Pi-specific interval/threshold defaults (5-min/10-min) are loop-tuning and move down to the CC/Pi conventions; opencode's thresholds are ensemble config (Topic 4).
  2. **Context-window note (17b):** reword "Both Claude Code and Pi auto-compact agent context near the limit" → "each tool handles context-window limits by its own mechanism," naming no fixed pair and asserting nothing about opencode's behavior.
  3. **Keep generic, unmoved:** the 4 signals, the 2-retry recovery table, the escalation payload, "assisted runs use no monitor," AND the Loop prompt template stay in `health-monitoring.md`. The template is the monitor's *content* (the signals/recovery it restates), already generic; CC/Pi keep referencing it from their `/loop` command; on opencode the orchestrator simply never launches a loop, so the template is unused — the no-op the spec relies on. The lifecycle rewording need only stop *presupposing* a launched loop in the lifecycle prose; the template section itself needs at most a framing touch so it reads as "what the monitor checks" rather than "the loop's prompt."
- **Decision — auth-error recovery rule for opencode.md (Req 8):** on the lead receiving an auth/login or fast-idle escalation for a spawned agent, the orchestrator runs **`opencode models`** to enumerate authenticated `provider/model` strings, picks one **other than the failed model**, and **re-spawns via `team_spawn({ agent, model: "<new provider/model>", worktree: false })`** — never interactive login (`opencode auth login`), and distinct from the per-agent Agent-models config. The 2-retry budget is the orchestrator's (Req 9), applied reactively to ensemble's always-on escalations; if `opencode models` yields no authenticated alternative, escalate to the owner. The orchestrator assembles the full escalation payload — agent name + verbatim error (from ensemble) + last-known progress (derived from the artifact folder / last commit / last message) + suggested next step.
- **Decision — setup.md edit (the second authorized generic edit, Req 17):** add one row to the Step-1 supported-tools table — `| opencode | opencode.md |`. Trivial; Step 3 ("consult the active tool's rules for a Setup actions section") is already generic and auto-picks up opencode.md's Setup actions, so no other setup.md edit.
- **Rationale:** Realizes Req 7 (always-on supervision, nothing to launch/cancel), Req 8 (model-swap-not-login recovery via `opencode models`), Req 9 (orchestrator-owned 2-retry budget + full escalation payload), and Req 17/18 (exactly two generic edits; the other four monitor-lifecycle files stay literally true as no-ops; CC/Pi behavior unchanged). The scope-minimal template choice (keep it in health-monitoring.md rather than relocating it into the CC/Pi conventions) is the most faithful reading of "exactly two existing generic files" and avoids any edit to cc.md/pi.md, reinforcing "Claude Code and Pi behavior unchanged"; the relocation option is recorded under Open Questions as a possible refinement for the writer if it judges the template genuinely CC/Pi-specific.

### Topic: Packaging artifact + ensemble config tuning

- **Spec link:** Requirements 11 (install obtains agents + skill + team layer; skill obtainable even if repo lacks it), 12 (packaging artifact analogous to Pi's; generic skill stays tool-agnostic), 13 (Node≥24/Bun prerequisite surfaced; setup not "ready" if unmet), 14 (ensemble tuned via opencode-side config); acceptance criteria "Installation and packaging".
- **Frame + analyst's independent repo-tooling finding:** Pi's packaging artifact is the `pi` block in this repo's root `package.json`; Claude Code's is `.claude-plugin/{plugin,marketplace}.json`. Both reference the SHARED `skills/` + `agents/` source — they don't fork it. The repo is a flat single-package layout (no npm/pnpm workspaces), versioned by changesets from the root `package.json` (the single source of truth), synced outward to secondary manifests via `scripts/sync-version.mjs` (`TARGET_MANIFESTS = [".claude-plugin/plugin.json"]`). The conflict to resolve: the root `package.json` carries Pi peer-deps (`@mariozechner/pi-*`), and an opencode runtime plugin needs its own deps (`@opencode-ai/plugin`, `@opencode-ai/sdk`, `@hueyexe/opencode-ensemble`) + `engines: node>=24` — so the opencode plugin cannot simply be another root-package key like the `pi` block.
- **Options (artifact shape):**
  1. **Non-private workspace sub-package in this repo** (e.g. `packages/opencode/`, `@automattic/radical-pipelines-opencode`, publishable, own deps + `engines`), with `agents/` + `skill` staying at repo root as shared source the sub-package bundles via `files:[]` + a build copy step. Root becomes a workspace root; root stays `private:true`, only the sub-package publishes.
  2. **Fully separate sibling repo** depending on this repo's agents/skill as a git/npm dep or vendoring them.
- **Trade-offs:** Option 1's dep sets are isolated by separate manifests (the Pi/opencode collision is resolved structurally), it's publishable, and it preserves single-edit-point shared source — exactly how the Pi block + CC manifest already share `skills/`+`agents/`. Cost: introduces a workspace where the repo is currently flat. Option 2 breaks shared source (agent/skill edits wouldn't flow without a sync step) and diverges from the in-repo multi-artifact pattern. Reject option 2.
- **Decision:**
  - **Artifact shape:** Option 1 — a non-private workspace sub-package in this repo (publishable, `engines: {node:">=24", bun:">=1.0"}`, deps = ensemble + `@opencode-ai/plugin` + `@opencode-ai/sdk`), with `agents/`+`skill` referenced as shared root source. This is the opencode analog of the Pi block, mirroring the established multi-tool shared-source relationship.
  - **Meta-plugin + delivery:** the package's plugin entry imports ensemble and merges its hooks (`const h = await ensemble(input); return {...h, …RP}`) — ONE `plugin:[]` entry delivers the team layer (re-export is the verified path; config-hook can't add to `plugin:[]`). The install rule is **list only the meta-plugin, never ensemble alongside** (avoids the double-init / dashboard-port collision). Agents and skill are delivered **file-based via a Setup action** (drop the config-hook injection from the design — file-based is verified, mirrors Pi, and Req 15/16 need the Setup flow anyway): install the 17 converted agent `.md` into `.opencode/agent/` (committed) or `~/.config/opencode/agent/` (per-user), and the bundled skill tree into `.opencode/skill/radical-pipelines/` (committed) or `~/.config/opencode/skill/radical-pipelines/` (per-user) — locations chosen by the artifact-storage mode, exactly as Pi chooses `.pi/agents/` vs `~/.pi/agent/agents/`. The bundled-skill copy is what satisfies Req 11 for an owner whose repo lacks RP's skill tree.
  - **ensemble config (Req 14):** RP writes a dedicated project-level `.opencode/ensemble.json` during setup with at minimum `mergeOnCleanup: false` (no-merge-on-cleanup, defensive atop `worktree:false`), and recommended explicit `stallThresholdMs: 300000` + `timeoutMs: 1800000` to pin RP's supervision thresholds. Model keys are left empty (RP passes model per `team_spawn`, Topic 2 — no second source of truth); dashboard stays on 4747 unless it conflicts.
  - **Runtime prerequisite (Req 13):** two layers — the package's `engines: {node:">=24", bun:">=1.0"}` (hard gate), plus a setup-time Node/Bun version check in opencode.md's Setup actions that blocks declaring opencode "ready" if unmet and surfaces the prerequisite to the owner.
- **Rationale:** Realizes Req 11 (one meta-plugin entry + Setup action delivers team layer + agents + skill, including for a repo that lacks the skill), Req 12 (artifact analogous to the Pi block; generic skill untouched), Req 13 (engines gate + setup check), Req 14 (`.opencode/ensemble.json` neutralizes the merge default and pins thresholds). Every load-bearing path is the VERIFIED one; no spike is required for the feature to ship. The double-init hazard and the workspace-tooling choice are flagged downstream (Risks / Open Questions) rather than left implicit.

### Topic: Interfaces, data flow, and the collaboration model

- **Spec link:** Requirements 3, 4, 10 (named agents, peer-to-peer + task board, per-agent model); acceptance criteria "Named agents and collaboration".
- **Decision (the interfaces the design depends on):**
  - **Spawn:** `team_spawn({ name, agent, prompt, model: "<provider/model>", worktree: false })` — `agent` = the RP agent filename (resolves to the registered `.opencode/agent/<name>.md` persona); `model` from `.rp.md`'s Agent-models table; `worktree:false` always. This is the orchestrator → teammate interface.
  - **Peer-to-peer messaging (Req 4):** spawned agents address each other directly via ensemble `team_message` (direct) / `team_broadcast` (all). The agent bodies' tool-agnostic "send a message to the orchestrator" maps to a `team_message` to the lead. The orchestrator only spawns, monitors, and waits; it intervenes only to repair a failed exchange, then agents resume direct messaging.
  - **Shared task board:** ensemble `team_tasks_add`/`team_tasks_list`/`team_tasks_complete`/`team_claim` (with `depends_on` for dependencies). RP tracks phase progress in the per-phase artifact subfolders, NOT on the task board (the board exists and idle teammates are nudged to claim from it — the same caution cc.md carries).
  - **Supervision → orchestrator:** ensemble surfaces stalls / message failures / auth (session.error + fast-idle) / network conditions to the lead session as persisted system `team_message`s; the orchestrator reacts (2-retry budget, model-swap recovery, escalation payload). No recurring orchestrator action.
  - **Artifact data flow (Req 1):** unchanged from CC/Pi — each phase agent reads/writes the same per-phase artifact files in the same subfolder structure (`0-intent/intent.md`, `1-spec/spec.md`, `2-design-doc/design-doc.md`, `3-plan/code-plan.md`, `5-docs/doc-plan.md`, …) in the single shared worktree; only tool-native value formats inside artifacts differ (provider-qualified models, opencode install destinations).
- **Rationale:** These are the public interfaces realizing Req 3 (full-fidelity named agents via name resolution), Req 4 (direct messaging + task board, orchestrator repair-only), and Req 10 (per-agent model via the `model` arg). The artifact data flow is deliberately identical to the other tools so the same set of inspectable artifacts is produced (Req 1, the central acceptance oracle).

### Topic: Dependencies, failure modes, and observability

- **Spec link:** Requirements 11, 13, 14 (dependencies); 7, 8, 9 (failure modes + observability).
- **Decision — new external dependencies:** `@hueyexe/opencode-ensemble` (pinned version — see Risks), `@opencode-ai/plugin`, `@opencode-ai/sdk` (ensemble's transitive deps, shared), and the Node≥24/Bun runtime (`node:sqlite`). These live entirely in the new opencode sub-package; the generic skill and the CC/Pi artifacts gain no new dependency. opencode itself (the host tool) and its `git worktree`, `opencode models`, `opencode <path>` / `opencode run --dir` CLI surface are runtime dependencies of the convention, not npm deps.
- **Decision — failure modes + how they surface (observability):**
  - **Spawned-agent stall / message failure / auth / network** → ensemble's always-on supervision detects and surfaces to the lead session as a persisted system `team_message` (+ TUI toast + dashboard at :4747); the orchestrator reacts within the 2-retry budget and escalates with the full payload (Req 7–9).
  - **Auth/login failure** specifically → re-spawn on a different authenticated `provider/model` via `opencode models`, never interactive login; escalate if no alternative (Req 8).
  - **Hard timeout (`timeoutMs`)** → ensemble aborts the session and toasts but does NOT message the lead (a known gap); visible via member status / dashboard. The orchestrator's monitoring of completion signals and last-known progress covers detection. Flagged so the implementer doesn't assume a lead message for the timeout path.
  - **Orchestrator (lead) auth/network failure** → NOT auto-supervised; surfaces in the owner's own session (spec acceptance note, see Risks).
  - **ensemble double-init** → watchdog duplication + dashboard EADDRINUSE; prevented by the "list only the meta-plugin" install rule + smoke test (see Risks).
- **Rationale:** Confirms the design has a detection + surfacing + recovery story for each of the four monitored signals (Req 7), the auth-recovery contract (Req 8), and the escalation contract (Req 9), and is explicit about the two observability gaps (timeout-path no-lead-message; lead-session not supervised) so they are handled by design intent rather than discovered late.

## Open Questions

<!-- Unresolved sub-questions deferred to the implementation phases. -->

- **Loop prompt template placement (Topic: health monitoring).** This design keeps the Loop prompt template in `health-monitoring.md` (scope-minimal: honors "exactly two generic edits" and touches no CC/Pi file). The researcher's alternative — relocate the template (and interval/threshold defaults) into a shared file referenced by cc.md+pi.md so the generic file is content-only — is structurally cleaner against the repo's anti-duplication rule but edits the tool conventions. The writer may adopt the relocation only if it judges the template genuinely CC/Pi-launch-specific AND confirms it stays within the spec's scope boundary (moving content into convention files, not adding opencode-awareness to generic files). Default: keep in place.
- **opencode interval/threshold default values (Topic: health monitoring → ensemble config).** The CC/Pi 5-min interval / 10-min no-output threshold are loop-tuning. opencode's equivalents are ensemble's `stallThresholdMs` / `timeoutMs` in `.opencode/ensemble.json` (settled in Topic 4). The plan must ensure the values RP writes there reflect RP's intended thresholds, not ensemble's stock defaults.
- **Workspace tooling choice (Topic: packaging).** The opencode sub-package needs the repo to become a workspace root. npm workspaces vs pnpm, the exact sub-package path (`packages/opencode/`), and the build step that copies the shared `agents/`+`skill` into the published tarball (`files:[]`) are implementation details for the code phase — the dep-isolation property holds under either tool. The plan should also extend `scripts/sync-version.mjs` `TARGET_MANIFESTS` and the changeset `changedFilePatterns` to cover the new sub-package manifest so its version stays in lockstep.
- **opencode `models`/`auth` command surface stability (Topic: health monitoring → auth recovery).** The recovery rule names `opencode models` to enumerate authenticated `provider/model`. The exact output format and command name are verified @ HEAD but are a CLI surface that could shift across opencode releases; the plan/docs should treat the command as the documented mechanism while keeping the rule's *intent* (enumerate authenticated models, pick a different one) primary.

<!-- Anything worth flagging to the design-doc-writer and downstream phases. -->

- **Worktree re-launch handoff (Topic: cwd ergonomics).** Because the instance directory is immutable, the orchestrator session that creates the worktree (rooted at the main checkout) cannot itself spawn the worktree-rooted team — a new opencode instance must be launched inside the worktree to act as the lead. opencode.md must make this hand-off explicit so the implementer/owner does not assume the original session continues as orchestrator. Mitigation: state the launch-rooted-in-worktree step plainly in the Worktrees convention (TUI: `opencode <path>`; automation: `opencode run --dir <path>`), as CC/Pi already imply with their enter-the-worktree step.
- **`worktree:false` is load-bearing on every spawn (Topic: agent conversion + Team spawning).** Ensemble only auto-applies `worktree:false`/read-only treatment when the agent string is literally `plan` or `explore`; RP's agent names never match, so omitting `worktree:false` on any single spawn silently gives that agent its own git worktree and re-arms ensemble's squash-merge for it — violating the one-worktree/one-branch model (Req 5). Mitigation: opencode.md's Team spawning convention must state `worktree:false` as an unconditional rule for *all* RP agents, not rely on ensemble's auto-detection.
- **ensemble double-initialization (Topic: packaging).** The meta-plugin re-exports ensemble by importing and calling it; if the owner ALSO lists `@hueyexe/opencode-ensemble` in `plugin:[]` alongside the meta-plugin, ensemble inits twice — two watchdog intervals and a dashboard port collision (EADDRINUSE on 4747). Mitigation: the install instruction and opencode.md must state to list ONLY the RP meta-plugin, never ensemble alongside it; the implementer should smoke-test that a single meta-plugin entry yields one watchdog + one dashboard with no port error.
- **Pinned ensemble version (Topic: packaging).** ensemble's README recommends pinning the plugin version (opencode has a known bug caching unpinned plugins). The meta-plugin should depend on a pinned ensemble version, and the install guidance should reflect that. Flagged from spec-research Q1.
- **Lead-session (orchestrator) auth/network failures are not auto-supervised (spec Out-of-Scope + acceptance note).** Ensemble supervises spawned teammates, not the lead; an orchestrator-level auth/network failure surfaces in the owner's own session (which the owner is watching), not via the team layer. This is the spec's explicit acceptance note, not a guarantee — the design honors it by not attempting to supervise the lead. opencode.md/docs should state it so it isn't mistaken for a gap.
