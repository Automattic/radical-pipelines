## Summary

The design is strong: every load-bearing empirical claim I probed is corroborated by retained evidence or re-execution, the RP-side integration claims all re-verify against the codebase, coverage of the 16 requirements is complete, traceability is explicit, scope is clean, and the open questions are properly deferred with named verifiers. The rejection is narrow: the ledger/notification contract at the center of requirement 11 is internally inconsistent — the declared ledger shape cannot deliver the declared completion notification, the spawn contract and ledger title key drift between sections in a way that would make two implementers key the durable ledger differently, the completion-notification policy rests on an unstated premise (notify on every terminal event) with unweighed cost consequences, and one observability claim overstates its verified scope. All four are fixable in the record and the doc without new research.

## Issues

### Issue 1: The declared ledger map cannot map a child to its spawner

**What's wrong:** The completion listener is specified to "map the child to its spawner via the ledger, and inject a notification message into the spawner's session" (Topic 3 decision; design-doc.md "Completion notifications"). But the declared ledger has no spawner in it: the in-memory map is `sessionID → {name, run}` (Topic 3 correction; design-doc.md `rp_spawn` bullet) and the durable title is `rp:<run>:<name>` — neither records who spawned the session, and opencode has no native session parenting (`session.create` has no `parentID`, per the record's own evidence). The declared interface cannot deliver the declared behavior.
**Where:** `design-doc-research.md` Topic 3 (decision and the amended-ledger correction); `design-doc.md` "Interfaces and Data Flow" (`rp_spawn` bullet and the "Completion notifications" paragraph).
**Suggestion:** Record the spawner in the ledger entry — `rp_spawn` captures the caller's `toolCtx.sessionID` (already verified unspoofable in Topic 4) and stores `sessionID → {name, run, spawner}`. State the restart behavior explicitly: the map dies with the daemon, in-flight executions die with it too, so a post-restart terminal event on a pre-restart child has no resolvable spawner and produces no notification — consistent with the git-based resume model, but it should be said, not inferred.
**Why it matters:** Requirement 11's completion notification is a required observable and feeds requirement 14's recovery flow. As declared, an implementer must invent the missing field; the design's own fidelity standard (two implementers build the same thing) fails at the exact point the spawning contract depends on.

### Issue 2: The spawn/ledger contract drifts between sections — `run` param, title key, and the `name`/`agent` distinction

**What's wrong:** Three related inconsistencies. (a) Topic 3's decision defines `rp_spawn {name, agent, model, directory, prompt}` — no `run` — yet the same decision sets the title to `rp:<run-branch>:<agent-name>` and the corrected map stores `{name, run}`; Topic 8 and design-doc.md define `rp_spawn {name, agent, model, directory, prompt, run}`. (b) The title key flips between `<agent-name>` (Topic 3) and `<name>` (design-doc.md). These are not the same value: `agent` is the profile (Topic 8: "the RP agent name"), while `name` is the run-unique instance name the generic skill mandates ("Give the agent a name unique within the run", autonomous-workflow.md) — and multi-instance profiles are the norm (two `spec-reviewer` instances per review round), so a title keyed by profile name collides within a run while a title keyed by instance name does not. (c) Neither the record nor the doc ever defines what `name` is; only `agent` is glossed. Similarly, Topic 5 defines `rp_loop_start {interval, prompt, target_session}` while Topic 8 and the doc define `rp_loop_start {interval, prompt}` with the target defaulting to the calling session — compatible only if `target_session` is declared optional, which no section says.
**Where:** `design-doc-research.md` Topic 3 decision vs Topic 8 decision 3 vs Topic 5 decision; `design-doc.md` "Interfaces and Data Flow" and "Canonical `.rp.md` blocks".
**Suggestion:** Fix Topic 3's parameter list to include `run`; define both parameters once (`agent` = profile name validated against the agent list; `name` = the run-unique instance name from the generic skill's spawn step) and state that the ledger title and map use `name`; declare `target_session` optional-with-caller-default in Topic 5 or align it to Topic 8's form.
**Why it matters:** The title is the durable ledger key for reconstruction by the monitor and a resumed orchestrator (requirements 14 and 16). Keyed by profile name it collides for multi-instance profiles; two implementers following different sections would build incompatible ledgers.

### Issue 3: The completion-notification policy — every terminal event notifies the spawner — is an unstated premise with unweighed costs

**What's wrong:** The listener as declared fires on every `session.execution.succeeded`/`.failed` of every ledger session, unqualified. Under the record's own verified semantics, every `rp_send` into an idle child creates an execution, and every execution ends with a terminal event — so every message exchange with a child notifies its spawner. Concretely: during lead ↔ researcher Q&A (both spawned by the orchestrator), every researcher answer to the lead also injects a message into the orchestrator, and each such injection into an idle orchestrator triggers a full LLM execution (verified: idle target → new execution). The requirement asks for "a notification when it completes"; the design delivers a notification when every turn completes, multiplying orchestrator turns and token cost during exactly the phases with the most inter-agent traffic, and delivering notifications for exchanges the spawner is not a party to. This multiplicity is never stated as a decision nor weighed against alternatives.
**Where:** `design-doc-research.md` Topic 3 decision (completion listener); `design-doc.md` "Completion notifications".
**Suggestion:** Decide and record the policy. Candidates the existing evidence already supports: notify only on the first terminal event per spawn (the record already reasons in terms of "first terminal event" for the title re-assert), notify only for the execution started by the spawn prompt, or keep per-event notification with a recorded justification for the cost and the noise. Whichever is chosen, keep `.failed` events flowing to the monitor's observables regardless.
**Why it matters:** This sits on the run's hottest path (requirement 11, feeding 14). An unstated always-notify policy either ships as an accidental behavior with real token cost and orchestrator noise, or gets silently redesigned at Build — both outcomes bypass the decision record.

### Issue 4: The network-error observability claim overstates its verified scope for tool-call failures

**What's wrong:** Topic 7 observable 4 claims "transient tool/provider failures surface on the same structured-error channel (`session.execution.failed` types other than `provider.auth` …)". The verified siblings (`provider.auth`, `provider.no-route`) are both provider-call failures that terminate the execution. A tool call failing with a transient network error inside an agent's turn — the health contract's fourth signal verbatim ("a tool call failed with a transient network error") — ordinarily returns an error result to the model and the turn continues; nothing verified shows it reaching `session.execution.failed`. The recorded open question covers only the exact type string, not whether the channel carries tool-call failures at all.
**Where:** `design-doc-research.md` Topic 7 decision-observables item 4 and the "Network-error type string" open question; `design-doc.md` "Failure Modes and Observability", auth-and-network bullet.
**Suggestion:** Re-scope the claim to provider-call failures (which is what the evidence establishes), and state how tool-call network failures are observed — the same way as on Claude Code: the agent's own report, worktree state, and messaging state, which the monitor already reads — or extend the open question to cover the channel and name the Build-phase check that settles it. The recovery action (retry once, wait an interval) is unaffected either way.
**Why it matters:** Requirement 14 and acceptance criterion 13 make this failure observable by contract. An overbroad channel claim would let the Build phase wire the monitor to an event that never fires for this signal class, leaving the fourth signal silently unobserved.
