# Build Plan Review

## Verdict: rejected

## Summary

The plan is strong: it is grounded in the design's live-verified mechanics, its task decomposition (pure helpers → plugin assembly → entry point → skill prose → integration suite → changeset) is well ordered with correct dependencies, every spec acceptance criterion maps to at least one E2E flow, and every task traces to spec requirements and design decisions. The codebase claims in the Overview all check out against the worktree (single Tool→Read row, no loader guard, `npm test` glob semantics, `TARGET_MANIFESTS`, changeset patterns, 17 profiles). The rejection rests on four real defects: the plugin's in-daemon HTTP reach path is specified as `opencode2 api` shell-out, which by the design research's own evidence has no discovery path under the harness's `serve` shape — so the plan's own automated loop/status flows cannot pass as specified; Task 1's procedure for the paired `@opencode-ai/plugin` version is infeasible (verified: the pinned CLI's dependency tree contains only platform binary packages); Task 12 hedges whether the integration suite is ever actually run green during the phase, leaving spec requirement 3 without an owned in-phase verification; and the plan cites spec acceptance criteria by `spec.md` line numbers, which the spec does not define as indices. One residual is accepted with justification: Tasks 9–11/13 are typed `tdd` with a note disabling RED/GREEN — the Type enum offers no prose type, the repo's "skill is prose, not software" rule forbids structural tests, and the note resolves the tension explicitly in the direction the rule requires; the note travels inside the verbatim task block, so the writer receives it.

## Flag adjudications

**Flag 1 — README install/update/version procedures deferred to the Document phase: CORRECT.** The `build-planner` profile forbids documentation tasks; `4 - document.md` lists READMEs among the Document phase's outputs; the design itself splits the docs (Topic 8 decision 8: "install/pin/update procedures live in README's opencode section"). The spec's "documented procedure" outcomes (requirements 1, 5) complete within this same run when the Document phase writes the README; the Build phase correctly delivers only the mechanics those procedures describe (entry point, materialization, version-embedding id, pin manifest), and manual Flows 1/3 specify exactly the config-edit + restart mechanics the README will later document. Residual, acceptable: at Build-phase end `opencode.md`'s Setup-actions will name a README section that exists only after the Document phase — same-run ordering; the shipped state is coherent.

**Flag 2 — pin defaulting to `0.0.0-next-15772` with the suite outside offline `npm test`: SOUND IN STRUCTURE, defective in two execution details (Issues 2 and 3).** Keeping the suite out of `npm test` is design-mandated, not a plan invention (the design defines the suite as "not part of the default offline `npm test`"; the fixed gate must stay offline-deterministic). Defaulting the pin to `0.0.0-next-15772` is evidence-backed: the design-phase smoke passed on 15772, and I verified the `next` dist-tag still points at `0.0.0-next-15772` at Build kickoff — the default is simultaneously the smoke-validated and the newest build, so the design's "chosen at Build kickoff via the mechanics smoke" intent is satisfied with zero staleness. However: (a) Task 1's procedure for the paired plugin version is infeasible as written (Issue 2), and (b) the plan never makes anyone accountable for actually running the suite green during the phase (Issue 3). With those repaired, the approach is consistent with spec requirements 2–3 and the design's pin decision.

## Issues

### Issue 1: The plugin's in-daemon HTTP reach path cannot work under the harness's `serve` — the plan's own automated flows can't pass as specified

**What's wrong:** Task 7 fixes the loop tick's idle check as "checks `GET /api/session/active` (via `opencode2 api` from the shell)", and `rp_status` needs `GET /api/session` + `/pending` per-session fields the same way (Task 7 doesn't specify their reach path at all). `opencode2 api` auto-discovers via the XDG_STATE service record — but the design research states verbatim that `serve` "writes no service record" (Topic 9 findings), and Task 12's harness is `serve --port <fixed>` + `OPENCODE_PASSWORD` under isolated XDG. Inside that process the plugin shelling `opencode2 api` has nothing to discover (`ctx.serverUrl` is verified undefined), so the tick's busy/idle check and `rp_status`'s session fields dead-end — and Flows 8, 9, and the loop/status parts of Flow 16 are automated in exactly that harness. Nothing in the research record shows the Topic 5 loop experiment used shell-out discovery, so the specified mechanism is unverified in the one environment the plan requires it to pass in. The Task 7 or Task 12 writer would have to invent a server-resolution scheme mid-task — a cross-task design decision the plan must make.
**Where in plan:** Task 7 (`rp_loop_start` tick bullet; `rp_status` bullet), Task 12 (harness), Flows 8, 9, 16.
**Suggestion:** Specify one resolution mechanism that works under both shapes and is testable in the harness — e.g. resolve the server base URL + credentials as: the XDG_STATE service record when present (daemon case, per the verified `{url, password}` record), else harness/env-provided overrides (e.g. the fixed port + `OPENCODE_PASSWORD` the suite already sets on the `serve` process), and perform the calls with node's built-in HTTP client (keeping the zero-dependency constraint) rather than shelling to `opencode2 api`. State it in Task 7's Changes and mirror the env contract in Task 12's harness description.
**Why it matters:** As written, Task 12 will fail against Task 7's implementation and the writers cannot fix it without making an unplanned design decision; the loop contract (requirement 13, criteria at spec.md:47-48) is the mechanic this reach path carries.

### Issue 2: Task 1's procedure for the paired `@opencode-ai/plugin` version is not executable

**What's wrong:** Task 1 instructs "Record the `@opencode-ai/plugin` version present in that same build read from the installed build." Verified against the registry: `@opencode-ai/cli@0.0.0-next-15772`'s dependency tree contains only the twelve platform binary packages — no `@opencode-ai/plugin` exists anywhere in an installed CLI to read (the plugin API surface is compiled into the binary). The design-phase researcher obtained the plugin version by separately installing `@opencode-ai/plugin@next` — a different procedure than the task states. Additionally, "the build validated by the Build-kickoff mechanics smoke" is undischargeable by the Task 1 writer: the smoke's procedure lives in `design-doc-research.md`, which writers are told not to need, and the task neither includes it nor names who runs it — the conditional is dead text.
**Where in plan:** Task 1 (Changes).
**Suggestion:** Fix the CLI pin at `0.0.0-next-15772` outright (smoke-validated in the design phase and verified still the `next` head at Build kickoff), and give a feasible procedure for the plugin field: record the version `@opencode-ai/plugin@next` resolves at pin time via the registry (today `0.0.0-next-15772`), noting the packages advance independently. Drop the smoke conditional or name its owner and the procedure's location.
**Why it matters:** The pin manifest is the feature's single source of truth (spec requirement 2; the owner's direction quoted in spec-research: "pin the exact CLI and plugin versions"); a writer facing an unexecutable instruction must either guess a value or blocker.

### Issue 3: Spec requirement 3's in-phase verification is hedged — nobody owns running the integration suite green

**What's wrong:** Task 12's Note says the suite "runs in the Build-phase manual smoke / a dedicated environment" and the writer "authors the suite so it runs green where the pinned binary is available" — a hedge on the load-bearing claim behind requirement 3 and its acceptance criterion (spec.md:55: the tests "run against it, then they pass"). No Task 12 acceptance criterion requires `npm run test:opencode` to have actually executed green, and "the Build-phase manual smoke" is not an owned step anywhere in the phase. The hedge is also unnecessary: the writer's environment has registry access (verified in this review by live `npm view` calls), and the design researcher ran full pinned installs plus stub-provider turns in this same environment class.
**Where in plan:** Task 12 (Acceptance, Note); E2E test plan preamble.
**Suggestion:** Add a Task 12 acceptance criterion: the core (stub-provider) path of `npm run test:opencode` has been executed against the pinned CLI in the writer's environment and passes, with the network-smoke path excluded from that requirement. If an environment genuinely cannot install the pinned CLI, the writer's blocker protocol handles it — the plan should not pre-authorize skipping execution.
**Why it matters:** Requirement 3 is the spec's whole warrant that the declared pin is real ("pinned verification"); as written the phase can complete with a never-executed suite and the claim unverified.

### Issue 4: Acceptance-criterion references use spec.md line numbers as if they were criterion indices

**What's wrong:** The spec's acceptance criteria are an unnumbered bullet list, yet the plan traces flows and tasks to "Acceptance criterion 40" … "56" — which are `spec.md` line numbers, resolvable only by opening the file with line numbering. Worse, the same Traces-to fields mix these with the spec's real requirement numbers 1–16 (e.g. Task 9: "Spec requirement 8, 9; supports 44"), inviting misreads. The plan must be standalone and unambiguous for writers and for the build-reviewer, who maps criteria to flows.
**Where in plan:** All Flow "Traces to" lines; Tasks 1, 9, 10 Traces-to.
**Suggestion:** Number the criteria 1–17 in list order (stating that convention once in the E2E preamble), or cite each by a short slug ("install", "version surface", …) alone; the parenthetical glosses already present can carry the reference.
**Why it matters:** Two readers of "criterion 44" resolve it differently (44th criterion does not exist; line 44 does); traceability that needs out-of-band knowledge to decode is not traceability.
