## Accepted residuals (non-blocking, with justification)

- **Multiple/stale `service-*.json` records.** The glob could match a stale record after a daemon crash. Accepted: the design records one record per service (created on start, removed on stop); a wrong resolution degrades to failed HTTP calls, which the plan already routes to skip-and-log and the monitor's observables — never a silent wrong action. Selection among multiple records is writer latitude, not a hidden design decision.
- **`rp_status` under a null reach resolution.** Only the loop tick's null-path is spelled out. Accepted: Task 6's pure shaping function plus its "not determinable" criterion determine the graceful degradation (report from the in-memory ledger, mark HTTP-derived fields unknown); realistic deployments always resolve via record (daemon) or env (harness).
- **Flow 9's step text says `opencode2 service restart` while the automated harness runs `serve`.** Accepted: the mechanic under test (registry survives process death; first project-scoped touch re-arms) is process-shape-independent, and Task 12's harness section governs the automated implementation — the writer restarts the serve process; no design choice is delegated.
