# Build Summary

## What

opencode v2 is now a second supported agentic coding tool alongside Claude Code. The phase produced:

- **`opencode/plugin.mjs`** — a zero-dependency ESM plugin (node builtins only) that supplies the coordination layer opencode lacks: six registered tools (`rp_spawn`, `rp_send`, `rp_loop_start`, `rp_loop_list`, `rp_loop_cancel`, `rp_status`), a singleton completion listener that notifies a spawner on its child's first terminal event (naming the outcome, succeeded or failed), an in-daemon health-loop scheduler over a durable registry (`$XDG_DATA_HOME/radical-pipelines/loops.json`), idempotent ownership-aware materialization of the 17 RP agent profiles into opencode's global agents directory (foreign-file collisions reported via `rp_status`'s `recentErrors`, never clobbered), skill-source registration of the repo's `skills/` tree by reference, and an in-process server-reach helper (service record, else `RP_OPENCODE_SERVER_URL`/`OPENCODE_PASSWORD` overrides) with a `node:http` Basic-auth client. Every pure helper is named-exported and unit-tested offline.
- **`opencode/pin.json`** — the single source of truth for the pinned target: `@opencode-ai/cli` `0.0.0-next-15772` and `@opencode-ai/plugin` `0.0.0-next-15772`, as independent fields.
- **`package.json`** — `main`/`exports` now resolve to `opencode/plugin.mjs` (the github-specifier install channel's entry point) and a `test:opencode` script runs the integration suite; the fixed `npm test` gate is unchanged.
- **Skill surface** — a new per-tool convention file `skills/radical-pipelines/reference/conventions/opencode.md` (canonical `## opencode conventions` blocks: Team spawning, Health monitoring, optional Agent models; worktree-root constraint; a Setup-actions check that the plugin is installed before `rp_*`-referencing conventions are written); one new `opencode → opencode.md` row in `setup.md`'s Tool→Read table; one tool-agnostic rule in `load.md` making a per-tool convention count as present only when its section's tool matches the active tool, folding a mismatch into the existing missing-conventions stop/explain/offer-setup flow.
- **`scripts/opencode-integration/`** — a hermetic integration suite (`npm run test:opencode`, outside the `npm test` glob) that installs the pinned CLI into a version-keyed cache, runs it XDG-isolated via `serve`, drives the plugin's real tools through an offline OpenAI-compatible SSE stub provider, and asserts 28 checks covering plugin load and version id, skill registration, materialization and collision reporting, spawn/seat/ledger/title (including the auto-title race), messaging attribution and the three-stage failure chain (synchronous 404, lingering `/pending`, structured execution error), the loop lifecycle including restart re-arm, interrupt, same-session model switch, auth-error recovery (model swap, then re-spawn), a tool-call network-error probe, and the pin assertion. A release-cadence `--network-smoke` path (github-specifier install, hosted free models) exists but is excluded from the default run.
- **Changeset** — a `minor` changeset for `@automattic/radical-pipelines`, and `opencode/**` added to `.changeset/config.json`'s `changedFilePatterns` so future changes to the packaging artifact are changeset-gated.
- **Unit tests** — eight offline test files under `scripts/test/opencode/` (157-test `npm test` gate overall), plus an adaptation of `scripts/test/release-version-script.test.mjs` to the additive `test:opencode` script.

## Why

RP previously ran only on Claude Code, consuming that tool's native team primitives. opencode v2 provides sessions, skills, and agent profiles but no teammate layer, no cross-session messaging convention, and no recurring-loop primitive; the plugin supplies exactly those missing pieces so an owner on opencode can install RP and run pipelines end-to-end, while the generic skill stays tool-agnostic per RP's per-tool pattern. The beta's API instability is contained by pinning one exact build and verifying against exactly it.

## How

The plugin is a single file exporting `{id, setup(ctx)}`; `id` embeds the `package.json` version read at load. `setup` registers the tools and skill source on every per-directory re-run and guards global concerns (event subscription, loop re-arm) behind `globalThis`-keyed singletons so they run once per daemon. The opencode session DB is the agent ledger: `rp_spawn` validates the agent against `ctx.agent.list()`, parses `provider/model[#variant]` into a `Model.Ref`, seats the session at the given directory, records `sessionID → {name, run, spawner}` in a process-wide map, and the listener asserts the durable `rp:<run>:<name>` title after the first turn. All message delivery uses `delivery: "queue"` with attribution derived from the caller's `toolCtx.sessionID`, never message content. The loop tick and `rp_status` reach the server in-process — the service record when a daemon runs, env overrides under `serve` — through injectable boundaries, which keeps the entire unit surface offline. Build order followed the dependency chain: pin manifest and pure helpers first, then the assembled plugin, the package entry, the skill prose, the integration suite, and the changeset. Eight runtime-contract mismatches invisible to fake-`ctx` tests (result envelopes, async agent list, `data`-wrapped GET responses, async-iterable event subscription, dotted error tags, version-string prefix, XDG-qualified materialization target) were found by live testing against the pinned build and folded back into code and tests.

## Key decisions

- The two pin fields (`cli`, `plugin`) are independent because the `next`-tag packages advance separately, even though both are `0.0.0-next-15772` at pin time.
- The integration suite lives outside `scripts/test/**` so the fixed `npm test` gate never runs network-adjacent code; conversely, every reach-touching unit test stubs the service-record read, the HTTP client, and the CLI-version exec, keeping the gate deterministic even on a machine running a real opencode daemon (verified under a poisoned-record simulation).
- The completion notification names the terminal outcome ("succeeded"/"failed") so a first-turn spawn failure reads as a failure; materialization collisions are recorded to the bounded error log and surface through `rp_status` rather than being silently dropped.
- The `serve`-backed harness sets `RP_OPENCODE_SERVER_URL`/`OPENCODE_PASSWORD` on the server's own environment because `serve` writes no service record; the daemon path was verified separately against a real `service start` process resolving the record alone.

## Known limitations

- Builds other than the pin are unverified by design; `rp_status` reports "outside the verified surface" on drift and "not determinable" when the running build cannot be read.
- The github-specifier install/update channel and the hosted-model smoke run at release cadence (the suite's `--network-smoke` path), not in the default hermetic run — a release tag is a precondition.
- The in-memory ledger, notified-children set, and error log die with the daemon; reconstruction relies on the durable `rp:` titles and the git-based resume model, so a post-restart terminal event on a pre-restart child notifies no one by design.
- Owner-conversational flows (setup dialogue, mismatch dialogue, monitor-driven recovery, full five-phase run, resume) are composed of mechanics verified here but were not driven as live LLM sessions in this phase; the README procedures they follow are Document-phase output.
