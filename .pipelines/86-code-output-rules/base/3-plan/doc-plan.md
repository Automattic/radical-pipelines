# Doc Plan: Default output rules for generated code

## Overview

This feature promotes two always-on, enforced output rules into the Radical Pipelines tool itself: Rule 1 (a change must not tidy comments or prose belonging to content it did not touch) and Rule 2 (the shipped host-project product — code, tests, inline and external docs, and product commit messages — must not reference this run's pipeline, its phases, its artifacts, or its agents). It also reconciles the commit-format convention so the agent-name provenance tag is documented as belonging to artifact-only commits, not to commits that introduce host-project product. The host project is Radical Pipelines itself, so the change is entirely to the tool's own skill reference files and agent profiles; the canonical rule statement and every agent-facing instruction are produced by the code phase. The documentation work that remains is the user-facing surface that describes the tool to its consumers: a release changeset recording the change, the marketing-site demo whose commit-message example now teaches behavior the tool forbids, and the top-level README's narrative of the tool's always-on behaviors. The internal canonical statement (`output-rules.md`) and the agent profiles are authored by the code phase and are deliberately not re-documented here, to respect the project rules that the skill stay minimalist and free of cross-path duplication.

## Tasks

### Task 1: Add a release changeset recording the output-rules change

- **Goal:** Record this user-facing behavioral change in a committed changeset so it lands in the changelog at the next release, per the repository's standing rule that every change records a changeset.
- **Audience:** Radical Pipelines consumers and maintainers reading the changelog / release notes to learn what changed in a version.
- **Files to change:** A new `.changeset/<descriptive-slug>.md` file. (The `CHANGELOG.md` is generated by Changesets from these files and is never hand-edited.)
- **Sections / scope:** A single changeset file with the Changesets front matter (the `@automattic/radical-pipelines` package and a bump type) and a one-paragraph imperative-mood summary. The summary should convey, in user-facing terms: that two always-on output rules now apply to every run's host-project output with no owner action and no opt-out; what each rule guarantees about the shipped product; that the rules are enforced by the code and docs phase reviewers and block phase completion on violation; and that the agent-name provenance tag is now confined to artifact-only commits (product commits carry no provenance). The doc-writer chooses the bump type by reading `CONTRIBUTING.md`'s bump-type guidance and judging the shipped change; if it is breaking under the pre-1.0 policy, apply the `BREAKING:` prefix convention.
- **Depends on:** none
- **Traces to:** Spec R1/AC1 (always-on, no owner action), R8/AC7 (enforced, blocks completion), R6/AC9 (provenance tag confined to artifact-only commits); Code plan Tasks 1-9 (the shipped behavior the changeset describes).
- **Acceptance:**
  - A new `.changeset/*.md` file exists with valid Changesets front matter naming the package and a bump type.
  - The reader of the resulting changelog entry learns that the two output rules are always-on, enforced, and apply with no owner action or opt-out.
  - The entry conveys what the product is now guaranteed to be (no tidying of untouched comments/prose; no references to the run's pipeline anywhere in the product) and that the agent-name provenance tag is now artifact-only.
  - The summary is in imperative mood and follows the repository's changeset summary conventions (including the `BREAKING:` prefix if the chosen bump warrants it).
  - The bump type is consistent with `CONTRIBUTING.md`'s guidance for this kind of change.

### Task 2: Fix the website demo's commit-message example

- **Goal:** Correct the marketing-site pipeline demo so its commit-message example no longer shows a host-project product commit carrying an agent-name provenance tag — a pattern the tool now reclassifies as artifact-only.
- **Audience:** Prospective and current users browsing the public website to understand how a run progresses and what its commits look like.
- **Files to change:** `website/demo.js` (the scripted demo step in which a code-phase writer commits product source, currently around line 103). The doc-writer should confirm the exact location against the shipped code and check the rest of `website/demo.js` and `website/index.html` for any sibling commit-message examples on product-producing steps.
- **Sections / scope:** Adjust the demo's product-commit example so the committed message reflects the reconciled convention (a product commit carries no agent-name provenance tag). Keep the demo otherwise intact — the writer/reviewer step labels and the artifact tree that legitimately name agents and artifact *types* are product documentation of the tool and must stay (they are not a Rule 2 violation; they document the tool, not a real run's artifacts). Only the commit *message* shown for a product-producing step changes.
- **Depends on:** Task 1 (so the changeset's framing of the reconciled provenance behavior is settled first; ordered for a single coherent working tree, no textual dependency).
- **Traces to:** Spec R6/AC9 (product commit messages carry no pipeline-naming provenance; tag confined to artifact-only commits); Code plan Tasks 2-3 (commit-format reconciliation in `setup.md` and `.rp.md`).
- **Acceptance:**
  - The viewer of the demo sees a product-commit example whose message carries no agent-name provenance tag, consistent with the reconciled commit-format convention.
  - No product-producing step in the demo shows an agent-name provenance tag on its commit message.
  - The demo's legitimate documentation of agent names and artifact types (step labels, artifact tree) is preserved unchanged.

### Task 3: Reflect the output rules in the README's behavior narrative

- **Goal:** Ensure the top-level README's description of the tool's always-on behaviors and conventions reflects that every run's host-project output is now governed by the two enforced output rules, at the same altitude the README already uses for tool-default behaviors (guardrails, per-phase summaries, conventions).
- **Audience:** Readers of the project README evaluating or adopting Radical Pipelines who want to know what the tool guarantees about the output a run ships.
- **Files to change:** `README.md`. The doc-writer judges placement by reading the README's existing sections that enumerate tool behaviors and conventions (the conventions/what-it-produces narrative around the commit-format and summaries discussion) and the shipped behavior; if, after reading both, the README's existing wording already covers this at the right altitude and a mention would be redundant or below the README's altitude, the doc-writer records that the README needs no change and why, rather than inventing prose.
- **Sections / scope:** A concise mention that two always-on output rules govern every run's host-project product (untouched comments/prose left alone; the product reads as if written by hand with no reference to the pipeline that produced it), that they are enforced by the producing phases' reviewers, and — where the README already discusses commit conventions — that the agent-name provenance tag is confined to artifact-only commits. Keep it brief and high-level; the operative definitions live in the skill, and the README must not duplicate them. Use the project's minimalist, generic voice and avoid restating the full rule text.
- **Depends on:** Task 1 (consistent user-facing framing of the rules and the provenance reconciliation).
- **Traces to:** Spec R1/AC1 (always-on, no owner action), R2/R3/R5 (what each rule covers), R8/AC7 (enforced), R6/AC9 (provenance tag artifact-only); Code plan Tasks 1-3.
- **Acceptance:**
  - A README reader learns that every run's host-project output is governed by two always-on, enforced output rules and what, at a high level, each guarantees.
  - Where the README discusses commit conventions, the reader understands the agent-name provenance tag is confined to artifact-only commits.
  - The addition stays at the README's existing altitude, does not duplicate the canonical rule definitions, and matches the project's minimalist, generic voice.
  - If the doc-writer determines no README change is warranted, the rationale is recorded explicitly (which existing wording already covers it) rather than leaving the surface silently unaddressed.

## Surfaces deliberately not changed

These surfaces were swept and need no documentation task; listing them so the docs phase does not treat their absence as an oversight:

- **`CHANGELOG.md`** — generated by Changesets from `.changeset/*.md`; never hand-edited (covered indirectly by Task 1).
- **`CONTRIBUTING.md`** — scoped to release/changeset mechanics and contribution flow; it documents neither the output rules nor the agent-name commit provenance behavior, so nothing in it drifts.
- **`AGENTS.md` (= `CLAUDE.md`)** — the rules for modifying the skill; it governs how the skill is authored, not the tool's runtime output behavior, so it is untouched by this feature.
- **`.github/` templates and workflows, `pr-description.md`** — contain no reference to the commit-format provenance behavior or the output rules.
- **The canonical `output-rules.md`, the five agent profiles, the two phase files, and the `setup.md`/`.rp.md` commit-format conventions** — these are authored by the code phase (code plan Tasks 1-9). Re-documenting their content here would duplicate it across reading paths, which the project's no-duplication rule forbids.
