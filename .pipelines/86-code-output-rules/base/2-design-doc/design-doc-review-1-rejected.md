# Design Doc Review

## Verdict: rejected

## Summary

This is a strong, well-grounded design. It is faithful to the research (every Topic and Decision in `design-doc-research.md` is reflected, no considered alternative was silently dropped), every spec requirement and AC traces to a named decision, and the chosen approach is correctly anchored to real codebase precedents that I verified: the blocker-protocol restatement pattern (~14 profiles under a shared name-handle), the `summary-format.md` launch-prompt delivery channel passed in step 4 of both phase files, the reviewer-as-sole-gate completion predicate, and the exact `code-writer-tdd.md:33` line and `.rp.md` commit-format convention it must reconcile. The enforcement story (no approval file ⇒ predicate unsatisfied ⇒ phase blocked) is mechanically sound for AC7. I am rejecting on three concrete gaps, all in the R6 / commit-message and AC9 area, where the design under-specifies the *input* its load-bearing reviewer check needs and leaves an internal inconsistency about which commits the distinction applies to. These are correctable without reworking the architecture.

## Issues

### Issue 1: The reviewer's R6 commit-message check has no specified input channel

**What's wrong:** R6/AC5 enforcement is assigned to the reviewers' new "Output rules" check, which the design says inspects "the batch's product commit messages." But the current reviewer workflow has no step that reads commit messages — `code-reviewer.md:19` and `docs-reviewer.md:21` inspect only the *diff* (base ref → HEAD), never the commit log, and the research itself confirms "Reviewers do not read product commit messages today" (`design-doc-research.md:470`). A diff does not carry commit messages. The design describes the change as "a small, in-seam addition" and says the reviewer "already commits in-format and inspects the batch," but neither establishes the actual input: nowhere does the design state that the reviewer must read the batch's commit messages (e.g. a base→HEAD `git log`) as a gather-context input. As written, the reviewer is told to *check* something it is never given. An implementer could add the checklist item and still leave the check with no data.

**Where in design doc:** "Components → Modified → Reviewer profiles" (the "Output rules" entry says it covers "Rule 2/R6 over the batch's product commit messages"); "Interfaces and Data Flow → Violation data flow" step 2 ("and the batch's product commit messages (R6)"); "Failure Modes" #4. None of these specifies how the reviewer obtains the commit messages.

**Suggestion:** State, at the design level, that the reviewer's gather-context step gains the batch's commit messages as an input (alongside the existing diff), so the Output-rules check over R6 has a defined source. The design should name this as a reviewer-workflow addition, not fold it implicitly into "inspect the diff."

**Why it matters:** R6/AC5 are load-bearing requirements of this feature (the leaked-comment motivation is partly a commit-provenance problem). If the enforcing reviewer has no defined access to commit messages, the R6 half of the rule is not actually enforced, and AC7's "a violation blocks completion" does not hold for commit-message violations.

### Issue 2: The product-vs-artifact-commit distinction is presented as a reviewer judgment, but in the Code/Docs phases every writer commit is a product commit — the framing is internally inconsistent

**What's wrong:** The design repeatedly frames the R6 check as applying the AC9 product-vs-artifact distinction ("artifact-only commits keep the tag, product commits do not"; "Rule 2 applies to product commits, artifact-only commits are exempt"). But in the Code and Docs phases — the only phases these two reviewers gate — the writers (`code-writer-tdd`, `code-writer-e2e`, `docs-writer`) commit *only* host-project product (code/tests/inline docs; external docs). They never commit pipeline artifacts. The reviewer's own approval commit (review file + summary) is the only artifact-only commit in the loop, and it is made *by the reviewer, after the check, outside the base→HEAD batch diff* it inspects. So within the batch a Code/Docs reviewer actually evaluates, the AC9 carve-out has no instances: the check is simply "no pipeline-naming provenance on any batch commit." The design never states this, leaving the reviewer to apply a product-vs-artifact discriminator that has nothing to discriminate, and inviting two implementers to resolve it differently (one writes "flag any tagged batch commit"; another writes a needless artifact-detection step that can misfire).

**Where in design doc:** "Components → Untouched but relevant" (3rd bullet, AC9 framing); "Key Decisions → Confine the provenance tag to artifact-only commits"; "Interfaces and Data Flow → Violation data flow" step 2. The AC9 carve-out is correct *globally* (it protects planner/spec/reviewer artifact commits elsewhere), but the design does not say it is vacuous *within the Code/Docs reviewer's own batch*, which is where the check runs.

**Suggestion:** Clarify scope: state that within the Code/Docs batch the reviewer inspects, all writer commits are product commits, so the R6 check is "no pipeline-naming provenance on any commit in the batch," and that the AC9 artifact-only exemption is what protects *other* phases' commits and the reviewer's own approval commit — not something the Code/Docs reviewer needs to adjudicate per-commit inside its batch.

**Why it matters:** Clarity and consistency: if two implementers read this design independently, one could build a spurious "is this an artifact commit?" branch into the reviewer (which can over- or under-fire), while the spec's actual need here is the simpler invariant. Ambiguity in the load-bearing enforcement check is exactly where AC7 reliability erodes.

### Issue 3: The new writer commit-message obligation collides with the writer profiles' existing "use the host project's commit format" instruction, and the design does not say how the writer-profile text is reconciled

**What's wrong:** The design gives each writer "guidance that product commit messages carry no pipeline-naming provenance." But each writer profile already instructs, in its commit step, "Commit ... using the host project's commit format" (`code-writer-tdd.md:49`, `code-writer-e2e.md:40`, `docs-writer.md:52`), and the host commit format for this very repo (`.rp.md:51`) mandates "Include the name of the agent in parenthesis." Until `.rp.md`/`setup.md` are reconciled, a writer obeying its own profile faithfully produces a tagged product commit — i.e. the profile would contain two directly conflicting instructions. The design resolves this only at the convention layer (reconcile `setup.md` and `.rp.md` so the tag is artifact-only) and defers the exact wording to an open question, but it does not address that the *writer profile's own commit step* must be worded so the two instructions cohere (e.g. "commit messages for product carry no pipeline-naming provenance, otherwise follow the host commit format"). Listing "writers get the no-provenance guidance" without reconciling it against the adjacent "use the host commit format" line leaves the conflict inside the profile.

**Where in design doc:** "Approach" move 2 and "Components → Modified → Producing profiles" both add the no-provenance guidance to the writer profiles; "Key Decisions → Confine the provenance tag to artifact-only commits" and the open questions handle only `setup.md`/`.rp.md`, not the writer profile's commit-step wording.

**Suggestion:** State at the design level that the writer profiles' commit step is reworded so the no-pipeline-provenance obligation and "use the host commit format" instruction are consistent (the host format, once reconciled, yields no tag on product commits) — so a writer reading only its own profile is never given two conflicting commit-message instructions.

**Why it matters:** Feasibility and consistency: an agent reads only its own profile (a project invariant). If that profile tells it both "no provenance tag on product commits" and "use the host commit format" while the in-repo host format still says "include the agent name," the agent has no consistent instruction to follow, and the self-hosting run will either tag-and-get-rejected every batch or behave non-deterministically. The convention reconciliation is necessary but not sufficient; the profile text must be made internally consistent too.
