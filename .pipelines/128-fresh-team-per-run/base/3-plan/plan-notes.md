## Code Plan Topics

### Topic: Task slicing / granularity

- **Spec / design link:** Design decisions 1 & 3; all acceptance criteria.
- **The four functional edits:** (A) canonical convention `claude-code.md` — define the unique-naming rule; (B) `review-pipeline.md` — correct "team unchanged"; (C) `health-monitoring.md` — monitor prompt uses the actual team name; (D) deployed `.rp.md` — carry the same rule. A and D state the *same* rule in two places (drift risk).
- **Options:**
  1. **One task per file (4 tasks):** A, B, C, D separately. Maximal traceability; A/D could drift if done independently.
  2. **Group the rule-definition (A+D) + B + C (3 tasks):** keep the two copies of the naming rule in one task so they can't drift; B and C are distinct corrections.
  3. **Single task (1 task):** the whole change is small and coherent.
- **Trade-offs:** (1) cleanest 1:1 traceability but splits the two coupled rule statements; (2) prevents A/D drift while keeping distinct corrections separate; (3) least overhead but bundles edits that trace to different decisions, weakening traceability.
- **Decision:** Option 2 — Task 1 = naming rule in both `claude-code.md` and `.rp.md`; Task 2 = `review-pipeline.md` wording; Task 3 = `health-monitoring.md` prompt.
- **Rationale:** Owner choice. Keeps the two copies of the naming rule in one task (no drift) while keeping the two distinct corrections independently traceable.

### Topic: Ordering, file scope, and per-task acceptance

- **Spec / design link:** All acceptance criteria; design decisions 1–3.
- **Decision (no real branching):** Task 1 lands first (defines the rule); Tasks 2 and 3 are independent and may follow in any order. File scope is exactly the four sites from Research. Each task carries observable acceptance criteria (see `code-plan.md`). Task 1 also carries a negative acceptance: worktree/branch wording in `claude-code.md` is left unchanged (AC5).
- **Rationale:** Markdown edits with no runtime coupling; ordering is logical, not technical.

- **Spec / code-plan link:** Whole change; code Tasks 1–3.

This change touches `skills/**`, so a `.changeset/*.md` is mandatory. Audience: changelog/release-note readers. This is the one doc surface that needs a task.

- **Bump type (the real choice):** `patch` vs `minor`. Per `CONTRIBUTING.md`: `patch` = bug fixes / backwards-compatible changes that add no feature; `minor` = new features/additions. This is a backwards-compatible fix to team-naming behavior, adding no feature → `patch` fits; `minor` is defensible if treated as a behavior change worth a feature-level note.
- **Options:**
  1. One doc task: add a `patch` changeset describing the unique-per-run team naming.
  2. One doc task: add a `minor` changeset.
- **Decision:** Option 1 — one doc task: add a `patch` changeset. No changeset for #128 exists yet (the only `.changeset/*.md` present, `agent-scoped-guardrails.md`, belongs to pipeline 121). README and website confirmed out of scope.
- **Rationale:** `patch` is the rule-defined fit (backwards-compatible fix, no new feature). Bump type is a mechanical CONTRIBUTING-driven call; defaulted rather than treated as an owner decision.
