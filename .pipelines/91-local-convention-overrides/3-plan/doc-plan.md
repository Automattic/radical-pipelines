# Doc Plan: Local, per-developer overrides of a project's Radical Pipelines conventions

## Overview

This feature lets a developer place a git-ignored `.rp.local.md` alongside the committed `.rp.md` to locally override a restricted subset of conventions (agent models, health-monitoring cadence, the Issues access-mechanism) for their own working copy or machine, never committed and never affecting others. Because Radical Pipelines is "documentation as code," the feature ships *as* skill-instruction documentation, and the approved code plan already owns the entire functional documentation surface: the canonical `skills/radical-pipelines/reference/conventions/local-overrides.md` (the full procedure, worked examples, and assisted-inertness note), the `load.md` gate step, the `setup.md` edits, the `SKILL.md` discoverability clause, the standalone `README.md` Configuration paragraph that satisfies the requirement-20 conventions-overview mention, the dogfood `.gitignore` entry, and the changeset. A whole-repository sweep of every live documentation surface (`README.md`, `CONTRIBUTING.md`, `AGENTS.md`, the agent profiles under `agents/`, the entire `skills/radical-pipelines/` reference tree, and the `website/` landing page) found **no additional surface that the code phase leaves out of sync** — with one exception. The README "Configuration" section is a continuous narrative that, in paragraphs the code plan deliberately does not touch, still frames the committed `.rp.md` as the *single/only* source of a project's conventions; once the new `.rp.local.md` overlay exists, that framing reads in tension with the capability the code plan introduces. This plan contains exactly one task: a narrative-coherence pass over the README Configuration section so the surrounding prose stays true alongside the new paragraph. Everything else the feature needs is already a code-plan deliverable and is intentionally not duplicated here.

## Tasks

### Task 1: Reconcile the README "Configuration" narrative with the local-override overlay

- **Goal:** Make the existing README "Configuration" narrative read coherently now that a sanctioned per-developer `.rp.local.md` overlay exists. The code plan inserts a self-contained paragraph advertising the capability but explicitly leaves the surrounding paragraphs untouched; those surrounding paragraphs currently frame the committed `.rp.md` as the *single/only* source of a project's conventions, which now reads as in tension with the new overlay. Adjust only that framing so the section as a whole is accurate and the new paragraph sits naturally within it — without restating the override mechanism (the canonical doc and the code plan's new paragraph own that).
- **Audience:** Readers of the public project README — primarily a developer or team evaluating or using a Radical Pipelines consuming project, who needs an accurate mental model of where conventions come from and that a committed-plus-local layering now exists.
- **Files to change:** `README.md` — the `## Configuration` section only (the two narrative paragraphs that present the committed file as the sole/whole convention source, currently the section's opening paragraph and the later "a single project keeps everything in one merged" paragraph). Do not touch the standalone `.rp.local.md` paragraph the code plan adds, the setup/agent-models paragraphs, or any section outside `## Configuration`.
- **Sections / scope:** A light prose pass that softens the "single source / everything in one file" framing into a "committed shared source, optionally layered by a per-developer local overlay" framing consistent with the new paragraph, and ensures the new paragraph and the surrounding text cross-read as one coherent narrative (ordering, transitions, and a single pointer to the canonical doc rather than competing or duplicated descriptions of the mechanism). Match the README's existing voice and paragraph rhythm. This is wording/narrative-fit work that depends on the final text of the code plan's new paragraph; the doc-writer reads the actual edited README in phase 5 and reconciles against it.
- **Depends on:** none within this plan. Sequencing note for phase 5: this task reconciles the surrounding narrative against the standalone `.rp.local.md` paragraph that the **code phase** (code-plan Task 5) lands in the same section, so it should be executed after that code-phase paragraph exists; the doc-writer reads the actual edited README.
- **Traces to:** Spec requirement 20 (the conventions-overview mention must be coherent and discoverable, not contradicted by adjacent prose); Design-doc "Discoverability touchpoints → 4" and "Components → Modified components → README.md"; code-plan Task 5 (which delivers the standalone paragraph and explicitly defers further README narrative refinement to the doc-plan phase). Precedent: the comparable per-agent-model-config feature treated "the README convention catalog" as a coherent narrative surface that is woven, not merely appended to.
- **Acceptance:**
  - After this task, a reader of the `## Configuration` section comes away understanding that a project's conventions live in a committed shared file that may be **layered** by a per-developer local overlay — with no sentence in the section asserting or implying the committed `.rp.md` is the project's *only* or *whole* source of conventions.
  - The standalone `.rp.local.md` paragraph and the surrounding narrative read as one coherent passage: no contradiction, no duplicated full description of the merge mechanism, and the canonical doc is pointed to from a single, clear place.
  - The section continues to accurately describe the committed-file setup flow and the per-tool/agent-models content that is unrelated to this feature; nothing outside the convention-source framing is rewritten, and no section outside `## Configuration` is changed.
  - The pass introduces no new normative detail about the override mechanism (filename, location, merge rule, overridable subset, warnings) beyond what the code-phase paragraph and the canonical `local-overrides.md` already state — it only reconciles framing and narrative flow.

## Surfaces deliberately not given a task

A whole-repository sweep confirmed the following surfaces need **no** doc-plan task, and they are listed here so the absence is explicit rather than an oversight:

- **The canonical `local-overrides.md`, `load.md`, `setup.md`, `SKILL.md`, the standalone `README.md` Configuration paragraph, the dogfood `.gitignore`, and the changeset** — all are functional requirement-20 / requirement-23 deliverables already owned by the code plan (code-plan Tasks 1–7). Duplicating them here is explicitly out of scope.
- **`CONTRIBUTING.md`** — its only feature-adjacent text classifies `.gitignore` as a non-release-relevant "meta file" needing no changeset. That classification stays true: the `.gitignore` edit ships alongside `skills/**` and `README.md` edits that *do* warrant the changeset (code-plan Task 7), so no statement in `CONTRIBUTING.md` becomes stale.
- **`AGENTS.md`** — a minimalist "rules when modifying the skill" doc with no convention catalog and no reference to `.rp.md`, `.gitignore`, agent models, health monitoring, or Issues access. Nothing the feature changes is described there.
- **`agents/*.md` profiles** (including `doc-writer.md`) — they reference "the host project's conventions" generically and never enumerate the convention catalog or the committed-file-as-sole-source framing, so the overlay does not contradict them.
- **`website/`** — the landing page (`index.html`, `demo.js`, assets) contains zero references to conventions, configuration, `.rp.md`, agent models, or any behavior this feature touches; it is marketing-only, confirming the design doc's whole-repo sweep.
- **The dogfood `.rp.md`** — the design doc's scope guard (b) deliberately leaves it as-is (the existing Issues prose already presents the named sub-statement the merge model needs), so it is intentionally untouched.
- **Historical changesets under `.changeset/`** (e.g. `restructure-repository-layout.md`) — already-released entries are frozen by repository convention and are never retroactively edited.
