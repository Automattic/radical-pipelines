# Code Plan Review

## Verdict: rejected

## Summary

The plan is strong overall: paths are real, the load.md/setup.md divergence note is correct (verified — `load.md` carries no gate-running enumeration; the enumeration lives at `setup.md` L183/L185 and there is no illustrative example row at L189), the `npm test` floor runs and stays green (22 pass), and the decision to treat the e2e plan as reviewer-re-driven inspection with no e2e task is defensible for a prose-only feature. But Tasks 3, 4, and Flow 3 are written against a writer-side guardrail model that **no longer exists in this worktree**. Commit `a0e3fd9` ("Gate reviewer guardrails on judgment; drop selection vocabulary"), which is an ancestor of HEAD here, deliberately deleted the very text these tasks instruct the writer to rename, preserve, and assert. The plan must be reconciled with the actual post-`a0e3fd9` agent files before it can be executed without forcing the code-writer to re-introduce removed vocabulary or to choose between two contradicting instructions.

## Issues

### Issue 1: Tasks 3 and 4 instruct preserving/renaming guardrail vocabulary that commit `a0e3fd9` already removed from the worktree

**What's wrong:** The plan's Overview divergence note flags only the load.md/setup.md enumeration. It does not account for commit `a0e3fd9` ("Gate reviewer guardrails on judgment; drop selection vocabulary"), which is in this worktree's history (`git merge-base --is-ancestor a0e3fd9 HEAD` → yes) and landed after the #124 merge the design/spec were grounded against. That commit changed the writer's guardrail handling in exactly the places Tasks 3/4 operate on. Against the **current** `agents/code-writer.md`:

- **Gather context has no guardrail-read line.** `a0e3fd9` removed "Read your guardrails — the gates you must run before completing" from step 1. Current Gather context is just: (1) read the task block, (2) read cited review issues. Task 3 says Gather context should carry "guardrails naming `code-writer-tdd` or no agents" and its Acceptance says "Its guardrail-read line names `code-writer-tdd` and it selects no-agent guardrails too." There is no guardrail-read line in the current file to model on, name, or carry over.
- **The step is "Run the guardrails," not "Run the writer guardrail selection."** `a0e3fd9` renamed it. Task 3 says to "rename to 'Run the gates'" and Task 6/Flow 3 assert a "Run the gates" step — but the source step is already named "Run the guardrails," and the design's premise that step 5 is named "Run the writer guardrail selection" (design §3) is stale.
- **There is no "two-question outcome model" and no agent-scoped "guardrail selection."** `a0e3fd9` explicitly removed the "two questions: did the command execute? / did the gate pass?" framing and the per-agent "selection" framing; the current step says "Run every gate in the guardrails convention, exactly as its command is written," with a plain three-bullet sort (no-convention / can't-execute = blocker / non-zero = work). Task 3's Run-the-gates spec ("under ONE shared two-question outcome model," "(i) its guardrail selection and (ii) the required-test-commands floor") and Flow 3 step 5 ("under one shared two-question outcome model") assert vocabulary that was deliberately deleted.

The sibling `agents/doc-writer.md` and `agents/code-reviewer.md` received the same `a0e3fd9` treatment, so the two new writer files modeled per Tasks 3/4 would re-introduce vocabulary (`guardrail selection`, `two-question outcome model`, a guardrail-read line) that no other live agent file still uses — making the new writers inconsistent with the rest of the agent set.

**Where in plan:** Task 3 (Changes: "Gather context"; "Run the gates"; "guardrail-read line names `code-writer-tdd`"; Acceptance bullets 4–5), Task 4 (Changes: Gather context, "Run the gates: identical to `code-writer-tdd`'s", self-containment; Acceptance bullets 5–6), Flow 3 steps 5–6, and the Required-test-commands / E2E sections insofar as they restate the two-question framing as a writer obligation. The root cause is in the Overview divergence note, which scopes the post-#121 reconciliation to load.md/setup.md only and misses `a0e3fd9`.

**Suggestion:** Re-anchor Tasks 3/4 (and Flow 3) on the **actual** post-`a0e3fd9` `code-writer.md`, the same way the plan already re-anchored Task 7 on the real setup.md. Concretely: model the new writers' "Run the guardrails"/"Run the gates" step and its outcome bullets on the current three-bullet sort (no "two-question" label, no "selection" framing); drop the Gather-context "guardrail-read line names the agent" item and the "selects no-agent guardrails" assertions, or replace them with whatever the current file actually expresses about how the writer learns its gates (it now relies on "the guardrails convention the orchestrator passes" — see `a0e3fd9`'s reviewer spawn-step inlining and `autonomous-workflow.md`). Add a divergence note paralleling the existing one, recording that the design's §3 "guardrail selection / two-question / guardrail-read line" references are stale post-`a0e3fd9` and naming the real current shapes the writers must match. The feature's substance (split into two writers, each running the floor before commit, no behavior-verification/derive step) is unaffected; only the guardrail-vocabulary scaffolding needs to track reality.

**Why it matters:** As written, a code-writer executing Task 3 faces two contradicting instructions — "model on the current `agents/code-writer.md` scaffolding" (which has none of this vocabulary) versus the explicit Changes/Acceptance demanding a guardrail-read line, a "guardrail selection," and a "two-question outcome model." Either it follows the current file and fails the Acceptance bullets, or it follows the Acceptance and re-introduces deleted vocabulary that diverges from every other agent file. Flow 3's reviewer re-drive (step 5: assert a "two-question outcome model"; step 6: assert "guardrail-read line names `code-writer-tdd`") would then either fail against a correctly-modeled file or pass only against the inconsistent one — and the two-writers-diverge risk this plan otherwise guards against (Task 4 copies Task 3 "verbatim") would bake the stale vocabulary into both files.

### Issue 2: Flow 3's `Type` field placement assertion is stricter than what any task implements

**What's wrong:** Flow 1 step 3 and Flow 3 are consistent, but note one minor mismatch for completeness: Flow 1 asserts the task-block template has `- **Type:** tdd | e2e` "directly after `- **Goal:**`," and Task 1 Changes/Acceptance say the same ("immediately after `- **Goal:**`"). That is fine. However, the plan never states where `Type` sits relative to the *existing* fields beyond Goal, and the autonomous task-block template (code-plan-writer.md L36–44) has `Goal` then `Files to change`. Placing `Type` between `Goal` and `Files to change` is the intended reading and is consistent — this is not a blocker, just confirm the writer is not left to guess whether `Type` precedes or follows `Files to change`. (Raised only so it is resolved alongside Issue 1; on its own it would not warrant rejection.)

**Where in plan:** Task 1 (task-block template change), Flow 1 step 3.

**Suggestion:** State explicitly that `Type` goes between `- **Goal:**` and `- **Files to change:**`, matching design §1 ("directly after `- **Goal:**`").

**Why it matters:** Two writers executing Task 1 should produce identical field order; "after Goal" alone is unambiguous enough only because Files is the next line, but making it explicit removes the last bit of latitude.
