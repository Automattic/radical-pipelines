# Spec research: Agent-scoped guardrails

Running record of the spec-phase Q&A between the spec-analyst and spec-researcher. The intent: replace the base run's two guardrail scoping dimensions (`phase` + `level`) with a single agent-name dimension, and delete `phase` outright.

## Grounding (analyst's direct reading)

Current state on this branch (`worktree-121-role-scoped-guardrails`, which already contains the base run's role-scoped guardrails):

- `skills/radical-pipelines/reference/conventions/load.md` — defines guardrails: phase targets `code`/`docs`, optional level `writer`/`reviewer`, selection rule (phase filter, then role filter within code phase; docs selection never consults level). Guardrails are committed-only, never from `.rp.local.md`.
- `skills/radical-pipelines/reference/conventions/setup.md` — captures per gate: name, exact command, phase(s), optional level (asked only for code-applicable gates). Validation: "did it execute?" three-way outcome model.
- `agents/code-writer.md` — runs the writer selection (leveled `writer` or unscoped), every gate must pass before each commit.
- `agents/code-reviewer.md` — runs the reviewer selection (leveled `reviewer` or unscoped) after judgment-based checks; fail-fast permission (may reject without running not-yet-run gates, recording them as skipped); approves only when every gate in its selection ran and passed that iteration; Checks table with pass/fail/skipped.
- `agents/doc-writer.md` — runs "docs-phase guardrails", all must pass before commit; no level filtering.
- `agents/doc-reviewer.md` — runs docs-phase guardrails, records them in its Checks table; no fail-fast permission spelled out, no skipped semantics.

Base run spec at `.pipelines/121-role-scoped-guardrails/base/1-spec/spec.md` (R1–R9) is the document this review revises.

## Open questions (analyst's initial list)

1. Selection rule successor: "an agent selects the gates that name it, plus the gates that name no agent" — confirm this is the full rule and that phase plays no part.
2. Unscoped gates now run for all four agents, including doc agents — a real semantic change from the base (a level-less `npm test` previously never ran in the docs phase). Confirm this consequence is intended and whether setup guidance must surface it.
3. Unknown/future agent names: a gate naming an agent not present in a run should be inert for everyone else, no error — mirrors the base R9 implicit-handling stance. Confirm.
4. Writer-type vs reviewer-type behavior rule: where does the mapping live (load.md vs each agent file), and what is the rule for arbitrary future agents?
5. Does doc-reviewer now gain the fail-fast permission and approving-iteration guarantee (it currently lacks skipped semantics)? Does doc-writer's step change beyond selection wording?
6. Setup capture: what replaces the Phase and Level columns/questions; is the agents field optional with "unset = every gate-running agent"?
7. Blast radius: every file mentioning phase/level guardrail vocabulary (including README, website, changeset) so the confinement criterion is accurate.
8. Backward compatibility: confirm no deployed `.rp.md` declares guardrails, so deleting `phase` without compatibility sugar is safe.

## Q&A rounds

### Round 1 — researcher's initial pass (unprompted findings)

The researcher's first pass, delivered alongside the round-1 question list, established:

- **Touched-file set is six, not four.** The doc agents identify their gates *by phase* (`agents/doc-writer.md:38-48` "Run the docs-phase guardrails"; `agents/doc-reviewer.md:33,98,99`). Deleting `phase` means docs gates can only be identified by naming `doc-writer`/`doc-reviewer`, so both doc agent files must change — a deliberate reversal of the base run's confinement guarantee (base spec AC11). Touched set: `load.md`, `setup.md`, and all four `agents/*.md`. The intent's "Likely touches" list already names all six.
- **Current state confirmed**: `load.md:24-30` holds the definition (¶ at :26 — phase targets + optional level) and the selection rule (¶ at :30 — phase filter, then writer/reviewer level filter within code; docs never consults level). `setup.md:179-184` captures name, command, phase(s), optional level; example table at :188-192 with columns Name|Command|Phase|Level.
- **Backward compatibility holds**: this repo's own `.rp.md` declares no Guardrails section at all; the only guardrail declarations anywhere in the tree are setup.md's illustrative example tables. Relaxing the base run's phase-compat constraint is safe.
- **Behavior-mapping gap confirmed**: today the fail-fast + approving-iteration guarantee lives in `code-reviewer.md` and the all-pass-before-commit obligation in `code-writer.md`; the level only filters selection. With level deleted, the intent generalizes these behaviors to "reviewer-type" and "writer-type" agents, and a rule is needed for how an arbitrary future agent maps to one of the two.

### Round 1 — researcher's detailed findings

**Blast radius (Q1).** Six files must change; exhaustive grep confirms they are the only non-`.pipelines` files encoding the phase/level selection model:

1. `load.md` — `:22` loader-table row ("gates … the code/doc phases must pass"), `:26` definition (phase targets + optional level), `:30` selection rule.
2. `setup.md` — `:183` phase capture bullet, `:184` level capture bullet, `:188-192` example table (`Name | Command | Phase | Level`).
3. `agents/code-writer.md` — `:13`, step 5 `:44-55`, `:73` (selection keyed off "leveled `writer` or unscoped").
4. `agents/code-reviewer.md` — `:18`, step 4 `:37-45`, `:110`/`:113`.
5. `agents/doc-writer.md` — `:38-48` ("Run the docs-phase guardrails"); changes *only because* phase is deleted.
6. `agents/doc-reviewer.md` — `:33`, `:98`, `:99`; same reason, plus the fail-fast generalization.

Mention-but-no-change files: `README.md:147` (phase-altitude prose; base run already classified it a docs-phase deferred touchpoint — spec should name it so the doc-plan picks it up), `CHANGELOG.md:8` (immutable historical entry), `CONTRIBUTING.md` (CI "Changeset Gate", unrelated), `website/index.html` (no guardrail content), phase runbooks (generic phase/gate words only). One genuinely awkward artifact: `.changeset/role-scoped-guardrails.md` — the base run's *unreleased* changeset describing the now-superseded `level` feature; left as-is it would ship a misleading changelog entry. Whether to amend/replace vs. stack a second changeset is open.

**Canonical agent list (Q2).** 17 agent files exist; only the four run gates. There is **no canonical "gate-running agents" roster** — the four appear together only in `README.md:112` and pairwise in the per-phase Required-agents tables (`4 - code.md:23`, `5 - docs.md:24`). `load.md`/`setup.md` currently name no agents. So "a gate naming no agents applies to every gate-running agent" requires load.md to enumerate the set itself. Precedent for keying a convention by exact agent name: the Agent-models convention (`setup.md:93`, `**<agent-name>:**` bullets).

**Backward compatibility (Q3).** This repo's `.rp.md` has no Guardrails section; the only declarations in the tree are setup.md's illustrative examples. Serialization is free-form — setup.md `:186` labels the table "illustrative, not a mandated block or parser input". Deleting phase is a prose/example edit, not a schema migration.

**Doc-reviewer mechanics (Q4).** Guardrails are a bullet *inside* step 2 (not a standalone step); the Checks table exists but its Result vocabulary is unspecified; no fail-fast, no skipped state, no approving-iteration guarantee, no stateless language. Generalizing reviewer behavior to doc-reviewer is a near-clone of the base run's code-reviewer restructure: promote guardrails to their own step after the judgment checks (step 2 review + step 3 accuracy spot-check), add fail-fast, skipped, approval guarantee, stateless line, and the pass/fail/skipped Checks vocabulary. Nothing in current ordering contradicts judgment-before-gates, but today the guardrail bullet sits mid-step-2, *before* the accuracy spot-check. Spec must make in-scope-vs-defer an explicit decision (analyst's reading of the intent: in-scope).

**Behavior placement (Q5).** Confirmed `load.md` defines only selection; all run-behavior lives in agent files (`code-writer.md:46-54`, `doc-writer.md:42-48` writer-type; `code-reviewer.md:37-45` reviewer-type; absent from doc-reviewer). No existing text names writer/reviewer archetypes as a concept — the intent's mapping rule would be the first place the skill states the two archetypes. Whether it lives centrally in load.md or stays distributed is a decision the spec must frame.

### Round 2 — researcher's findings

**Pending changeset.** `.changeset/role-scoped-guardrails.md` (unreleased, `minor`) describes the superseded `level` feature verbatim: "Add an optional per-gate `level` to code-phase guardrails so a project can scope each gate to the writer, the reviewer, or both…". Changeset conventions (CONTRIBUTING.md:117-156, :242) say nothing for or against amending an unreleased changeset. Options: (i) reword/rename it in place to describe agent scoping, or (ii) stack a second changeset — which would ship two bullets, the first describing a `level` field that never existed in any release. (i) is clearly better; the changeset is a docs-phase deliverable (the base run committed its changeset in phase 5, commit `24a6cd9`). The spec should leave the text to the docs phase but explicitly signal that the pending base changeset must be reconciled, so a doc-writer doesn't blindly stack a second one.

**Gate-running agent set.** No existing abstraction; load.md must define the set itself. Two shapes: enumerate the four (drift only happens when a new gate-running agent is added — exactly the intent's motivating scenario, so the list is load-bearing by design; precedent: Agent-models keys by exact agent name) or describe intensionally ("every agent that runs guardrails" — circular without an anchor). Spec must fix which.

**Doc-reviewer restructure (full answer).** Checks table exists but Result vocabulary unspecified; guardrails are a bullet inside step 2, ahead of the step-3 accuracy spot-check, so judgment-before-gates is not currently load-bearing there. Generalization = the base run's code-reviewer restructure cloned: own step after judgment checks, fail-fast + skipped recording, approval guarantee + stateless line, `pass|fail|skipped` vocabulary with the absent-vs-skipped rule, guidelines reconciliation.

**The subtlest semantic shift (researcher's flag).** "No agents named = every gate-running agent" is a real behavior change, not a rename: today phase bounds a bare-level gate to the code roles; with phase gone, a bare gate leaks across the code/docs boundary (doc-writer would run `npm test`). The "natural successor to no-level-=-both-roles" analogy is imperfect — "no level" never spanned doc agents. To preserve code-only behavior, owners must explicitly name the two code agents. No existing setup text steers owners on this; the old `phase: code` tag gave that scoping for free. The example-table consequence: rows that used a blank Level cell for "both code roles" must now name `code-writer, code-reviewer` explicitly; a blank Agents cell means all four. Minimal table reshape: `Name | Command | Agents` (net −1 column).

**Validation.** Setup validates only "did the command execute?"; no schema/enum check on phase or level exists anywhere. "Unknown agent name is inert" introduces no conflict and needs no new path — and is more principled than base-R9's "malformed" framing: naming a not-yet-existing agent is a legitimate forward declaration, inert until that agent exists.

**Behavior-rule placement evidence.** Selection is centralized (`load.md:30`) with agent files back-referencing their own slice — base design D1's deliberate split. Run-behavior is per-agent and never abstracted. Option (a) (keep run-behavior per-agent; future authors copy the archetype prose) is today's structure and lowest churn but provides no single mapping rule, which the intent explicitly asks for. Option (b) (state the two archetypes once — writer-type: all selected gates pass before commit; reviewer-type: judgment first, fail-fast, approving-iteration guarantee — and have agent files reference theirs) mirrors the selection-centralization precedent and satisfies "needs a rule", at the cost of raising load.md's altitude from "what each agent loads" to "what it does with it". No third shape exists in the tree.

### Round 3 — researcher's final findings

**Changeset precedent.** The prior review run (95, review-1) handled its base run's pending changeset with an explicit discipline: evaluate staleness, name the changeset in the spec, never stack a second one (its doc-plan: "Adding one here would double-announce the same rename in the merged changelog"). There the conclusion was "leave unchanged" because the rename didn't make it stale; here the conclusion flips — the pending changeset describes the exact feature being replaced, so it must be reworded in place (and likely renamed, since the slug is descriptive). In-place changeset edits are routine in the git history (`147e5c3`, `afd9c9c`, `644106d`). The changeset remains a docs-phase deliverable; the spec names the obligation, not the text.

**Setup capture.** With phase gone, the "ask only for code-applicable gates" conditional has nothing to hang on — the agents question is asked for every gate. The old decision criterion (expensive suites leveled `reviewer`) translates partially ("name only `code-reviewer`"), but the new axis the old criterion never needed — code-vs-docs leakage — has no existing steering and genuinely needs owner-facing guidance: setup must surface that a gate naming no agents runs for every gate-running agent, doc agents included, so code-specific suites get their agents named. Example-table reshape: `Name | Command | Agents`; the old lint=blank-Level row must now name `code-writer, code-reviewer` explicitly because blank means all four.

**Validation.** Confirmed zero validation/error path on the phase/level vocabulary anywhere ("These are the only valid phase targets" is descriptive, never enforced). Silent no-match is produced by the membership test alone; nothing conflicts with inert unknown names, nothing to remove.

**Mechanism.** Agents self-read `.rp.md` — base design §6: "Guardrails are never in a launch payload — each code agent self-reads `.rp.md`." Each gather-context step says "Read the … guardrails" (`code-writer.md:13`, `code-reviewer.md:18`, `doc-writer.md:38-40`, `doc-reviewer.md:33`). And every gate-running agent knows its canonical name — each file's first body line is "You are the `<name>` agent" (all four at `:6`), matching the spawn/addressing name and the Agent-models keying. "Select the gates that name you" resolves with no new plumbing; the selection rule's run-time audience is the agent itself.

**Assisted mode.** Zero guardrail mentions in any assisted-mode doc, and assisted runs only advance through phase 3 (`review-pipeline.md:52`) — guardrails live exclusively in phases 4–5. The base run's carve-out carries over verbatim.

**Multiplicity.** Confirmed: the agents field accepts one or more names; set membership over four-plus agents needs multi-valued, and no evidence anywhere points to single-valued. (The base `level` was single-valued only because it partitioned two roles.)

## Resolved requirements (analyst's decisions)

Research is complete. The decisions below resolve the intent's open directions; the spec-writer should synthesize spec.md from them.

1. **Single scoping dimension.** A guardrail declaration carries one optional field: the **agents** that run it — one or more exact agent names. `phase` and `level` are deleted outright; no compatibility sugar (safe: no deployed `.rp.md` declares guardrails — this repo's own `.rp.md` has no Guardrails section, and serialization was never fixed). Guardrails stay shared and committed-only, never from `.rp.local.md`. Exact `.rp.md` serialization remains a design-phase decision, as in the base spec.
2. **Gate-running agent set.** The guardrail definition names the set of gate-running agents explicitly: `code-writer`, `code-reviewer`, `doc-writer`, `doc-reviewer`. No existing roster abstraction exists to lean on; the enumeration is load-bearing by design — adding a future gate-running agent updates it (the intent's motivating scenario).
3. **Selection rule.** An agent's selection = the gates that name it plus the gates that name no agents. Phase plays no part. A gate naming no agents applies to every gate-running agent — accepted as the owner's stated direction, with the boundary-leak consequence (a bare gate now also runs for doc agents) mitigated by setup guidance (decision 7). The empty-selection rule (run none, proceed, no warning) and the agent-self-reads-`.rp.md` mechanism are preserved; agents know their own canonical names, so self-selection needs no new plumbing.
4. **Unknown names are forward declarations.** A gate naming only agents not in the set is selected by no current agent — inert until such an agent exists. No validation, error, or warning path; framed as a legitimate forward declaration (the intent's future-e2e-agent scenario), not as malformed input.
5. **Behavior archetypes stated once.** The skill states, in one place, the two run-behaviors and the mapping rule for any gate-running agent: **writer-type** agents (they produce commits) run every gate in their selection and all must pass before each commit; **reviewer-type** agents (they issue verdicts) run their judgment checks first, may fail-fast (reject without running not-yet-run gates, recording each as skipped), and approve only when every gate in their selection has run and passed in that same iteration, fresh and stateless per instance. A future agent maps by whether it commits work or reviews it. Exact placement (the natural home is with the guardrail definition in load.md) is a design decision; each gate-running agent file carries behavior consistent with its archetype.
6. **Doc-reviewer generalization is in scope.** `doc-reviewer.md` gains the reviewer archetype — guardrails promoted out of step 2 into their own step after the judgment checks (review + accuracy spot-check), fail-fast permission, skipped recording, approval guarantee, stateless line, and the `pass|fail|skipped` Checks vocabulary with the absent-vs-skipped distinction — mirroring the base run's code-reviewer restructure. `doc-writer.md` keeps writer behavior with its selection re-keyed to agent names. All four agent files change; the spec's confinement claim covers six files (`load.md`, `setup.md`, four `agents/*.md`), deliberately reversing the base spec's AC11.
7. **Setup captures agents and surfaces the default.** Per gate, setup captures: name, exact literal command, and the optional agents (one or more names) — asked for every gate, since no phase remains to condition on. When unset, the gate applies to every gate-running agent; setup surfaces this consequence to the owner (doc agents included) so code-specific or expensive gates get their agents named deliberately. The owner's decision criterion re-anchors to names (naming only `code-reviewer` runs an expensive suite on the reviewer's side instead of on every writer commit). Example table reshapes to `Name | Command | Agents` with the code-scoped rows naming their agents explicitly. The command-execution validation flow is untouched.
8. **Pending changeset reconciled in place.** `.changeset/role-scoped-guardrails.md` describes the superseded `level` feature and is unreleased; the docs phase rewords it in place (renaming the slug as appropriate) to describe agent scoping — no second changeset is stacked (95-review precedent: never double-announce). The spec names this obligation; the text is the doc-writer's.
9. **Out of scope (carried or adapted from base).** Assisted mode (no guardrail surface; assisted runs end at phase 3). Cross-iteration gate-result caching. README prose (`README.md:147` stays at phase altitude — a docs-phase touchpoint the spec names for the doc-plan, not a requirement). `CHANGELOG.md` history (immutable). Migration of deployed `.rp.md` files (none exist with guardrails). Exact serialization of the agents field.
