### Analyst grounding: how profiles consume passed context, and the duplication rule (analyst's own read, pre-researcher)

Read directly from the worktree to frame topics; to be confirmed/extended by the researcher.

- **Profiles consume passed context via a placeholder, not by reading `passing.md`.** Agent profiles reference `<artifacts-folder>` as a placeholder filled from the spawn-time `## Conventions` block (e.g. `spec-writer.md:12-13,19`, `code-writer-tdd` reads its task block). Per CLAUDE.md, "agent profiles must not reference any skill file or `.rp.md`; an agent reads only its own profile and its initial prompt." So an agent's knowledge of the worktree = whatever the orchestrator injects into the prompt (the Conventions block) plus the profile's own prose. A new worktree-root anchor would be a new labeled field in that block, consumed the same way `<artifacts-folder>` is.
- **Commit instructions are bare and branch-free.** `spec-writer.md:51` "Commit your output using the commit format"; `code-writer-tdd.md:49` "Commit the code, tests, and inline documentation using the host project's commit format." No profile names a branch or a pre-commit environment check. This is the attachment point for any "confirm branch before committing" behavior.
- **Authoring-rule tension for the "verify before acting" behavior.** CLAUDE.md: "A shared instruction is duplicated into each profile, not extracted to a referenced file." The anchor VALUE is centralized in `passing.md` (one field). But a behavior instruction that lives in profile prose would have to be duplicated across ~18 profiles. Possible alternative that avoids 18-way duplication: carry the behavior instruction as CONTENT the orchestrator injects into the `## Conventions` block at spawn time (it arrives in the prompt, so the profile does not "reference" a file — `passing.md` is the single authoring home, and every agent receives it identically). This is a key decision to make once the wiring is confirmed.
- **`passing.md` `## Conventions` block today carries 4 fields** (`passing.md:5-17`): Artifact folder (all), Commit format (all), Guardrails (5 execution agents), Guardrail scopes to fill (4 plan agents). Only Artifact folder is path-bearing. Adding a worktree-root anchor (all agents) and branch name (committing agents = all) extends this block.

### Researcher: form of the confirm-before-acting behavior, and Requirement 7 isolation

- **"Run command -> compare to a fixed criterion -> stop on mismatch" is already the skill's idiom** (a branch check is a new INSTANCE, not a new mechanism): guardrails exit-code pass/fail (`guardrails.md:3`, acted on at `code-writer-tdd.md:44`, `code-reviewer.md:43`); plan-reviewer "did the command's runner resolve?" (`code-plan-reviewer.md:19`); setup "executed => write; did not => don't" (`setup.md:183-184`); TDD RED "Run them and confirm they fail" (`code-writer-tdd.md:19`, closest analogue); behavior verification "confirm the new behavior actually happens… evidence or reject" (`code-reviewer.md:35`). What does NOT exist anywhere: literal stdout STRING-equality comparison (precedents compare exit codes / executed-or-not / observed behavior).
- **Cheapest guards.** (i) Branch check before commit `git branch --show-current` is near-free (~0.02s) and the skill already has an agent run a git identity command (`load.md:36`). (ii) WRITES: no practical per-write command-check — **the passed worktree-root value IS the guard.** A write is a single Write/Edit call against a path; there is no natural pre-write command/exit-code to compare; a per-write `--show-toplevel` assert would be disproportionate (writes are constant, commits rare) and would catch a bad path only AFTER it is constructed. Robust guard: anchor every absolute path on the passed worktree root; never construct main-anchored paths — paralleling the declarative `claude-code.md:12` rule. => write-side command-check is NOT as practical as the branch check.
- **Style: terse declarative wins; a full procedural compare-and-stop recipe is over-specified.** CLAUDE.md minimalism: "State the instruction, not the reasoning" (`CLAUDE.md:7`), general rule stated once (`:9`), avoid negatives unless necessary (`:10`). House-style models: `claude-code.md:12` (declarative rule naming the command only as a thing to avoid); `load.md:36` (when an exact command IS the instruction, named inline in one clause — the model for a branch check); `setup.md:183` (compare-and-decide compressed into one declarative clause). Proportionate in-idiom form: a one-clause declarative — e.g. "Commit on branch `worktree-<slug>`; confirm you are on it before committing", optionally naming the command inline (`confirm with git branch --show-current`). One load-bearing command in one clause, no surrounding rationale.
- **Requirement 7 isolation confirmed clean and structurally untouchable.** (B1) The `## Conventions` block is ONLY ever attached to spawned-agent prompts, never consumed by the orchestrator (`passing.md:3` "it includes a `## Conventions` block at the top of that agent's initial prompt"; `autonomous-workflow.md:63` attach-on-spawn; `assisted-workflow.md` spawns no agents and has no mention; full-tree grep = exactly 2 hits, definition + attach). (B2) `passing.md` is EXCLUSIVELY an instruction-to-spawn-agents file — every field carries an explicit **Agents:** recipient line (`:5-17`); a new field/defer-pointer is read only in the spawn context and cannot leak into the orchestrator's own main operations. (B3) File separation confirmed: orchestrator main commits live in `setup.md:211,213,214,220` (`.rp.md`/`.gitignore` to project/fork main); lineage SHA reads in `pipeline-versioning.md:62-65,73,86` (`git rev-parse <ref>:…`, reads not edits); neither references `passing.md`. Adding discipline via the injected block touches none of them.
- **Caveats (researcher):** git timings are env-dependent; "no literal string-equality compare exists" is a negative-grep result (high but not absolute confidence).

### Topic: Overall approach — anchor + verify before acting

- **Spec link:** All 7 requirements; the whole feature. Frames how Requirements 1-6 are realized in prose.
- **Decision:** A two-part, correct-by-construction-plus-instruction design, expressed entirely in skill/agent prose (no runtime layer):
  1. **Anchor (what agents are given).** The orchestrator passes two new values into every spawned agent's prompt via the spawn-time `## Conventions` block (`passing.md`): an **absolute worktree-root path** and the **pipeline branch name** (`worktree-<pipeline-slug>`). The orchestrator computes the worktree root fresh with `git rev-parse --show-toplevel` run inside the worktree (NOT the `load.md:36` primitive, which resolves to main); the branch name is the literal `"worktree-" + slug` it already holds. This gives agents a reliable, skill-blessed anchor that does not depend on inferring location from the artifact folder, from git, or from prior knowledge (Requirements 4, 5).
  2. **Verify before acting (agent behavior).** Before editing a file or committing, an agent establishes it is operating against the passed worktree root and branch rather than assuming it by inherited cwd: it anchors absolute paths on the passed worktree root, confirms the current branch matches the passed branch name before committing, and never constructs main-anchored paths or redirects git at the main checkout / its common git dir (Requirements 1, 2, 3, 5, 6 behavior half).
- **Why this shape (rationale):**
  - The spec research established the fix is a NEW "anchor/verify before acting" behavior with zero precedent, and that a correct cwd alone is insufficient (an agent can compute the main root from inside the worktree and write a main-anchored absolute path that silently succeeds). So the design must both *provide* a reliable anchor and *instruct* its use — neither alone closes the gap.
  - The two halves of the goal (wrong-tree edit, wrong-branch commit) are mechanically independent (git's "outside repository" firewall means a wrong-tree edit cannot silently become a trunk commit; a trunk commit needs a separate `-C`/`--git-dir`/`cd`-out action). So the behavior covers both write-time path anchoring AND commit-time branch confirmation as distinct guards.
  - Both anchors are purely additive to a Conventions block the orchestrator already hand-composes; the only genuinely new computation is the worktree-root derivation. This keeps the change small and within the skill's existing structure (Requirement 6, authoring rules).
- **Alternatives considered (and rejected at the approach level):**
  - *Verify-only, no passed anchor* (instruct agents to self-derive worktree root via `git rev-parse --show-toplevel`): rejected — Requirement 4 demands the anchor come from what the agent is GIVEN, not inferred from git; and self-derivation re-introduces the chance of reaching for the wrong primitive.
  - *Anchor-only, no verify behavior* (pass the values, trust inherited cwd): rejected — spec research showed inherited cwd is the status quo that already fails; passing a value an agent is never told to use changes nothing.
  - *Make it a guardrail*: rejected by spec research Q5 (wrong question, wrong timing, wrong optionality, wrong authorship). Recorded as settled; not re-litigated here.
- **Open sub-questions feeding later topics:** where the "verify before acting" behavior instruction physically lives (centralized passed-content vs. duplicated per-profile) — see Topic "Where the verify-before-acting behavior lives".

### Topic: Where the verify-before-acting behavior instruction lives

- **Spec link:** Requirements 1, 2, 3, 5, 6 (the behavior half); plus authoring rules (minimalist, no cross-path duplication, self-contained profiles).
- **Options:**
  1. **Centralized in the passed Conventions block** — both the anchor VALUES and the behavior instruction that operates on them live as content the orchestrator injects into the spawn-time `## Conventions` block (authoring home = `passing.md`), received identically by every agent (commit-confirm line scoped to committing agents); no per-profile edits.
  2. **Duplicated per-profile** — anchor values in the block; the behavior instruction ("anchor absolute paths on the worktree root; confirm branch before commit; never target main") added as standing prose to each of ~18 profiles.
  3. **Hybrid** — values + a short behavior note in the block; profiles additionally restate it.
- **Trade-offs:** Both homes are rules-legitimate (block = part of the initial prompt; not a forbidden external reference). (1) keeps the whole feature in one authoring home, makes the passed values self-describing (a value with no instruction to use it is inert — that is the rejected "anchor-only" failure), mirrors the Guardrails precedent exactly (block carries per-pipeline content + the expectation it be acted on; profile holds minimal static control flow), and avoids ~18-way duplication and its drift risk. Cost: a reader of a single profile does not see the behavior in the profile body — but they DO see it in the spawn prompt, and profiles already depend on the block this way for `<artifacts-folder>` and Guardrails. (2) makes each profile self-narrating in isolation but duplicates a static instruction 18 times (high edit cost, drift risk) and splits the feature across 18 files plus `passing.md`. (3) is the worst of both: duplication AND two homes that can disagree.
- **Decision:** Option 1 — carry both the anchor values and the verify/anchor behavior in the spawn-time `## Conventions` block, authored once in `passing.md`. Scope: a worktree-root anchor field + its "anchor absolute paths here, never the main checkout" instruction -> all agents (matches Artifact folder's "all"); a branch field + "confirm current branch == this before committing, never redirect git at the main checkout / common git dir" instruction -> committing agents (all except the two researchers, paralleling how Guardrails omits non-gate agents). Profiles are left untouched.
- **Rationale:** The anchor values MUST be injected (per-pipeline, resolved at spawn — exactly like Guardrails). The behavior is inseparable from the values it governs, so colocating them keeps the feature coherent and in a single authoring home, honors the minimalist / no-cross-path-duplication rules better than 18-way duplication, and follows the established Guardrails precedent for behavior delivered through the block. The researcher confirmed this violates no authoring rule. The two researchers are excluded from the commit-confirm line because they have no own commit step (their analysts commit); they still receive the worktree-anchor line because they mutate the working tree during experiments (Requirement 3 / spec-research Q4).
- **Consequence for downstream phases:** the change set is concentrated in `passing.md` (new fields + their behavior text and per-agent scoping) plus the per-tool conventions for the worktree-root derivation step; agent profiles need no edits for this behavior. (To be confirmed against the per-tool wiring in the next topic.)

### Topic: Per-tool wiring of the worktree-root derivation and branch (Claude Code and Pi)

- **Spec link:** Requirement 6 (outcomes hold under every supported tool, fitting each tool's worktree/spawn model, prose-only); Requirement 4 (anchor available from what the agent is given).
- **Decision:** Split the change across the generic spawn surface and the per-tool conventions, following the `health-monitoring.md:13` defer precedent:
  - **`passing.md` (generic):** add two block fields — a worktree-root anchor (absolute path; agents: all) and a branch name (`worktree-<pipeline-slug>`; agents: committing agents) — plus the generic instruction that the orchestrator injects them, with the value of the anchor described as "the absolute path of the pipeline's worktree root" and the derivation deferred to the active tool's convention. No tool-specific command appears here (honors `CLAUDE.md:11`).
  - **`claude-code.md` (tool-specific):** the orchestrator obtains the absolute worktree root with `git rev-parse --show-toplevel` run from its own cwd (the worktree) — verified stable.
  - **`pi.md` (tool-specific):** the orchestrator obtains the absolute worktree root from the Pi worktree path it already uses as spawn `cwd` (capture from `/worktree create` if it surfaces the absolute path; otherwise resolve `.pi/worktrees/<folder-name>` against the repo root). For Claude Code the derivation is verified correct and drift-free; for Pi the shape is the same (reuse the absolute worktree path the orchestrator already needs for spawn `cwd`), with a tool-detail to confirm.
- **Branch name** is tool-agnostic: `"worktree-" + slug`, already in hand; stated generically in `passing.md`.

### Topic: Concrete form of the confirm-before-acting behavior

- **Spec link:** Requirement 5 (agent confirms it is acting against the worktree/branch before editing/committing, not relying solely on inherited cwd); Requirement 6 (prose, not runtime); supports Requirements 1, 2, 3.
- **Options:**
  1. **Observable self-check** — before committing, the agent runs `git branch --show-current` and confirms it equals the passed branch; before writing by absolute path, it (optionally) confirms with `git rev-parse --show-toplevel`. Produces evidence; hard stop on mismatch.
  2. **Declarative anchoring** — the agent is instructed to use the passed worktree root for any absolute path and to commit on the passed branch, without a mandated verification command.
  3. **Mixed (asymmetric)** — declarative anchoring for writes (the passed value IS the guard) + a one-clause observable branch confirmation before commit.
- **Trade-offs:** A per-write command-check is impractical and disproportionate (writes are constant, no natural pre-write exit-code, catches a bad path only after construction) — so for writes the passed worktree-root value enforced at path-construction is the only realistic and the strongest available guard. For commits, a branch confirmation is near-free (~0.02s) and is a new instance of the skill's established "run command, compare, stop on mismatch" idiom — high value at trivial cost. A full procedural "run X, capture, compare, if differ stop" recipe is over-specified for the skill's minimalist house style; the idiom is a single declarative clause that may name the command inline (`load.md:36` model).
- **Decision:** Option 3, expressed in the skill's terse declarative house style:
  - **Writes (all agents):** "Anchor every absolute path on the pipeline's worktree root `<worktree-root>`; never construct a path into the main checkout." The passed worktree-root value is the guard; no per-write command.
  - **Commits (committing agents):** "Commit on branch `worktree-<pipeline-slug>`; confirm you are on it before committing" — optionally naming the command inline (`confirm with git branch --show-current`). One load-bearing clause, no rationale, no multi-step recipe.
  - Both are carried in the injected `## Conventions` block (per Topic 2), scoped per Topic 2 (anchor -> all; branch confirm -> committing agents).
- **Rationale:** This matches the asymmetry the research found (write-side has no practical command-check; commit-side has a near-free one), satisfies Requirement 5 (the agent establishes branch correctness rather than assuming it by inheritance, and anchors writes on a given value rather than inferring location), and respects the minimalism/no-rationale authoring rules. The branch confirmation is a new instance of an existing idiom, not a novel mechanism, so it sits naturally in the skill.
- **Note:** literal stdout string-equality comparison has no precedent in the skill (precedents compare exit codes / executed-or-not / observed behavior). The phrasing therefore reads as "confirm you are on branch X" rather than a scripted string-diff, keeping it in-idiom.

### Topic: Requirement 7 — orchestrator main-branch exceptions stay unconstrained

- **Spec link:** Requirement 7 (orchestrator's deliberate main-checkout/main-branch operations remain correct and unconstrained: `.rp.md`/`.gitignore` setup commits to project/fork main; lineage tree-SHA reads from main during versioning).
- **Decision:** No special carve-out is needed; isolation is structural. The new discipline is delivered exclusively through the injected `## Conventions` block, which is attached only to spawned-agent prompts and is never consumed by the orchestrator. `passing.md` is exclusively a spawn-instruction file (every field carries an explicit **Agents:** recipient). The orchestrator's main-branch operations live in separate files (`setup.md`, `pipeline-versioning.md`) that never reference `passing.md`. Therefore adding fields/instructions to `passing.md` cannot reach or constrain the orchestrator's own operations.
- **Rationale:** Requirement 7 is satisfied by construction because the design scopes all new discipline to the spawned-agent passing path, which the spec's actor split already isolates from the orchestrator. No additional prose is required to protect the exceptions; adding any would risk the "special-case restatement of a general rule" the authoring rules forbid.
- **Guidance for the design-doc-writer:** state plainly that the discipline targets spawned agents only and that the orchestrator's main operations are untouched by construction — do NOT add defensive carve-out language into `setup.md`/`pipeline-versioning.md` (it would be an unnecessary restatement).

### Topic: Interfaces and data flow

- **Spec link:** Requirements 4, 5 (what agents are given and how they use it); Requirement 6 (per-tool).
- **Decision (the "interface" is the spawn-time `## Conventions` block shape):**
  - **Two new labeled fields** in the block (the public interface between orchestrator and every spawned agent):
    - `Worktree root:` -> absolute path of the pipeline's worktree root. Agents: all. Carries the write-anchoring instruction.

### Topic: Failure modes and observability (prose-only design)

- **Spec link:** Requirement 6 (prose, no runtime enforcement — the guarantee is behavioral, not mechanical); informs Risks.
- **Decision / analysis:**
  - **Residual failure mode:** because the design is prose (Requirement 6, and Out-of-Scope excludes runtime enforcement), the ultimate failure mode is an agent that disregards the instruction — constructs a main-anchored absolute path anyway, or commits without confirming the branch. The design cannot mechanically prevent this; it minimizes the probability by (a) removing the need to guess the worktree root (a reliable anchor is now given) and (b) adding an explicit confirm-before-commit step where none existed.
  - **What the design strengthens vs. today:** today isolation rests entirely on inherited cwd with zero per-agent restatement; the design adds a given anchor + an explicit confirmation, converting a silent assumption into a stated, checkable precondition.
  - **Detection/observability:** the misplaced-write/commit problem is observable after the fact at the run boundary — the acceptance criteria ("main checkout's working tree shows no agent-made modifications; main branch gained no agent-made commits") are themselves the observable signal. The branch-confirm step makes a wrong-branch commit self-evident to the agent at commit time (it would see a mismatched branch). No new logging surface is introduced (consistent with prose-only scope); the existing health monitor and the orchestrator's post-phase reporting remain the operational surface.
  - **Explicitly out of scope (per spec):** automatic detection, cleanup, or recovery of a stray write/commit already made. The design prevents; it does not undo.

## Risks

<!-- Anything worth flagging to the design-doc-writer and downstream phases. -->

- **Pi worktree-root derivation is unverified against live tooling.** The design assumes the orchestrator can obtain an absolute Pi worktree root (the same value it uses for spawn `cwd`). If `/worktree create` does not surface an absolute path and the folder-name convention is ambiguous, the `pi.md` derivation wording must be pinned at implementation time. Mitigation: the deterministic fallback (resolve `.pi/worktrees/<folder-name>` against the repo root) works once the folder name is confirmed; the design shape is unaffected.

- **Prose-only guarantee is behavioral, not mechanical (inherent, accepted).** Per Requirement 6 and the spec's Out of Scope, there is no runtime layer; a sufficiently errant agent could still construct a main-anchored path or commit without confirming the branch. The design minimizes probability (reliable given anchor + explicit confirm-before-commit) but cannot eliminate it. This is an accepted property of the spec, not a design defect — flagged so the design-doc-writer frames the guarantee honestly (strongest-available prose mechanism, not enforcement).

- **Authoring-rule adherence is a writer-phase concern.** The decision to carry the behavior in the injected `## Conventions` block (not per-profile) and to defer the tool-specific derivation command to `claude-code.md`/`pi.md` is rules-compliant per the researcher, but the exact wording must hold the line on: minimalism (one-clause declarative, no rationale), tool-mention-free `passing.md`, and no special-case restatement of the discipline into `setup.md`/`pipeline-versioning.md`. Flagged for the design-doc-writer and the design-doc-reviewer.
