The plan is strong on coverage, traceability, ordering, and scope discipline. Every spec acceptance criterion and every key design decision maps to a task; the two-part anchor/verify design is faithfully decomposed into one authoring task (`passing.md`) plus two deferred per-tool derivation tasks and a final inspection task; the `## Guardrail scopes` is correctly rendered as `None` (no guardrails defined, no scoped gate passed, so the single `| None | — |` row is the valid rendering and there is no filled command to execute); the `## E2E test plan` is correctly framed as inspection-and-reasoning flows over the resulting prose rather than automated tests; no unit tests are prescribed; no documentation tasks are present; Requirement 7 is preserved by construction with no carve-out language; and the Pi open question is correctly recorded as a deterministic-wording-plus-flagged-assumption rather than a blocker. ## Issues

### Issue 1: Task 2 (and Task 3) placement instruction is unsatisfiable as written — the named anchor content lives entirely inside the `.rp.md` canonical block

**What's wrong:** Task 2 instructs: "Place it where the file's worktree/branch conventions live (near the `## Worktrees` / `## Branch names` content), **not inside the `.rp.md` canonical block**." But in `claude-code.md` (44 lines), the entire `## Worktrees` and `## Branch names` content lives *inside* the fenced canonical `.rp.md` block — the fence opens at line 9 (` ```markdown `) and closes at line 44, which is the last line of the file. There is no prose outside the fence at all; the file body *is* the canonical block. So "near the `## Worktrees` content" and "not inside the `.rp.md` canonical block" point at mutually exclusive locations. A code-writer cannot satisfy both. Task 3 has the same tension in `pi.md`: its `## Pi worktrees` / `## Pi branch names` conventions are inside the fence (lines 8-21, fence 7-41), and the only out-of-fence region is the unrelated `## Setup actions` section (lines 43-65), which is *not* "near the Pi worktree conventions."

**Where in plan:** Task 2 → Changes, second bullet ("Place it where the file's worktree/branch conventions live …"); Task 3 → Changes, third bullet (same shape); and the matching Acceptance bullets in both tasks ("placed as orchestrator-injection guidance, not inside the canonical `.rp.md` block").

**Suggestion:** Resolve the placement explicitly so no decision is left to the writer. The plan's *intent* is clearly correct — this is orchestrator-injection guidance (how the orchestrator derives a value to inject), not `.rp.md` content the orchestrator copies verbatim into a project's convention file — so "not inside the canonical block" is the right constraint and the design (`design-doc.md:33,35`) agrees. The fix is to stop also pointing "near the `## Worktrees` content," which is inside the block, and instead state where the out-of-fence guidance goes: e.g. "Add a short prose paragraph *after* the closing ` ``` ` of the canonical `.rp.md` block (introducing the file's first out-of-fence section in `claude-code.md`), titled/worded so it reads as orchestrator-injection guidance distinct from the `.rp.md` content." For `pi.md`, name the concrete out-of-fence anchor that already exists (after the closing fence, alongside / before `## Setup actions`) rather than "near the Pi worktree conventions."

**Why it matters:** The fence boundary is load-bearing: content inside it becomes `.rp.md` content the orchestrator writes into the project's committed convention file; content outside it is file-level skill prose the orchestrator reads but does not copy. Putting orchestrator-injection guidance inside the `.rp.md` block would change what gets written into every project's `.rp.md` — a real correctness defect, not a style nit. As written, the task forces the code-writer to make exactly this placement/correctness decision mid-task (add a brand-new out-of-fence section vs. bend the "not inside" rule), and two writers could resolve it differently — so the plan is neither unambiguous nor decision-free at this point.

### Issue 2 (minor, fold into the Task 2/3 fix): Acceptance does not pin the fence-boundary outcome

**What's wrong:** Because the placement is contradictory, the Acceptance bullets ("placed as orchestrator-injection guidance, not inside the canonical `.rp.md` block, and is phrased minimally in the file's existing voice") are not independently checkable against the file as structured — there is no existing out-of-fence "voice" near the worktree content for `claude-code.md` to match, since the file has no out-of-fence prose. After fixing Issue 1, make the Acceptance observably testable: it should assert the new text sits **after the closing code fence** (verifiable by line position relative to the fence) and does not appear inside the fenced `.rp.md` block.

**Where in plan:** Task 2 Acceptance, third bullet; Task 3 Acceptance, fourth bullet.

**Suggestion:** Reword to a fence-relative, observable criterion (e.g. "the new statement appears after the closing ` ``` ` of the canonical `.rp.md` block and is absent from inside it").

**Why it matters:** Keeps the per-task acceptance observable and consistent with the corrected placement, so the code-reviewer can verify it without re-deriving intent.
