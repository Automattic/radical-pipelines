# Code Plan Review

## Verdict: rejected

## Summary

The plan is well-grounded: every codebase claim it makes was verified against the worktree and holds — the quoted step texts in `agents/code-reviewer.md` and `agents/doc-reviewer.md`, the step 4 / step 6 wording in both phase reference files, the "Per-phase completion" table rows and the phase 3 "and" join, the SKILL.md Produces cells, the byte-identical omit-empty line in `intent-format.md`, the absence of `summary-format.md` and of run-summary remnants, the changeset machinery (`changedFilePatterns`, package name, `validate-changesets.mjs`, pre-1.0 minor policy), and the delegation of resume/review/fork to the completion predicate by reference. Coverage is complete: every spec requirement and acceptance criterion maps to a task or to a documented structural no-task rationale that mirrors an approved design decision, and every design key decision is executed. Ordering and dependencies are sound. The rejection is for wording-level defects in Tasks 1–3: mandates that restate format content the design confines to `summary-format.md`, an internal contradiction in Task 1 about whether the file content is fixed or flexible, a hard no-other-changes constraint that leaves the reviewer agents internally inconsistent, and mandated prose that violates the host project's writing rules. Each is small, but Tasks 1–3 produce the most load-bearing artifacts of this change, and the phase 4 code-reviewer checks convention compliance against the same rules the plan is mandating violations of.

## Issues

### Issue 1: Tasks 2 and 3 restate format content (the rendered H1s) in the agent files

**What's wrong:** The design's Risks section draws a hard boundary: "The format content lives only in `summary-format.md` and is referenced, never restated, by the phase reference files and the agent files." The rendered H1 naming (`# Code Summary` / `# Docs Summary`) is format content — the design defines it inside "The summary file format" (Interfaces section), and Task 1's template carries it in the purpose line. Yet Task 2 requires the agent file to say the reviewer writes `<artifacts-folder>/4-code/code-summary.md` "(H1 `# Code Summary`)", and its acceptance criteria enforce the parenthetical; Task 3 mirrors this with "(H1 `# Docs Summary`)". The reviewer receives the format in its launch prompt, and the format itself maps each rendered file to its H1, so the agent-file restatement is operationally unnecessary and creates a second copy in the same reading path.
**Where in plan:** Task 2, Changes item 1 and Acceptance bullet 1; Task 3, Changes item 1 and Acceptance bullet 1.
**Suggestion:** Drop the H1 parentheticals from both tasks' Changes and Acceptance. The agent file names only the file path it writes and defers everything else to "the summary format from your launch prompt", which already determines the H1.
**Why it matters:** It contradicts an explicit design constraint the plan elsewhere takes pains to honor, and it gives one format fact three homes (format file, two agent files), exactly the multi-place update surface the single-definition decision exists to prevent.

### Issue 2: Task 1 contradicts itself about whether the file content is fixed or flexible

**What's wrong:** Task 1 opens its Changes with "Create the file with exactly this content:" followed by a complete template, then closes with "The exact prose of the purpose line, the authoring-discipline bullets, and the asset line is implementation wording; the section set, the omit-empty rule, the coverage statement, and the asset clause are fixed above." Both cannot hold: either the content is verbatim-fixed or parts of it are the writer's to phrase. The acceptance criteria only pin the fixed parts, so a writer who copies the template verbatim and a writer who rewrites the purpose line both pass — two code-writers executing this task can produce different files, in the single artifact the whole change hangs on.
**Where in plan:** Task 1, Changes (the "exactly this content" lead-in versus the closing "implementation wording" paragraph).
**Suggestion:** Pick one. The cleaner fix is to make the template authoritative: keep "exactly this content" and delete the implementation-wording sentence (the design's open question delegated the final prose to the plan, and the plan has now written it). Alternatively, present the template as a draft and keep only the load-bearing constraints binding — but then say so in the lead-in.
**Why it matters:** Task 1 is the single source of format truth that every other task references. Ambiguity about what is binding in it propagates to the reviewers' output and invites a phase 4 rejection over wording the plan itself left undecided.

### Issue 3: Tasks 2 and 3 forbid the one edit that keeps the reviewer agents internally consistent

**What's wrong:** Both reviewer agent files open with a gather-context step that enumerates what to read from the launch prompt: step 1 item 1 names the batch metadata (task IDs, base ref, iteration number N), and item 5 separately tells the reviewer to read the guardrails — another launch-prompt-delivered input. The design extends the launch-prompt contract with one new item (the resolved summary format), and the plan's step 4 edit references "the summary format from your launch prompt" — but the plan's constraints ("Do not alter … any other step") and acceptance ("No other step or guidance bullet in the file is changed") bar the code-writer from mentioning the format anywhere in gather-context. The resulting file tells the reviewer what its launch prompt carries, omits one item, then relies on that item mid-step-4.
**Where in plan:** Task 2, Constraints and Acceptance bullet 4; Task 3, Constraints and final Acceptance bullet.
**Suggestion:** Decide it in the plan: either add the summary format to the reviewers' gather-context step (one phrase, mirroring how the guardrails input gets its own line), relaxing the no-other-changes acceptance to permit exactly that edit — or state explicitly that gather-context stays untouched because the format is only consumed on approval, so the prohibition reads as a choice rather than an oversight.
**Why it matters:** The no-other-changes acceptance is checked by the phase 4 reviewer as written; if the inconsistency is later judged worth fixing, the writer will have violated acceptance to fix it, and if not, the agent file ships with its launch-prompt enumeration silently incomplete. Either way the plan, not the writer, should own the call.

### Issue 4: Mandated prose that violates the host project's writing rules

**What's wrong:** Two mandates conflict with the writing rules in the project's `CLAUDE.md`, which the plan itself invokes ("Minimalist wording per `CLAUDE.md`") and which the phase 4 reviewer enforces as convention compliance. First, Tasks 2 and 3 require the agent files to "State that on a **rejected** verdict nothing changes — rejected iterations produce no summary", and their acceptance enforces it — but the instruction "on an **approved** verdict only" already covers the rejected case, and the rules say a general rule is stated once, with no special-case restatements, and negative phrasing only where strictly necessary. Second, Tasks 4 and 5 require the phase files to state the format is included on every launch "because the verdict is not known in advance" — design rationale, not operation; the orchestrator launches the reviewer once per batch with one prompt and has no decision point where the clause changes behavior. The design left this exact wording open as an implementation choice.
**Where in plan:** Task 2, Changes item 1 and Acceptance bullet 1; Task 3, Changes item 1 and Acceptance bullet 1; Task 4, Changes item 2 and Acceptance bullet 2; Task 5, Changes item 2 and Acceptance bullet 2.
**Suggestion:** In Tasks 2/3, drop the mandated rejected-verdict sentence and let "on an approved verdict only" carry it. In Tasks 4/5, mandate only the operational content — include the resolved content of `summary-format.md` in the reviewer launch prompt alongside the existing items — and drop the "because the verdict is not known in advance" rationale clause from the required wording and acceptance.
**Why it matters:** The acceptance criteria force the writer to commit prose the host project's own rules reject, setting up avoidable churn when the phase 4 reviewer checks convention compliance against `CLAUDE.md`.
