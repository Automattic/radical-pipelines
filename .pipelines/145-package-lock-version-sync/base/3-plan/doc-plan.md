# Doc Plan: Keep package-lock version in sync with package.json automatically

## Overview

This feature adds `package-lock.json` to the set of files the repository keeps version-synchronized with the source-of-truth `package.json`, makes the release version step patch the lockfile's two version fields automatically, corrects the current live drift, and adds a read-only CI drift check (`scripts/check-version-sync.mjs`) wired into the existing `changeset` job. Several existing documentation surfaces describe the version-sync behavior, the release process, and the CI gates, and they currently omit the lockfile and the new check — they will drift out of sync with the shipped code unless updated. This plan updates four prose surfaces so they reflect the new behavior: the root `README.md` "Changelog and versioning" section (the single-source-of-truth file list, the sync-step description, and "Cutting a version"), `CONTRIBUTING.md` (versioning policy, the changeset-gate description that now runs a third check, the release-relevant-path classification of `package-lock.json`, and the release-process file list), the `scripts/sync-version.mjs` module/JSDoc narrative (which describes "every secondary manifest" and must now account for the lockfile's two-field handling), and a verify-only pass over `.changeset/README.md`. The doc-writer fills wording in phase 5 by reading the shipped scripts, workflow, and the corrected lockfile. Final wording is not prescribed here.

**Changeset (release metadata) — out of scope for this doc plan, flagged for the orchestrator.** A changeset `.md` file is release metadata consumed by the `changeset version` tooling to drive a version bump and changelog entry, not documentation that conveys the feature to a reader, so it is not a documentation surface this plan owns. It is also a release/bump-type judgment that belongs to the human/orchestrator at PR time, not to a doc-writer reading the shipped code. Note for the orchestrator: this plan's tasks edit `README.md`, which is a release-relevant path under `.changeset/config.json`'s `changedFilePatterns`, so the `changeset` gate's presence check (`npx changeset status`) will require a changeset on the resulting PR even though the code changes alone (`scripts/**`, `.github/**`, `package-lock.json`) are not release-relevant; `CONTRIBUTING.md`'s "Adding a changeset" / "Empty changesets" sections describe how to satisfy the gate and how to choose the bump type. Authoring it is left to the release process, not to a doc task here.

**Out of scope (no task).** `CHANGELOG.md` is a generated, historical record (its existing entry describes the prior release verbatim); it is not hand-edited and is regenerated by the release flow, so no task touches it. The `website/` assets carry no version-sync, release, or lockfile documentation, so they are not a surface here.
