# Doc Plan Review

## Verdict: rejected

## Summary

The plan is strong and close to complete: its four tasks cover the right four prose surfaces (README "Changelog and versioning", `CONTRIBUTING.md`'s versioning/gate/changeset-relevance/release/escape-hatch content, the `scripts/sync-version.mjs` in-file docstring/JSDoc, and a verify-only pass over `.changeset/README.md`), every task traces to concrete spec requirements/acceptance criteria and code tasks, the per-task acceptance criteria are reader-outcome-framed and drift-resistant, and the audiences are concrete. The out-of-scope reasoning is sound: `CHANGELOG.md` is a generated historical record (verified — its entries describe prior releases verbatim), `website/` carries no version-sync/release/lockfile prose (verified), and the changeset `.md` is release metadata for the bump tooling rather than reader-facing documentation. The "editing README.md makes the PR changeset-required" note to the orchestrator is correct (`README.md` is in `.changeset/config.json`'s `changedFilePatterns`), so the changeset is a sound scope deferral, not a silently dropped surface. The `## Guardrail scopes` section renders the valid `None` form: `.rp.md` defines no `Guardrails` convention, so no gate exists, no scope was passed, and there is no command to run — this matches `code-plan.md`. The plan is rejected for a single concrete missed surface inside a file it already owns (Task 2 / `CONTRIBUTING.md`): the "Running tests and checks locally" section names the test suite by its individual test files and will drift once the new check's test ships, but no task touches it.

## Issues

### Issue 1: `CONTRIBUTING.md` "Running tests and checks locally" will drift but no task covers it

**What's wrong:** `CONTRIBUTING.md` lines 25-26 describe `npm test` as running "the `node --test 'scripts/test/**/*.test.mjs'` suite (the `sync-version` and changeset-validator tests)." That parenthetical enumerates the suite by its two current test files. Code plan Task 2 adds a third test file, `scripts/test/check-version-sync.test.mjs` (paired with the new `scripts/check-version-sync.mjs` drift check). After phase 4 the parenthetical will name two of three test groups and be factually incomplete — a live drift surface in a contributor-facing doc. The doc plan's Task 2 owns `CONTRIBUTING.md` and explicitly enumerates the sections it will touch ("Versioning policy", "The changeset gate (CI)", "When a changeset is required", "Release process", "Manual release escape hatch"), but that enumeration omits the "Running tests and checks locally" section, so a doc-writer following the plan would leave the stale two-test parenthetical untouched.

**Where in plan:** Task 2, the "Sections / scope" list. The affected source is `CONTRIBUTING.md` lines 25-26 ("This runs the `node --test 'scripts/test/**/*.test.mjs'` suite (the `sync-version` and changeset-validator tests).").

**Suggestion:** Add a sub-bullet to Task 2's "Sections / scope" naming the "Running tests and checks locally" section, framed at the what/where level: the suite enumeration should account for the newly added drift-check test group alongside the existing sync-version and changeset-validator tests, with the exact phrasing left to the doc-writer to verify against the shipped `scripts/test/` files in phase 5. Add a matching acceptance bullet (e.g. "the test-suite description in 'Running tests and checks locally' reflects that the suite now also covers the version-drift check's tests, verified against the shipped test files"). Keep it drift-resistant — do not hard-code the test file name or count in the acceptance criterion.

**Why it matters:** This is exactly the class of surface the plan exists to keep in sync: prose that names the affected behavior and will read incorrectly after the code ships. It lives in a file the plan already edits, so the omission is a coverage gap, not a scope question. Left unaddressed, `CONTRIBUTING.md` would still tell contributors the suite is only the sync-version and changeset-validator tests after a third tested script lands.
