# Design Doc Review

## Verdict: rejected

## Summary

This is a strong, well-researched design. Every spec requirement and acceptance criterion traces to a decision or component, the key decisions each name credible alternatives with trade-offs, and the load-bearing technical claims hold up against the real codebase: I confirmed that `JSON.parse → JSON.stringify(obj, null, 2) + "\n"` round-trips `package-lock.json` byte-for-byte (154336 == 154336), that the structured two-field patch changes exactly lines 3 and 9, that the `@changesets/logger` dependency at line 721 stays `0.1.1` (validating the structured-not-regex requirement), that `release:version` and `release.yml` wire the sync as described, and that the `changeset-gate.yml` job-level `if` bot-PR exemption exists as claimed. The two flagged risks ("blocks merge" is repo config; "commits all working-tree changes" is documented action behavior) are appropriate and correctly scoped. The design stays at architecture/decision altitude and addresses failure modes and observability. It is being rejected for one concrete internal inconsistency: the modified `syncVersion` will now always touch `package-lock.json`, which contradicts the doc's explicit claim that the existing `plugin.json`/`syncManifestVersion` tests are "preserved" untouched, and leaves the `syncVersion` contract undefined for the case where no lockfile is present. A secondary clarity note is included.

## Issues

### Issue 1: The "preserving already-passing tests" claim conflicts with the new always-on lockfile patch, and the `syncVersion` contract for an absent lockfile is unspecified

**What's wrong:** The design says `syncVersion()` will now "call both the existing per-manifest path (unchanged) and the new lockfile path," and asserts that "the existing `TARGET_MANIFESTS` / `syncManifestVersion` behavior for `plugin.json` is left untouched, **preserving its already-passing tests**." But the existing tests do not call `syncManifestVersion` in isolation — every one of them drives `syncVersion({ repoRoot: root })` against the shared `makeFixture`, which builds only `package.json` plus the target manifests and **no `package-lock.json`** (`scripts/test/sync-version.test.mjs:23-44`). If the modified `syncVersion` unconditionally patches `package-lock.json` from `repoRoot` (as the design states, since the lockfile is deliberately not in `TARGET_MANIFESTS`), then `readFileSync(join(repoRoot, "package-lock.json"))` throws `ENOENT` and the existing `syncVersion` tests ("copies the root version...", "reports which targets changed", "is idempotent") all break. So the claim that those tests are preserved untouched is not achievable as stated — the shared fixture must change, or `syncVersion` must tolerate a missing lockfile. The doc does not specify which, and these are materially different function contracts: one makes the lockfile mandatory (and forces a `makeFixture` change), the other makes lockfile patching conditional on the file's presence (a robustness behavior never described). Two implementers reading this design would not build the same `syncVersion`.

**Where in design doc:** "Components → `scripts/sync-version.mjs` (modified)" (the "preserving its already-passing tests" sentence) and "Interfaces and Data Flow → `scripts/sync-version.mjs` interfaces" (the `syncLockfileVersion` / `syncVersion` contracts); also "Failure Modes and Observability → Sync," which describes a missing/malformed lockfile only for the CLI-against-the-real-repo case, not for the `syncVersion` function contract.

**Suggestion:** Decide and state the `syncVersion` contract when `package-lock.json` is absent — either (a) the lockfile is mandatory and the shared test fixture is updated to always include one (then drop or reword the "preserving already-passing tests" claim, since the shared fixture and existing tests do change), or (b) lockfile patching is skipped when the file is absent (state this as the defined behavior, not left implicit). Make the doc's testing claim consistent with whichever contract is chosen.

**Why it matters:** This is the single most-touched function in the change, and its behavior on the existing fixture is the difference between the current test suite passing or throwing. An unspecified contract here is exactly the kind of ambiguity that produces divergent implementations and a surprising test break in the next phase.

### Issue 2: The drift check's behavior on a structurally malformed lockfile (`.packages` or `.packages[""]` missing) is asserted only loosely

**What's wrong:** `checkVersionSync`/`main()` must read `package-lock.json` `.packages[""].version`. The doc's Failure Modes section says "a missing or malformed file among the three → throws, exits non-zero." That covers an unparseable file, but the more likely structural case — a lockfile that parses fine yet lacks `.packages` or the `""` self-entry — would surface as a `TypeError` on `undefined`, not a clear version-mismatch message. The doc treats "malformed JSON" and "structurally unexpected JSON" as one bucket without saying so. For the *sync* path this is addressed (the doc explicitly assumes `.packages[""]` always exists in this `lockfileVersion: 3` repo and notes the risk), but the read-only *check* path's reliance on the same assumption is not stated.

**Where in design doc:** "Failure Modes and Observability → Drift check"; "Risks and Open Questions → `packages[""]` presence assumption" (which is framed around the patch, not the check).

**Suggestion:** State explicitly that the drift check also relies on the `.packages[""]` self-entry being present (the same `lockfileVersion: 3` assumption already documented for the sync), so a structurally malformed lockfile throws rather than passing falsely — or note that this is acceptable and intentional for both paths. One sentence reconciles the two.

**Why it matters:** It is a minor gap, but the check is the regression guard; being explicit that both the sync and the check share the `.packages[""]`-present invariant keeps the failure contract unambiguous and prevents a later implementer from "defensively" making the check silently skip an unexpected lockfile shape (which would defeat the guard).
