# Design doc research — Normalize issue content into the standard intent format

Iterative Q&A between `design-doc-analyst` (questions, decisions) and `design-doc-researcher` (evidence). Input: the approved spec at `base/1-spec/spec.md` (plus `base/1-spec/spec-research.md` and `base/0-intent/intent.md`).

The deliverable of this pipeline is edits to the orchestrator skill's reference docs. The design questions below settle *how those doc/process changes are structured*: where each behavior is anchored, how the rewritten text is organized, and the exact shape of the shared artifacts (provenance header, convention capabilities).

## Q&A record

### Q1 — Anchor location of the full-picture read, and the step structure of `create-pipeline.md`

Spec requirement 4 leaves open whether the full-picture read (body + comments + one-level references + external URLs) is anchored at `work-on-an-issue.md` step 1 ("capture its content") and/or `create-pipeline.md` step 4; requirement 3 demands the step-4 rewrite keep the authoring discipline separable from the fetch mechanics (the `review-pipeline.md:37` "step-4 pattern" cross-reference must keep resolving). Asked: (1) full text and all paths through `work-on-an-issue.md` step 1, and whether a heavy read there taxes the resume path; (2) all callers of `create-pipeline.md` and whether it assumes content in hand vs fetches on its own; (3) every cross-reference to a numbered `create-pipeline.md` step (renumbering cost); (4) the house idiom for multi-part steps.

**A1 (researcher, verified with file:line evidence):**

1. `work-on-an-issue.md:11-15` step 1 runs on **every** "work on an issue" entry; "capture its content" is a lightweight verify-exists-plus-grab-body. After step 1, step 2 branches: match exists → resume/fork/review/merge/close (`:28-41`), where the captured *content* is never used to author an intent (intent already on disk; fork copies, `fork-pipeline.md:36-44`; resume re-attaches); no match → `create-pipeline.md` (`:43`), the only path that authors a new intent. A full-picture read anchored in step 1 would be wasted, expensive work on every resume/fork/review/close invocation — the majority once a pipeline exists.
2. `create-pipeline.md` has exactly one caller: `work-on-an-issue.md:43`. (`review-pipeline.md:37` references the "step-4 pattern" as an authoring pattern, not a call.) Step 4 already performs its **own** Issues-convention tracker access — the asset download at `create-pipeline.md:26` ("using the access mechanism captured by the **Issues** convention") — so it does not lean on step 1's capture; there is in-file precedent for step 4 reaching the tracker itself.
3. Repo-wide, exactly **one** reference to a numbered `create-pipeline.md` step exists: `review-pipeline.md:37` "the `create-pipeline.md` step-4 pattern". No reference to step 5 or any other number. A literal split of step 4 into gather/synthesize/confirm steps would make "step 4" name the *gather* step — exactly the part of the pattern the review path does **not** borrow (requirement 3), so a split would also force a rewrite of `review-pipeline.md:37`.
4. House style: numbered `### N. <Title>` steps whose body is intro prose + bullets, with **bold lead-in labels** on bullets for sub-parts (`review-pipeline.md:36-42`, `manage-issues.md:37-42`). No sub-numbered steps (no "4a/4b") exist anywhere. `manage-issues.md:48-50` packs a whole draft→confirm→write sequence into one titled step — direct precedent for a single-step gate.

**Decision D-Q1:**

- **The full-picture read is anchored in `create-pipeline.md` step 4 only.** `work-on-an-issue.md` step 1 is left unchanged (its lightweight "verify and capture its content" remains correct for all paths). Rationale: sole-caller topology, the read only pays off on the creation path, and step 4 already does its own Issues-convention access (asset download) — the new read extends an existing in-step mechanic instead of taxing every resume/fork/review entry.
- **Step 4 stays a single numbered step** ("Generate the initial intent"), restructured internally with the house idiom (intro prose + bold-lead-in bullets/paragraphs for gather → synthesize → passthrough/confirm), mirroring `manage-issues.md` step 5's one-step draft→confirm→write precedent. Commit stays step 5; zero renumbering; `review-pipeline.md:37`'s "step-4 pattern" keeps pointing at the whole authoring unit, with the authoring discipline kept textually separable from the issue-fetch mechanics inside the step (requirement 3).

### Q2 — Issues-convention capability extension in `conventions/setup.md`, and the web-access mechanism for external URLs

Spec requirement 7 extends the Issues convention's required capabilities (comments + cross-references); requirement 4 routes external URLs through "the orchestrator's own web-access mechanism (a tool binding in the consuming project, not skill text)". Asked: (1) exact current capability text + sibling conventions' phrasing pattern; (2) `.rp.md` binding impact and whether any setup-time capability validation exists; (3) any existing skill-text precedent for web fetching or other unbound "use your own tooling" phrasing; (4) stale-copy check for the capability list.

**A2 (researcher, verified):**

1. `setup.md:62-66`: the Issues convention's capability statement is the single clause "the orchestrator needs **a way to read, comment on, and update them**" (`:64`), followed by the "Ask the owner which issue tracker… and how to access it" line. Sibling conventions (Artifact folder `:46-52`, Worktrees `:68-72`, Branch names `:74-80`) all use a one/two-sentence "what + why" statement; Issues is the only one with a verb list. House-consistent edit: extend the verb list in place; leave the "Ask the owner" line untouched. **Hard constraint:** `AGENTS.md:12` — skill text must never name a tracker (no GitHub/Linear, no `#NN` notation) outside the existing ask-the-owner parenthetical; the new clause must say "cross-references" tracker-agnostically (the spec's own AC at spec.md:71 phrases it this way).
2. This project's `.rp.md:7-24` binds Issues as a generic access mechanism ("accessed via the `gh` CLI" / "via the Linear MCP") with no per-capability enumeration — generic bindings already satisfy the extended capabilities. No capability-level validation exists anywhere: `load.md:24-29` checks only convention *presence*; `setup.md:186` warns about missing answers. The extension is purely additive — no new setup gate, no `.rp.md` migration for existing consumers.
3. **No web-fetch phrasing exists anywhere in skill text** (grep: only "network errors" as a failure category, and git-remote URLs). `create-pipeline.md` step 4 will be the first skill text to mention fetching an external URL. The only adjacent precedent is the asset-download line (`create-pipeline.md:26`), which routes through the Issues convention — but the spec explicitly forbids extending that convention to web pages. The natural phrasing is an unbound orchestrator capability ("fetch external URLs with the orchestrator's own web-access tooling"), parallel to how the skill never names `gh`: skill text says *what*, the consuming project's runtime supplies *how*. The two channels (tracker reads via Issues convention; external URLs via web access) must stay textually distinct in step 4.
4. The capability verb list exists in exactly one place (`setup.md:64`). `load.md:16`'s table row ("Where to find the project issues and how to create/modify them") is a loose one-line summary, not a capability enumeration — flagged as an optional consistency touch, not load-bearing. README/website contain no capability list.

**Decision D-Q2:**

- **`setup.md:64` gets a single in-place extension of the existing verb-list clause** so the convention covers: reading the issue body, reading all of its comments, commenting, updating, and following in-tracker cross-references. No new sub-structure, no new convention, the "Ask the owner" line unchanged. Wording stays tracker-agnostic per `AGENTS.md:12`.
- **`load.md` is not edited.** Its `:16` row is a purpose summary, not a capability list; "where to find the project issues and how to create/modify them" remains true. Keeping the diff minimal outweighs a cosmetic sync.
- **No setup validation, no `.rp.md` changes.** The design doc states explicitly that the extension is additive: generic bindings ("via <tool>") already satisfy it, and no capability-validation step exists or is added.
- **External-URL fetching is phrased in `create-pipeline.md` step 4 as the orchestrator's own web-access tooling** — tool-agnostic, unbound, first mention in skill text, kept as a separate channel from the Issues convention (which is never used for arbitrary web pages). No web-access convention is created.

### Q3 — Provenance header: standard format, placement, scoping

Spec requirement 14: a short standard provenance header (blockquote naming the source issue + self-containment statement) documented in `intent-format.md`, added in both passthrough and synthesis, scoped to base intents created from an issue (not issue bodies, not review intents). Asked: (1) the existing ad-hoc variants in `.pipelines/` artifacts and a tracker-agnostic template; (2) placement options inside `intent-format.md`; (3) the established terms for the scoping sentence; (4) whether anything parses `intent.md`'s leading lines, and where existing artifacts put the blockquote.

**A3 (researcher, verified):**

1. Exactly two base intents exist. Both place a **two-line blockquote after the H1, before `## Goal`**. The #71 intent is the short form ("> Source: GitHub issue [#71](url). / > This file is self-contained; agents do not need to open the issue."). The #95 intent is a long form that (a) says "self-contained **prompt**" — stale pre-rename terminology (PR #109 renamed prompt→intent) — and (b) leaks the "open for later phases / not settled requirements" disclaimer into the header, which belongs to the body's Assumptions discipline (`intent-format.md:13,22`). The #71 short form is the clean model. A tracker-agnostic template (artifacts may render tracker-specific text; skill text may not, per `AGENTS.md:12`): `> Source: <issue reference and link, per the Issues convention>.` + `> This file is self-contained; agents do not need to open the source issue.`
2. Placement: a scoped bullet inside the shared "Schema and rendering" H2 would be read by the issue-body (`manage-issues.md`) and review-intent (`review-pipeline.md:37`) consumers — inviting exactly the mis-application requirement 14 warns against. Documenting only in `create-pipeline.md` is ruled out by the spec's own text. Best fit: **a new third H2 in `intent-format.md` whose heading carries the scope** (e.g. "## Provenance header (intents created from an issue)"), plus a one-line pointer in `create-pipeline.md` step 4 ("prepend the provenance header per `intent-format.md`" in both branches) — consistent with how step 4 already delegates format to `intent-format.md` instead of restating it.
3. Established terms (from `intent-format.md:3`): **tracker issue body / base intent / review intent**. "Base intent" is the established term for the create-from-issue intent (`review-pipeline.md:37` "the base intent is orchestrator-authored"); every base intent is created from an issue (sole-caller topology, Q1), so "base intent created from an issue" has no second case. The Origin mirror-statement to echo: `review-pipeline.md:38-39` "MANDATORY for reviews and unique to them — issue and base intents have none."
4. Nothing parses `intent.md`'s leading lines: phase 1 embeds it verbatim as opaque prose (`assisted-phases/1 - spec.md:36`), tree-SHA rooting hashes the whole folder content-blind (`pipeline-versioning.md:82,87`), forks copy byte-for-byte. Blockquote-after-H1 (matching both artifacts) is safe; the H1 stays line 1.

**Decision D-Q3:**

- **Canonical header = the #71 short form, generalized:** a two-line blockquote placed **after the H1 title, before the first H2** — line 1 `> Source:` with the issue reference and link (concrete form supplied by the project's Issues binding; skill text stays tracker-agnostic), line 2 the self-containment assertion ("This file is self-contained; agents do not need to open the source issue."). The header carries no other content — in particular not the Assumptions-are-open disclaimer (#95's long form is the anti-pattern).
- **Documented as a new third H2 in `intent-format.md`** with the scope in the heading ("Provenance header (intents created from an issue)") and an explicit scoping statement using the file's own terms: applies only to a base intent created from an issue by the create-pipeline flow; not added to tracker issue bodies (`manage-issues.md`); not added to review intents, which keep their mandatory **Origin** section (`review-pipeline.md`).
- **`create-pipeline.md` step 4 carries only a one-line pointer** to apply the header (in both passthrough and synthesis branches), never duplicating the template.

### Q4 — Internal structure of the rewritten `create-pipeline.md` step 4

The core design artifact: the outline of the new step-4 text covering reqs 4–6 and 8–13. Asked: (1) ordering sanity-check (gather-first vs any constraint); (2) house branch-phrasing and the exact gate/self-containment sentences to mirror; (3) how to keep the authoring discipline textually separable from fetch mechanics (req 3) and which current sentence the "step-4 pattern" reference leans on; (4) whether `intent-format.md`'s shared sections need edits for reqs 6/10; (5) a retention map of current step-4 lines.

**A4 (researcher, verified):**

1. No text constrains ordering other than gather-first. The three passthrough predicates (canonical format / no comments / no refs-attachments, spec.md:43-45) can only be evaluated after reading the body and enumerating comments/references, and req 13's "synthesis would be a no-op" test presupposes the read. Passthrough does not skip the gather — it degenerates to "read body + verify the comment/reference/attachment sets are empty"; only the full path does the heavier substance-read. One linear order covers both.
2. House branch idiom is bold-lead-in "**If X** … / **If not-X** / Otherwise" (work-on-an-issue.md:28,43; fork-pipeline.md:42-43; resume-pipeline.md:15-16). Gate to mirror, `manage-issues.md:48-50` verbatim: "Render the issue in the format above (omitting empty sections) and show it to the owner. Do not write to the tracker until the owner explicitly approves. On approval, create the new issue … through the **Issues** convention." Self-containment sentence to mirror, `review-pipeline.md:39`: "…carries the substance of the request … PLUS a convenience link, so a later phase reading only this review intent understands what prompted it without following the link."
3. The "step-4 pattern" reference (`review-pipeline.md:37`) leans on exactly one current sentence — `create-pipeline.md:25` "Adapt the issue content into the intent …, following the schema and authoring discipline in `intent-format.md`" — and borrows none of the fetch/asset/self-containment bullets. If the rewrite keeps a standalone authoring-discipline sentence retaining the phrase "following the schema and authoring discipline in `intent-format.md`", with fetch mechanics in separate preceding bullets, req 3 holds with **zero edits to `review-pipeline.md`**.
4. No edit to `intent-format.md`'s "Schema and rendering" or "Authoring discipline" is needed. Req 10 is already covered by `intent-format.md:13` ("labeled open…") and `:22` ("recorded under Assumptions, not as a requirement") — step 4 points at them and adds the one new clause ("including proposals from participants other than the owner"; precedence resolves at the gate). Req 6's unresolved-reference note is just content the existing schema admits — Context (`intent-format.md:12` "links, prior decisions, motivation only the owner holds") is the natural home; step-4 text can say "noted visibly in the draft" without pinning a section. The only `intent-format.md` change in the whole design remains the provenance-header H2 (Q3).
5. Retention map for `create-pipeline.md:23-27`: `:23` (folder mechanics intro) survives unchanged; `:25` expands into the new structure (fetch bullets, branch, standalone authoring sentence, conversation-synthesis clause, gate, header pointer) while preserving its sentence's role; `:26` (asset download) survives with attachments wired into the passthrough test as a disqualifier; `:27` (self-containment rule) survives — it is the principle the new fold-substance-in bullet implements.

**Decision D-Q4 — the step-4 design (the heart of the change):**

Step 4 keeps its heading and intro (`:23`), then proceeds in one linear order, expressed in house idiom (intro prose + bold-lead-in bullets, "**If …** / **Otherwise**" branch):

1. **Gather** — read the issue body and enumerate its comments, in-tracker cross-references, external links, and attachments through the **Issues** convention.
2. **Passthrough test** — **If** the body is already in the canonical format of `intent-format.md` (structural check, and synthesis would be a no-op) **and** there are no comments, no cross-references, no external links, and no attachments: write the body to `intent.md` unchanged apart from the provenance header (per `intent-format.md`), with no owner confirmation, and go to step 5.
3. **Otherwise, the full path:**
   - *Fetch mechanics (issue-specific, not part of the borrowed pattern):* read all comments and the substance of in-tracker cross-references through the **Issues** convention; fetch external URLs with the orchestrator's own web access; follow references **one level only** (deeper exploration belongs to phase 1); a reference that cannot be read is noted visibly in the draft (e.g. under Context), never silently dropped.
   - *Authoring discipline (standalone sentence — the pattern `review-pipeline.md` borrows):* synthesize the gathered material into the intent, **following the schema and authoring discipline in `intent-format.md`** — fold the substance of comments, references, and pages into `intent.md` with links kept only as convenience pointers (mirroring the Origin substance-plus-link wording); capture the latest agreed state of the conversation; record unsettled proposals — including from participants other than the owner — as open Assumptions.
   - *Assets:* current `:26` bullet unchanged.
   - *Confirmation gate (mirrors `manage-issues.md` step 5):* render the draft intent (with the provenance header) and show it to the owner, surfacing any unresolved references; do **not** write `intent.md` until the owner explicitly approves; on approval, write the file. No approval artifact is produced (the gate is transient, spec req 12).
4. Self-containment rule (`:27`) stays as the closing principle. Step 5 (Commit) is unchanged.

### Q5 — Cross-file coherence sweep (final)

Asked: (1) does `manage-issues.md:14`'s "The issue body _is_ the phase-0 intent" need a clarifying touch, and can anything in that file leak the provenance header into issue bodies; (2) does any SKILL.md/README/work-on-an-issue prose go stale; (3) do the phase docs constrain `intent.md`'s shape/provenance; (4) is a changeset required; (5) any other echo of the current step-4 wording.

**A5 (researcher, verified):**

1. `manage-issues.md:14`: "The issue body _is_ the phase-0 intent — when the pipeline is created, the orchestrator turns the issue into `base/0-intent/intent.md`. Author the issue using the shared schema, rendering rules, and authoring discipline in `intent-format.md`." The "turns the issue into" clause already carries the one-time-transform meaning, and spec req 2 (spec.md:20) explicitly adopts that reading; the file is outside the spec's declared edit set (spec.md:9 names only `create-pipeline.md`, `conventions/setup.md`, `intent-format.md`). An optional one-word softening of "_is_" exists but is not spec-mandated. Header-leakage check: `manage-issues.md` points only at the *shared* schema/discipline (`:14`, `:18`); nothing says "apply everything in `intent-format.md`", so the scope-named provenance H2 (Q3) is sufficient to keep the header out of issue bodies.
2. SKILL.md/README/work-on-an-issue: all phase-0 descriptions are generic ("The input", SKILL.md:35; "The initial idea or request", README:27; "an input rather than an agent-produced artifact", README:112 — still true, the new flow is orchestrator-driven and spawns no agent). `work-on-an-issue.md` never claims `intent.md` is written "from the issue body". Nothing goes stale; no edits.
3. Phase docs treat `intent.md` as an opaque input ("copied verbatim", `assisted-phases/1 - spec.md:36`); nothing constrains its shape or provenance. The header even reinforces the self-containment message to phase-1 readers. No edits.
4. **A changeset is required.** `skills/**` is a release-relevant path (CONTRIBUTING.md:63-66); the Changeset Gate CI fails without one. This is a backwards-compatible behavior addition → **`minor`** for `@automattic/radical-pipelines` (per CONTRIBUTING.md:87-115; precedent `.changeset/pipeline-reviews.md`). Not the empty/`none` case — the change alters orchestrator behavior.
5. "Adapt the issue content" and the "Generate the initial intent" heading appear nowhere else; no script/CI parses skill prose. No other stale references.

**Decision D-Q5:**

- **`manage-issues.md` is not edited.** Spec req 2 supplies the authoritative one-time-transform interpretation, the "turns the issue into" clause already reads that way, and the spec deliberately scoped the edit set. (The optional "_is_" softening is recorded here as considered and declined — out of the spec's edit set; adding it would be scope creep.)
- **No edits to SKILL.md, README, `work-on-an-issue.md`, `review-pipeline.md`, `load.md`, or any phase doc.**
- **The deliverable set is four files:** the three skill edits plus a new `minor` changeset for `@automattic/radical-pipelines` summarizing the behavior change (full-picture read, canonical synthesis, owner confirmation, provenance header, passthrough fast-path).
