# Spec: Normalize issue content into the standard intent format when creating a pipeline

## Overview

Radical Pipelines turns an issue into a pipeline's phase-0 artifact, `base/0-intent/intent.md`, during the pipeline-creation flow (`create-pipeline.md` step 4, reached only via `work-on-an-issue.md` step 2). Today that step says only "Adapt the issue content into the intent … following the schema and authoring discipline in `intent-format.md`." In practice this reads the issue **body** and nothing else: there is no instruction to read the issue's comments, to follow its in-tracker cross-references (`#NN`, linked PRs) or external links, and no owner-confirmation step before the file is written and committed. As a result the shape of `intent.md` varies with the shape of the originating issue, and a free-form third-party discussion produces a different kind of intent than a project-authored, already-canonical issue.

This change makes the creation flow synthesize the **full picture** of the issue — its body, all its comments, the substance of its linked and external references, and the participants' conversation — into the single canonical intent format (`Title / Goal / Constraints / Context / Assumptions`). Every downstream phase then starts from the same canonical, self-contained input regardless of how the originating issue was written. Because synthesis is a judgment-laden transformation, the orchestrator shows the rendered draft to the run owner and writes `intent.md` only on explicit approval — the synthesis is never committed silently. A narrow fast-path preserves today's zero-friction behavior for the one case where no transformation is possible: an issue already written in the canonical format with no comments and no references maps through unchanged, with no confirmation.

This is a change to the **Radical Pipelines orchestrator skill itself**. The primary edit is to `create-pipeline.md` step 4; supporting touch-points are the **Issues** convention's required capabilities in `conventions/setup.md` (which must now cover reading comments and following in-tracker cross-references) and `intent-format.md` (to document the provenance header, see requirement 14). The full-picture read may be anchored at `work-on-an-issue.md` step 1 ("capture its content") and/or `create-pipeline.md` step 4 — which file carries it is a design-phase choice (requirement 4 states the behavior without fixing its location). The tracker-side reads are phrased against the tracker-agnostic **Issues** convention throughout — never against a specific tracker tool such as `gh`, whose binding lives in a consuming project's `.rp.md`; external-URL fetching uses the orchestrator's separate web-access binding (requirement 4).

The orchestrator decisions D1–D4 raised during requirements research are settled in this spec as follows (each is justified inline at the relevant requirement): D1 — bare in-tracker cross-refs (`#NN`) **do** disqualify passthrough (requirement 13). D2 — the provenance header is documented and added in **both** passthrough and synthesis cases (requirement 14). D3 — owner confirmation is a **transient Q&A gate**, not a new approval artifact (requirement 12). D4 — the confirmation gate is **not** extended to review-intent authoring (Out of Scope).

## Requirements

Each requirement below is an observable outcome of the pipeline-creation flow. The things that change are the orchestrator skill's reference documents; the behaviors they must produce are stated here. Throughout, "the owner" is the single human the orchestrator interacts with in the `work-on-an-issue` session (the run owner), who may differ from the issue's author or its commenters.

### Scope of the change

1. The normalization-and-confirmation behavior applies to the **pipeline-creation flow only**: `create-pipeline.md` step 4 ("Generate the initial intent"), reached via `work-on-an-issue.md` step 2 when no existing pipeline matches the issue. This is the sole path that synthesizes an issue into an intent.
2. The source issue is **never modified** by this flow. The synthesized `intent.md` may legitimately diverge from the issue body (it folds in comments, references, and conversation that the body alone does not carry); the normalized result is not written back to the tracker. (`manage-issues.md`'s "the issue body _is_ the phase-0 intent" describes a one-time issue→intent transform at creation, not a maintained equality.)
3. The rewrite of `create-pipeline.md` step 4 keeps the **general canonical-format authoring discipline separable** from the issue-specific fetch mechanics (read body + comments + references). `review-pipeline.md` step 5 references "the `create-pipeline.md` step-4 pattern" for authoring a review intent from a different source; that cross-reference must continue to resolve coherently — the shared discipline it borrows is "synthesize into the canonical format and follow `intent-format.md`," not "fetch the issue's comments and links."

### Gathering the full picture

4. Before writing `intent.md`, the orchestrator reads the full picture of the issue. The tracker-side reads go through the **Issues** convention (tracker-agnostic — the skill text names the convention, never a specific tracker tool): the issue **body**, **all of the issue's comments** (the participants' conversation), and the **substance of in-tracker cross-references** (`#NN`, linked PRs/issues). **External URLs** linked from the body or comments are fetched through the orchestrator's own web-access mechanism (a tool binding in the consuming project, not skill text — the **Issues** convention is the tracker abstraction and is not extended to cover arbitrary web pages, per requirement 7).
5. Reference-following is **bounded to one level**: the orchestrator follows references reachable directly from the issue body and its comments, and reads their substance, but does **not** recurse into those references' own onward links. Deeper exploration is the job of phase 1 (research), not phase 0. (No prior depth guidance exists in the skill; this bound is established here.)
6. A reference that cannot be read (unreachable, deleted, private, or auth-walled) is **not silently dropped**. The orchestrator notes the unresolved reference explicitly in the synthesized intent (visible, not omitted) and surfaces it to the owner during the confirmation gate (requirement 11), so a failed fetch is something the owner sees before the intent is committed. (No prior fetch-failure precedent exists in the skill; this behavior is established here.)
7. The **Issues** convention's required capabilities (defined in `conventions/setup.md`) are extended so the convention covers reading an issue's **comments** and following its **cross-references**, not only reading/commenting/updating the issue body. The requirement stays phrased against the convention; how a given tracker satisfies it is the consuming project's binding.

### Synthesis into the canonical format

8. `intent.md` is always written in the **canonical intent format** of `intent-format.md`: an H1 title; a required `## Goal`; optional `## Constraints`, `## Context`, and `## Assumptions / directions to explore`; empty sections omitted (no `N/A` placeholders). The flow follows that file's authoring discipline — capture, don't converge; lead with the goal; no requirements/design/implementation; reflect the owner's hypotheses back as **open** Assumptions. This holds regardless of the originating issue's shape.
9. The **substance** of comments, linked references, and external pages is folded **into** `intent.md` so the phase-0 folder stays self-contained (`create-pipeline.md`'s self-containment rule): a later phase reading only `intent.md` understands the issue without reaching back to the tracker or following any link. Links are retained only as **convenience pointers** alongside the substance, mirroring the self-contained "substance plus a convenience link" pattern that `review-pipeline.md`'s Origin section already uses. No sidecar snapshot files are created for textual references. Binary assets (screenshots and other attachments) continue to be downloaded into `base/0-intent/` and referenced by relative path, exactly as `create-pipeline.md` already specifies.
10. **Conversation synthesis.** When the issue's body and comments come from multiple participants or evolve over the thread, the synthesized intent captures the **latest agreed state** of the discussion. Unresolved disagreements and proposals that are not settled — including proposals from participants other than the run owner — are recorded as **open Assumptions** (per `intent-format.md`'s "reflect hypotheses back as open" / "owner proposals about _how_ are recorded under Assumptions"), not as Goal or Constraints. The run owner is the single decision-maker: the confirmation gate (requirement 11) is where "whose statement wins" is resolved, so no participant-precedence rule is invented.

### Owner confirmation before writing

11. **Confirmation gate.** Whenever passthrough (requirement 13) does **not** apply — i.e., the issue carries any comment, any in-tracker cross-reference, or any external link — the orchestrator renders the proposed `intent.md` and shows it to the owner, and does **not** write the file until the owner **explicitly approves**. The gate and passthrough are exact complements: reading and weighing comments and references is itself a judgment-laden transformation, so the gate fires even in the edge case where the resulting text happens to match the body verbatim (e.g., a canonical issue plus one `"thanks!"` comment). This mirrors the "Draft, confirm, write" pattern of `manage-issues.md` step 5 and the confirm-before-write discipline of `conventions/setup.md`. On approval, the orchestrator writes `intent.md` and proceeds to commit (`create-pipeline.md` step 5). The synthesis is never committed silently. This gate is always feasible: pipeline creation runs interactively in the `work-on-an-issue` session **before** the workflow mode (autonomous vs assisted) is even chosen, so the owner is present at intent-write time on every creation path; there is no unattended issue→intent path.
12. The confirmation is a **transient interactive gate**, not a recorded artifact. Owner approval is given in the session and gates the write; no separate approval file (such as the assisted workflow's `<artifact>-review-approved.md`) is produced for the intent. (The intent requires only the gate.)

### Passthrough fast-path

13. **Passthrough.** When the issue is **already in the canonical format** AND has **no comments** AND has **no linked or external references** (including no in-tracker cross-references such as `#NN` or linked PRs), it maps to `intent.md` with its body content **unchanged** and **no owner confirmation** is required.
    - "Already in the canonical format" means the structural heading criterion of `intent-format.md` is met (H1 title; `## Goal` present; only the allowed optional H2s; nothing else) **and** no transformation would change the content — the structural check is the necessary signal, but the test is that synthesis would be a no-op.
    - Any comment, any in-tracker cross-reference, any external link, or any embedded binary attachment (screenshot/asset) disqualifies passthrough and routes the issue through the full read → synthesize → confirm path of requirements 4–11. An embedded attachment counts as an external reference: passthrough requires the body content to map through unchanged, but an attachment is downloaded into `base/0-intent/` and its reference rewritten to a relative path (requirement 9), which is a body-content change — so a "canonical issue + screenshot, no comments, no other links" goes through the full confirm path, not passthrough. The rationale is self-containment: an issue that says "Depends on #95" is not self-contained until #95's substance is pulled in, so it must be synthesized and confirmed, not passed through. (Research shows passthrough is the minority case in practice; canonical project-authored issues commonly carry comments and cross-references.)

### Provenance header

14. **Provenance header.** A short, standard provenance header (a blockquote that names the source issue and states that the file is self-contained — agents need not open the issue) is documented as part of the intent flow and added to `intent.md` in **both** the passthrough and the synthesis cases. In the passthrough case, "unchanged" therefore means the body content is unchanged **apart from** this standard provenance header (the source issue body does not itself contain a `> Source:` line). The header is **scoped to intents created from an issue** by the create-pipeline flow (both passthrough and synthesis); it is **not** applied to issue bodies authored via `manage-issues.md`, and **review intents are unaffected** — they keep their mandatory **Origin** section as their provenance mechanism (`review-pipeline.md` step 5). Because `intent-format.md` is the shared format for issue bodies, base intents, and review intents alike, documenting the header there must state this scoping so a `> Source:` line is not erroneously added to issue bodies or review intents. The header is documented in shared intent-flow guidance (`intent-format.md`) so it is applied consistently rather than authored ad hoc per pipeline.

## Out of Scope

The following are explicitly out of scope for this change and recorded here so later phases do not silently expand it:

- **Forks.** A forked pipeline inherits its intent by **literal filesystem copy** of the parent's `base/0-intent` (`fork-pipeline.md` step 5); it never re-synthesizes from the issue and never invokes `create-pipeline.md`. A fork is a byte-copy of an intent already normalized and confirmed on the original create path, so it needs no separate handling here.
- **Review intents.** Review-pipeline authoring (`review-pipeline.md` step 5) produces a **review** intent from a **different source** — the review request (a PR comment, a PR review, the owner's change description) — captured in its mandatory **Origin** section, not from the issue. The original issue and `base/0-intent` are never rewritten by a review. The issue→intent fetch/synthesis/confirmation logic of this change does not apply to review intents; the confirmation gate of requirement 11 is **not** extended to review-intent authoring (decision D4). The only constraint on the review path is requirement 3 (its reference to "the `create-pipeline.md` step-4 pattern" must keep resolving).
- **Write-back / tracker sync.** Writing the normalized intent back to the issue, or otherwise keeping the issue body and `intent.md` in sync after creation, is out of scope (the issue is left untouched per requirement 2).
- **Recursive reference exploration.** Following references beyond one level (a linked issue's own links, and so on) is out of scope for phase 0 (requirement 5); deeper exploration belongs to phase 1 research.
- **Multi-participant precedence rules.** Inventing a formal rule for whose statement wins when issue participants disagree is out of scope; conflicts are carried as open Assumptions and resolved by the owner at the confirmation gate (requirement 10).
- **Snapshotting textual references as sidecar files.** Textual references are folded into `intent.md` as substance; only binary assets continue to be downloaded as files (requirement 9).

## Acceptance Criteria

These criteria drive the tests. They are expressed against the pipeline-creation flow (`work-on-an-issue.md` step 2 → `create-pipeline.md` step 4). "Shows the owner" / "confirmation" refers to the interactive channel the orchestrator uses with the run owner.

### Gathering

- Given an issue whose body references its comments, an in-tracker cross-reference (`#NN` or a linked PR), and an external URL, when a pipeline is created from it, then the orchestrator reads the issue body, all of its comments, and the substance of those references before drafting `intent.md`.
- Given a referenced item that itself links onward to a further reference, when the issue is synthesized, then the orchestrator reads the first-level reference's substance but does not follow its onward link (one-level bound).
- Given an issue with a reference that cannot be read (deleted, private, or unreachable), when the issue is synthesized, then the unresolved reference is noted explicitly in the drafted `intent.md` and surfaced to the owner at the confirmation gate, rather than being silently omitted.
- Given the Issues convention's required-capabilities definition in `conventions/setup.md`, when the change is in place, then the convention's stated capabilities include reading an issue's comments and following its cross-references, phrased against the convention rather than any specific tracker tool.

### Synthesis

- Given any originating issue (canonical or free-form, with or without comments/references), when synthesis produces `intent.md`, then `intent.md` is in the canonical format of `intent-format.md` (H1 title; `## Goal` present; only the allowed optional H2s; empty sections omitted) and follows its capture-don't-converge authoring discipline.
- Given an issue whose substance lives partly in its comments and linked references, when `intent.md` is written, then a reader of `intent.md` alone understands the issue without opening the tracker or following any link; links appear only as convenience pointers beside their substance, and no sidecar snapshot files are created for textual references.
- Given an issue carrying screenshots or other binary attachments, when the pipeline is created, then those assets are downloaded into `base/0-intent/` and referenced by relative path (unchanged from today's behavior), and the path-rewrite disqualifies passthrough so the issue goes through the full confirm path.
- Given an issue thread with multiple participants and an unsettled proposal from someone other than the run owner, when `intent.md` is synthesized, then the latest agreed state is captured as Goal/Constraints/Context and the unsettled proposal is recorded as an open Assumption, not as a requirement.

### Confirmation gate

- Given an issue for which passthrough does not apply (it carries any comment, in-tracker cross-reference, external link, or binary attachment) — including the edge case where the synthesized text matches the body verbatim — when `intent.md` is ready to write, then the orchestrator shows the rendered draft to the owner and does not write the file until the owner explicitly approves; on approval the file is written and then committed.
- Given that pipeline creation runs in the interactive `work-on-an-issue` session before the workflow mode is chosen, when the synthesis requires confirmation, then the gate is reached with the owner present (no unattended issue→intent write occurs), regardless of which mode is later selected.
- Given an owner approves the synthesized intent, when the file is written, then no separate intent-approval artifact file is produced — the approval is a transient gate.

### Passthrough fast-path

- Given an issue already in the canonical format with no comments and no linked or external references, when a pipeline is created from it, then `intent.md` is written with the body content unchanged apart from the standard provenance header, and the owner is not asked to confirm.
- Given an otherwise-canonical issue that carries at least one comment, one in-tracker cross-reference (`#NN` or a linked PR), or one external link, when a pipeline is created from it, then passthrough does not apply: the issue is read, synthesized, and confirmed per the full path.

### Provenance, scope, and non-write-back

- Given either a passthrough or a synthesized intent, when `intent.md` is written, then it carries the standard provenance header naming the source issue and stating the file is self-contained.
- Given any pipeline creation from an issue, when `intent.md` has been written, then the source issue in the tracker is unchanged (no normalized version is written back), even when `intent.md` diverges from the issue body.
- Given the review-pipeline authoring flow that references "the `create-pipeline.md` step-4 pattern," when `create-pipeline.md` step 4 is rewritten, then that reference still resolves to a coherent shared authoring discipline (canonical format + `intent-format.md`), and the review path's confirmation behavior is unchanged by this change.
- Given a fork of an existing pipeline, when the fork is created, then its intent is inherited by copy and is not re-synthesized from the issue (the new flow does not run for forks).
