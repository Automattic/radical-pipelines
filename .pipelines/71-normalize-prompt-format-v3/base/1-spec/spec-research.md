2. Quote the "Draft, confirm, write" pattern from `manage-issues.md` step 5 as precedent for how owner confirmation is phrased in this skill.
3. Are there other owner-confirmation precedents in the skill (e.g. `assisted-workflow.md`, `review-pipeline.md`, conventions) worth mirroring?

**A2 —**

1. **Creation is always interactive.** Pipeline creation (phase 0) happens *before* the workflow mode is even chosen: `work-on-an-issue.md:43` (step 2) runs `create-pipeline.md`; `work-on-an-issue.md:45-52` (step 3) only then asks the owner to pick autonomous vs assisted; `work-on-an-issue.md:54-61` (step 4) dispatches the chosen workflow. So for a new pipeline, `intent.md` is always written by the orchestrator in the interactive `work-on-an-issue` session with the owner present — autonomous mode only governs phases 1–5. Corroborating: `work-on-an-issue.md:49` ("**Autonomous** — agents drive each phase end-to-end without further questions…" — phase 0 is orchestrator-driven, not agent-driven) and `assisted-workflow.md:18` maps "0 - Intent" as "Already in place". 2. **"Draft, confirm, write" precedent:** `manage-issues.md:48-50` — "Render the issue in the format above (omitting empty sections) and show it to the owner. **Do not write to the tracker until the owner explicitly approves.** On approval, create the new issue — or apply the modification — through the **Issues** convention." Caveat flagged: `create-pipeline.md` is also reachable from `fork-pipeline.md` and the review flow — not yet verified whether those invoke the intent-write step in a non-interactive context (→ Q3). Open decision flagged: transient confirmation gate vs recorded approval artifact.

### Q3 — Fork and review paths: does normalization apply there?

The intent scopes #71 to "when a pipeline is created from an issue". But `create-pipeline.md` is reportedly also reachable from `fork-pipeline.md` and the review flow.

1. Verify: do `fork-pipeline.md` and `review-pipeline.md` actually invoke `create-pipeline.md` (or its step 4 intent-write)? Quote the invocation and describe where their intent comes from (e.g. a review intent synthesized from review findings rather than an issue).
2. If they do, is the owner interactively present at that point, or can it happen unattended?
3. Based on what you find: does the issue→intent normalization/confirmation logic in #71 naturally apply to those paths, or are their intents produced by a different mechanism that #71 should leave alone?

**A3 —** (researcher answered proactively; messages crossed)

1. **Fork does NOT touch the issue.** `fork-pipeline.md:36-38` (step 5 "Seed the inherited phase folders"): the fork *copies* `base/0-intent` (up to the inherited phase) from the parent pipeline. Even forking "from scratch" at `0-intent` (`fork-pipeline.md:14`) inherits the intent **by copy** — never re-synthesized from the issue. Fork never invokes `create-pipeline.md`. Out of scope for #71.
2. **Review re-authors a *review* intent from a different source.** `review-pipeline.md:36-42` (step 5): the review authors a new intent at `review-N-…/0-intent/intent.md` "the same way the base intent is orchestrator-authored (**the `create-pipeline.md` step-4 pattern**), following the schema and authoring discipline in `intent-format.md`" — but its **source is the review request** (PR comment, PR review, owner's change description), not the issue (`review-pipeline.md:39` Origin section; `:42` "The original issue and `base/0-intent` are never rewritten").
3. **Takeaways:** (a) #71's normalization-from-issue + confirmation belongs specifically in `create-pipeline.md` step 4, reached only via `work-on-an-issue.md:43`; forks are out of scope; reviews are a separate authoring path. (b) **Coupling risk:** `review-pipeline.md:37` references "the `create-pipeline.md` step-4 pattern" — if #71 rewrites step 4 to add issue-comment/link fetching + confirmation, that cross-reference must not silently break (the synthesis-and-confirm discipline may transfer, but the "fetch all issue comments + linked refs" mechanic does not map 1:1 to a review's Origin source). Conservative read consistent with the intent: keep #71 in the issue→intent create path and ensure the review's pattern-reference remains coherent.

There is **no unattended path that re-synthesizes an issue into an intent** — fork copies, review authors from a different source, and the only issue→intent synthesis is the interactive create path (per A2).

Additional detail from the researcher's full answer: the fork copy is a literal filesystem copy (`fork-pipeline.md:42` — `cp -r <parent>/base/<phase> …`), so a fork's intent is a byte-copy of an intent already produced (and, post-#71, already normalized + confirmed) on the original create path. The owner *is* interactively present on both fork (`fork-pipeline.md:9-16` step-1 Q&A) and review (`review-pipeline.md:21` — confirm review count/boundaries with the owner before creating any run folder; mode/dispatch deferred until after the review intent is authored, `review-pipeline.md:48-50`), so extending confirmation to reviews would be *feasible* — but the #71 intent doesn't ask for it; conservative default is no. Researcher's recommendation: when rewriting step 4, keep the general synthesis-and-canonical-format discipline cleanly separable from the issue-specific "fetch body + comments + links" mechanic, so `review-pipeline.md:37`'s pattern reference still resolves sanely; add an explicit out-of-scope note for forks and review intents.

### Q4 — Passthrough condition mechanics and the provenance header

The intent's second constraint: when the issue "is already written in the canonical format and has no comments and no linked or external references, it maps to `intent.md` unchanged and no owner confirmation is needed."

1. **Detecting "already canonical":** per `intent-format.md`, what would the detection criterion be in practice — headings exactly matching Goal / Constraints / Context / Assumptions (with optional sections omitted)? Is there any wording elsewhere in the skill (e.g. `manage-issues.md`, which authors issues in this format) that defines or labels the canonical shape, so the spec can reference it rather than invent a new definition?
2. **Tension in "no linked or external references":** the canonical Context section is *defined* as "links, prior decisions, motivation only the owner holds" (`intent-format.md:12`). So a canonical, project-authored issue will often contain links — which per the constraint would disqualify passthrough and force fetch+synthesis+confirmation. Check real project-authored issues (e.g. recent issues in this repo created via `manage-issues.md`, and existing pipelines' `intent.md` files under `.pipelines/`) — how common are links in otherwise-canonical issues? Report what you find so the spec can decide whether the constraint as literally written matches reality or needs the owner's "links present → fetch + confirm" reading made explicit.
3. **Provenance header:** the current pipeline's `intent.md` begins with "> Source: GitHub issue [#71](…). This file is self-contained; agents do not need to open the issue." Is that blockquote a documented convention anywhere (intent-format.md, create-pipeline.md, conventions), or an ad-hoc practice? If ad-hoc, note it — the "maps unchanged" requirement needs to define whether the provenance line is added even in the passthrough case (strictly "unchanged" vs "unchanged + provenance header").

**A4 —**

1. **No named "canonical shape" definition exists anywhere in the skill** — the spec will be defining the criterion. De-facto definition is `intent-format.md:9-15`: H1 title; `## Goal` always present (`:10`, the only required section); `## Constraints`, `## Context`, `## Assumptions / directions to explore` optional (`:11-13`), omitted when empty (`:7`); "A vague idea yields just a Title and a Goal. That is a complete, valid intent" (`:15`). `manage-issues.md:14` authors issues in this exact format ("The issue body _is_ the phase-0 intent") and sorts input into the same buckets (`:38-42`) but defines no detector. Practical criterion: H1 + `## Goal` + only the allowed optional H2s, nothing else — **but this structural check is necessary, not sufficient** (headings could match while the prose violates the authoring discipline, `intent-format.md:17-22`). "Already canonical" should mean *no transformation would change it*, with the heading-set as the structural signal.
2. **Links data (30 most recent repo issues scanned):** canonical format is the norm (e.g. #99, #100, #89, #87, #91, #75, #73, #94, #80 all Goal+Context+Assumptions). But the "no comments / no links" precondition is frequently NOT met on perfectly canonical issues: comments are routine (#113, #101, #72, #66, #70, #78); bare in-tracker cross-refs (`#NN`, `PR #92`) are pervasive in Context (#101: "Depends on #95… Supersedes #66… PR #92"; #103: `#11 #60 #89`; #113: `#112 #51` + many `.md` refs); external http URLs appear too (#86, #83 → other repos — exactly the "external references" case). #71 itself has no links and no comments → would qualify for passthrough; the passthrough case is real but the *minority* shape. **Open decisions the spec must nail down:** (a) does a bare in-tracker cross-ref count as a "linked reference" disqualifying passthrough? Researcher's read: yes — the broad interpretation (any link/comment ⇒ fetch + confirm) serves #71's self-containment purpose, since "Depends on #95" is not self-contained until #95's substance is pulled in; (b) literally, *any* comment disqualifies passthrough regardless of content (even "thanks!").
3. **Provenance header is ad-hoc, not documented.** Grep across the skill: only "self-contained" mentions are `create-pipeline.md:27` (the concept) and `review-pipeline.md:39` (the review **Origin** section — reviews *do* have a specified provenance mechanism; "issue and base intents have none"). `intent-format.md` says nothing about a Source line. The blockquote is established but inconsistent practice (#95's base intent uses a longer variant than #71's). **Conflict to resolve:** the source issue body won't contain a "> Source:" line, so "maps unchanged" and "always carries provenance" are in direct conflict. Researcher's recommendation: document the provenance header as part of the intent format, added in BOTH passthrough and synthesis cases — "unchanged" then means "body content unchanged apart from the standard provenance header". This touches `intent-format.md`, which is shared by issue bodies, base intents, and review intents — a real authoring decision.

### Q5 — Fetch mechanics and self-containment of the synthesized intent

The intent: "the issue body, all of its comments, any linked or external references, and the participants' conversation" are read and synthesized; the phase-0 folder must stay self-contained (`create-pipeline.md:27`).

1. **What lands in the 0-intent folder:** today only screenshots/assets are downloaded (`create-pipeline.md:26`). When the synthesis pulls in linked issues/PRs/external pages, is there any existing precedent in the skill (or in existing `.pipelines/` artifacts) for *snapshotting* fetched reference content as files vs *summarizing its substance into* `intent.md`? How do existing base intents under `.pipelines/` handle referenced material?
2. **Depth and recursion:** any existing guidance (skill or conventions) limiting how far to follow references (a linked issue's own links, etc.)? If none, say so — the spec will need a bound (e.g. one level: only references reachable directly from the issue body/comments).
3. **Failure handling:** any precedent for unreachable/auth-walled links (fetch fails, paywalled, private repo)? E.g. does the skill say anything about web access or degraded operation anywhere (conventions, health-monitoring)?
4. **Tooling fit:** with this project's Issues convention (`gh` CLI), confirm comments and cross-referenced issues/PRs are fetchable (`gh issue view --json comments`, `gh pr view`, etc.) — and note the skill must stay tracker-agnostic (the Issues convention abstracts the tracker), so the requirement should be phrased against the convention, not `gh`.

**A5 —**

1. **Summarize-into-intent, not snapshot.** The only download-to-folder precedent is binary assets (`create-pipeline.md:26`). For textual references the established pattern is inline self-containment: `review-pipeline.md:39` — the Origin section "carries the substance of the request (a direct quote or faithful paraphrase…) PLUS a convenience link, so a later phase reading only this review intent understands what prompted it without following the link." Verified in existing artifacts: `.pipelines/95-pipeline-reviews/base/0-intent/intent.md` carries substance in prose with `#58` as a convenience ref; `review-1-adopt-intent-rename/0-intent/intent.md` pulls PR #109's substance into Context plus the URL; **no** `0-intent/` folder contains snapshotted pages or linked-issue dumps. Likely requirement: fold the substance of comments/linked refs/external pages into `intent.md`; links kept as convenience pointers; binary assets continue per `create-pipeline.md:26`. Snapshotting sidecar files would be a new mechanism — only flag if warranted.
2. **No depth/recursion guidance exists anywhere.** The spec must introduce a bound. Researcher's recommendation: one level — references reachable directly from the issue body and its comments; fetch their substance; do NOT recurse into those references' own links (real chains like #95→#58→… fan out quickly). Deeper exploration is phase-1+ research's job.
3. **No fetch-failure precedent.** `health-monitoring.md:21-22`/`setup.md:102` cover provider/network failures of the *run* (and the monitor isn't even active during creation — it's autonomous-only, `autonomous-workflow.md:35`, while creation is pre-dispatch per A2). Nothing covers "a reference link in the issue 404s". Spec must define degraded behavior; researcher's suggestion: note unresolved references explicitly in the synthesized intent (visible, not silently dropped) and surface them in the owner-confirmation step — a failed fetch is exactly what the owner should see before commit.
4. **Tracker-agnosticism is mandatory.** The whole `reference/` tree goes through the **Issues** convention abstraction, never `gh` directly (`work-on-an-issue.md:13`, `create-pipeline.md:26`, `manage-issues.md:6`; convention defined generically in `setup.md:62-66`). Requirements must be phrased against the Issues convention; the `gh` binding lives in this project's `.rp.md:9-12`. **Gap:** `setup.md:64` says the orchestrator needs to "read, comment on, and update" issues — it does not mention reading *comments* or following *cross-references*; if #71 requires those, the Issues convention's required capabilities may need expanding (a `setup.md` touch-point). Feasibility verified live for this project: `gh issue view <n> --json comments` works (#101 has 1 comment); `gh pr view 92` resolves cross-refs; external URLs via web fetch (github.com links via `gh` per the user's tooling rules — a project/tool binding, not skill text).

### Q6 — Conversation-weighing semantics, the "owner" role, and divergence from the issue

Last substantive area. The intent says the synthesis reads "the participants' conversation"; and after synthesis, `intent.md` will legitimately diverge from the issue body.

1. **Who is "the owner"?** Where does the skill define the owner role (conventions, SKILL.md, workflows)? Is there anything about multi-participant issues — e.g. whose statements carry decision weight when issue comments come from several people, or when a later comment supersedes the body?
2. **Any guidance on conversation synthesis** anywhere in the skill (e.g. treating later comments as superseding earlier ones, capturing disagreements as open questions/assumptions)? If none, say so — the spec will define it (likely: synthesize the latest agreed state; record unresolved disagreements and non-owner proposals as open Assumptions, per `intent-format.md:23`'s "reflect hypotheses back as open").
3. **Divergence safety:** does anything in the skill assume `intent.md` equals the issue body after creation — e.g. `manage-issues.md:14`'s "The issue body _is_ the phase-0 intent", `resume-pipeline.md`, `pipeline-versioning.md`, or any sync/write-back expectation? In particular: when the synthesis transforms the source, is there any existing expectation that the normalized version is written *back* to the issue, or does the issue stay untouched? (The intent doesn't ask for write-back; verify nothing else implies it.)

**A6 —**

1. **The "owner" is defined only implicitly** — the single human the orchestrator talks to: `SKILL.md:14` ("Humans only talk with you, never with the other agents"), `SKILL.md:19` (owner chooses mode), `:29` (owner reviews and explicitly approves artifacts before commit), `:50` (owner starts sessions). The intent format frames the owner as the holder of intent (`intent-format.md:11-13,19`). **No guidance exists on multi-participant issues** (grep: nothing on participant precedence, author-vs-owner, superseding comments). Subtlety the spec should name: the run owner may not be the issue author or a commenter. Researcher's framing: synthesize all participants' conversation as *input/evidence*; the **run owner is the single decision-maker who confirms** the result — the confirmation gate resolves "whose statements win" without inventing a precedence rule.
2. **No conversation-synthesis guidance exists.** The reusable principle is "reflect hypotheses back as open": `intent-format.md:13` (Assumptions "labeled open so later research may confirm or overturn them"), `:22` ("Anything the owner proposes about _how_ or about the current state is recorded under Assumptions, not as a requirement"); echoed at `manage-issues.md:44-46` ("never silently substitute a different goal"). The proposed rule — synthesize the latest agreed state; record unresolved disagreements and non-owner proposals as open Assumptions — is the natural extension, anchored to `intent-format.md:13,22`.
3. **No write-back expectation; divergence is structurally safe.** `manage-issues.md:14` ("The issue body _is_ the phase-0 intent — … the orchestrator turns the issue into `base/0-intent/intent.md`") is directional (issue → intent at creation), not a maintained equality — "turns" already implies a transform. No sync/write-back instruction exists anywhere; `create-pipeline.md:27` points the other way (don't reach back to the issue). `resume-pipeline.md` never re-reads the issue (only `:42` "Return to `work-on-an-issue.md`"); `pipeline-versioning.md:87,113` roots the version tree on the *committed intent's tree SHA* with the issue as an abstract content-less root — divergence is assumed by the data model. `review-pipeline.md:42`: "The original issue and `base/0-intent` are never rewritten." `.rp.md:27-37` Linear-mirror obligations cover labels/status/assignee, not body content. **Spec should state explicitly that the issue is left untouched** (no normalized version written back), preempting any misreading of `manage-issues.md:14`.

## Requirements summary (for the spec writer)

Synthesized from Q1–Q6. "Researcher-recommended default" marks judgment calls grounded in existing skill discipline but not literally settled by the intent; the spec writer should adopt them unless the owner overrides.

### Scope

- **R1.** The change lives in the pipeline-creation flow: `create-pipeline.md` step 4 ("Generate the initial intent"), reached via `work-on-an-issue.md:43`. Touch-points that may also need edits: `work-on-an-issue.md` step 1 ("capture its content" — A1), the Issues convention's required capabilities in `setup.md:62-66` (must cover reading comments and following cross-references — A5.4), and `intent-format.md` if the provenance header is documented (A4.3).
- **R2.** Out of scope: forks (intent inherited by literal copy, `fork-pipeline.md:36-42` — A3) and review intents (different source: the review request, `review-pipeline.md:39` — A3). The rewrite of step 4 must keep the general canonical-format authoring discipline separable from the issue-specific fetch mechanics so `review-pipeline.md:37`'s reference to "the `create-pipeline.md` step-4 pattern" still resolves coherently (A3).
- **R3.** No write-back: the source issue is never modified by this flow; the synthesized `intent.md` may diverge from the issue body (A6.3).

### Gathering

- **R4.** Before writing `intent.md`, the orchestrator reads the full picture via the **Issues** convention (tracker-agnostic phrasing — never `gh` in skill text, A5.4): issue body, all comments, and the substance of linked references — both in-tracker cross-refs (`#NN`, PRs) and external URLs (A4.2: broad reading recommended; bare cross-refs count as linked references).
- **R5.** Reference depth is bounded to one level: references reachable directly from the issue body and its comments; no recursion into those references' own links (researcher-recommended default; no existing guidance — A5.2). Deeper exploration belongs to phase 1+.
- **R6.** Unreachable/auth-walled references are not silently dropped: note them explicitly in the synthesized intent and surface them during owner confirmation (researcher-recommended default; no existing precedent — A5.3).

### Synthesis

- **R7.** `intent.md` is always written in the canonical format of `intent-format.md` (H1 title; `## Goal` required; optional `## Constraints`, `## Context`, `## Assumptions / directions to explore`; empty sections omitted), following its authoring discipline (capture-don't-converge, hypotheses labeled open).
- **R8.** Substance of comments/linked refs/external pages is folded *into* `intent.md` (self-containment per `create-pipeline.md:27`); links remain as convenience pointers only — mirroring `review-pipeline.md:39`'s Origin pattern. No sidecar snapshot files for textual references; binary assets continue to be downloaded per `create-pipeline.md:26` (A5.1).
- **R9.** Conversation synthesis: capture the latest agreed state of the thread; record unresolved disagreements and non-owner proposals as open Assumptions (anchored to `intent-format.md:13,22` — A6.2). The run owner — who may differ from the issue's participants — is the single decision-maker, via the confirmation gate (A6.1).

### Confirmation gate

- **R10.** Whenever the synthesis transforms the source in any way, the orchestrator shows the rendered draft to the owner and does not write `intent.md` until the owner explicitly approves — mirroring the "Draft, confirm, write" pattern (`manage-issues.md:48-50`; file-write analog `setup.md:179-186`). This is always feasible: creation runs interactively in `work-on-an-issue` *before* mode selection; there is no unattended issue→intent path (A2, A3).
- **R11.** Passthrough fast-path: when the issue is already canonical AND has no comments AND no linked or external references, it maps to `intent.md` unchanged with no confirmation. "Already canonical" = the structural heading criterion (necessary signal) plus "no transformation would change it" (A4.1). Data shows passthrough is the minority case — canonical issues commonly carry comments and cross-refs (A4.2).

### Open decisions (for the spec writer to settle, with recommended defaults)

- **D1.** Do bare in-tracker cross-refs (`#NN`) disqualify passthrough? Recommended: yes — any link or comment ⇒ fetch + synthesize + confirm; "Depends on #95" is not self-contained (A4.2a). Literally per the intent, any comment disqualifies regardless of content (A4.2b).
- **D2.** Provenance header ("> Source: …"): currently ad-hoc and inconsistent across existing base intents. Recommended: document it as part of the flow (or `intent-format.md`) and add it in BOTH passthrough and synthesis cases; "unchanged" then means "body content unchanged apart from the standard provenance header" (A4.3). Touches `intent-format.md`, which is shared with issue bodies and review intents.
- **D3.** Is the owner's confirmation a transient Q&A gate or also recorded as an artifact (cf. `assisted-workflow.md:28` approval files)? The intent only requires the gate; recommended default: transient gate, no new artifact (A2.3).
- **D4.** Whether to extend the confirmation gate to review-intent authoring (`review-pipeline.md` step 5). The intent doesn't ask for it; recommended: no — keep #71 scoped to the create-from-issue path (A3).
