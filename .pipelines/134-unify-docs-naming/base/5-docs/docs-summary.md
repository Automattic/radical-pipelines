# Docs Summary — Unify the documentation concept on plural "docs"

## What

The Docs phase added a single new changeset fragment,
`.changeset/unify-docs-naming.md`, recording the docs-naming rename. It is a canonical
**empty** changeset (empty front matter, empty body) — no version bump.

## Why

The rename touches `skills/**` and `agents/**`, both release-relevant paths under
`.changeset/config.json`'s `changedFilePatterns`, so the Changeset Gate CI workflow
requires a changeset to be present on the PR. The pre-existing
`.changeset/agent-scoped-guardrails.md` describes a different pending feature and
cannot serve as this change's release entry, so a new fragment was needed to satisfy
the gate.

## How

Created with the changesets CLI as an empty changeset so the front matter is in the
canonical form the shape validator accepts. Verified against the shipped code:
`node scripts/validate-changesets.mjs` exits 0, `npx changeset status` exits 0
(presence satisfied), and `npm test` passes 22/22 — the full Changeset Gate would be
green.

## Key decisions

- **Empty bump, not patch/minor.** The change is a pure identifier/prose rename with no
  consumer-observable behavior change (agents are discovered by filename; a consumer
  simply uses the renamed profiles going forward). Per CONTRIBUTING's "Empty changesets"
  guidance, a prose-only edit to release-relevant files that should not trigger a
  version bump uses an empty changeset — it satisfies the presence gate without a
  release entry. No body is included, so nothing can drift or misdescribe the change.

## Known limitations

- The published `CHANGELOG.md` is a historical release record (regenerated by
  `changeset version`) and is left unchanged; it retains one pre-rename "code and doc
  phases" reference in the PR #118 entry, which is correct — rewriting it would falsify
  a published release note. `.pipelines/**` historical run records likewise retain the
  old singular names by design. Both are out of scope per the spec.
