# Spec — Track changes with a changelog and keep the project version in sync

## Overview

The Radical Pipelines repository has no changelog and its project version has
drifted out of sync across the files that carry it. Three files declare a
version: the root `package.json` (`@automattic/radical-pipelines`, the Pi
manifest resolved by a git-source install), the Claude Code plugin manifest
`.claude-plugin/plugin.json`, and the Pi extension manifest
`.pi-extension/package.json` (`@automattic/radical-pipelines-pi`). They are
currently inconsistent (`0.1.1`, `0.1.0`, and `0.1.0` respectively) because of an
accidental, stray bump to the root file. A fourth file,
`.pi-extension/package-lock.json`, mirrors the extension manifest's version and
is regenerated by npm.

This work adopts the Changesets library to record every repository change as a
changelog entry and to drive version bumps, makes the root `package.json` the
single source of truth, and ensures that whenever the version is bumped it is
propagated identically to the other version-bearing files (and the lockfile is
regenerated). As a one-time correction, the existing drift is resolved so all
three files converge on a single baseline.

The repository is consumed direct-from-git — the Pi package via
`pi install git:github.com/Automattic/radical-pipelines` (or local path) and the
Claude Code plugin via the marketplace `source: "./"`. The root package is
`"private": true`. Consequently, "release" here means the version files and the
changelog are updated and committed; consumers pick up the new version on their
next git-source or marketplace install.

## Requirements

### Scope and source of truth

- **R1 — Changesets is adopted.** The repository uses the Changesets library to
  manage the changelog and version bumps. After setup, a `.changeset/` directory
  containing a `config.json` exists, and `@changesets/cli` is available to run
  (declared as a development dependency of the project).
- **R2 — The Changesets config targets the real default branch.**
  `.changeset/config.json` sets `"baseBranch": "trunk"` (the repository's default
  branch), not the tool's `master` default. Private-package handling stays at the
  Changesets default so the private root package is still versioned and recorded
  in the changelog but is never tagged.
- **R3 — The root `package.json` is the single source of truth for the version.**
  The version that Changesets maintains in the root `package.json`
  (`@automattic/radical-pipelines`) is the value every other version-bearing file
  must match. No other file is independently authoritative.

### Changelog

- **R4 — A changelog exists and is generated by Changesets.** A `CHANGELOG.md` at
  the repository root is produced and updated by the Changesets version step. It
  is not hand-maintained.
- **R5 — Each repository change can be recorded as a changeset.** A contributor
  (human or pipeline agent) can add a changeset entry that describes a change and
  declares its bump type (patch, minor, or major). The entry is a committed
  `.changeset/*.md` file that lives on the branch and travels with the pull
  request. Running the version step consumes the pending changeset files and
  folds them into `CHANGELOG.md`.
- **R6 — Recording a changeset is documented as a per-change obligation.** The
  contributor-facing documentation states that each repository change records a
  changeset, mirroring the repository's existing rule that the README is updated
  on every change.

### Version synchronization

- **R7 — The version is identical across all three version-bearing files.** After
  the version step runs, the root `package.json`, `.claude-plugin/plugin.json`,
  and `.pi-extension/package.json` all carry the exact same version string.
- **R8 — The bumped version is propagated automatically as part of the version
  step.** When the version is bumped via Changesets, the new root version reaches
  `.claude-plugin/plugin.json` and `.pi-extension/package.json` without a separate
  manual edit of those files.
- **R9 — The extension lockfile stays in sync.** After the version reaches
  `.pi-extension/package.json`, the top-level version in
  `.pi-extension/package-lock.json` is regenerated to match, so no silent
  lockfile drift remains.
- **R10 — `.claude-plugin/marketplace.json` is not modified for version sync.** It
  carries no version field and references the plugin by `source: "./"`, so it is
  intentionally excluded.

### Drift correction (one-time, part of this work)

- **R11 — The existing version drift is corrected.** As part of this work, all
  three version-bearing files are brought to a single consistent baseline of
  `0.1.1` — the highest existing value, already held by the root source of truth
  (a version must not regress). After this work, no two version-bearing files
  disagree.
- **R12 — The next version is not pinned in advance.** This work does not fix a
  specific next version number. Any version beyond the `0.1.1` baseline is
  whatever the applicable changeset's bump type yields when applied to that
  baseline.

### Project hygiene

- **R13 — The README is updated.** Per the repository's standing rule that the
  README is updated whenever a change is made, the README documents the new
  changelog and versioning workflow: how to add a changeset, that the version
  step propagates the version to every version-bearing file, and that consumers
  pick up new versions on their next git-source or marketplace install.

## Out of Scope

- **No publishing or registry release.** The root `package.json` is
  `"private": true`, and both artifacts are consumed direct-from-git. This work
  performs versioning and changelog generation only; there is no `npm publish`, no
  registry target, and no git tags.
- **No release CI added by default.** No Changesets GitHub Action and no automated
  "Version Packages" pull request are introduced. The version step is run locally
  / via the pipeline. The existing `deploy-landing.yml` workflow is left untouched.
- **`.claude-plugin/marketplace.json`** is not touched for version sync (see R10).
- **`.pi-extension/package-lock.json` is not hand-edited.** It is regenerated by
  npm tooling (see R9) rather than edited directly.

## Acceptance Criteria

- **AC1 — Changesets is installed and configured (R1, R2).**
  - **Given** the repository after this work,
  - **When** a reviewer inspects the repository,
  - **Then** a `.changeset/` directory with a `config.json` exists, `config.json`
    sets `"baseBranch": "trunk"`, private-package handling is at the Changesets
    default (versioned and changelogged but not tagged), and `@changesets/cli` is
    declared as a development dependency.

- **AC2 — A changeset can be authored for a change (R5).**
  - **Given** the configured repository and a pending change,
  - **When** a contributor adds a changeset describing the change and its bump
    type,
  - **Then** a committed `.changeset/*.md` file exists on the branch describing
    the change and its bump type, and it is part of the pull request.

- **AC3 — The version step generates the changelog and consumes changesets (R4,
  R5).**
  - **Given** one or more pending changeset files,
  - **When** the version step is run,
  - **Then** a root `CHANGELOG.md` is created or updated with entries reflecting
    those changesets, and the consumed changeset files are removed.

- **AC4 — All version-bearing files match after the version step (R3, R7, R8).**
  - **Given** a version bump driven by Changesets,
  - **When** the version step completes,
  - **Then** the `"version"` field of the root `package.json`,
    `.claude-plugin/plugin.json`, and `.pi-extension/package.json` are all the
    same string — equal to the root `package.json` version — with no separate
    manual edit of the latter two files required.

- **AC5 — The extension lockfile matches the extension manifest (R9).**
  - **Given** a version bump that has propagated to `.pi-extension/package.json`,
  - **When** the version step completes,
  - **Then** the top-level version in `.pi-extension/package-lock.json` equals the
    version in `.pi-extension/package.json`.

- **AC6 — The marketplace manifest is unchanged for version sync (R10).**
  - **Given** a version bump,
  - **When** the version step completes,
  - **Then** `.claude-plugin/marketplace.json` is unmodified (it has no version
    field).

- **AC7 — The drift is corrected to a single baseline (R11, R12).**
  - **Given** the pre-work state where the three files read `0.1.1`, `0.1.0`, and
    `0.1.0`,
  - **When** this work is complete,
  - **Then** the root `package.json`, `.claude-plugin/plugin.json`, and
    `.pi-extension/package.json` all read `0.1.1` (and
    `.pi-extension/package-lock.json` matches), with no specific next version
    pinned beyond that baseline.

- **AC8 — The per-change changeset obligation is documented (R6, R13).**
  - **Given** the contributor-facing documentation after this work,
  - **When** a reviewer reads it,
  - **Then** it states that each repository change records a changeset, and the
    README documents how to add a changeset, that the version step propagates the
    version to every version-bearing file, and that consumers pick up new versions
    on their next git-source or marketplace install.

- **AC9 — No publishing, tags, or release CI are introduced.**
  - **Given** the repository after this work,
  - **When** a reviewer inspects it,
  - **Then** there is no `npm publish` step, no git tags are created by this work,
    no Changesets GitHub Action or automated "Version Packages" pull request
    exists, and `deploy-landing.yml` is unchanged.
